### 4.1 知识库的职责边界（实测后定的）

**问：要不要去知识库看「这个指标要查哪些库」「这个问题要查哪些维度」？**
**答：不要。这两件事写在指标定义里；知识库只干三件事 —— 消歧、背景、知识类问答。**

理由三条：
1. **实测它没有这类知识。** 问「预算执行率怎么定义」只召回「公司业务知识库」整篇，里面没有定义；命中的全是业务背景文档（公司概况 / 新闻简报 / 政务知识库）。
2. **"查哪些表"是确定性的，不该用检索决定。** 表映射有限、可枚举、唯一；用召回概率去决定它，等于把确定的事变成概率的事 —— 这就是上一版"关键词表"的病，只是把 if-else 换成了向量检索。检索不到就静默走错，还不报警。
3. **一个事实只能有一个出处。** 若"查哪张表"既能从指标定义读、又能从知识库检索，冲突时听谁的？上一版正是死在**两套路由并行**（模型 + 关键词 fallback）。

知识库该干的（都是它的强项）：
- **消歧 / 术语归一**：用户说"执行率"，是预算执行率还是项目执行率？需要业务语境 → 同义词表 +（只在真有歧义时）检索知识库
- **背景与解释**：为什么高 / 低、历史、政策背景 → 混合类问题里调
- **知识类问答本身**：口径解释、公司概况

（现状提醒：实测它连口径解释都答不出 —— 问"线损率是什么"没命中定义。这正好是缺口清单要交给上游补的内容。）

**分工红线**：如果上游往业务知识库里塞"问题 → 指标 → 维度"的映射条目，那就是**第二套路由**，和指标定义必然打架 —— 二选一，不能并存。

## 4. 分诊：四类问题四条路

    补全后的问题
      ├ 知识类（"这是什么/什么背景/历史"）→ 百炼知识库应用直接答
      ├ 数据类（"多少/怎么样/排名"）      → 指标库 + 业务数据库（确定性）
      ├ 混合类（"为什么低/怎么改善"）      → 先取数拿事实，再调知识库拿背景/方法，合成
      └ 答不了 → 四种"没有"，四种话术

| 情形 | 话术 | 去向 |
|---|---|---|
| 知识库里没这条 | 「知识库里没有这条口径」 | 记知识缺口 → 上游补知识库 |
| 指标库里没这统计 | 「目前没有这个口径的统计」 | 记指标需求 → 人工定口径 |
| 指标不支持该粒度 | 「不支持按县公司统计，可用口径：…」 | 沿用 UnsupportedScope |
| 超出业务范围 | 直接拒答 | 记超范围 |

## 5. Agent 实现方式（本节是重点）

### 5.1 执行图：有界状态机 + 至多一次回环

    ① 归一化（确定性，0 次模型）
       extract_as_of / _infer_scope / 同义词表 / 术语索引
       → 时间口径、粒度、对象、归一后的业务术语

    ② 分诊 + 规划（模型 1 次，qwen3.8-flash）
       输入：问题 + ①的结果 + 检索到的候选指标定义（top 8）+ 槽位定义
       输出：Plan（JSON Schema 强约束）

    ③ 校验（确定性）
       metric_id 在候选集合内？参数合法？粒度支持？→ 不合格降级为 knowledge / unknown

    ④ 执行（确定性，并行）
       metric    → 指标实现（白名单 SQL + 公式）→ Fact
       knowledge → 百炼应用（解析 SSE）→ 切片 + 答案

    ⑤ 自检（确定性）
       子问题是否都有答案？缺的补一条 unknown 记录（不静默）

    ⑥ 作答（模型 1 次，qwen3.8-max）
       吃：facts + 知识片段 + 标签 + 口径；按子问题①②③编号

    ⑦ 组装推导链 + 缺口落库 + 返回

    **回环只有一处**：③ 校验失败时带失败原因重规划一次，最多 1 次，之后不再循环。
    延迟预算：数据类 4–8 秒；知识类 5–10 秒（知识库本身 3–8 秒）。

### 5.2 每个模块的实现方式

| 模块 | 干什么 | 实现 |
|---|---|---|
| agent/normalize.py | 时间/粒度/对象/术语归一 | 搬运现有 extract_as_of、_infer_scope、_resolve_scope_name |
| agent/triage.py | 知识/数据/混合/超范围 | 小模型分类 + 规则（含"多少/排名/同比"→数据类） |
| agent/registry.py | 指标注册表 + 检索 | 启动时读 metrics/*.yaml 建索引（名称/同义词/术语→id） |
| agent/planner.py | 选指标 + 组 Plan | 1 次模型调用，JSON Schema 校验，候选集合白名单 |
| agent/knowledge.py | 调百炼应用 | httpx 流式，解析 SSE：tool_calls / 切片 / 答案 / request_id |
| agent/executor.py | 跑 Plan | 线程池并行，逐指标调 metrics/ 里的实现，产出 Fact |
| agent/judge.py | 阈值 → 标签 | 搬运现有 app/rules/ |
| agent/compose.py | 作答 + 降级 | 搬运现有 app/answer.py 与 app/output/template.py |
| agent/trace.py | 推导链 | 每个模块 append step，模型只写"结论"那一步的措辞 |
| agent/gaps.py | 缺口记录 | 落 SQLite/Postgres 表，可导出给上游 |
| playbooks/ | 定时与固化 | YAML 剧本 + APScheduler，走同一套 ④⑤⑥⑦（无 ②） |

### 5.3 模型契约（强约束，这是防幻觉的关键）

    {
      "sub_questions": ["...", "..."],
      "calls": [
        {"kind":"metric","metric_id":"budget_total","params":{"year":2026,"scope":"city"}},
        {"kind":"knowledge","query":"随州新能源装机"}
      ],
      "shape": ["结论","趋势","建议"]
    }

三条校验：metric_id 必须在候选集合内（不在就丢，转 unknown）；params 只允许白名单键；kind 只能是 metric / knowledge / unknown。

### 5.4 指标目录怎么注入（不是全塞进提示词）

133 张表、20+ 指标不可能全塞。做法：
1. 一个指标 = 一个 YAML 文件，字段：id / 名称 / 同义词[] / 单位 / 口径说明 / 公式 / 数据源表 / 支持的粒度 / 参数 / 什么时候用 / 示例问法 / 缺口规则。
2. 启动时把「名称 + 同义词 + 术语」建成内存索引。
3. 查询时用问题 + 归一术语检索出 **top 8**，只把这 8 条完整定义塞进 prompt。
4. **加指标 = 加 YAML；新说法 = 加同义词（数据，不是代码）。** 这就是"打地鼠"的解药：变化收敛到数据。

### 5.5 推导链怎么产生

**不是模型写的，是执行器产生的。** 每个模块执行时 append 一条 step：

    { seq, kind, title, detail, inputs, output }
    kind ∈ 归一 / 分诊 / 选指标 / 口径 / 取数 / 计算 / 知识检索 / 判断 / 结论

模型只贡献最后「结论」那一步的措辞，其余全是代码写的事实（含真实 SQL、命中切片 id）。**所以右栏不可能编造。**

### 5.6 失败与降级（每条都要有出路）

| 失败 | 处理 |
|---|---|
| 规划模型超时/返回非法 | 带原因重试 1 次 → 仍失败则退到确定性兜底（只判"能不能答"，不选技能） |
| 某指标执行失败 | 该子问题报缺口，其余照常返回（单点失败不影响整体） |
| 作答模型失败 | 模板渲染（搬运 app/report.py）并在 warnings 注明 |
| 知识库不可用 | 标注「知识库暂不可用」，不阻塞数据部分 |

## 5.7 查询要"基本答对"，靠什么（新技术选型）

### 正确性：四个杠杆，按杠杆率排序

**① 语义层是准确率的最大单一变量（有实测，不是观点）**

Cube 2026-04 配对基准：100 个问题、三个前沿模型、同一 harness / 同一 judge / 同一单发协议，**唯一变量是提示词里有没有那份 4 KB 的语义层文档**：

| 模型 | 只有表结构 | 加语义层 | Δ |
|---|---|---|---|
| Claude Opus 4.7 | 50.5% | 67.7% | +17.2pp |
| Claude Sonnet 4.6 | 46.5% | 68.7% | +22.2pp |
| GPT-5.4 | 45.5% | 68.7% | +23.2pp |

并且：**有语义层时三个模型彼此无显著差异（p ≥ 0.79）**。同一结论被 BIRD 外部知识消融（+20pp）与 dbt Labs 配对基准（+15pp）印证。
→ **准确率的瓶颈是口径写没写清楚，不是模型强弱。** 力气该花在指标定义（YAML）上，不在换模型上。

**② 结构化输出（约束解码）—— 上一版一类 bug 从根上消失**

百炼官方文档：JSON Schema 严格模式（response_format.type = json_schema，strict = true）**已支持 Qwen3.8-Max 与 Qwen3.8-Flash 系列**（正是我们用的两个）。
把候选指标 id 写进 schema 的 enum → 模型**物理上无法**输出不存在的指标名，也不会再有 JSON 解析失败。
**已实测（qwen3.8-flash，三条探针）**：可用。问预算总额 → 只输出 budget_total + project_execution_rate；问远场问题「全市酒店入住率」→ 在 enum 约束下输出 unknown（**拒答路径同样能被 schema 覆盖**）；问「线损率近三个月」→ 输出 line_loss_city。
两条实测教训：① **参数不能让模型硬填** —— 问句没写年份时它编了 2023，所以时间/粒度必须由**确定性归一化层**填，模型只填它明说的；② 输出语言会漂（子问题写成英文），提示词要显式要求中文。

**③ 确定性校验 + dry-run 探针 —— 校验不问模型**

模型给出 Plan 后，代码逐条检查：粒度支不支持？参数齐不齐？**先跑一次 LIMIT 0 探针**确认这个参数组合真能取到数（防"空集当没有数据"，这个坑踩过）。
不合格 → 带失败原因重规划**一次**（只一次）→ 仍不行按四类缺口回话。

**④ 拒答门限 —— 宁可说没有，不给"大概齐"**

检索分低 / 候选为空 / 探针为空 → 直接走缺口话术。给领导看的数，错一个不如不答。

### 效率：四个杠杆

| 杠杆 | 做法 | 收益 |
|---|---|---|
| 上下文缓存 | 百炼 Context Cache **显式缓存**：messages 里加 cache_control ephemeral，最少 1024 token，命中后 5 分钟有效并重置 | 固定前缀（指标目录）命中后输入按 **10%** 计费；隐式缓存约 20%；两者互斥 |
| 计划缓存 | 归一化后的（问题 + 参数）→ Plan 映射缓存 | 同义问法跳过规划模型调用；现有项目只有 30 秒结果缓存，太短 |
| 单次模型规划 | 分诊与规划合并成**一次** flash 调用 | 少一次往返 |
| 并行取数 | 多指标线程池并行 + 连接池预热 | 已有，保留 |

**暂不做**：指标物化（预聚合宽表）。收益是数量级，但要建 ETL；等评测显示慢再说 —— 不先做没被需要的优化。

### 三条红线（防止重演上一版）

1. 业务知识只许存在于 **YAML 指标定义 / 同义词表 / 说明书**里；不许写成代码里的 if-else，也不许写成提示词里的"如果问 X 就选 Y"。
2. 任何"选择"都必须落在**候选集合内**（schema enum，加白名单校验兜底），集合外的值一律不接受。
3. 答不了 → 落缺口清单 → **由人决定**加指标还是加同义词；系统不自动改代码、不自动改提示词。

## 7. 怎么开始：第一个垂直切片（建议第一周就这一个）

**只支持一个指标打穿全链路**，验证的是"链路对不对"，不是"覆盖多少"：

    /api/v1/ask
      问题：「截至2026年9月，全市预算总额多少？」
      → ①归一 → ②规划（候选只有 budget_total）→ ③校验 → ④取数（真库）
      → ⑥作答 → ⑦返回 answer + steps[]

验收这个切片的四条：
1. 答案数字与现有 facts_snapshot 一致；
2. steps[] 能追到真实 SQL、表名、公式；
3. 换 5 种说法问同一个指标，全部命中（这条测的是检索与同义词，不是提示词）；
4. 问一个没有的指标，正确说"没有这个口径"并落缺口。

跑通后再加指标 —— 每个指标只加 YAML + （必要时）一个实现，链路不动。
