## Q2 — 五条需求的覆盖情况

**1. 复杂任务开工前必须先落一份计划文件 —— 已覆盖（writing-plans，且 brainstorming 提供硬门禁）**
- `writing-plans/SKILL.md`："**Save plans to:** `docs/04-计划/YYYY-MM-DD-<feature-name>.md`"
- `brainstorming/SKILL.md`（同一条链的上游，也是唯一真正的"门禁"）："Do NOT invoke any implementation skill, write any code, scaffold any project, or take any implementation action until you have presented a design and the user has approved it."
- 注意口径：brainstorming 落的是**设计/spec**（`docs/03-设计/specs/...-design.md`），writing-plans 落的才是**实施计划**。"计划文件"这条命中后者。

**2. 每一步都要有明确的验证方式 —— 已覆盖（writing-plans + karpathy-guidelines）**
- `writing-plans/SKILL.md`：步骤模板硬性给出 Run/Expected，如 "Run: `pytest tests/path/test.py::test_name -v`" / "Expected: FAIL with \"function not defined\""。
- `karpathy-guidelines/SKILL.md`："For multi-step tasks, state a brief plan: `1. [Step] → verify: [check]`"；"Weak criteria (\"make it work\") require constant clarification."
- 缺口见 Q4：这两处只约束**计划文本**，没有"说不出来就不许往下走"的执行期拦截。

**3. 先写会失败的测试，再改到通过 —— 已覆盖（test-driven-development，极硬）**
- `test-driven-development/SKILL.md`："NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST"；"### Verify RED - Watch It Fail **MANDATORY. Never skip.**"
- 计划侧同源：`writing-plans/SKILL.md` 任务模板 Step 1 "Write the failing test" → Step 2 "Run test to verify it fails"。
- bug 场景由 `systematic-debugging/SKILL.md` 补充："Create Failing Test Case ... MUST have before fixing"。

**4. 测试结果要落盘保存 —— 无技能覆盖**
- 13 个技能里没有任何一句要求把测试输出写进文件目录。`verification-before-completion/SKILL.md` 只要求**在本轮消息里跑并读输出**："If you haven't run the verification command in this message, you cannot claim it passes."
- 最接近的是 subagent-driven-development 的间接做法：report 文件要求实现者"appends its fix report to the same report file"，且"confirm the fix report contains the covering tests, the command run, and the output"——但这是**子代理报告**，不是落盘的测试结果库，且只在用 SDD 时成立；`subagent-driven-development/SKILL.md` 明确说自己只回传摘要："returns only status, commits, a one-line test summary, and concerns"。
- 这条属于 Fred 自己在 `~/.dsh/AGENTS.md §6` 加的要求（"测试结果必须落盘"），技能里没有对应物。

**5. 声称完成前必须跑过验证并贴出实际输出 —— 已覆盖（verification-before-completion，极硬）**
- `verification-before-completion/SKILL.md`："NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE"；Gate Function 第 2-3 步 "RUN: Execute the FULL command (fresh, complete)" / "READ: Full output, check exit code, count failures"。
- 贴输出的正反例："✅ [Run test command] [See: 34/34 pass] \"All tests pass\"" 对 "❌ \"Should pass now\" / \"Looks correct\""。

## Q3 — 重复与冲突

**重复（讲同一件事）**
| 对 | 重叠内容 | 该用哪个 |
|---|---|---|
| writing-plans ↔ subagent-driven-development | 都把计划拆成带复选框的 2-5 分钟小步、都要求 TDD 顺序、都要求每任务结束提交 | 不冲突，是上下游：writing-plans 定义**步**，SDD 定义**任务级审查门禁**。真要"强制"就用 SDD —— 它把门禁写成了不可跳过的循环（"Never skip the task review"），writing-plans 只约束文档格式 |
| karpathy-guidelines ↔ 用户级 `~/.dsh/AGENTS.md` §1-§5 | 四节标题与正文几乎逐字相同（"Don't assume. Don't hide confusion. Surface tradeoffs."） | AGENTS.md 优先级更高（`using-superpowers/SKILL.md` 自认 "User instructions ... take precedence over skills"）。karpathy 可作为模型可见的等价入口，但不应被当成额外规则来源 |
| requesting-code-review ↔ subagent-driven-development | 都要求"每任务完成后审查" | SDD 更完整（双裁定 + diff 文件 + 复审循环）；requesting-code-review 是它调用的模板持有者（SDD 直接引用 `../requesting-code-review/code-reviewer.md`） |

**冲突（要求互相矛盾）**
1. **要不要在步骤之间停下来核对** —— `executing-plans/SKILL.md` 描述自己是 "with review checkpoints" 的批量执行；`subagent-driven-development/SKILL.md` 明文禁止："**Continuous execution:** Do not pause to check in with your human partner between tasks." 同一份计划在"人盯每一步"和"别打断我"之间是矛盾的两种模式。Fred 要的"每一步都有完成标准"更靠近前者，但真正的强制力在后者（有审查子代理当刹车，不靠人）。
2. **小改动要不要写测试** —— `karpathy-guidelines/SKILL.md`："For trivial tasks, use judgment."；`test-driven-development/SKILL.md`："NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST"，并预先否掉了这个理由："Thinking \"skip TDD just this once\"? Stop. That's rationalization."；`systematic-debugging/SKILL.md` 也否掉 "Issue is simple, don't need process"。**TDD 更该用**，karpathy 那句是软化词。
3. **计划文件的验收口径** —— 见 Q4 第 4 条：技能模板与 Fred 的 `AGENTS.md §1.4` 四段式不同，谁为准需要 Fred 定。

**写法强度排序（同一件事谁更强）**：verification-before-completion / test-driven-development / systematic-debugging（Iron Law，最硬）> subagent-driven-development（Never + 轮次上限）> brainstorming / writing-plans（HARD-GATE / MUST 格式）> executing-plans / requesting-code-review（Mandatory/must）> karpathy-guidelines（明示"用判断"）。

## Q4 — 仍然空白的部分

1. **"什么时候必须调技能"的机制本身没有技能覆盖。** Fred 抱怨的"不主动调用技能"，13 个技能全部假设调用已经发生；`using-superpowers/SKILL.md` 只声明 "If you think there is even a 1% chance a skill might apply... you ABSOLUTELY MUST invoke the skill"，但没有任何检查点、门禁函数或宿主钩子去**验证**它被调用。这是唯一真正的空白，而且正是主诉。
2. **执行期没有"无计划不得改代码"的拦截。** 只有 `brainstorming/SKILL.md` 有真正拦人的 HARD-GATE，而它要求你先想起 brainstorming。`writing-plans` 只管"写了就该这么写"，没有任何一句禁止没写计划就动手。Fred 的"开工前不落计划"正是从这个缝里漏出来的。
3. **测试结果落盘无覆盖**（见 Q2-4）。没有任何技能规定测试输出/验证证据的存放目录与文件粒度。
4. **计划的验收口径与 Fred 自己的格式要求不一致。** `writing-plans/SKILL.md` 的 MUST header 是 Goal / Architecture / Tech Stack / Global Constraints；Fred 在 `~/.dsh/AGENTS.md §1.4` 要求的是"实际情况 — 建议 — 预计成功 — 验收标准"四段，且"动手前定死，事后不许改"。技能模板里没有这四段，也没有"验收标准先定"的位置。两条都生效时，计划文件该长什么样是没定义的。
5. **"别再犯同一个错"没有承接机制。** 13 个技能的防错资产是红牌清单、Rationalizations 表、Pressure Test（都在 `systematic-debugging/`），但没有一个要求把**本次**踩的坑写进记忆或复盘。SDD 的 ledger 只在单计划内有效，且结束时明文销毁："delete this plan's workspace (`rm -rf <workspace>`) — the git history is the record now"。Fred 的"同一个错误反复犯"没有对应兜底。
6. **技能几乎全部假定"git + 测试套件 + 仓库"。** worktree、commit、diff、SHA、test runner 是 13 个技能的公分母。对 Fred 日常大量存在的非代码任务（文档解析、数据分析、报表生成）没有任何步骤级强制流程 —— 这是覆盖面缺口，不是措辞问题。
