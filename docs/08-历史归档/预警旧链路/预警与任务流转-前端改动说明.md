# 预警与任务流转 · 前端改动说明（2026-10-27）

> 给前端同学的对接说明。只写**这次变了什么、你还差什么**，完整字段字典见
> `docs/01-接口/预警与任务流转-接口文档.md`。

## 0. 先说最重要的一条：没有推送

系统**不会主动把预警或任务推给浏览器**。没有 WebSocket、没有 SSE、没有 webhook。
所有内容都是先落库（PostgreSQL），前端去拉。

所以信息是**先落库、前端来取**。机制在下一节写清楚了；**多久取一次由你们定**，
我们不规定频率，只保证接口口径稳定。

**为什么不做推送**：单进程 FastAPI + 单机部署，加 WebSocket 要引入连接管理和多进程广播，
现阶段不划算。如果后面确实要"秒级到达"，最小代价是前端把未读数轮询压到 10 秒。

﻿## 0.5 前端怎么拿到这些信息（机制，不是频率）

系统这边分工固定：

| 环节 | 谁做 | 落在哪 |
|---|---|---|
| 算预警 | 服务端定时任务（时间写在站点包 `jobs.yml`，改时间不动代码） | `alert_item` |
| 派任务 / 人操作 | 服务端接口 | `dispatch_task` + 事件流水 `dispatch_task_event` |
| 要通知某人 | 动作发生时就写好通知 | `dispatch_notice`（有自己的未读标记） |
| 取数据 | **前端** | 下面这些只读接口 |

也就是说：库里永远是「当前状态」，前端任何时候取都是全的，**不存在错过一条就丢**。
这正是没有推送也能用的原因。

### 可用的取数入口（全部只读、幂等、可随时重试）

| 想拿什么 | 接口 | 怎么判断有没有新的 |
|---|---|---|
| 有没有事等我处理（红点） | `GET /api/dispatch/notices?unread=1` | 返回 `total`，比上次大就是有新的 |
| 通知列表 | `GET /api/dispatch/notices` | 每项有 `read_flag`、`sent_at` |
| 我的预警 | `GET /api/alerts` | 每条有 `last_seen`、`status` |
| 单条预警详情 / 卡片 | `GET /api/alerts/{id}`、`/card` | — |
| 我的任务 | `GET /api/tasks?role=mine` / `created` / `cc` | 每条有 `update_time` |
| 单个任务详情 | `GET /api/tasks/{id}` | `update_time` 变了再重渲染 |
| 一件事的全貌 | `GET /api/tasks/case/{case_id}` | 同上 |

### 三条约定（免得踩坑）

1. **不增量、不分页游标**：每次取都是当前全量（列表有 `limit/offset`），不需要「从上次位置继续」。
2. **未读是一个独立的数**：`notices?unread=1` 的 `total` 就是红点数字，不用自己数列表。
3. **时间有两份**：`reply_due_at` / `due_at` 是 ISO（排序、算差值用）；
   卡片另给 `reply_due_text` / `due_text`（「10月30日 18:00」，直接显示）。
   消息正文里也是人话时间，不用再格式化。

### 如果你们要秒级

现在没有推送。要更快只有两条路：把取数间隔压短（你们定），或者我们加一个
服务端到浏览器的单向长连接（SSE）。要哪种、做不做，你们提，我们再实现。
**接口口径不会因为加了推送而变，取数入口永远保留。**


## 1. 新增的三个接口（这次主要改动）

### 1.1 事项全景 —— 同一件事只有一张单

```
GET /api/tasks/case/{case_id}
```

`case_id` 形如 `C20261027-00001`，在任务对象里叫 `case_id`。也接受直接传 `case_key`。

用途：上级点开一件事，看到的不是空白页，而是**整棵树 + 各层交的方案 + 补充说明时间线**。

返回要点：

```json
{
  "case_id": "C20261027-00001",
  "title": "全市预算执行率偏低…",
  "status": "doing",
  "my_role": "creator | owner | superior | collaborator | cc | observer",
  "tree":  [ { "id": 3, "depth": 1, "title": "...", "status": "...", "assignees": [...] } ],
  "plans": [ { "task_id": 3, "kind": "owner_plan", "version": 1, "content": "...", "accepted": 0 } ],
  "timeline": [ { "task_id": 3, "action": "supplement", "actor_name": "...", "content": "..." } ],
  "can": { "comment": true, "supplement": true, "revise_plan": false, "change_status": false,
           "create_task": false }
}
```

**前端必须按 `can` 决定给不给按钮**，不要自己判断：
- `create_task` 永远是 `false` —— 同一件事不允许再建第二张单，页面不要给"新建"按钮
- `change_status=false` 的人只能补充、写说明

### 1.2 说明（不要求谁办，只留记录）

```
POST /api/tasks/{task_id}/comment
{ "content": "已协调运检部，下周走审批" }
```

同一事项上的人都能写。返回精简对象（不是完整任务）：
`{ task_id, task_no, case_id, status, added: "comment", requirement }`

### 1.3 补充要求（会通知承办人，追加到任务要求里）

```
POST /api/tasks/{task_id}/supplement
{ "content": "本周五前额外报一份进度" }
```

返回同上，`added: "supplement"`，`requirement` 是追加后的全文，前端可直接回填。

> 这两个接口是"不能重复建任务"之后的唯一替代动作。UI 上建议：点"新建任务"被
> `CASE_EXISTS` 拦下时，弹层直接跳到这条单，给"补充要求 / 写说明"两个按钮。

## 2. 字段变更

### 2.1 任务对象新增两个字段

| 字段 | 含义 | 前端怎么用 |
|---|---|---|
| `case_id` | 对外事项号，整棵树共用 | 列表里显示，点击跳事项全景 |
| `case_key` | 事项指纹（内部用） | 一般不用显示，排查时可带上 |

`/api/tasks` 列表、`/api/tasks/{id}` 详情、子任务、事项全景，**都会带这两个字段**。

### 2.2 任务详情新增 `plan_offer`（要不要我替你起草方案）

```json
"plan_offer": {
  "offer": true,
  "message": "这个任务要求交方案。要不要我按本所/本级的数据先起草一份，你改完再提交？",
  "endpoints": { "draft": "/api/tasks/12/ai/plan", "submit": "/api/tasks/12/plan" },
  "deadline": "2026-10-29T18:00:00+08:00"
}
```

`offer=true` 时，前端在任务详情顶部弹一条一次性提示（**不要每次刷新都弹**，
用 `localStorage` 记住这条任务已经提示过）。`offer=false` 的 `reason` 会有三种：
`这个任务不要求交方案` / `不是我承办` / `方案已交`。

## 3. 新增错误码（前端要能识别）

| code | HTTP | 什么时候 | 前端怎么办 |
|---|---|---|---|
| `LEVEL_SKIP` | 409 | 越级派活/上报（市财务直接派给所长等） | 直接把 `message` 弹出来——里面写了"该发给谁"，例如"中间还隔着县公司财务部，请先发给县公司财务部" |
| `OUT_OF_CHAIN` | 409 | 层级对但跨单位（曾都的县财务派给随县的所） | 同上，弹 `message` |
| `CASE_EXISTS` | 409 | 同一件事已经有单了 | **不要当错误弹**。按返回的 `existing_task_no` / `existing_task_id` 跳转到那条单，提示"这件事已有任务，你可以补充或写说明" |
| `MASTER_GUARD` | 409 | 执行层直接上报市领导 | 弹 `message`，引导改用"抄送" |

`CASE_EXISTS` 的返回体（`detail` 里）：

```json
{
  "code": "CASE_EXISTS",
  "message": "这件事已经有任务在办了（D20261027-0001，两水供电所所长 发起，当前 open）。…",
  "detail": {
    "existing_task_id": 12, "existing_task_no": "D20261027-0001",
    "case_id": "C20261027-00001", "creator": "两水供电所所长", "status": "open",
    "actions": ["comment", "supplement", "plan"],
    "endpoints": { "comment": "...", "supplement": "...", "plan": "...", "case": "..." }
  }
}
```

## 4. 任务到底有哪些字段（一张单长什么样）

### 4.1 必填（系统一定给，不会空）

| 字段 | 谁定的 | 说明 |
|---|---|---|
| `task_no` | 系统 | `D20261027-0001` |
| `case_id` | 系统 | 事项号，整棵树共用 |
| `title` / `requirement` | 发起人（可 AI 拟稿） | 要求正文；补充要求会追加到这里 |
| `creator` | 系统 | `{employee_id, name, login_name}` |
| `status` | 系统 | `draft/open/doing/verify/closed/cancelled` |
| `level` | 预警级别 | `high/mid/low` |
| `reply_due_at` | **系统默认 + 人可改** | 回执时限。不传就按级别：高 24h / 中 72h / 低 168h |
| `due_at` | **系统默认 + 人可改** | 完成时限。不传按子判据默认（一般 30 天） |
| `require_reply` | 系统默认 + 人可改 | `1`=要在回执时限前交东西；`0`=不用回执，系统按时限盯数据判完成（「月底前把钱花完」就是 0） |
| `verifier_type` | 系统默认 + 人可改 | `auto`（数据达标自动闭环）/ `human`（人工确认） |
| `verify_rule` | 来自预警 | 自动核销的判据，`human` 时可空 |

### 4.2 承办人：**必须有，缺了直接拒绝建单**

`POST /api/alerts/{id}/dispatch` 的 `assignees` 为空 → `422 NO_ASSIGNEE`；
没有 `part=owner` 的 → `422 NO_OWNER`。

所以"派给谁"这件事不会漏——系统宁可拒单也不建一张没人负责的单。

### 4.3 信息不全时谁补（这是你问的重点）

三道关，按顺序：

**第一道：下发确认页先补齐**
`POST /api/alerts/{id}/dispatch/preview` 会返回推荐承办人、默认时限、拟办草稿。
前端应该把它做成**表单预填**，让人确认/改，而不是空表单。

**第二道：对话拟稿 → 人确认**
走对话建任务时，系统先拟一张 `draft`（不是正式任务），并发一条确认消息。消息里逐项列出：
事项、责任、承办人、回执时限、完成时限、核销方式。**没人可派时明确写"（还没找到人，请指定）"**。
人回"确认"才变正式单；回"取消"就作废；说"换人/改时间"就改草稿。

所以：**不会出现"发出去了才发现没写派给谁"**。缺的信息在草稿阶段就被逼着补。

**第三道：发出后发现漏了**
- 派错了 → `POST /api/tasks/{id}/transfer` 转派（只能转给相邻层级）
- 时间改了 → 目前没有专门的"改时限"接口，**这是缺的**（见下面待办）
- 要求漏了 → `POST /api/tasks/{id}/supplement` 补充要求，会通知承办人

### 4.4 全字段清单

`/api/tasks/{id}` 返回：

```
id, task_no, case_id, case_key, task_type, title, requirement, status, level,
alert_id, root_task_id, parent_task_id,
scope_type, scope_key, scope_name, biz_type, biz_keys,
creator{employee_id,name,login_name},
reply_due_at, due_at, require_plan, verifier_type, verify_rule,
verify_state, last_check_at, escalate_level, overdue_flag, archived_flag,
closed_at, close_reason, create_time, update_time,
my_parts[], assignees[], events[], plans[], checks[], children[], alert{}, plan_offer{}
```

## 5. 前端要做的改动清单

1. 任务列表/卡片加 `case_id` 展示，点击进事项全景
2. 新增事项全景页：树 + 方案 + 时间线，按钮受 `can` 控制
3. 任务详情顶部按 `plan_offer` 给一次性提示
4. "新建任务"被 `CASE_EXISTS` 拦下时，跳转已有单，给"补充要求/写说明"两个按钮
5. 越级报错（`LEVEL_SKIP`/`OUT_OF_CHAIN`/`MASTER_GUARD`）直接弹 `message`，不要自己编文案
6. 未读数、预警列表、任务列表按第 0 节的频率轮询

## 6. 还缺的（我们这边待办，不是前端的问题）

| 缺什么 | 影响 |
|---|---|
| 改时限接口（`reply_due_at` / `due_at` 建单后不能改） | 发起人想延期只能口头说，系统里没入口 |
| 真正的实时推送 | 目前靠轮询，最慢 60 秒才看到 |
| 预警详情页的 AI 分析还没接身份建议 | 现在"点开预警详情"给的分析和"下发确认页"给的建议口径可能不一致 |
