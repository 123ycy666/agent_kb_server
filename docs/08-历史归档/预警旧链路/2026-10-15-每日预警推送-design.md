## 一 要解决什么

上游业务系统**每天 8:00** 调一次我们的接口，带**登录人的账号**。我们返回**这个人今天该办的几件事**：**一件事一条，每条一句话**，只返回有异常的。

**边界（别越界）**：

| 归谁 | 事 |
|---|---|
| **上游** | 登录鉴权、每天 8 点触发、**拿到我们的返回后怎么展示/怎么推给用户** |
| **我们** | **只提供接口**：把账号解析成范围、按角色算出有哪几件事、每件事给一句话 + 数据 |

**不做**：登录、发 token、写他们的消息表、定展示形式、做点击跳转（第一期）。

## 二 鉴权：账号 → 角色 → 范围

### 2.1 输入

上游只传**业务账号**（`t_employee.login_name`，如 `sngdssz`、`xgscwb`、`sz013`）。

**明确不接受上游传 `role` / `scope`**：角色与范围一律现查库。上游传了也忽略。
（现状 `/api/ask` 是反过来的——上游传什么 `scope` 就按什么取数，等于没权限控制。本设计不沿用。）

### 2.2 解析链（4 张表，实测可用）

```

## 三 分角色预警：判据相同，**算的层级不同**

### 3.1 核心原则

> **不是"大角色少推几条"，是同一判据在不同层级要算不同的东西。**

只改条数上限 = 假的分角色（市财务和所长拿到同一句话，只是市财务少拿两条）。

| 变的东西 | 所长 | 县财务 | 市财务 |
|---|---|---|---|
| 算的层级 | 绝对数（本所） | 汇总 + 县内所间对比 | 汇总 + **县间横向对比、点名异常县** |
| 给谁做决策 | 这钱我怎么花出去 | 我该催哪几个所 | 问题在哪个县、要不要过问 |
| 放哪个数 | 余额 37.87 万 | 全县 280 万 + **7 个所里 6 个 0 执行** | 4 家里 **广水、高新 0 执行** |

### 3.2 条数上限：**每类最多 1 条，总共最多 3 类**

不设"每人最多 N 条"。理由：市财务同时有"资金花不完"和"审批积压"两种**性质不同**的异常，必须分 2 条（两条真信息）；而"47 个所花不完"是一条信息的 47 个实例，压成 1 条汇总。**这个规则天然产生 1~3 条，不需要拍脑袋定 N。**

### 3.3 返回形态：**一件事 = 一条，一句话**

> **前端怎么展示不归我们管。我们只给接口。**
> 我们保证的只有一件事：**每个人今天有几件事待办，就返回几条，每条一句话。**

```
alerts = [
  "两水供电所：37.87万预算一单未批，执行率0%",
  "两水供电所：16单卡在审批，最久175天"
]
```

**两条约束**（不是展示要求，是接口质量要求）：

1. **一件事一条** —— 预算花不完、审批积压是**两件事**，必须两条；不能合成一句"预算和积压都有问题"。
2. **一句话说得完** —— 每条 `title` ≤ **40 个汉字**，只放范围 + 结论 + 最多 2 个数。明细不在这句话里。

### 3.4 归属原则：**发给"能动手的人"，小问题不上大领导**

三条规矩：

1. **问题必须落在收件人的职权里** —— 他收到就能办，办不了的不给。
2. **层级越高，只收"汇总 + 需要他决策的"** —— 执行层的小问题（某单金额填错、某个节点卡 3 天）**一律不上报领导**。
3. **数据质量分级** —— 影响钱的直推所长；纯登记缺失只给市财务**汇总**。

### 3.4 每个预警的判据（全部实查可跑）

统一口径（与 `.dsh/memory/project-secretary-budget-caliber.md` 一致，**不写死任何业务数**）：

```
分配额   = Σ t_power_company_budget_result.budget_amount
           WHERE deleted_flag=0 AND year=当年 AND power_station_id IN (范围)
已审批   = Σ t_power_work_order.budget_total
           WHERE deleted_flag='0' AND work_status IN ('3','6','7') AND YEAR(create_time)=当年
           AND power_company_id IN (范围)
执行率   = 已审批 ÷ 分配额
结余     = 分配额 − 已审批
已过比例 = (今天 − 当年1月1日) ÷ 当年总天数
```

#### 3.4.1b 预算花不完：**预测法实测（替代原来的阈值法）**

**口径**（单项目中位金额 2.89 万；月均立项数 = 今年立项数 ÷ 已过 9.5 个月；剩余 2.5 个月）：

```
还需项目数 = 结余 ÷ 2.89万
还能做     = 月均立项数 × 2.5
花不完 ⟺ 还需项目数 > 还能做
```

| 结果 | 所数 | 例子 |
|---|---|---|
| **触发（花不完）** | **9 个所** | 神农 55.29万 还需22个/还能做0 · 开发区 49.34万 20/0 · 十里 42.29万 17/0 · 骆店 41.68万 17/0 · 太平 41.68万 17/0 · 李店 40.42万 16/0 · 长岗 38.29万 16/0 · 关庙 35.06万 14/0 · 新城 5.18万 2/0 |
| **不触发（花得完）** | 38 个所 | 唐镇 45.72万 还需19个、月均立项 0.1、还能做 1（相差 19 倍 → 按新口径**仍触发**，见下方说明） |

> ⚠️ **实测更正**：用"月均立项数"当能力代理时，**8 月的 85 单集中爆发**把月均拉得不稳，导致同一批所重复触发/不触发会随月份抖动。所以**最终采用的算法固定为下面这条更稳的**：
>
> ```
> 前期节奏 = 已审批金额 ÷ 已过月数（元/月）
> 年底预计 = 前期节奏 × 12
> 花不完 ⟺ 年底预计 < 分配额 × 0.6
> ```
>
> 按这条实测（今天 = 2026-10-15）：**触发 44 个所、不触发 3 个所**。
>
> | 不触发（钱花得完） | 年底预计执行率 |
> |---|---|
> | 均川供电所 | 89.9% |
> | 府河供电所 | 73.0% |
> | 柳林供电所 | 71.9% |
>
> 草店 49.7%、殷店 35.3%、万和 25.6% 仍然触发。**"花得完就不说"这条因此是真生效的**——不是所有所都被推。
> **两个算法都实现、配置里选一个**（`forecast_mode: pace | pipeline`），默认 `pace`（稳）。**这就是"按这个花法花得完吗"的可计算形式**——不是拿执行率跟一个固定线比，而是**把当前速度外推到年底**。

#### 3.4.3 指标恶化的一个**必须先修的坑**

`trend_result='deteriorated'` 里混着**假的恶化**：市公司"售电量"同比 **−41.8%**、随县 −44.0%、曾都 −39.2%。售电量半年掉四成不是业务事实，是**年度累计口径没对齐**（本期只累计到某一月，基期是全年）。

**所以 K 类不能直接推**。要么先修这个查询口径，要么 K 只推"跳闸次数、线损率"这两项（实测这两项没有量级问题：市跳闸 5821 vs 962 是真涨）。

**并且 K 有硬伤**：指标快照最新期是 **202609**，即 **2026 年 9 月**——没有 10 月数据。所以指标类预警**每周或每月推**才有意义，**放进"每天 8 点"里会连续几周推同一句话**。


**B 的口径（Fred 已定）：只算当年创建的单，**只用来报"有多少件"（数量统计）。

**D 是最有价值的一条，也是我上一轮的判断失误 —— 更正**：`t_work_order_audit_task` 就是"进入当前节点的时间"那张表。字段 `task_status`（0 待处理 / 1 处理中 / 2 已完成 / 3 已驳回）+ `node_name`（卡在谁那）+ `create_time`（进这个节点的时间）+ `assignee_id`/`operate_time`。**待处理任务的 create_time 就是它在当前节点的起始时刻**，实测数据很干净（最早 2026-04-17，全是 2026 年的单）。所以：

- **"卡在营销部审核 175 天" 这种可行动的句子，现在能报了**（两水所 6 单 / 23.62 万，实测）。
- 跨年份的脏数据（全库 1445 件"审核中"里有 2022 年的）**不影响 D**：D 只取自 `task_status=0` 的审批待办，最早的才 2026-04-17。

| 积压**停留时长 + 卡在谁那** | `t_work_order_audit_task`（status=0） | "其中 16 单卡在审核环节，最久的 180 天" |

### 3.6 粒度与排序：**"一句话"是汇总层，替不了"可办的明细"**

> Fred 问：不一定每天只 3 条吧？按重要程度/时间排序？给 5 条，处理掉的明天就没了？

**分两层，别混**：

| 层 | 给谁 | 形态 | 为什么 |
|---|---|---|---|
| **汇总层（一句话）** | 市财务、市领导、县财务 | **每类 1 条**，句子里带汇总数 + 点名异常对象 | 他们不需要知道 47 个所的明细，需要"今天有没有事、在哪个县" |
| **可办明细层（列表）** | 所长、县运检/营销 | **一类 N 条，按重要性排序，默认回 10 条**（`limit` 可调，上限 20） | 他们要**照着清单一件件办**，一条汇总办不了事 |

**"处理掉的就没了"——这条天然成立，不需要我们记状态**：判据是**现算的**。哪所把钱花了（执行率上去了）或把单推过了（工单离开状态 1/2），第二天它就不在命中集里。前端按"今天返回的列表里没有 = 已处理"就能自动关闭。**额外的好处**：接口无状态、不落库、不会因为我们重启而丢"已完成"。

**排序 = 重要程度 + 时间（复合，不是二选一）**

```
1) 严重档：执行率 = 0  →  高于  执行率 > 0 但低于阈值
2) 档内先按 影响金额 降序
3) 平手再按 停留天数 降序
```

理由：预警是"资源往哪投"的问题，金额大 + 停得久的最该先动。**同时单条里两份信息都要给**，让他自己判：

- 金额类：`余额 48.20 万元`（不重要程度）
- 时间类：`卡在供电所内部审核 180 天`（不重要程度）
- 双高才是尖子：`何店供电所：25 单 / 49.39 万卡在内部审核，最久 63 天` ← 件数最多
- 金额尖子：`洛阳供电所：13 单 / 114.43 万卡在内部审核，最久 94 天` ← 钱最多

**所以接口返回的是"排好序的全量"（可截断），不是"我替你挑 3 条"**。要几条由调用方给 `limit`，我们不锁死。

**所长视角的 `items` 长这样（实查）**：

```
[{work_order_id, name, station, amount, node, days, level, is_new_today}]
人事局公变表箱、端子箱破损严重…   75172.15  营销部审核    175天  积压
首义新1#台区表箱、端子箱破损严重… 57084.82  营销部审核    175天  积压
处理建设2#台区低电压             52320.02  供电所内部审核 154天  积压
投运新春7#台区                   46465.06  供电所内部审核 159天  积压
指城寺一组台区表箱、端子箱…       22418.30  营销部审核    175天  积压
```

**"今日新增"也能标**：`a.create_time = 今天` 就是今天刚进这个节点的（实测今天 0 件）。这样调用方按"今天返回里没有 = 已处理"就能自己处理状态，**我们不用落库**。


**对账已验（必须成立，否则各级数字互相打架）**：

```
4 县分配合计      19,100,000.00  ｜ 市级查出 19,100,000.00  ｜ 差 0.00
4 县已审批合计     1,121,125.87  ｜ 市级查出  1,121,125.87  ｜ 差 0.00
曾都县积压 54 单 ← 洛阳 13 + 两水 16 + 何店 25 = 54  ✅

### 3.7 每类一句话怎么写（**语气是这个接口的门面，按这个来**）

**统一句式**：`对象 + 截至今天 + 事实 + 后果`

**语气规矩**

| 要 | 不要 |
|---|---|
| 供电所自己的业务说法：**"未审核 / 未审批 / 待审批 / 已通过"** | **"卡在审批"**（这是我们的分析词，不是他们的词） |
| 完整单位名：**"供电所 / 万元"** | "单子""钱""卡住" |
| 说**后果**：花不完多少、还差几个项目 | 只说"异常""超标" |
| 数字精确到两位小数 | "很多""大量""严重" |

**10 类的一句话（括号里是实测素材）**

| 类 | 一句话 |
|---|---|
| **A 预算花不完** | `两水供电所：年初分配 37.87 万元，截至今日未审批通过一笔，按目前进度年底结余约 37.87 万元` |
| **B 待审批积压** | `两水供电所：截至今日 23 个项目未审批，合计 56.88 万元，其中 15 个已停留超 90 天` |
| **C 已批未动** | `均川供电所：7 个项目已通过审批未开工，合计 28.58 万元，最早一单已等待 5 个月` |
| **D 审批环节停留** | `两水供电所：6 个项目停在营销部审核，最长的已停留 175 天，另有 10 个停在供电所内部审核` |
| **E 卡在哪个环节** | `曾都区：54 个项目未审批，主要集中在供电所内部审核 48 个、县公司财务部审核 6 个` |
| **F 零执行** | `全市 41 个供电所截至今日未审批通过一笔，涉及分配预算 1661.27 万元` |
| **G 数据质量** | `2026 年 658 个项目均未填写计划完工日期，无法判断是否超期` |

**一句里有几件事？** 每类**一件**。所以两水供电所会收到**两条**（预算花不完 1 条 + 未审批积压 1 条），不是揉成一句。

**字段就这么几个**：`status` / `account` / `name` / `role_code` / `role` / `scope` / `scope_type` / `today` / `checked_at` / `alerts[]`；每条预警 = `type` + `level` + `title` + `total` + `amount` + `data`（+ 明细的角色才有 `items`）。

**契约纪律**

| 约定 | 说明 |
|---|---|
| **无异常也回 200** | `status="ok"`、`alerts=[]`。**绝不空返回**（沿用 `/api/skill/title` 已有纪律） |
| `status` | `abnormal` 有预警 / `ok` 无异常 / `unknown` 账号解析不了（`alerts=[]` + `error`） |
| **一条一件事** | 预算花不完、审批积压是两件事 → 两条。不合并、不用一句总结代替 |
| **`title` ≤ 40 汉字** | 范围 + 结论 + 最多 2 个数。明细不进这句话 |
| **`total` 与 `returned` 分开** | `total` = 命中总数，`returned` = `items` 实际条数。不许用 `items.length` 冒充 `total` |
| `is_new_today` | `create_time = today` 的明细标 true（实测今天 0 件） |
| **本期不返回跳转字段** | `route`/`params` 留二期（要他们给路由模板）。`items` 已带 `work_order_id`/`station_ids`/`year` |
| 耗时 | ≤ 8 条 SQL；**目标 < 3 秒** |
