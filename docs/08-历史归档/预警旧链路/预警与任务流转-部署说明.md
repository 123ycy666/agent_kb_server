## 二 配置（都可不配，默认能跑）

| 变量 | 默认 | 作用 |
|---|---|---|
| `DISPATCH_ON` | `1` | 总开关；`0` 时新接口返回 503（回滚用） |
| `DISPATCH_AI_ON` | `1` | `0` 时只用规则建议，不调模型 |
| `DISPATCH_TICK_MINUTES` | `10` | 内部催办/升级/自动核销循环间隔；`0` = 关闭，改由外部 cron 调 `/api/dispatch/tick` |
| `DISPATCH_FILES_DIR` | `<server>/data/dispatch` | 附件与报告落盘目录 |
| `DISPATCH_SCAN_ACCOUNTS` | 空 | 逗号分隔；只扫这些账号（调试用），空 = 全部有效账号 |

> `INTERNAL_SERVICE_TOKEN` 沿用现有 `.env`，不新增。

## 三 升级步骤

```bash
# 0) 备份（可选但建议）
pg_dump -h 127.0.0.1 -p 5433 -U kb -d ad_new -Fc -f ad_new_before_dispatch.dump

# 1) 建表（幂等；空库/老库都跑这一条）
psql -h 127.0.0.1 -p 5433 -U kb -d ad_new -v ON_ERROR_STOP=1 -f db/dispatch_tables.sql

# 2) 升级依赖（无新依赖；确认 docx 可用）
python -c "import docx; print('docx ok')"

# 3) 重启服务（启动时会 create_all + 增量迁移，幂等）
#    Windows: 启动全部.bat    Linux: systemctl restart secretary

# 4) 冒烟（见第四节）
```

**为什么还要跑 SQL**：`create_all` 只建"不存在的表"，但 DDL 文件里还带索引与 CHECK；
先跑 SQL 可以保证索引/约束一定在。两步都幂等，谁先谁后都行。

### 四之二 2026-10-28 增量验收（裂变 / 双条件闭环 / 改时限）

```bash
# 5) 迁移到位的三项自检（都应返回非空）
psql -h 127.0.0.1 -p 5433 -U kb -d ad_new -c "\d dispatch_task" | grep -E "case_id|case_key|require_reply"
psql -h 127.0.0.1 -p 5433 -U kb -d ad_new -c "\di uk_task_case_root"

# 6) 裂变冒烟（县财务账号，把县级单下发给各所）
curl -s -X POST http://127.0.0.1:8200/api/tasks/<task_id>/fanout \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" -d '{}'

# 7) 改时限 / 申请延期（各自 200，事件里多 adjust / extend_request）
curl -s -X POST http://127.0.0.1:8200/api/tasks/<task_id>/adjust \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"due_at":"2026-11-30T18:00:00+08:00"}'
```

| 判据 | 期望 |
|---|---|
| `uk_task_case_root` 唯一索引 | 存在（老数据里根任务 `case_key` 已回填，不会撞） |
| fanout `created` | 等于该县所数；每条 `verify_rule.station_ids` = 该县自己的所（不是全市） |
| fanout 再来一次 | `created` 为空、`reused` 命中（不重复开单） |
| 上级闭环 | 子任务没全闭环时 tick 记 `verify_state=pending`，不自动闭环 |
| adjust 子任务改晚 | 实际落到父任务时限（不会出现"父逾期、子还早"） |

> **迁移前置检查**（只在老库升级时需要）：若历史上手工造过多棵同 `case_key` 的根任务，
> 建唯一索引会失败。先跑
> `SELECT case_key, count(*) FROM dispatch_task WHERE parent_task_id IS NULL AND deleted_flag=0 AND status NOT IN ('cancelled','closed') GROUP BY 1 HAVING count(*)>1;`
> 有行就先人工并单，再执行 `db/dispatch_tables.sql`。

### 四之三 定时任务搬进包内之后（2026-10-28 首次实跑踩到的三个坑）

**导火索**：`jobs.yml` 里已经有 `dispatch_tick`，内置 tick 循环会因此主动让位；
但调度器没起、依赖没装、站点包没进镜像 —— 结果线上**周期 tick 直接停摆**。三处都已在仓库修掉：

| 坑 | 现象 | 修法 |
|---|---|---|
| 镜像里没有站点包 | 容器内 `/config/sites` 不存在 → `jobs.yml` 读不到，调度器空转 | `deploy/Dockerfile.merged` 加 `COPY config/ /config/` |
| 镜像里没有 apscheduler | 启动日志 `站点包定时任务启动失败：No module named 'apscheduler'` | `server/requirements.txt` 补声明；Dockerfile 的 pip 行加 `apscheduler` |
| 应用从没 `start()` 调度器 | `jobs.yml` 读得到但没人调 `scheduler.start()` | `main.py` lifespan 里 start/stop；`SITE_JOBS=0` 只让单进程跑 |

**部署后必查这一条**（running=true + 6 条 job + next 时间，才说明定时活真在跑）：

```bash
T=$(grep -E '^INTERNAL_SERVICE_TOKEN=' /root/agentkownlg/merged/.env.production | cut -d= -f2-)
curl -s http://127.0.0.1:8200/api/dispatch/jobs -H "X-Internal-Token: $T" | python3 -m json.tool
```

期望 6 条：`selfcheck_daily` / `dispatch_tick`（每 10 分钟）/ `dispatch_scan_daily|weekly|monthly|yearly`。
`recent` 里能看到已经跑过的活（`dispatch_tick` 启动后最多等 10 分钟就会出现一条）。

**旧 crontab**：2026-10-28 已清空（备份 `/root/agentkownlg/_bak_crontab_20261028_115037.txt`），
扫描交给包内调度器；**不要再把 `alert_cron.sh` 加回 crontab**，否则一天扫两遍。

**多 worker**：APScheduler 是进程内调度器，多 worker 会每个进程各跑一遍 → 设 `SITE_JOBS=0`，
只让一个进程跑（或单独起一个只有调度器的进程）。

## 五 定时任务

| 频率 | 调用 | 说明 |
|---|---|---|
| 每天 8:00 | `POST /api/alerts/scan {"cadence":"daily"}` | 预算 + 项目类 |
| 每周一 | `POST /api/alerts/scan {"cadence":"weekly"}` | 目前只有默认关的子判据，可不配 |
| 每月 5 日 | `POST /api/alerts/scan {"cadence":"monthly"}` | 指标类 + 完工未复盘 |
| 每年 1/7 月 | `POST /api/alerts/scan {"cadence":"yearly"}` | 复盘类 |
| 每 10 分钟 | 服务内部已自带（`DISPATCH_TICK_MINUTES`）；也可外部调 `POST /api/dispatch/tick` | 催办/升级/自动核销 |

**多进程/多实例**：内嵌 tick 会每个进程各跑一遍（幂等，但白耗 DB）。
多实例部署请设 `DISPATCH_TICK_MINUTES=0`，只让一个实例（或外部 cron）调 tick。

## 七 性能实测（2026-10-19，本机 → 远程 MySQL 3306）

| 动作 | 账号/范围 | 耗时 |
|---|---|---|
| 全量 daily 扫描 | 122 账号 / 63 个口径 | **31 秒** |
| 全量 monthly 扫描 | 同上 | **8.5 秒** |
| 全量 yearly 扫描 | 7 个口径 | **1 秒** |
| 单账号列表 `GET /api/alerts` | 1 | < 100ms |
| tick（< 100 个在办任务） | — | < 1 秒 |
| 附件/报告 docx | 1 | < 1 秒 |

瓶颈在**业务库网络往返**（每条 SQL 约 120ms），不在代码逻辑。
已做两个优化：批量解析（58s → 0.5s）、按 cadence 跳过不用的取数（月/年扫描 59s → 9s/1s）。

## 八 已知限制

| 项 | 现状 | 何时补 |
|---|---|---|
| 4 个子判据默认关 | `acceptance_overdue` / `amount_structure` / `no_effect` / `stale` | 业务补字段（状态流转时间、产出数据）后开 |

| 通知 | 站内信；不写业务库 `t_message`（只读） | 要外部推送由上游拉接口 |
| 多实例 tick | 需关内嵌循环 + 外部统一调 | 部署时按第五节处理 |
