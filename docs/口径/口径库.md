# 查数速查手册（口径库 v2 · 已对齐《电力业务口径文档》）

本文件是查数时最先看的速查表。完整业务交接说明见同库的《电力业务口径文档》；表用途清单见《数据地图》。

## 一、查数前必须遵守的 10 条

1. **业务层级**：随州市 → 4 个供电公司 → 47 个供电所 → 线路 / 台区。四个层级各自统计，**不能默认互相加总**。
2. **时间口径**：默认"今年"= 当前自然年度 1 月 1 日至截止日；月度用 yyyy-MM 格式（如 2026-09）。
3. **summary_type 是生死线**：月末结果表里**每个 stat_month 有两行**：
   - summary_type='currentMonth' → 当月口径
   - summary_type='upCurrentMonth' → 当年截至该月累计口径
   - **2026-09 实测**：currentMonth 那行是空的（当月尚未采集，loss_rate 与 month_loss_rate 都是 NULL、售电量 0）；upCurrentMonth 那行才有数（loss_rate=2.61、售电量 34.55 亿 kWh、平均停电 1.9316 小时、故障报修 3087、意见工单 156、跳闸 5821）。
   - 所以：问"截至 X 月 / X 月累计"→ 取 upCurrentMonth 行；问"X 月当月"→ 取 currentMonth 行；**当月行为空就如实说"当月未采集"，不要拿累计值当当月值，也不要因为 currentMonth 行空就说整个指标查不到。**
4. **缺失不等于 0**：指标缺失要显"暂无数据"，不能当 0（会影响排名）。t_power_station_monthly_core_stat.line_loss_rate 在 2026 年 2–7 月有 47 行全为 0，那是未采集。
5. **比率和平均类指标不能相加，也不能对下级简单平均**：线损率、用户平均停电时长属于这一类。
6. **市/公司级结果必须用中台结果性数据**，不能用 47 个供电所加总替代——公司组织下还有大客户班组等本系统没有记录的单位。
7. **线损率、用户平均停电时长不在本系统重算**：中台过程数据不完整，直接展示中台结果。
8. **统计要排除已删除数据、按归属去重**；同一资源在同一月份原则上只保留一条有效记录。
9. **公司维度不能拿公司 ID 当供电所 ID**：必须先展开该公司下的供电所集合。
10. **回答里必须说清**：统计范围、统计时间、数据来源、指标范围（是供电所 6 项还是台区 2 项）、以及缺失/估算说明。

## 二、两套"成效指标"范围（不要混）

**供电所成效 = 只要这 6 项**：售电量、线损率、意见工单、故障报修工单、用户平均停电时长、故障跳闸次数
（用户数、台区数、低电压次数、影响户次、优先级分数等只是辅助解释字段，不算成效指标）

**台区成效 = 只要这 2 项**：售电量、线损率
（意见工单、故障报修工单、停电时长、跳闸次数**不属于**台区成效）

## 三、工单状态码（业务定义，必须照这张表解释）

| 值 | 名称 | 业务含义 |
|---|---|---|
| 0 | 草稿 | 可编辑，尚未提交 |
| 1 | 提交审核 | 已提交，等待审批流 |
| 2 | 审核中 | 当前存在审批任务 |
| 3 | 审核通过，待施工 | 审批完成，可进入施工 |
| 4 | 已驳回 | 审批未通过，需修改后重新提交 |
| 5 | 已取消 | 工单已取消 |
| 6 | 施工中 | 已开始施工 |
| 7 | 施工完成，待验收 | **系统用状态 7 作为"已完成"分支** |
| 9 | 已修改，待重新提交 | 驳回后已修改 |

- 早期阶段（尚未施工）= 0、1、2、9
- 系统把 7 当"已完工"，但业务上是否要求"验收完成"才算完成，仍未确认——回答时说明这一口径。
- 未审批通过的工单不能直接施工。

## 四、台区治理成效的时间窗口

- 工单状态 = 7（施工完成待验收）：以**实际完成时间**所在月为基准，取 **前 1 个月 + 当月 + 后 1 个月**；完成时间取不到时依次退到 plan_end_time、create_time，并标注"估算"。
- 工单状态 ≠ 7：取**当前月之前的 3 个完整月份**（不含当前未结束的月）。
- 结果要带上：工单状态、台区、月份、售电量、线损率、时间基准来源、是否估算。

## 六、预算口径的两个坑

1. **默认"今年"**：问"精益预算分配了多少"默认查当前自然年度，不是历史累计；过滤要用工单/预算记录的**业务年份**，不能只按创建时间推断。
2. **t_power_company_budget_allocation 按版本重复存**：有 version / is_new 字段，全量 SUM 会重复计算（2026 年 21 条全加 = 7750 万，实际有效的是 is_new=1 的 4 条 = 1880 万）。**先按 is_new=1 过滤，再 SUM**；按单位拆分时同样先过滤。

## 七、待业务确认（回答时不要自己猜）

1. 4 个供电公司的正式名称与编码；
2. 47 个供电所的正式名称、所属公司、有效状态；
3. 台区与线路的直接关联字段；
4. "今年预算"用发布年份 / 预算年度 / 其他业务年份字段；
5. 用户平均停电时长统一用分钟/户还是小时/户；
6. 线损率跨台区、供电所、公司的加权规则；
7. 排名正负向、并列与缺失值处理规则；
8. 状态 7 是否等于实际施工结束，还是要新增"验收完成"状态；
9. 市公司财务部、市公司领导节点是否需要启用。

在确认前：**保留原始值与统计月份，回答里写明统计时间和数据范围。**

## 八、范例：查「2026 年 9 月全市线损率」

    SELECT stat_month, summary_type, loss_rate, month_loss_rate, sales_volume, average_outage_duration,
           fault_repair_work_order, feedback_work_order, trip_count
    FROM t_power_push_city_month_summary
    WHERE stat_month = '202609' AND deleted_flag <> '1'

结果两行：

| summary_type | loss_rate | month_loss_rate | 售电量 | 停电时长 | 故障工单 | 意见工单 | 跳闸 |
|---|---|---|---|---|---|---|---|
| currentMonth | NULL | NULL | 0 | NULL | 0 | 0 | 0 |
| upCurrentMonth | **2.61** | NULL | 34.55 亿 | 1.9316 | 3087 | 156 | 5821 |

→ **答案：2026 年 9 月全市线损率 2.61%（当年 1–9 月累计口径）**；当月值未采集。
→ 同一张表同一行还带着全市其余 5 项指标，问"各项核心指标"时应一并给出，不要只答线损率。

## 九、历史踩坑（真踩过）

1. 线损率只在 t_power_push_line_loss 一张表找 → 那张表 0 行 → 误报"数据缺口"。全市/区县实际在月度汇总表，所级在考核表。
2. 预算表不按 is_new 过滤 → 数字翻约 4 倍。
3. 把 line_loss_rate 的 0 当"线损为零"。
4. 县级下钻：很多推送表没有县公司字段，只能用 power_station_id / company_id 关联 t_power_company → t_power_supply_company。
5. 意见工单有部分记录没有 power_station_id，县级之和小于全市——这是数据现状，不是 bug。
6. 估算行数不可信（InnoDB 估算 25 万实际 0 行），用前先 COUNT。
