# 工作流接口文档（前端对接）

| 项 | 值 |
|---|---|
| 版本 | v1（2026-11-06） |
| 基址 | `/api/workflows`（**不带 v1**，与问数同一套，前端用 `agentHttp`） |
| 鉴权 | `Authorization: Bearer <JWT>`，全部接口都要登录 |
| 时间 | ISO 8601，带时区（`2026-11-06T16:44:12+08:00`） |
| 错误体 | `{"detail": {"code": "...", "message": "...", "detail": null}}` |
| 代码位置 | `server/app/workflow/api.py`；数据表 `wf_*`（9 张） |

> 长耗时接口：`/docs/{id}/dry-run`、`/run`、`/schedules/{id}/run`、`/schedules/{id}/dry-run` 会真实调用模型，**单份文档约 2~4 分钟**。它们不阻塞其它请求，前端要自己给 loading 和超时（建议 300s）。

---

## 一、页面与接口对照

| 页面 | 用到的接口 |
|---|---|
| 规则文档列表 | `GET /docs`、`POST /docs`、`DELETE /docs/{id}`、`PUT /docs/{id}`（只改 enabled） |
| 文档编辑 | `GET /docs/{id}`、`PUT /docs/{id}`、`GET /docs/{id}/export` |
| 文档测试 | `POST /docs/{id}/dry-run`、`GET /runs/{run_id}`（取步骤留痕） |
| 定时任务 | `GET /schedules`、`POST /schedules`、`PUT /schedules/{id}`、`DELETE /schedules/{id}`、`POST /schedules/{id}/run` |
| 运行记录 | `GET /runs`、`GET /runs/{id}` |
| 事项 | `GET /items`、`GET /items/{id}`、`POST /items/{id}/close`、`POST /items/{id}/chat` |
| 发送记录 | `GET /notifications` |

## 二、数据结构

### 2.1 文档 `doc`

```json
{
  "id": 3, "name": "预算花不完", "work_type": "detect", "work_type_label": "取数工作流",
  "alert_type": "预算", "enabled": true, "disabled_reason": null, "scope_level": "station",
  "doc": {"what": "…", "data": "…", "calc": "…", "judge": "…", "store": "…"},
  "version": 9, "updated_by": "admin", "updated_at": "2026-11-06T17:12:03+08:00",
  "missing": [], "complete": true,
  "schedules": [{"id": 4, "name": "预算花不完 08:00"}]
}
```

- `work_type`：`detect`（取数）/ `send`（发送）
- `doc` 的键由工种决定：取数五节 `what/data/calc/judge/store`；发送五节 `what/source/who/cadence/store`
- `missing`：还没填的节标题；`complete` = `missing` 为空
- 详情接口额外返回 `sections`（[{key,title,hint,example}]）与 `versions`

### 2.2 定时方案 `schedule`

```json
{
  "id": 4, "name": "预算花不完 08:00", "cron": "0 8 * * *", "crons": ["0 8 * * *"],
  "timezone": "Asia/Shanghai", "enabled": false, "note": null,
  "doc_count": 1, "doc_ids": [3], "doc_names": ["预算花不完"],
  "next": ["2026-11-07 08:00", "2026-11-08 08:00"], "cron_error": ""
}
```

- 一个方案一个时间点：**要 8 点、9 点各跑一次，就建两个方案，两个方案都挂同一份文档**（多对多，不会重复建事项）
- `next`：未来 5 次触发时间，字符串 `YYYY-MM-DD HH:MM`

### 2.3 运行批次 `run`

```json
{
  "id": 21, "doc_id": 3, "doc_name": "预算花不完", "doc_version": 9, "work_type": "detect",
  "trigger": "test", "status": "ok", "dry_run": true,
  "started_at": "2026-11-06T17:20:01+08:00", "finished_at": "2026-11-06T17:23:15+08:00",
  "data_as_of": "2026-11-06",
  "checked_n": 47, "hit_n": 45, "new_n": 0, "closed_n": 0, "sent_n": 0, "error": null
}
```

- `trigger`：`cron`（定时）/ `manual`（页面点运行）/ `test`（试跑）
- `dry_run=true`：没写结果表、没写事项表
- 详情 `GET /runs/{id}` 额外返回 `logs[]`（步骤）、`doc_snapshot`（那一轮的文档原文）、`sections`

`logs[]` 元素：

```json
{"seq": 3, "at": "…", "kind": "sql", "payload": {"sql": "SELECT …", "rows": 47, "error": null}}
```

`kind`：`read_doc` / `sql` / `tool` / `error`

### 2.4 事项 `item`

```json
{
  "id": 2, "doc_id": 3, "alert_type": "预算",
  "object_key": "18", "object_name": "吴山供电所",
  "scope_type": "station", "scope_key": "18",
  "value": 0.0, "threshold": 0.6, "op": "<", "tier": "high",
  "detail": {"分配额": "68.87 万", "已花": "0 万", "执行率": "0%", "预计结余": "68.87 万"},
  "evidence": {"分配额": "t_power_ai_company_budget_result.budget_amount 合计", "数据截止日": "2026-11-06"},
  "reliable": true,
  "title": "吴山供电所 预计年底结余 68.9 万", "body": null,
  "status": "open", "close_reason": null,
  "first_seen": "2026-11-06T16:20:00+08:00", "last_seen": "2026-11-06T17:23:00+08:00",
  "seen_times": 2, "sent_at": null
}
```

- `tier`：`high` / `mid` / `low`（可能为 null）
- `status`：`open` / `closed`；`close_reason`：`数据恢复` / 人工填写
- 详情额外返回 `doc_name`、`history[]`（最近 30 轮取值）、`notifies[]`

### 2.5 发送记录 `notify`

```json
{"id": 1, "item_id": 2, "login": "sngdssz", "name": "张所长", "channel": "station",
 "reason": "所级事项，发给该所负责人", "ok": true, "error": null,
 "sent_at": "2026-11-06T08:31:00+08:00"}
```

### 2.6 运行参数 `param`

```json
{"key": "max_steps", "value": "80", "note": "单轮最多几步工具调用"}
```

键：`max_steps`、`max_items_per_run`、`no_repeat_days`、`retention_months`、`send_channel_default`

## 三、接口

### 3.1 模板

`GET /templates/{work_type}`（`detect` | `send`）

```json
{"work_type": "detect", "label": "取数工作流",
 "sections": [{"key": "what", "title": "一 管什么", "hint": "…", "example": "…"}]}
```

### 3.2 文档

| 方法 | 路径 | 参数 / 请求体 |
|---|---|---|
| GET | `/docs` | `work_type?`（detect/send） |
| POST | `/docs` | `{name, work_type, alert_type?, scope_level?}` |
| GET | `/docs/{id}` | — |
| PUT | `/docs/{id}` | 见下 |
| DELETE | `/docs/{id}` | — |
| POST | `/docs/{id}/duplicate` | `{name?}` |
| GET | `/docs/{id}/export` | 返回 `text/markdown` 附件 |
| POST | `/docs/{id}/import` | `{markdown}`（按 `## 标题` 覆盖对应节） |
| GET | `/docs/{id}/versions/{version}` | — |
| POST | `/docs/{id}/dry-run` | `{today?}` |
| POST | `/run` | `{doc_id, dry?}` |

**PUT /docs/{id}** 请求体（都可选，只传要改的）：

```json
{"name": "预算花不完", "doc": {"what": "…", "data": "…"}}
```

- 传了 `doc` → `version` 自动 +1
- 传 `enabled: false` → **自动从所有定时方案上解挂**，响应里 `detached_from` 是被解挂的方案名
- 响应 = 文档对象

**POST /docs/{id}/dry-run** 响应：

```json
{"run_id": 21, "status": "ok", "checked_n": 47, "hit_n": 45,
 "steps": 24, "elapsed_s": 194.2, "dry": true, "closed_n": 0}
```

- 文档没填全 → `422 {"code":"DOC_INCOMPLETE","missing":["三 怎么算"]}`
- 跑失败 → `500 {"code":"RUN_FAILED"}`；失败原因也写进了那一轮的 `run.error`

### 3.3 定时方案

| 方法 | 路径 | 参数 / 请求体 |
|---|---|---|
| GET | `/schedules` | — |
| POST | `/schedules` | `{name, crons:["0 8 * * *"], doc_ids:[3], enabled?}` |
| PUT | `/schedules/{id}` | 同上任意子集，含 `doc_ids`（整体替换挂载） |
| DELETE | `/schedules/{id}` | 还挂着文档 → `409 SCHEDULE_IN_USE` |
| POST | `/schedules/{id}/run` | 立即跑（多份并行） |
| POST | `/schedules/{id}/dry-run` | 该方案下所有文档试跑（不落库） |

`cron` 与 `crons` 都接受；单时间点传 `crons:["0 8 * * *"]` 即可。

**POST /schedules/{id}/run** 响应：

```json
{"schedule": "每天 08:00 取数",
 "docs": [{"doc": "预算花不完", "run_id": 22, "status": "ok", "hit_n": 45},
          {"doc": "已批未开工", "status": "failed", "error": "…"}]}
```

### 3.4 运行记录

| 方法 | 路径 | 参数 |
|---|---|---|
| GET | `/runs` | `doc_id?`, `status?`, `limit?`(≤200), `offset?` |
| GET | `/runs/{id}` | — |

响应：`{"total": 21, "items": [run, …]}`；详情多 `logs`、`doc_snapshot`、`sections`。

### 3.5 事项

| 方法 | 路径 | 参数 |
|---|---|---|
| GET | `/items` | `status?`(open/closed), `doc_id?`, `alert_type?`, `tier?`, `q?`, `limit?`(≤500), `offset?` |
| GET | `/items/{id}` | — |
| POST | `/items/{id}/close` | `{reason}`（必填）→ 响应事项对象 |
| POST | `/items/{id}/chat` | 无体 → `{session_id, chat_store, item}` |

- `chat_store`：`ok` / `unavailable`（会话表缺失时）；前端拿到 `session_id` 后跳对话页并渲染 `item`

### 3.6 发送记录 / 参数

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/notifications` | `limit?`(≤500), `offset?` |
| GET | `/params` | `{items:[{key,value,note}]}` |
| PUT | `/params` | `{items: {"max_steps": "60"}}` |

## 四、错误码

| HTTP | code | 场景 |
|---|---|---|
| 401 | `UNAUTHORIZED` | 没带或带错 JWT |
| 404 | `DOC_NOT_FOUND` / `SCHEDULE_NOT_FOUND` / `RUN_NOT_FOUND` / `ITEM_NOT_FOUND` / `VERSION_NOT_FOUND` | 对象不存在或已删 |
| 409 | `NAME_TAKEN` | 文档重名 |
| 409 | `SCHEDULE_IN_USE` | 删方案时还挂着文档，响应带 `docs` |
| 422 | `NO_NAME` / `EMPTY` | 文档名或导入内容为空 |
| 422 | `BAD_CRON` / `BAD_SCHEDULE` | cron 非法 / 名称或时间点为空 |
| 422 | `DOC_DISABLED` | 挂载了已停用的文档，响应带被拒名单 |
| 422 | `DOC_INCOMPLETE` | 文档缺节就试跑/运行，响应带 `missing` |
| 422 | `NO_REASON` | 关闭事项没写原因 |
| 500 | `RUN_FAILED` | 跑一轮失败（见 `run.error` 与运行日志） |

## 五、前端注意事项

1. **无推送**：所有列表靠轮询/手动刷新，没有 WebSocket、SSE。
2. **长耗时**：测试/运行建议 300s 超时，按钮置 loading，跑完再刷新列表与运行记录。
3. **一方案一时间**：要同一份文档跑两次（8 点、9 点），就建两个方案各挂它；不要复制文档（会各建一套事项）。
4. **停用即解挂**：`PUT /docs/{id} {enabled:false}` 会把文档从所有方案摘掉；重新启用后需重新挂。
5. **不能挂停用文档**：挂载接口会返回 422 并列出被拒文档，前端下拉应把停用文档置灰。
6. **事项的唯一性**：同一份文档的同一个对象只有一条事项，重复命中只更新 `last_seen` / `seen_times`。
7. **数字口径**：`value`/`threshold` 是数值（0.00、0.6），展示时按 `detail` 里的中文项渲染更稳妥；`detail`/`evidence` 的键由文档第五节决定，前端不要写死键名。
