## 〇、接口一览

| 想做什么 | 调用 | 备注 |
|---|---|---|
| 会话列表 | `GET /api/sessions` | **不传 `limit` = 全部返回**；默认只看自己 |
| 某场会话的全部消息 | `GET /api/history?session_id=…` | `limit` 不传 = 全部 |
| **删除一场历史对话** | `DELETE /api/sessions/{id}` 或 `POST /api/sessions/{id}/delete` | 软删，仅限本人 |
| 继续聊 | `POST /api/ask` 回传同一个 `session_id` | 服务端自动带上上下文 |
| 预设问题 | `GET /api/presets` | 问答页"一点就问"的入口 |
| 服务/能力状态 | `GET /health` | 含 `kb`（知识库检索连通性）|

> 排障第一步永远是 `GET /health`：看服务活着之外，各能力（`name_fix` / `qa_log` / `kb` / `session_summary`）是否正常。

## 一、历史对话：怎么拿到"全部"

**核心结论：不传 `limit` 就是全部返回**，不需要翻页，也没有"默认 20 条"这回事。

⚠️ **`uid` 参数已废除**（统一用户表之后）。身份一律以登录 token 为准，
传了也会被忽略 —— 默认**只返回自己的会话**，这是刻意的权限隔离，不是 bug。
管理员要跨用户查看，用 `all_users=true`（见下表）。

### 1.1 会话列表：`GET /api/sessions`

| 参数 | 说明 |
|---|---|
| `limit` | **不传 / 传 `0` = 全部**；传正整数 = 只要前 N 条 |
| `offset` | 跳过多少条（配合 `limit` 分页）|
| `all_users` | **管理员专用**。`true` 返回所有人会话；权限不足服务端静默降级为 `false` |

响应里多了两个字段：

- `can_view_all`（bool）：当前账号有没有"看全部"的权限 —— **前端用它决定开关显不显示**，
  不要自己按角色名判断（`/auth/me` 返回的 `role_names`、`administrator_flag` 可能是 null）。
- `all_users`（bool）：本次请求实际有没有按全部用户返回。

> 排查"管理员看不到别人的历史"时先看这两个字段：`can_view_all=true` 但 `all_users=false`
> 说明前端没传参；`can_view_all=false` 说明这个账号确实没权限（不是 bug）。

```json
{
  "total": 214, "returned": 214, "limit": 5000, "offset": 0, "truncated": false,
  "sessions": [
    {
      "session_id": "s_5f224f10aaed42a2bbcf45e2d0c504dd",
      "user_code": "PROV-FIN-001",
      "title": "环潭供电所上个月的线损率",
      "ai_model": "qwen3.8-max", "channel": "webapi", "client_ip": "127.0.0.1",
      "msg_count": 4, "status": 1,
      "create_time": "2026-09-20 15:37:41", "last_msg_at": "2026-09-20 15:37:51",
      "ended_at": null, "ask_count": 2, "gap_count": 0
    }
  ]
}
```

**外层四个分页字段 —— 判断"拿全了没有"就看这几个：**

| 字段 | 说明 |
|---|---|
| **`total`** | 符合条件的**真实总数**（不受 `limit` 影响）|
| `returned` | 本次实际返回条数（= `sessions` 长度）。**不传 `limit` 时 `total == returned`** |
| `limit` | 本次生效上限；"全部返回"时等于防呆上限 **5000** |
| `truncated` | `true` = 超过防呆上限被截断，**这时才需要 `limit`+`offset` 取下一页** |

### 1.2 某场会话的全部消息：`GET /api/history`

| 参数 | 必填 | 说明 |
|---|---|---|
| `session_id` | ✅ | 不存在返 **404** |
| `limit` | | **不传 / 传 `0` = 该会话全部消息** |
| `with_steps` | | 传 `1` 时每条 AI 回答多一个 `steps` 数组（调了什么工具、SQL、耗时）|

响应结构：`{session, total, returned, limit, truncated, messages[]}`。

**渲染对话流用这几个字段就够：**

| 字段 | 说明 |
|---|---|
| `seq_no` | **排序就用它**（从 1 开始）|
| `sender_type` | **`1` = 用户，`2` = AI** → 决定左右气泡 |
| `content` | 正文 |
| `create_time` | 时间 |
| `qa_id` | **只有 AI 那条有**，做"赞/踩"时回传它 |

**做增强交互（可选）：** `fixed_question`（展示"我理解为：…"）、`unverified=1`（这条回答**没查库**、不可信 → 加警示标）、`is_gap=1`（当时答不上来）、`feedback`（`1`/`0`/`null`）、`steps`（需 `with_steps=1`）。

### 1.3 ★ "翻出历史对话继续聊"

**回传同一个 `session_id` 即可**，服务端自动带上该会话上下文：

```js
async function continueChat(sessionId, question) {
  const d = await (await fetch(`${BASE}/api/ask`, {
    method: 'POST', headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ question, session_id: sessionId })
  })).json();
  return d;   // d.session_id 仍是同一场；d.history_used 告诉你带上了几轮
}
```

| 字段 | 说明 |
|---|---|
| `history_used` | 本轮带上了几轮历史（**`0` 说明记忆没生效** —— 多半 `session_id` 传错）|
| `summary_used` | 更早轮次是否用了**会话摘要**（长会话才有）|
| `summary_skip` | 非 `null` 时写明"本轮为什么没用摘要"，排障先看它 |
| `history_injected` | 其中真正塞进提示的轮数（已摘要覆盖的不重复塞）|

> 会话聊长以后，更早的轮次会被自动压成一段摘要带入 —— 服务端行为，**前端不需要做任何事**。

### 1.4 删除一场历史对话

```
DELETE /api/sessions/{session_id}
POST   /api/sessions/{session_id}/delete      ← 兼容拦 DELETE 的网关/代理
```

两个方法行为完全一致，无请求体。成功返回 `{"ok": true, "session_id": "..."}`。

| 情况 | 返回 |
|---|---|
| 成功 | `200 {"ok": true}` |
| 不存在 / 已删 / **不是你自己的** | `404`（统一 404，不返回 403 —— 不告诉对方"这个 id 存在"） |

要点：

- **软删**：数据仍在库里（`deleted_flag=1`），管理员可恢复；删除后列表和明细都查不到。
- 明细消息与问答轨迹一并标记删除，不会继续计入统计。
- `session_id` 不是密钥（会出现在页面、日志、截图里），所以服务端强制校验归属。
- 写审计日志，动作码 `chat.delete`。

> 前端别把"删除"按钮做成"清空当前对话"——用户会误解成只删这一轮。
> 语义是"删掉一条历史记录"，按钮就该出现在历史列表的每一行上。

## 二、错误码

| 码 | 含义 | 你要做什么 |
|---|---|---|
| **200** | 成功。**"查不到 / 不存在"也走 200**（如 `total: 0`）| 正常解析 body |
| **400** | **你传错了**：缺必填参数、类型不对、请求体不是合法 JSON | 改请求；原因在 `error` 字段 |
| **404** | 资源不存在（`session_id` 查不到、路径不存在）| 看 `error` 说明 |
| **405** | HTTP 方法用错 | 看第〇节接口表 |
| **500** | **服务端故障**（不是你的错）| 把 `error` 全文给我们 |
| **502 / 503 / 504** | 云端故障 / 本地没配好 / 云端超时 | 找我们，先看 `/health` |

> **400 与 500 一定要分清**：400 是"改请求就行"，500 是"找我们"。
> 服务端保证：**传错参数一律 400**，所有未预料的异常兜成 **500 JSON + 日志**（不会直接掐断连接）。

## 三、端到端（历史对话部分）

```js
const BASE = 'http://47.121.183.81:8200';

// ① 会话列表（全部）
async function sessions() {
  const d = await (await fetch(`${BASE}/api/sessions`)).json();   // 不传 limit = 全部
  return d.sessions;                                              // d.total === d.returned
}

// ② 某场会话的全部消息
async function messages(sessionId, withSteps = true) {
  const u = new URL(`${BASE}/api/history`);
  u.searchParams.set('session_id', sessionId);
  if (withSteps) u.searchParams.set('with_steps', '1');
  return (await (await fetch(u)).json()).messages;
}

// ③ 接着这场继续聊
async function ask(sessionId, question) {
  return (await (await fetch(`${BASE}/api/ask`, {
    method: 'POST', headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ question, session_id: sessionId })
  })).json()).answer;
}
```

## 四、排障速查

| 现象 | 先看这个 |
|---|---|
| 会话记忆好像没生效 | `/api/ask` 响应看 `history_used` 和 `summary_skip` —— **这两个字段就是为排障加的** |
| `total` 和 `returned` 对不上 | 只有超过防呆上限（5000）才会发生，此时 `truncated: true` |
| `/health` 里 `kb: false` | 知识库检索不通（`kb_reason` 写明原因）：多为对接账号密码错 / 网络不通 |
| 访问 `/kb` 或 `/api/kb/**` 返回 404 | **正常**：知识库管理接口已于 2026-10-13 移除，改用知识库系统自己的界面 |
| `/api/ask` 说"查不到"但知识库明明有 | 该文档对你不可见（private 非本人），或 `KB_IDS` 里没包含它所在的库 |
