## 1 概览

### 1.1 这套接口解决什么

| 能力 | 说明 |
|---|---|
| 四类预警 | 预算 / 项目全过程 / 穿透式复盘 / 指标，13 个子判据；一条预警一行，每轮扫描 upsert |
| 预警查询 | 按登录人角色 + 数据范围过滤；一条一句话 + `data` 明细 + 建议核销规则 |
| **点预警进对话** | 前端点一下 → 后端建/复用会话、写入卡片消息、返回首段 AI 话 |
| 任务流转 | 推荐承办人（可多人）→ 确认下发 → 接单 → 方案 → 回执 → 核销；催办/升级/督办/转派/继续下发/归档 |
| **对话建任务** | 用户说"让 X 3 天内办 Y" → 智能体拟草稿（draft）→ **在会话里发一条确认消息** → 人回「确认」才建任务 |
| 两种闭环 | **自动核销**（预算率/指标值/工单状态/审批待办数实测达标）/ **人工回执**（方案质量、现场情况） |
| AI | 根因分析、拟办草稿、执行建议、实施方案、上报报告（docx）、润色；**数字只来自实测，模型只写措辞** |
| 通知 | 站内信（主责/协办/抄送/发起人/上级），未读数轮询 |

### 1.2 前后端边界（重要）

| 谁 | 做什么 |
|---|---|
| **后端** | 本文全部 43 个接口：扫描、查询、卡片、会话落库、AI、任务动作、通知、统计 |
| **前端** | 列表/对话/下发确认/任务/通知 5 个界面；点击预警 = 调 `POST /api/alerts/{id}/chat` 并渲染 `messages`；**对话页把 `/api/ask` 返回的 `task_draft` 渲染成确认卡，用户确认后调 `/api/tasks/draft/confirm`** |
| **外部定时任务** | 每天调 `POST /api/alerts/scan`；tick 默认由服务内嵌循环代跑（见 §12） |

### 1.3 数据流

```
定时/手动 scan ──> alert_item（一条预警一行，dedupe_key 唯一）
                         │
      GET /api/alerts ───┤ 列表/详情/卡片
                         │
   点击（前端）── POST /api/alerts/{id}/chat ──> 会话（卡片 + 首段话 + 建议）
                         │
        AI 拟办 ── POST /propose ──> draft（不落库）
                         │
   确认下发 ── POST /dispatch ──> dispatch_task + assignees + notice + event
                         │
   对话里说"让 X 3 天内办 Y" ── /api/ask（自动 task_draft）/ /api/tasks/draft
                         └──> draft（草稿，**还不是任务**）+ 会话里发"确认消息"
                                   │ 人回「确认」→ /api/tasks/draft/confirm
                                   └──> open 任务（后续动作同上）
                         │
  任务动作（接单/方案/回执/转派/子任务/催办/督办/升级/归档）
                         │
   tick（默认 10 分钟）──> 催办/升级/自动核销/停用转派 ──> closed
```

## 2 通用约定

| 项 | 约定 |
|---|---|
| Base URL | `http://127.0.0.1:8200`（局域网换成主机 IP） |
| 协议/编码 | HTTP/1.1，请求与响应均 **UTF-8**；JSON 用 `Content-Type: application/json` |
| 上传 | 仅附件接口用 `multipart/form-data`（字段名 `file`） |
| 时间 | 响应一律 **ISO8601 带时区**（如 `2026-10-19T16:45:30.848392+08:00`）；查询参数 `today` 用 `YYYY-MM-DD` |
| 分页 | `limit`（默认 50，上限 200）+ `offset`（默认 0）；响应带 `total` |
| 排序 | 预警：级别高→低，再按 `last_seen` 倒序；任务：`update_time` 倒序；通知：`sent_at` 倒序 |
| 幂等 | `scan` 用 `run_key` 唯一；`dispatch` 用 `idempotency_key`；`tick` 用通知 `dedupe_key` |
| 空结果 | **不返回空响应**：无预警 `status=ok, items=[]`；账号解析失败 `status=unknown, items=[], error=...`（HTTP 200） |
| 错误格式 | 统一 `{"detail": {"code": "...", "message": "...", "detail": ...}}`（见 §13） |
| 缓存 | 本组接口不设 HTTP 缓存；通知建议 30s 轮询 |
| 版本 | 新增字段保持兼容；破坏性变更走 `/api/v2` |

## 3 鉴权与权限

### 3.1 两种通道

| 通道 | 请求头 | 适用 |
|---|---|---|
| 用户 JWT | `Authorization: Bearer <token>` | 除 `scan`、`tick`、`health` 外的全部接口 |
| 内部令牌 | `X-Internal-Token: <INTERNAL_SERVICE_TOKEN>` | `POST /api/alerts/scan`、`POST /api/dispatch/tick` |

> 内部令牌来自 `.env` 的 `INTERNAL_SERVICE_TOKEN`；未配置时内部接口一律 401（**不允许无鉴权**）。

### 3.2 账号 → 角色 → 数据范围

| 部门层级 | 能看的所 | 典型角色 |
|---|---|---|
| 市公司（department_id=1） | 全市 47 个所 | `sgscwb` 市财务、`master` 市领导 |
| 县公司（10/11/12/13） | 该县全部所（曾都 7 / 随县 20 / 高新 3 / 广水 17） | `xgscwb`、`cto`、`yxb` |
| 供电所 | 仅本所 | `sz` 所长、`codea` 录入 |

- **不接受调用方传 `role` / `scope`**：一律按账号现查（`alert_scope.resolve`）。
- 解析失败（查不到/停用/无角色/映射不到所）→ 关闸：`unknown` + 空列表，**绝不默认全市**。
- 广水 3 个县级账号（部门挂在关庙所）由服务端上溯到县公司，调用方无感。

### 3.3 权限矩阵

| 接口组 | 谁能调 | 说明 |
|---|---|---|
| `POST /api/alerts/scan`、`POST /api/dispatch/tick` | 内部令牌 | 系统调用 |
| `GET /api/alerts*` | 登录用户 | 只看 `assignee_role = 我的角色` 且在账号范围内 |
| `POST /api/alerts/{id}/chat|analysis|propose` | 同上 | 预警必须对我可见 |
| `POST /api/alerts/{id}/dispatch/preview|dispatch` | 同上 | 只能下发**派给我这个角色**的预警 |
| `GET /api/tasks*` | 登录用户 | `mine`=参与/发起；`created`=我发起；`cc`=抄送我；`all` 仅管理员 |
| 任务动作 | 见 §7.2 表 | 主责/协办/发起人/上级/管理员各不同；协办不能接单/回执 |
| `GET /api/dispatch/notices` | 登录用户 | 只能看自己的通知 |
| `GET /api/dispatch/health` | 无鉴权 | 只返回数量，不含业务明细 |

## 4 枚举与字典

### 4.1 四类与 13 个子判据

| category | category_name | subtype | 名称 | 默认级别 | 频率 | 默认核销 | 收件角色 |
|---|---|---|---|---|---|---|---|
| `budget` | 预算预警 | `budget.underspend` | 预算花不完 | high | 日 | 自动 | sz/xgscwb/sgscwb/master |
| `budget` | 预算预警 | `budget.overrun` | 预算超支风险 | high | 日 | 自动 | 同上 |
| `project` | 项目全过程管理预警 | `project.approval_stay` | 审批停留超期 | high/mid | 日 | 自动 | 节点角色（§4.2） |
| `project` | 项目全过程管理预警 | `project.approved_not_started` | 已批未开工 | mid | 日 | 自动 | sz |
| `project` | 项目全过程管理预警 | `project.exec_stalled` | 施工停滞 | high | 日 | 自动 | sz |
| `project` | 项目全过程管理预警 | `project.acceptance_overdue` | 完工未上报 | mid | 日 | 自动 | sz（**默认关**） |
| `project` | 项目全过程管理预警 | `project.amount_structure` | 申报金额存疑 | low | 周 | 自动 | sz/xgscwb（**默认关**） |
| `review` | 穿透式复盘预警 | `review.low_roi` | 投入产出偏低 | mid | 年 | 人工 | xgscwb/sgscwb/master |
| `review` | 穿透式复盘预警 | `review.no_effect` | 投入未见效 | mid | 年 | 人工（**默认关**） |
| `review` | 穿透式复盘预警 | `review.not_reviewed` | 完工未复盘 | low | 月 | 人工 | sz |
| `metric` | 指标预警 | `metric.deteriorated` | 指标同比恶化 | mid | 月 | 自动 | xgscwb/cto/yxb/sgscwb/master |
| `metric` | 指标预警 | `metric.threshold` | 指标越阈值 | mid | 月 | 自动 | sz/xgscwb/cto/sgscwb |
| `metric` | 指标预警 | `metric.stale` | 指标数据过期 | low | 月 | 自动（**默认关**） |

**默认关的 4 个**（原因在 `dispatch_rules.SUBTYPES[*].note`）：
`acceptance_overdue`（2026 年状态 7 无状态流转记录）、`amount_structure`（常驻噪音）、
`no_effect`（2026 产出全空、2024 投入全空）、`stale`（数据治理项，不占每日待办）。

### 4.2 审批节点 → 应办角色

| node（`data.node`） | 收件角色 | 承办层级 |
|---|---|---|
| 供电所内部审核 | `sz` | 本所 |
| 县公司运检部审核 | `cto` | 该所所属县 |
| 营销部审核 | `yxb` | 该所所属县 |
| 县公司财务部审核 | `xgscwb` | 该所所属县 |
| 市公司财务部审核 | `sgscwb` | 市 |
| 市公司领导审批 | `master` | 市 |

### 4.3 其它枚举

| 枚举 | 取值 | 含义 |
|---|---|---|
| `level` | `high` / `mid` / `low` | 级别；决定默认回执时限（24h/72h/168h） |
| `alert.status` | `open` / `dispatched` / `closed` / `ignored` / `resolved` | 未下发 / 已下发 / 手工关闭 / 忽略 / 数据恢复自动关闭 |
| `task.status` | `draft` / `open` / `doing` / `verify` / `closed` / `cancelled` | 草稿 / 待接单 / 处理中 / 待核销 / 已闭环 / 已撤回 |
| `part` | `owner` / `collaborator` / `cc` | 主责（可多人，至少 1）/ 协办 / 抄送 |
| `assignee.state` | `pending` / `accepted` / `replied` / `done` / `declined` | 待接单 / 已接单 / 已回执 / 已完成 / 已拒接 |
| `verifier_type` | `auto` / `human` | 自动核销 / 人工确认 |
| `verify_state` | `pending` / `passed` / `failed` / `unavailable` | 未判定 / 达标 / 未达标 / 数据不可得 |
| `role_code` | `sz` `xgscwb` `cto` `yxb` `sgscwb` `master` `codea` `admin` | 所长/县财务/县运检/县营销/市财务/市领导/录入/管理员 |

**实际会发出的 `event.action`**：
`confirm`、`accept`、`decline`、`plan_submit`、`plan_accept`、`plan_reject`、`reply`、`urge`、`escalate`、
`supervise`、`transfer`、`subtask`、`close`、`reopen`、`cancel`、`archive`、`auto_close`、`comment`。
保留未用：`create`、`assign`、`verify_pass`、`verify_fail`、`reject_invalid`、`tick`。

**实际会发出的 `notice.notice_type`**：
`assign`、`urge`、`escalate`、`supervise`、`plan`、`reply`、`verify`、`close`、`reopen`。

| `message` | 人话（如「实测 0.0 >= 目标 0.0」） |
| `check_time` | 检查时间 |

### 5.8 `attachment`

| 字段 | 说明 |
|---|---|
| `id` / `task_id` | 附件 / 任务 |
| `file_name` / `size_bytes` / `md5` | 文件名 / 字节数 / MD5 |
| `uploader_name` | 上传人（系统生成的报告为「系统生成」） |
| `download_url` | 下载路径（需 JWT） |
| `create_time` | 时间 |

### 5.9 `notice`

| 字段 | 说明 |
|---|---|
| `id` / `task_id` | 通知 / 任务 |
| `notice_type` | §4.3 通知类型 |
| `title` / `content` | 标题 / 正文 |
| `read` | 0 未读 / 1 已读 |
| `sent_at` | 发送时间 |

### 5.10 会话消息（`messages[]`）

| 字段 | 说明 |
|---|---|
| `seq_no` | 会话内序号（从 1 开始） |
| `sender_type` | 1 用户 / 2 AI / 3 系统 |
| `msg_type` | 1 文本 / 2 卡片 |
| `content` | 文本内容（Markdown） |
| `meta` | 卡片为 `{kind:"alert_card", alert_id, card}`；AI 首段话为 `{kind:"ai_brief", ai_used}` |

### 7.1 扫描与预警（1~9）

#### 1) `POST /api/alerts/scan`

鉴权：`X-Internal-Token`　说明：跑一轮判据并 upsert 预警；本轮没命中的 open 项自动 `resolved`（只关本轮扫过的口径）。

请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `accounts` | string[] | 否 | 不传=全部有效业务账号（约 122 个） |
| `cadence` | string | 否 | `daily`(默认)/`weekly`/`monthly`/`yearly`/`all` |
| `today` | string | 否 | 业务日期，默认服务器当天；回放测试用 |
| `trigger` | string | 否 | `cron`/`manual`/`api`，仅记录 |

响应：

```json
{
  "run_id": 4, "run_key": "manual-daily-2026-10-19-33feddd9",
  "cadence": "daily", "today": "2026-10-19",

  "accounts": 1, "groups": 1, "errors": []
}
```

| 字段 | 说明 |
|---|---|
| `found` | 本轮命中条数 |
| `new` | 新增行数 |
| `resolved` | 本轮关闭的条数 |
| `accounts/groups` | 参与账号数 / 去重后的（角色×范围）口径数 |
| `errors[]` | `{account|role|scope, error}`；单账号解析失败不影响整轮 |

### 7.5 对话建任务（40~43）

> 设计原则：**对话触发、智能体拟稿、人工确认后才建任务**。AI 不直接建任务。

#### 40) `POST /api/tasks/draft`

请求：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `session_id` | string | ✅ | 会话 ID（与 `/api/ask` 返回的 `session_id` 同一个） |
| `question` | string | ✅ | 用户原话 |
| `alert_id` | int | 否 | 从某条预警的对话发起时带上 |
| `today` | string | 否 | 业务日期（解析时限用） |

响应（识别到意图）：

```json
{
  "intent": true,
  "task_id": 12,
  "status": "draft",
  "draft": {
    "task_id": 12, "task_no": "D20261019-0003",
    "title": "让两水供电所3天内提交整改方案并回执",
    "scope_name": "两水供电所", "role": "sz",
    "assignees": [{"employee_id": 2044600606679294102, "login_name": "sngdssz",
                   "name": "两水供电所所长", "dept_name": "两水供电所"}],
    "reply_due_at": "2026-10-22T18:00:00+00:00", "due_at": "2026-11-18T18:00:00+00:00",
    "verifier_type": "human", "verify_rule": {}, "require_plan": 1,
    "due_note": "3 天内"
  },
  "message": "我理解你要办这件事，已拟好任务草稿：…回复「确认」我就下发…",
  "session_id": "chat-xxx", "reused": false
}
```

识别不到意图：

```json
{"intent": false, "reason": "是在问进度，不是派事", "task_id": null,
 "message": "这段话我没听出\"要办一件事\"。要建任务请说：让谁、办什么、几号前。"}
```

**意图判断：语义判断，不是关键词**

> 实测四个象限都存在：有"任务/完成"等词可能只是问进度或汇报；没有这些词也可能是在让人办事
> （"这执行率得有人盯到月底"）；有词且是任务；没词也不是任务。
> 所以**不用关键词判意图**，由模型做语义判断；即使判错，也必须**人工确认**才会建任务。

| 模式 | 谁用 | 生效门槛 |
|---|---|---|
| `auto` | `/api/ask` 自动挂 | `is_task=true` 且 `confidence ≥ 0.70` |
| `explicit` | 用户主动调 `/api/tasks/draft` | `confidence ≥ 0.40` |
| `force` | "把这段对话变成任务"按钮（§43） | **不判意图**，直接拟稿 |

分类器输出（写进事件 `payload.classifier`，也随响应返回）：

```json
{"available": true, "is_task": true, "confidence": 0.86,
 "reason": "隐含要求盯到月底", "scope": "供电所", "action": "盯执行率", "deadline": "月底"}
```

- 模型不可用 / 被关闭（`DISPATCH_AI_ON=0`）→ **保守降级**：只认明确指令（建任务 / 创建任务 / 发起任务 / 下发 / 派给 / 督办），其余不拟稿；
- 判"是任务"但置信度不够 → 不弹草稿；人可以说"把这变成任务"或点按钮（`force`）；
- 判"不是任务"但用户确实想建 → 走 §43，不受分类器影响。

**时限解析**：`N 天内` → 回执 +N 天、完成 max(+N, +30)；`月底/本月` → 月底；`年底` → 12-31；`本周` → 本周日；都没有 → 默认 3 天回执 / 30 天完成。

**范围识别**：先从话里匹配 47 个所名（全名或简称，如"两水"）→ 所；再匹配 曾都/随县/高新/广水 → 县；再"全市" → 市；都没有 → 用发起人自己的范围。

**草稿规则**：
- 存成 `dispatch_task.status='draft'`，**不出现在"我的任务"列表**（除非显式 `status=draft`）；
- 承办人按范围 + 应办角色推荐（所→所长、县→县财务、市→市财务）；
- 同一会话已有待确认草稿 → **复用**，不重复建（`reused=true`）；
- 草稿 **7 天没人确认 → tick 自动取消**；
- 同时往会话里写一条 AI 消息（`meta.kind=task_draft`），即"确认消息"。

#### 41) `POST /api/tasks/draft/confirm`

请求：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `task_id` | int | 二选一 | 草稿任务 ID |
| `session_id` | string | 二选一 | 按会话找最新草稿 |
| `message` | string | 否 | 传「确认」→ 建任务；传「取消」→ 作废；其它 → 409 `NEED_CONFIRM` |
| `overrides` | object | 否 | 确认前改：`assignees` / `title` / `requirement` / `reply_due_at` / `due_at` / `require_plan` / `verifier_type` / `verify_rule` |

响应：**任务详情**（`status=open`，已发 `assign` 通知）。
取消时返回任务详情 + `"cancelled": true`。

错误：`404 DRAFT_NOT_FOUND`、`403 NOT_PARTICIPANT`（只有发起人能确认）、`409 INVALID_TRANSITION`（已确认过）、
`409 NEED_CONFIRM`（回复不是确认词）、`422 NO_OWNER`（没承办人且没传 overrides.assignees）。

#### 42) `GET /api/tasks/draft/pending?session_id=...`

```json
{"has_draft": true, "task_id": 12,
 "draft": { "…task…" },
 "message": "我理解你要办这件事，已拟好任务草稿：…"}
```

#### 43) `POST /api/tasks/draft/from-conversation`

把**整段对话**变成任务草稿（前端"把这段对话变成任务"按钮）。**不判意图**：用户已经明确要求，
直接按最近一轮用户原话/补充指令拟稿。

请求：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `session_id` | string | ✅ | 会话 ID |
| `instruction` | string | 否 | 补充一句要求；空 = 用最后一条用户原话 |
| `alert_id` | int | 否 | 从预警会话发起时带上 |
| `today` | string | 否 | 业务日期 |

响应：同 §40（`intent=true`、`status=draft`、`message` 为确认消息）。
错误：`422 EMPTY_CONVERSATION`（会话没内容）。

> 与 §40 的分工：§40 是"智能体判断这句话要不要办一件事"；§43 是"用户明确要求把这段对话变成任务"，
> 不依赖模型判断，**不会漏**。

#### `/api/ask` 的 `task_draft` 字段

`POST /api/ask` 回答完后会**自动**做一次语义判断（`auto` 模式：`is_task=true` 且置信度 ≥0.70），是则返回：

```json
{
  "answer": "…",
  "session_id": "s_xxx",
  "task_draft": {
    "intent": true, "task_id": 13, "status": "draft",
    "draft": {"title": "…", "scope_name": "…", "assignees": ["…"], "reply_due_at": "…"},
    "message": "我理解你要办这件事…回复「确认」我就下发…"
  }
}
```

- 触发失败/无意图时不返回该字段（**不影响问答**；拟办失败只打日志）。
- 前端做法：有 `task_draft` 就把它渲染成确认卡；用户点「确认」→ 调 `POST /api/tasks/draft/confirm`（`task_id` 用 `task_draft.task_id`），点「取消」→ 同接口 `message:"取消"`。

## 8 任务状态机

```
 [draft] ──confirm──> [open] ──accept──> [doing] ──submit──> [verify] ──pass──> [closed]
    │                   │ ↺decline          │  ▲                │
    │                   │ 留 open + 升级     └──┼────────────────┘  fail 退回 doing
    └──cancel──> [cancelled]  ←── cancel ──（open/doing/verify，需发起人）
```

| 迁移 | 允许 | 失败码 |
|---|---|---|
| draft → open / cancelled | ✅ | — |
| open → doing / cancelled | ✅ | — |
| doing → verify / cancelled | ✅ | — |
| verify → closed / doing / cancelled | ✅ | — |
| closed → doing（reopen，≤7 天） | ✅ | 超期 `REOPEN_EXPIRED` |
| 其它（open→closed、doing→closed、closed→open…） | ❌ | `INVALID_TRANSITION` 409 |

**两个标志位不是状态**：`escalate_level`（0→1→2）、`overdue_flag`（0/1）。
自动核销可从 open/doing/verify 直接到 closed（`close_reason=auto_verified`）。

## 9 核销规则

`verify_rule` 是 JSON，`kind` 决定算法：

| kind | 参数 | 判定 |
|---|---|---|
| `budget_rate` | `station_ids` `year` `op` `target` | 已审批（状态 3/6/7）÷ 分配额，与 target 比较 |
| `audit_node` | `station_ids` `node` `op` `target` | 该节点待处理（task_status=0）件数 |
| `status_count` | `station_ids` `status` `year` `op` `target` | 某状态工单件数（如状态 3 清零） |
| `metric_value` | `scope_type` `scope_key` `metric_code` `period_type` `op` `target` | 最新快照指标值 |
| `task_tree` | `require_child_closed` | 子任务是否全部闭环（值为未闭环子任务数） |
| `manual` | `evidence` | 不自动判，必须人工核销 |

示例：

```json
{"kind":"budget_rate","station_ids":[42],"year":2026,"op":">=","target":0.8,"close_when_met":true}
{"kind":"audit_node","station_ids":[42],"node":"营销部审核","op":"<=","target":0,"close_when_met":true}
{"kind":"metric_value","scope_type":"station","scope_key":"42","metric_code":"lossRate",
 "period_type":"yearToDate","op":"<=","target":3.0}
{"kind":"manual","evidence":"复盘报告"}
```

语义：

- `close_when_met=true`（默认）：达标即闭环；`false`：只记录进度，到 `due_at` 才闭环。
- **数据取不到 → `passed=null`**（`verify_state=unavailable`），任务**不闭环**，转人工。
- 每次 tick 的实测值都写进 `dispatch_check`，可在任务详情 `checks` 回看。

## 10 典型流程（可直接 curl）

### 10.1 自动核销（预算预警 → 下发 → 数据达标自动闭环）

```bash
# 1) 扫描（定时任务）
curl -X POST http://127.0.0.1:8200/api/alerts/scan \
  -H "X-Internal-Token: $INTERNAL_SERVICE_TOKEN" -H "Content-Type: application/json" \
  -d '{"cadence":"daily","today":"2026-10-19"}'

# 2) 我的预警（所长）
curl "http://127.0.0.1:8200/api/alerts?today=2026-10-19" -H "Authorization: Bearer $JWT"

# 3) 点开进对话（前端点击）
curl -X POST http://127.0.0.1:8200/api/alerts/1/chat -H "Authorization: Bearer $JWT"

# 4) 确认页（推荐承办人 + 默认时限）
curl -X POST http://127.0.0.1:8200/api/alerts/1/dispatch/preview -H "Authorization: Bearer $JWT"

# 5) 下发
curl -X POST http://127.0.0.1:8200/api/alerts/1/dispatch \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"assignees":[{"employee_id":2044600606679294102,"part":"owner"}],
       "requirement":"11-19 前执行率到 80%",
       "verify_rule":{"kind":"budget_rate","station_ids":[42],"year":2026,"op":">=","target":0.8,"close_when_met":true},
       "idempotency_key":"demo-1"}'

# 6) tick：数据达标后自动闭环（closed/auto_verified）
curl -X POST http://127.0.0.1:8200/api/dispatch/tick -H "X-Internal-Token: $INTERNAL_SERVICE_TOKEN"
```

### 10.2 人工回执（多人：主责 + 协办）

```bash
# 下发（主责 1 人 + 协办 1 人）
curl -X POST http://127.0.0.1:8200/api/alerts/1/dispatch \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"assignees":[{"employee_id":A,"part":"owner"},{"employee_id":B,"part":"collaborator"}],
       "requirement":"3 天内交方案","require_plan":1,"verifier_type":"human"}'

# 主责接单 → 方案 → 发起人通过 → 回执（带附件）→ 核销
curl -X POST http://127.0.0.1:8200/api/tasks/1/accept -H "Authorization: Bearer $JWT"
curl -X POST http://127.0.0.1:8200/api/tasks/1/plan \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"content":"1. 补储备 2. 走审批 3. 周跟踪"}'
curl -X POST http://127.0.0.1:8200/api/tasks/1/plan/1/accept -H "Authorization: Bearer $JWT"
curl -X POST http://127.0.0.1:8200/api/tasks/1/attachments \
  -H "Authorization: Bearer $JWT" -F "file=@回执材料.pdf"
curl -X POST http://127.0.0.1:8200/api/tasks/1/reply \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"content":"已完成整改","attachment_ids":[1]}'
curl -X POST http://127.0.0.1:8200/api/tasks/1/close \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"conclusion":"核销通过"}'
```

> 协办不能接单/回执（403），但可以看详情、提意见；主责可多人，**任一人回执**即进入核销。

### 10.3 继续下发 + 超时升级

```bash
# 主责把事压给下游（子任务）
curl -X POST http://127.0.0.1:8200/api/tasks/1/subtask \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"title":"本周补 2 个储备项目","requirement":"周五前",
       "assignees":[{"employee_id":C,"part":"owner"}],"verifier_type":"human"}'

# 超时：tick 自动催办；再超宽限期自动升级到职责线上一级
# （预算：所长→县财务→市财务；项目：所长→县运检；市公司无对口角色时 → 发起人+管理员）
curl -X POST http://127.0.0.1:8200/api/dispatch/tick -H "X-Internal-Token: $INTERNAL_SERVICE_TOKEN"
```
