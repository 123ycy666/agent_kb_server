> 面向执行部署的人。**新增接口是纯代码改动，不需要建表、不需要动数据库、不需要改配置。**
> 一键部署脚本：`tools/deploy_update.py`（用法见 `deploy/部署脚本使用说明.md`）

| 文件 | 动作 | 说明 |
|---|---|---|

## 二 部署步骤

```bash
# 0) 本机先跑一遍验收（必须 16/16 PASS）
cd secretary && py -X utf8 test_alerts.py

# 1) 先看差异，只读、不写任何东西
py -X utf8 tools/deploy_update.py --check

# 2) 正式部署（会：备份 → 上传 → md5 校验 → 原子切换 → 重启 → 分级自检 → 冒烟）
py -X utf8 tools/deploy_update.py
```

脚本的 `[6/7] 重启服务并做分级自检` 里现在会多打一行：

```
/api/alerts/daily：status=abnormal role=供电所所长 scope=两水供电所 预警=5 条
```

**看到这一行 = 接口在线上通了。**

## 三 上线后的验收（3 条，照着敲）

```bash
# 1) 健康检查：ok / name_fix / qa_log / kb 都要 true
curl -s http://47.121.183.81:8200/health

# 2) 预警接口 —— 所长
curl -s -X POST http://47.121.183.81:8200/api/alerts/daily \
  -H "Content-Type: application/json" \
  -d '{"account":"sngdssz","today":"2026-10-16"}'

# 3) 预警接口 —— 市领导（应当只有 1~2 条，且全是全市口径）
curl -s -X POST http://47.121.183.81:8200/api/alerts/daily \
  -H "Content-Type: application/json" \
  -d '{"account":"sgsld","today":"2026-10-16"}'
```

| 判据 | 期望 |
|---|---|
| `sngdssz` 的 `scope` | `两水供电所`（**不是全市**），`alerts` 4~5 条 |
| `sgsld` 的 `alerts` 条数 | **≤2**，类型只有 `budget_underspend` / `metric_deteriorated` |
| 乱传账号 | `status=unknown`、`alerts=[]`、**不含任何全市数** |
| 传 `scope` | 无效（范围只由账号决定） |
| 响应时间 | 1~2 秒 |

> 线上库的身份表（`t_employee` / `t_role` / `t_department`）如果哪天数据变了，
> 接口会回 `status=unknown` + `error`。**那是数据问题，不是代码问题** ——
> 所以部署脚本对这一步只**警示**、不判失败（避免误回滚）。

## 五 上游（业务系统）接哪一步

| 步骤 | 谁做 | 做什么 |
|---|---|---|
| 1 | **上游** | 每天 8:00 的定时任务：遍历要推的账号（或按角色筛一批），逐个调 `POST /api/alerts/daily` |
| 2 | **上游** | 拿 `alerts[].title` 写进他们的消息表 / 站内信（库里已有 `t_message` 可用） |
| 3 | 我们 | 只提供接口，**不写他们的库、不做定时器** |

**建议的调用方式**（伪码）：

```python
for acct in accounts_daily_push:          # 121 个账号，或按角色只推需要的
    r = post("/api/alerts/daily", {"account": acct, "today": today, "when": now})
    if r["status"] == "abnormal":
        for a in r["alerts"]:
            push_message(acct, title=a["title"], level=a["level"], data=a["data"])
    elif r["status"] == "unknown":
        log.warning("预警账号解析失败 %s: %s", acct, r.get("error"))
```

**每天只需 1 次/账号**；单次 1~2 秒，121 个账号串行约 2~4 分钟。

## 六 上线后还有两件事没做（等业务方/前端）

| 项 | 前置条件 |
|---|---|
| **点击跳转** | 前端给「预警类型 → 路由模板 + 参数名」，我们在每条 `alert` 里加 `route`/`params`（`data` 里已备好 `station_ids` / `year` / `work_order_id`） |
| **指标类改每周** | 指标快照最新期是 **202609（9 月）**，没有 10 月数据；塞进每日会连续几周推同一句。建议 `metric_deteriorated` 走每周任务 |
| **待我审批（按人）** | 130 件待处理任务的 `assignee_id` **全为 NULL**；业务方把办理人指派上，才能做"你的待办" |

## 七 风险与兜底

| 风险 | 兜底 |
|---|---|
| 业务库身份表数据变了导致解析失败 | 接口回 `unknown` + `error`，**不会返回全市数**；部署脚本只警示 |
| 单次调用变慢 | 判据 SQL 共 8 条，都带所 id 范围 + 年度条件；实测最慢 1.8 秒（广水 17 所）。若以后变慢，先把 `SECRETARY_ALERT_FORECAST` 保持默认 `pace`（pipeline 会多一次中位金额查询） |
| 有人想调阈值/条数上限 | 改 `secretary/alert_rules.py`（阈值、`ROLE_ALERTS`、`MAX_ALERTS`）→ 重新部署；**不用改逻辑代码** |
| 想临时过滤小额预警 | 环境变量 `SECRETARY_ALERT_MIN_AMOUNT=50000`（低于 5 万的预警不返回），无需改代码 |
| 想换预测口径 | 环境变量 `SECRETARY_ALERT_FORECAST=pipeline`（按立项能力推算，默认 `pace` 按审批速度外推） |
