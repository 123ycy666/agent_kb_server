# 分析问题拆解 · 09「我这块积压得严不严重？该催谁？」

## 一、谁问、问谁
各审批角色（所长 / 运检部 / 营销部 / 财务部 / 领导）；对象：本节点（有时要限定本所 / 本县）。

## 二、想要什么答案
**跟我同级的别的节点比一比**（严不严重是相对的）+ 分档 + 逐条责任人。

## 三、思维链
1. **取本人待办**：`t_work_order_audit_task`，**只有 `task_status=0`（待处理）才算**；限定自己的 `node_name`。
2. **再按身份收窄**：节点名是所有所共用的 —— 所长还要再按自己所属供电所过滤，县公司部门再按本县公司过滤。**不滤就把别人的活算到他头上**。
3. **算停留**：系统当天 − **进入本节点的时间**（就是任务表的创建时间）；查不到用创建时间兜底并注明。
4. **分档**：≤15 正常 / 16–90 偏慢 / >90 积压。
5. **横向对比**：其他节点的待办数与超 90 天比例 → "我这块严不严重"。
6. **找遗漏**：同一张工单上一节点已完成且未驳回、但本节点没有生成待处理任务 → 该到我却没到。
7. **排序**：先按停留最久，其次按金额大。
8. **定责 + 建议**：先办哪几张、为什么。

## 四、回答要出现什么
结论（我这条有多少、各档几条、跟别的节点比如何）→ 最久的清单 → 遗漏 → 先办哪几张 → 排序依据。

## 五、数据可得性 / 坑
- 只有 `task_status=0` 是待办（1 处理中 / 2 已完成 / 3 已驳回都不算）
- **节点名不区分所/县** → 必须再按身份过滤
- 任务表**没有 deleted_flag**
- 严禁把全库"审核中"的量当某个人的待办
