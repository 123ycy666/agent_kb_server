# 数据库设计说明（2026-10-14）

> 依据 `server/app/models/*.py` 全部源码 + `app/db_init.py` 的幂等迁移清单整理。
> 数据库：**PostgreSQL + pgvector**，向量维度由 `EMBEDDING_DIM`（默认 1024）决定。

---

## 一、总览：12 张表，5 个域

| 域 | 表 | 作用 |
|---|---|---|
| **知识库与内容** | `knowledge_base`、`document`、`document_chunk` | 核心内容三件套 |
| **标签** | `tag` | 标签词表（只做下拉复用 + 使用统计） |
| **权限（RBAC）** | `app_user`、`role`、`permission`、`role_permission`、`user_role` | 用户/角色/权限点三张字典 + 两张关联 |
| **冲突** | `conflict_record` | 冲突检测与人工处理记录 |
| **平台** | `async_task`、`audit_log` | 异步任务队列态 + 审计留痕 |

> 主键策略：全部 `BigInteger` 自增，**唯一例外是 `async_task.id` 用 UUID**
> （`platform.py:36`，`default=uuid.uuid4`）—— 因为任务 ID 会暴露给前端轮询，可枚举的递增 ID 不合适。
> 所有表都用 `lowercase_with_underscore` 命名，**不设 plural**（`document` 而不是 `documents`）。

---

## 二、表联系（文字 ER）

### 2.1 有数据库外键的 8 条（全部 `ON DELETE CASCADE`）

```
knowledge_base ──1:N──> document           (document.kb_id → knowledge_base.id)
document      ──1:N──> document_chunk      (document_chunk.doc_id → document.id)
document      ──1:N──> conflict_record     (×2：new_doc_id / old_doc_id)

app_user      ──1:N──> user_role           (user_role.user_id → app_user.id)
role          ──1:N──> user_role           (user_role.role_id → role.id)
role          ──1:N──> role_permission     (role_permission.role_id → role.id)
permission    ──1:N──> role_permission     (role_permission.permission_id → permission.id)
```

### 2.2 ⚠️ 只有"逻辑关联"、没有外键约束的一大批

这是本项目**最值得注意的设计取舍**。以下字段看起来是外键，但模型里只是普通 `BigInteger`：

| 字段 | 指向 | 为什么没有 FK |
|---|---|---|
| `document.root_id` | `document.id`（版本链自引用） | 自引用 FK 会让 `create_all` 建表顺序变复杂；且版本链的维护全在应用层 |
| `document.superseded_by` | `document.id`（谁取代了我） | 同上，自引用 |
| `document.owner_id` | `app_user.id`（上传者） | 用户来自公司外部库，不参与级联删除 |
| `document_chunk.kb_id` | `knowledge_base.id` | **冗余字段**，靠 `doc_id → document → kb_id` 间接保证一致；省一次 JOIN，但需要应用层自己守 |
| `document_chunk.superseded_by` | `document.id`（切片级取代者） | 2026-10-09 为解决"被覆盖内容永久失联"新增 |
| `conflict_record.kb_id` | `knowledge_base.id` | 冗余，便于按库查冲突 |
| `conflict_record.new_chunk_id / old_chunk_id` | `document_chunk.id` | **有脏引用风险**：切片删了记录还在（见隐患 T-4） |
| `conflict_record.resolved_by` | `app_user.id` | 同 owner_id |
| `knowledge_base.created_by`、`tag.created_by` | `app_user.id` | 同上 |
| `async_task.ref_id` | `document.id`（任务对象） | 任务类型多样（doc_ingest/reindex/kb_delete），指向不固定 |
| `async_task.kb_id`、`async_task.created_by` | KB / 用户 | 冗余，便于任务中心过滤 |
| `audit_log.actor_id`、`resource_id` | 用户 / 任意资源 | 审计是只读流水，不级联 |

**这样取舍的利弊**：
- 好处：写入路径短、不受删用户的级联影响、审计日志永不被级联清掉、`create_all` 建表简单。
- 代价：**一致性全靠应用层保证**，DB 不会帮你兜底。典型例子就是
  `document_chunk.kb_id` —— 它跟 `document.kb_id` 是两处独立写入，理论上能不一致。

## 三、逐表结构

### 3.1 `knowledge_base` —— 知识库

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BigInteger PK | |
| `name` | String(128) | |
| `description` | Text | |
| `embedding_model` | String(64) | **向量模型绑定**，切模型时校验维度 |
| `embedding_dim` | Integer | 与上一项一起构成「切模型必须重建索引」的判据 |
| `chunk_size` / `chunk_overlap` | Integer | 默认 512 / 64 |
| `status` | String(16) | 默认 `active` |
| `created_by` | BigInteger | → `app_user.id`，**无 FK** |
| `created_at` / `updated_at` | timestamptz | 来自 `TimestampMixin`，`server_default=now()` |

> `TimestampMixin`（`mixins.py:11-24`）给 5 张表自动加了这两个字段。
> 关键点是**默认值放在数据库侧**（`server_default`），避免应用层时区漂移。

### 3.2 `document` —— 文档（带完整版本链）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BigInteger PK | |
| `kb_id` | BigInteger FK → knowledge_base | **CASCADE** |
| `root_id` | BigInteger | **版本链根 ID**：同一份文档的版本族共享同一个 root_id，**无 FK** |
| `version_no` | Integer | 递增；仅最新版 `is_active=true` |
| `is_active` | Boolean | 是否当前活跃版本 |
| `superseded_by` | BigInteger | 谁取代了我（删除新文档时据此复活旧版），**无 FK** |
| `retired_reason` | String(32) | `version_supersede` / `conflict_overwrite` |
| `filename` / `file_ext` | String(512) / String(16) | |
| `file_size` / `storage_path` | BigInteger / String(1024) | 磁盘绝对路径 |
| `content_hash` | String(64) | SHA256，用于判重 |
| `parse_status` | String(16) | `pending / parsing / embedding / ready / failed` |
| `parse_error` | Text | |
| `has_conflict` | Boolean | **仅作 UI 提示，不参与检索过滤** |
| `chunk_count` | Integer | |
| `visibility` | String(16) | `public`（人人可检索）/ `private`（仅上传者+管理员），默认 private |
| `tags` | `ARRAY(String(64))` | **标签直接存数组**，不建关联表；`server_default='{}'` |
| `owner_id` / `uploaded_by_app` | BigInteger / String(64) | 无 FK；后者是 API Key 时代的残留 |
| `chunks` | relationship | `cascade="all, delete-orphan"`、`lazy="selectin"` |

索引：`idx_doc_kb`、`idx_doc_root`、`idx_doc_superseded_by`、`idx_doc_hash(kb_id,content_hash)`、
`idx_doc_conflict(has_conflict) WHERE has_conflict=true`（部分索引）、`idx_doc_status(kb_id,parse_status)`。

> ⚠️ **没有 `(kb_id, filename)` 唯一约束**。版本判定完全靠应用层
> `pipeline.py:102-139` 的 `_detect_version()` 查出来。并发上传同一文件名时，
> 两个事务可能都判定为"新文档"，产生两个 root。

### 3.3 `document_chunk` —— 文档切片（含向量）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BigInteger PK | |
| `doc_id` | BigInteger FK → document | **CASCADE** |
| `kb_id` | BigInteger | **冗余，无 FK**（避免检索时 JOIN document） |
| `chunk_index` | Integer | 片内序号 |
| `content` | Text | 纯正文（标题前缀统一在片首拼一次） |
| `heading_path` | String(512) | 如「第三章 > 3.2 报销标准」 |
| `embedding_model` | String(64) | **记录生成该向量的模型**，切换模型后据此识别待重建切片 |
| `embedding` | `Vector(1024)` | pgvector 向量列，可空 |
| `search_text` | `TSVECTOR` | 关键词检索路全文索引列 |
| `tags` | `ARRAY(String(64))` | **文档级标签的冗余副本**，检索时单表过滤免 JOIN |
| `is_retrievable` | Boolean | 切片是否可检索。⚠️ **与权限无关**，由版本取代/冲突隔离决定 |
| `retired_reason` | String(16) | `version` / `conflict` / `overwrite` |
| `superseded_by` | BigInteger | **切片级**取代者 doc_id，无 FK |
| `parent_content` | Text | **parent-child 检索**：命中小块所属父块文本，不另占向量索引 |
| `document` | relationship | back_populates |

索引：`idx_chunk_doc`、`idx_chunk_kb`、`idx_chunk_tags`（**GIN，标签过滤**）、
`idx_chunk_vec`（**HNSW，`vector_cosine_ops`，m=16 / ef_construction=64**）、
`idx_chunk_retrievable(kb_id,is_retrievable)`、`idx_chunk_fts`（**GIN，全文**）。

> 这张表是整个系统的性能核心：**一张表同时承担向量召回 + 关键词召回 + 权限/标签过滤**，
> 靠三个 GIN/HNSW 索引各自支撑。

### 3.4 `tag` —— 标签词表（已大幅简化）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BigInteger PK | |
| `name` | String(64) **unique** | 全局唯一，避免「行政」「行政 」并存 |
| `description` | String(256) | |
| `usage_count` | Integer | 用于列表排序 + 清理长期未使用标签 |
| `created_by` | BigInteger | 无 FK |

索引：`idx_tag_usage(usage_count)`。

> **关键设计决策：标签不建关联表。** 原设计的「标签维度/值类型/枚举值/命名空间/同义检测/合并废弃」
> 全部删掉，标签就是字符串，关系直接存在 `document.tags` 数组上。
> 理由（`tag.py:16-19`）：在「标签即字符串」模型下，`document_tag` 那层间接性是纯负担 ——
> 检索要 JOIN、写入要两次操作、还得处理一致性。数组列 + GIN 索引直接完成
> `tags && ARRAY['行政']`，更简单也更快。
> **代价**：重命名标签必须同步改写 `document.tags` 和 `document_chunk.tags` 两处。

### 3.5 RBAC 五张表

| 表 | 字段 | 关键点 |
|---|---|---|
| `permission` | `id`、`code` unique、`description`、`group_name` | 权限点字典，20 个点由 `db_init.py:40-66` 播种 |
| `role` | `id`、`name` unique、`description`、`is_builtin`、`created_at/updated_at` | **只固定 admin / user 两种**，`is_builtin=true` 不可删 |
| `app_user` | `id`、`external_id` unique、`username` unique、`display_name`、`password_hash`、`email`、`status`、`synced_at`、`created_at/updated_at` | `external_id` 预留给公司用户库对接 |
| `role_permission` | `(role_id, permission_id)` 复合主键 | 双 CASCADE |
| `user_role` | `(user_id, role_id)` 复合主键 | 双 CASCADE |

> `rbac.py:8-10` 明确记录：**文档级 ACL 已移除**。
> 可见性只有 `public`/`private` 二值，判定统一收敛在 `services/permission.py` 一个出口。

### 3.6 `conflict_record` —— 冲突记录

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BigInteger PK | |
| `kb_id` | BigInteger | 冗余，无 FK |
| `new_doc_id` / `old_doc_id` | BigInteger FK → document | **双 CASCADE**，`nullable=False` |
| `new_chunk_id` / `old_chunk_id` | BigInteger | 切片级定位，**无 FK（脏引用风险）** |
| `conflict_type` | String(32) | `fact` / `rule` / `temporal` / `wording` |
| `relation` | String(32) | `contradiction` / `entailment` / `duplication` / `unrelated` |
| `similarity_score` / `rerank_score` | `Numeric(5,4)` | 小数而非 float，便于精确展示 |
| `reason` / `new_snippet` / `old_snippet` | Text | 供人工决策展示 |
| `resolution` | String(32) | `overwrite` / `keep_old` / `coexist` / `cancel` / `ignore` |
| `resolved_by` / `resolved_at` | BigInteger / timestamptz | 无 FK |
| `status` | String(16) | `pending` / `resolved` / `ignored` |
| `created_at` | timestamptz | 应用层写入，**无 server_default** |

索引：`idx_conflict_newdoc`、`idx_conflict_olddoc`、`idx_conflict_kb(kb_id,status)`、
`idx_conflict_status WHERE status='pending'`（部分索引）。

> ⚠️ **两个 doc 外键都是 CASCADE** —— 这是 2026-10-14 线上 `StaleDataError` 500 的根因：
> `keep_old`/`cancel` 分支 `db.delete(new_doc)` 会把**本条冲突记录一起级联删掉**，
> 而代码还在对它赋值。已在 `conflicts.py` 修掉（先写决策再删文档 + `expunge`）。
> **由此产生的约定**：这类决策的留痕只能靠 `audit_log`，`conflict_record` 行会随新文档消失。

### 3.7 `async_task` —— 异步任务

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | **UUID** PK | `default=uuid.uuid4`，不用自增 ID（会被枚举） |
| `task_type` | String(32) | `doc_ingest` / `conflict_scan` / `reindex` / `kb_delete` |
| `ref_id` / `kb_id` | BigInteger | 任务对象 / 所属库，**均无 FK** |
| `status` | String(16) | `pending` / `running` / `done` / `failed` / `conflict_pending` |
| `progress` / `stage` | Integer / String(32) | 进度百分比 + 当前阶段 |
| `error_msg` | Text | |
| `result` | **JSONB** | 上传结果（doc_id、chunk_count、conflict_count…）都塞这里 |
| `created_by_app` / `created_by` | String(64) / BigInteger | 前者是 API Key 时代残留；后者**无 FK，且 tasks 接口不按它过滤** |
| `created_at` / `started_at` / `finished_at` | timestamptz | 三层时间戳，便于算各阶段耗时 |

索引：`idx_task_status`、`idx_task_ref(task_type,ref_id)`。

### 3.8 `audit_log` —— 审计日志

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BigInteger PK | |
| `actor_type` / `actor_id` / `actor_name` / `actor_app_id` | String / BigInteger / String | `actor_app_id` 是 API Key 时代残留，现在恒空 |
| `action` | String(64) | 如 `doc.upload` / `search` / `conflict.resolve` |
| `resource_type` / `resource_id` / `resource_name` | String / BigInteger / String | 无 FK |
| `detail` | **JSONB** | 检索类必须含 `hit_doc_ids`（`platform.py:74-76`） |
| `result` | String(16) | 默认 `success` |
| `ip` | **INET** | PG 原生 INET 类型，兼容反向代理 |
| `user_agent` | String(256) | |
| `created_at` | timestamptz | `server_default=now()` |

索引：`idx_audit_actor(actor_type,actor_id,created_at)`、`idx_audit_action(action,created_at)`、
`idx_audit_res(resource_type,resource_id)`、`idx_audit_time(created_at)`。

> **四个索引全部带 `created_at` 尾列** —— 因为审计查询几乎总是「某人/某动作/某资源 + 时间倒序」，
> 这样能直接走索引顺序扫描，避免额外排序。

## 四、设计亮点（值得学的点）

1. **版本链用 `root_id + version_no + is_active` 三元组**，而不是"每版一行独立文档"。
   配合 `superseded_by` + `retired_reason` 实现**可回滚的版本下架** ——
   删除新文档时反查复活旧版，版本链能自愈（2026-10-08 修的孤儿版本缺陷）。
2. **切片级取代关系 `document_chunk.superseded_by`**：部分覆盖时只标记被覆盖的那几片，
   删除新文档时能精确恢复，不会误复活（2026-10-09 用户复现的"被覆盖内容永久失联"）。
3. **`is_retrievable` 与权限彻底解耦**：它只表达"切片在库里是否可用"，
   可见性判断全部走 `permission.py` 一个出口。混在一起就会互相污染。
4. **标签冗余 + 数组 + GIN**：检索时单表完成过滤，零 JOIN。
5. **向量与关键词双路都建在 `document_chunk` 一张表上**：HNSW 管向量、GIN 管 tsvector，
   检索时两路各自召回再 RRF 融合。
6. **`embedding_model` 逐片记录**：这是"切换向量模型必须重建索引"的机制基础 ——
   没有它，混用不同模型的向量不会报错，只会静默返回垃圾结果。
7. **`db_init.py` 的 `EXTRA_DDL` 幂等迁移清单**：`create_all()` 只建新表、
   **不给已存在的表补列**，所以每个新增字段都显式登记一条 `ADD COLUMN IF NOT EXISTS`。
   与模型里的 `Index(...)` 重复声明也没关系（`CREATE INDEX IF NOT EXISTS` 幂等）——
   模型声明服务新库，EXTRA_DDL 服务老库，双保险。
8. **部分索引用得精准**：`WHERE has_conflict = true`、`WHERE status = 'pending'`，
   把索引体积压到只覆盖热点行。

## 五、表结构层面的隐患

| # | 隐患 | 位置 | 后果 |
|---|---|---|---|
| T-1 | **`(kb_id, filename)` 无唯一约束**，版本判定纯应用层 | `document` / `pipeline.py:102-139` | 并发上传同名文件可能产生两个 root、两条 v1 |
| T-2 | **`document_chunk.kb_id` 冗余且无 FK** | `document.py:123` | 与 `document.kb_id` 理论上能不一致 |
| T-3 | **`conflict_record` 双 doc FK 都是 CASCADE 且无 ORM relationship** | `conflict.py:47-52` | 删新文档会连带删掉冲突记录 ⇒ 决策历史丢失，只能靠 audit_log 追溯（2026-10-14 已踩） |
| T-4 | `new_chunk_id` / `old_chunk_id` 无 FK | `conflict.py:53-54` | 切片被删后留下脏引用 |
| T-5 | `conflict_record.created_at` 无 `server_default` | `conflict.py:76-78` | 依赖应用层赋值，直接插库会 NULL |
| T-6 | `document_chunk.kb_id` 没走 EXTRA_DDL 也没有 FK | — | KB 级联删除只靠 `document` 间接实现 |
| T-7 | `retired_reason` 两处长度不一致 | document `varchar(32)` vs chunk `varchar(16)` | chunk 侧写超长值会被截断/报错 |

## 六、一句话总结

**12 张表、8 个真实外键（全部 CASCADE）、其余靠约定在应用层维护。**
核心是 `knowledge_base → document → document_chunk` 这条内容链，
配上 `conflict_record` 做切片级冲突隔离、`async_task` 承接异步流水、`audit_log` 全程留痕。
设计上最值得学的是**版本链可回滚**和**标签数组化**这两处取舍；
最需要补的是**版本唯一约束**和**冗余字段的应用层一致性校验**。
