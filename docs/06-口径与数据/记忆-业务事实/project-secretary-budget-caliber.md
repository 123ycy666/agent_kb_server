**结论（2026-10-14 甲方口径变更，取代 2026-09-24 版）**
- **已审批 = 工单状态 3、6、7**（3 审核通过待施工 / 6 施工中 / 7 完成待验收）。**状态 2 不算** —— 2 表示这单还在审批流里（按项目类型分别送县公司运检部或营销部审核，审完才进 3）。不算 0/1/2/4/5/9。
- **实际投入 = 已审批工单的预算金额**（budget_total）；reality_* 实测基本为空，用前先 COUNT，一律不用。
- **执行率 = 当年已审批（3/6/7）预算合计 ÷ 当年分配预算**；分配只取**供电所级**结果（t_power_company_budget_result，该所 + 年度 + deleted_flag=0 唯一有效行）；**全市 = 各所之和，一律现查**（不要写死；公司级总预算表取 is_new=1 的行）。
- 口径写在哪：**`ai_prompt.caliber_rules`（2026-10-19 从代码 CALIBER 搬进库，每轮固定注入）** + skills/判据规则.md（零节①、三节 1/5、四节 1）+ skills/预算执行.md。**改口径要一起改**，2026-10-14 这次共 8 处。

**Why（这条才是要记的）**
- 旧口径 2/3/6/7 把"在运检部/营销部审核中"的单算成已通过 → 甲方要求以运检/营销审核通过为准。
- **更坏的是硬编码**：业务字典（ai_data 的表/字段/指标说明）和代码 CALIBER 里都写死了「2026 年全市 = 1880 万」。数据早已变成 1910 万，但这句**每轮随提示注入、还标明"不用检索"**，模型照抄 → SQL 查到 1910 也写 1880；加规则、刷知识库、换模型都拦不住。
- 模型另有一类行为缺陷（未解决）：查到空集后**摘掉条件重查**凑数（实测环潭余额题被算成 −143.45 万）。

**How to apply**
- 业务数**一个都不许写死**（字典 / 代码提示 / 规则文档 / 记忆都不行），要写就写口径与算法。
- 排查"模型老写某个错数"的顺序：① 抓服务真实系统提示（agent._system() 落盘，grep 那个数）② 查业务字典三张表 ③ 查 ai_prompt ④ 查 KB 全文 ⑤ 直连模型端点对照。别先改规则。
- **生效链路**：改字典 → 必须重启（semantic._ensure 进程内缓存、无 TTL）；改 ai_prompt → 60 秒 TTL；改规则文档 → 上传知识库（output/kb_refresh_rule.py）后按问句检索生效。
- 跨题通用的口径必须固定注入（`ai_prompt.caliber_rules`），只写知识库会"检索到才生效"。**口径正文在库、不在代码**（2026-10-19 Fred 定）。
