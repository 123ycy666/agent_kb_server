# 实施计划：预警四类归并 + 任务流转（问题全过程追踪）

> 依据：`docs/superpowers/specs/2026-10-19-预警四类归并与任务流转-design.md`（**待 Fred 审**）
> 本文件只记「目标 / 验收 / 步骤 → verify / Progress」，不复制设计细节。

## 目标

1. 预警从 **11 类收成 4 类 13 个子判据**（预算 / 项目全过程 / 穿透式复盘 / 指标），同一件事只出一条。
2. 预警能**转成处置任务**：系统推荐处理人（可多人）→ 发起人确认下发 → 接单 → 方案 → 执行 → 回执 → 核销；
   全过程有时间线、时限、催办、升级、继续下发。
3. 两套闭环：**可算的自动核销（可见指标变化）** / **算不出的人工回执（超时催促 + 上报）**。
4. 全部新增数据落在 **PG `ad_new`**，不写任何业务库表；本次设计**不动代码**（等评审）。
5. （v2）**点预警 = 进对话**：卡片 + AI 首段话 + 3 条建议 + 「要不要我帮你发起」（拟办，人确认才下发）。
6. （v2）执行侧 AI 先给"怎么干"，报告可**代写/润色**；升级按**职责线**给对应的人，市领导只收大方向。

## 根因（本轮同一文件多次修改的原因）

**现象**：`dispatch_service.py` 里承办人的 `role_code` 有三处写入点（下发 / 转派 / 子任务）都没填，全部留 NULL。

**复现**：建一个主责为县财务的任务 → 触发升级 → `_escalate_once` 取 `owners[0].role_code` 为 None → 兜底成 `'sz'` → 按所长的职责线升级，升错人。

**证据**：代码里三处 `DispatchTaskAssignee(...)` 均未传 `role_code`；`_emp()` 返回里没有角色字段。

**为什么**：角色只存在 MySQL `t_role_employee`，`_emp()` 只取员工主表；而配置的 `DUTY_CHAIN` 按角色分叉，角色为空就只能兜底。

**改法（根因，不是补丁）**：新增 `_role_of(employee_id)`（按 `alert_rules.ROLE_PRIORITY` 取最高权限角色），在**所有写入承办人的地方**统一调用；不在升级处猜角色。

**追加（2026-10-19 晚，对话建任务）**：
- **现象**：任务只能从"预警下发"创建，Fred 要求改为**对话触发 + 智能体拟稿 + 人工确认后建任务**。
- **根因**：会话（`t_chat_session/t_chat_message`）的写入只存在于 `alert_service` 的私有函数里（`_ensure_session/_append`），
  `dispatch_service` 想往会话里写"确认消息"只能复制一份 SQL —— 复制就会出现两套 seq/msg_count 逻辑，迟早不一致。
- **改法**：把"确保会话存在 + 追加消息"抽成 `alert_service` 的**公共函数**（`ensure_chat_session/append_chat_message`），
  `dispatch_service` 调用公共函数；预警卡片路径保留原行为。新增"对话拟办"服务与 3 个接口（draft / confirm / pending）。

## 边界（本轮不做）

- 不做 BPMN/会签/加签；不做移动端/短信/钉钉；不做节假日日历；不写业务库任何表；不重构 `/api/ask` 主链路。
- P4 之前不承诺"页面能用"；P4 之前接口可用即可联调。
