# Agent 能力扩充 —— 能力清单 + 路由架构（对标豆包/WorkBuddy 那条路）

> 需求（2026-10-21 第二轮澄清）：工具尽量多、对标豆包/WorkBuddy 这类真实工作平台；想清楚还能加什么；核心追问是「**是不是做好意图识别就够了**——每个分支给不同工具？」最终目的：功能多、且真能用。
> 状态：调研 + 架构决策，**没动业务代码**。许可标 ⚠ 的接之前复核一次。

---

## 0. 结论

**意图识别是必要的，但只做它不够。** 它只解决「工具不撞车」，解决不了另外三件事：长流程会漏步骤、复合任务会被砍成一半、判错时用户直接失去能力。

所以架构不是「一个路由器 + 一堆工具」，而是：

**一个入口 + 一次路由 + 三个执行器 + 一个能力目录**

| 层 | 干什么 | 是不是新写 |
|---|---|---|
| L0 路由 | 规则优先、小模型兜底，输出 `{mode, intent, 附带产物}` | 新写 ~80 行 |
| 执行器 ①② | **查数循环**、**文档流水线**（digest/proofread/table_audit） | **已有，一行不改** |
| 执行器 ③ | **技能循环**：工具集 = `capabilities.tools_for(intent)`，每次 5–7 个 | 新写 ~150 行 |
| 能力目录 | 一张表：活 → 零件 → wrapper | 新写 ~120 行 |

**关键原则：路由只决定「用哪条路、给哪些工具」，不决定「能不能用」。** 判错了最坏是慢一点（工具多给几个），不是「这活我干不了」。

---

## 1. 为什么「只做意图识别」不够（三条，都能对上现状）

1. **长流程会漏步骤。** 20 页文件 → 抽字段 → 归并 → 生成 → 自检，让模型在工具循环里自由发挥，**每次都漏**（2026-10-19 设计稿已踩过，方案 A「纯工具化」就是因此被否掉）。所以文档类必须走固定流水线（执行器②），不是工具循环。
2. **复合任务是常态。** 「把这份 Excel 跟上月对一下，顺手出个 PPT」= 读表 + 对账 + 生成，跨两个执行器。单标签意图分类会砍掉一半。做法：路由输出「主意图 + 附带产物」，交给执行器③ 按步骤串，**不需要多 agent**。
3. **意图误判的代价必须可控。** 内网小模型分类不可能 100%。所以要「能力始终可达」：判错了，用户说一句「不对，我是要…」就切过去；而不是弹「我没听懂」。

另外两条硬约束（已核实，来自现状代码与公开数据）：
- 查数轮强制 `tool_choice='required'` → **办公工具绝不能进查数轮的工具表**，必须分片。
- 工具越多越不准（370 个工具里平均只给 7 个覆盖 90.3%）→ 需要**分片机制**。

> ⚠️ **2026-10-21 12:00 修正**：上面第二条我原来写成「每轮 5–7 个是上限」，那是**假设内网跑 7B–32B 小模型**——错的。实际内网是 **deepseek v4flash（强模型）**（`config.py:143` online 默认 `deepseek-v4.1-flash-1017`），后续还要上**多模态**（识图 / 生图）。正确写法：
> - **工具预算按模型能力可配**（模型表里标 `tool_budget`，强模型给 12–15），不要写死 5–7；
> - **分片机制保留**，因为 `tool_choice='required'` 是**流程性**风险，与模型强弱无关；
> - **模型不能写死一个**：能力要声明「我需要什么模型」，由模型表来配（见 §3.5）。

```
              问一句 / 传个文件 / 选个任务
```

## 3.5 模型层：从「一个全局模型变量」改成「一张能力表」

**现状（已核实）**

- `config.py` 里已经有「不同模型干不同活」的**零散先例**：`MODEL`（主）、`SUMMARY_MODEL`（摘要可单独指定）、`PAGE_MODEL`（页面生成，默认 `qwen3.8-flash`）。但只是三个变量，没有统一表 —— **再加一种模型就得改代码**。
- `app/providers/` 已有正经抽象：`LLMProvider` / `EmbeddingProvider` / `RerankProvider` + `ProviderBundle` + `factory.build_bundle()`。**这是好事：加 vision 就是再加一个 ABC 实现，不是重构。**

**要做的两件事**

**① 一张模型能力表（配置驱动，换模型不改代码）**

| 字段 | 例 |
|---|---|
| `id` | `deepseek-v4flash` |
| `caps` | `chat, tools, long-ctx` |
| `tool_budget` | 15（强模型）/ 6（弱模型） |
| `max_ctx` | 131072 |
| `endpoint` | OpenAI 兼容 base_url |

放 `.env`（JSON 或多行表）。启动时 `probe()`：拉 `/v1/models` + 各发一次最小请求，实测 `tools` / `vision` / `image-gen` 到底支不支持；**实测与声明不一致以实测为准**，并打日志。

**② 能力声明 + 选择器**

```
能力 = { needs: ('chat','tools'), tools: [...], pipeline: ... }
pick_model(needs, prefer=None) -> 主选 + 2 级降级     # 按 caps 过滤，按 cost 排序
```

调用点**只写 needs、不写模型名**。于是：v4flash 上线 = 配置加一行；多模态上线 = 配置加一行 + 能力声明 `needs=('vision',)`；某模型挂了 = 降级链路自动走，调用方零改动。

**③ 降级矩阵（"不能因为难就不用"落成硬规则）**

| 能力 | 有对应模型 | 没有时**也必须出活** |
|---|---|---|
| 识图 | vision 直接看图 | OCR 出文字 + 表格结构还原，**结果里标注"图片未直读，已按 OCR 处理"** |
| 生图 | image-gen 出配图 | 用原生图表 / 形状 / 图标（pptx、docx 都能画），**不空着** |
| 表格截图 | vision 直读 | OCR + 规则重建表头 |
| 长文 | 长上下文整篇 | 分块 + 召回（现有 `doc_context` 已是这形状） |
| 工具调用 | 模型原生 function calling | pipeline 写死步骤，只让模型产 JSON（现有 digest/proofread 就是） |

**一条硬规则**：任何能力不可用时，必须回「做了什么 + 缺什么 + 建议怎么补」，**禁止静默降级、禁止一句"做不到"了事**。

## 6. 红线

- AGPL 先不碰：MinerU、PyMuPDF、PPTist、MaxKB —— 除非确认「只自己机房用、不交付甲方」（AGPL 只在 convey 时触发）。
- 办公工具**不进查数轮**（`tool_choice='required'` 会流程性调错）。
- 每轮工具 5–7 个（有公开数据，不是感觉）。
- 服务端只生成 docx/pptx，字体名写进 XML，**不打包 ttf、不渲染 PDF**（方正小标宋收费；GB/T 9704 只要求"仿宋/小标宋"）。
- 不做「PPT 自动美化重排版」：出来更丑的概率大于更好看。
