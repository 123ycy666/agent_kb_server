| 主题 | 初版设计（下文） | **现行实现（以此为准）** |
|---|---|---|
| 角色 | 自定义 RBAC，角色 + 权限点自由组合 | **只有 `admin` / `user` 两种固定角色** |

| 管理员检索范围 | 全知 | **与普通用户一致**：只听「公开 + 自己上传」；全知权限仅用于管理视图 |
| 标签 | 标签维度 + 值类型（enum/number/date/text）+ 同义检测 + 合并废弃 | **标签即自由字符串**，自动登记词表，支持重命名 / 删除 |
| 标签筛选语义 | 维度内 OR、维度间 AND | **多标签为「全部命中」**（数组 `@>`） |
| 建知识库 | 持有 `kb:create` 权限 | **仅管理员** |
| 改 / 删文档 | 持有 `doc:*` 权限 | **上传者本人 或 管理员** |

**代码位置**（现行实现的权威定义）：

- 可见性判定唯一出口：`server/app/services/permission.py`
- 数据模型：`server/app/models/document.py`（`visibility` / `tags`）、`server/app/models/tag.py`

- 验证用例：`server/tests/e2e_check.py`（64 项）、`server/tests/selfcheck.py`（49 项）

## 1. 项目目标与范围

### 1.1 一句话目标

先搭建一个**可运行的壳子**：所有基础功能有真实可用的界面与数据流，模型层通过**三档 Provider 抽象**支持切换；本阶段使用**线上 API（阿里云百炼 + DeepSeek）做全链路真实验证**，公司本地模型（bge-m3 / bge-rerank-m3 / DeepSeek / 千问3.6）**接口预留、后续接入零改业务代码**。

### 1.2 本期做

- 多知识库管理
- 5 类文档（PDF / Word / Excel / Markdown / TXT）上传、解析、切片、入库
- 元数据标签体系（预设 schema + 上传时选择）
- 文档级权限（自定义角色 + ACL）
- 检索与问答（含标签过滤、权限过滤、版本压制）
- 上传冲突检测（切片级检测、文档级呈现）
- 对外 REST API（另一个项目可通过 API 完成知识库各项操作）
- 审计日志

### 1.3 本期不做

- OCR（已确认所有 PDF 均为纯文本 PDF）
- 用户管理系统（用户来自已有数据库，本期只做适配接口 + 测试账号）
- 开放平台完整度（应用注册审批、计费、开发者文档站）—— 调用方为公司内部系统
- 真实生产部署、压测、监控告警（后续阶段）

## 3. 整体架构

### 3.1 分层结构

```
┌─────────────────────────────────────────────────────────────┐
│ 接入层                                                       │
│   Web UI (React + Ant Design)   │   对外 REST API (/api/v1)  │
├─────────────────────────────────────────────────────────────┤
│ 应用层                                                       │
│   知识库管理 │ 文档流水线 │ 检索编排 │ 冲突检测 │ 标签治理 │ 审计 │
├─────────────────────────────────────────────────────────────┤
│ 模型适配层（Provider 抽象）                                   │
│   EmbeddingProvider │ RerankProvider │ LLMProvider           │
│   三档实现：mock │ online(阿里+DeepSeek) │ local(公司本地)     │
├─────────────────────────────────────────────────────────────┤
│ 存储层                                                       │
│   PostgreSQL + pgvector (元数据/向量/全文)                    │
│   Redis (任务队列/限流)   │  文件存储 (本地目录 → MinIO)       │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 关键设计原则

1. **模型零耦合**：业务代码永远不直接调用模型 HTTP 接口，只依赖 Provider 抽象
2. **单一存储**：元数据、向量、全文检索全部在 PostgreSQL 内完成，部署只需 PG + Redis 两个中间件
3. **权限强制注入**：权限过滤由后端无条件拼接，绝不依赖调用方传参
4. **契约先行**：对外 API 全部 `/api/v1` 前缀，一经发布即承诺兼容性

## 4. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 后端框架 | FastAPI + Python 3.11+ | 异步支持好，RAG 生态成熟，自动生成 OpenAPI 文档 |
| ORM / 迁移 | SQLAlchemy 2.0 + Alembic | 类型友好，迁移可控 |
| 数据库 | PostgreSQL 16 + pgvector | 元数据过滤 + 向量检索单库完成，事务一致 |
| 中文全文检索 | `pg_bigm` 扩展 + `tsvector` | pg_bigm 对中文分词友好，无需引入 ES |
| 任务队列 | Celery + Redis | 文档解析/向量化/冲突检测均为耗时操作 |
| 前端 | React 18 + Vite + Ant Design 5 | 企业级中后台生态最成熟，Table/Form/Upload 开箱即用 |
| 文件存储 | 本地目录（本期）→ MinIO（后续） | 接口抽象，切换成本低 |
| 文档解析 | pdfplumber / python-docx / openpyxl / markdown | 覆盖 5 类格式，均无需 OCR |
| 部署 | Docker Compose（PG + Redis + App） | 一条命令起环境 |

**为什么不用 Elasticsearch**：本期规模不到千万级，且元数据过滤是核心需求，PostgreSQL 的 `jsonb` + GIN 索引 + `pg_bigm` 已完全覆盖，减少一个中间件即减少一份运维成本。

## 5. 数据模型设计

### 5.1 实体关系概览

```
knowledge_base ──┬── tag_definition        标签维度定义（schema）
                 ├── document ──┬── document_chunk    切片（含向量）
                 │              ├── document_tag      文档标签实例
                 │              └── document_acl      文档级权限
                 └── conflict_record                 冲突记录

app_user        用户（本期 Mock，后续对接外部库）
role ──┬── role_permission   角色权限点
       └── user_role         用户角色关联

api_client ── service_account_id ──→ app_user    对外 API 应用绑定服务账号
audit_log                                        审计日志
async_task                                       异步任务表
```

### 5.2 核心表 DDL

```sql
-- ═══════════════════════════════════════════════
-- 知识库
-- ═══════════════════════════════════════════════
CREATE TABLE knowledge_base (
    id                  BIGSERIAL PRIMARY KEY,
    name                VARCHAR(128) NOT NULL,
    description         TEXT,
    embedding_model     VARCHAR(64)  NOT NULL,     -- 绑定的 embedding 模型标识
    embedding_dim       INT          NOT NULL,     -- 维度，切换模型时校验
    chunk_size          INT          NOT NULL DEFAULT 512,
    chunk_overlap       INT          NOT NULL DEFAULT 64,
    status              VARCHAR(16)  NOT NULL DEFAULT 'active',  -- active|archived
    created_by          BIGINT,
    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- ═══════════════════════════════════════════════
-- 文档（含版本链）
-- ═══════════════════════════════════════════════
CREATE TABLE document (
    id                  BIGSERIAL PRIMARY KEY,
    kb_id               BIGINT       NOT NULL REFERENCES knowledge_base(id),
    root_id             BIGINT,                    -- 版本族根 id（首版等于自身 id）
    version_no          INT          NOT NULL DEFAULT 1,
    is_active           BOOLEAN      NOT NULL DEFAULT true,   -- 仅最新版为 true
    filename            VARCHAR(512) NOT NULL,
    file_ext            VARCHAR(16)  NOT NULL,
    file_size           BIGINT       NOT NULL,
    storage_path        VARCHAR(1024) NOT NULL,
    content_hash        VARCHAR(64)  NOT NULL,     -- SHA256，判重与版本识别
    parse_status        VARCHAR(16)  NOT NULL DEFAULT 'pending',
                        -- pending|parsing|embedding|ready|failed
    has_conflict        BOOLEAN      NOT NULL DEFAULT false,  -- 冲突挂起标记
    chunk_count         INT          NOT NULL DEFAULT 0,
    visibility          JSONB        NOT NULL DEFAULT '[]',   -- 可见范围快照
    owner_id            BIGINT,                    -- 上传者（服务账号亦可）
    uploaded_by_app     VARCHAR(64),               -- 若由 API 上传，记录 app_id
    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_doc_kb       ON document(kb_id);
CREATE INDEX idx_doc_root     ON document(root_id);
CREATE INDEX idx_doc_hash     ON document(kb_id, content_hash);
CREATE INDEX idx_doc_conflict ON document(has_conflict) WHERE has_conflict = true;

-- ═══════════════════════════════════════════════
-- 切片（向量 + 元数据冗余下沉）
-- ═══════════════════════════════════════════════
CREATE TABLE document_chunk (
    id                  BIGSERIAL PRIMARY KEY,
    doc_id              BIGINT      NOT NULL REFERENCES document(id) ON DELETE CASCADE,
    kb_id               BIGINT      NOT NULL,
    chunk_index         INT         NOT NULL,
    content             TEXT        NOT NULL,
    heading_path        VARCHAR(512),              -- 标题路径，如「第三章 > 3.2 报销标准」
    embedding_model     VARCHAR(64) NOT NULL,      -- ⚠️ 记录生成该向量的模型
    embedding           vector(1024),              -- 维度随模型，schema 内置 1024
    tags                JSONB       NOT NULL DEFAULT '{}',  -- 文档级标签的冗余副本
    is_retrievable      BOOLEAN     NOT NULL DEFAULT true,  -- 权限下推
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_chunk_doc     ON document_chunk(doc_id);
CREATE INDEX idx_chunk_kb      ON document_chunk(kb_id);
CREATE INDEX idx_chunk_tags    ON document_chunk USING GIN (tags jsonb_path_ops);
CREATE INDEX idx_chunk_vec     ON document_chunk USING hnsw (embedding vector_cosine_ops)
                               WITH (m = 16, ef_construction = 64);
```

> **设计说明（重要）**
> - `embedding_model` 字段是**必须的**：不同模型的向量**即使维度相同也不可混用**。该字段用于识别哪些切片需要重建索引。
> - `tags` 冗余下沉是**检索性能的关键**：过滤时单表完成，避免 JOIN。
> - `is_retrievable` 是权限的**下推缓存**，由文档 ACL 变更时同步刷新。

```sql

-- 标签体系
-- ═══════════════════════════════════════════════

    permission          VARCHAR(16) NOT NULL DEFAULT 'read',  -- read | write | manage
    granted_by          BIGINT,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),

);
CREATE INDEX idx_acl_doc     ON document_acl(doc_id);

-- ═══════════════════════════════════════════════
-- 冲突记录
-- ═══════════════════════════════════════════════
CREATE TABLE conflict_record (

    old_chunk_id        BIGINT,

                        -- contradiction | entailment | duplication | unrelated

    reason              TEXT,                        -- LLM 给出的判定理由
    resolution          VARCHAR(32),                 -- overwrite|keep_old|coexist|cancel|pending
    resolved_by         BIGINT,
    resolved_at         TIMESTAMPTZ,

    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_conflict_newdoc ON conflict_record(new_doc_id);
```

## 6. 权限模型设计

### 6.1 模型选择：RBAC + 文档级 ACL

| 层 | 机制 | 管什么 |
|---|---|---|
| **RBAC** | 角色 → 权限点 | 能做什么：建库、上传、删除、管理标签、看审计 |

**注意**：本期不做知识库级入口权限（已确认），但**建库/删库属操作权限，仍由 RBAC 管控**，不是谁都能建。

**Mock 档（本期默认）**

```python
# ⚠️ 硬约束 1：确定性。同文本必须得到同向量，否则测试不可复现
seed = int(hashlib.md5(text.encode()).hexdigest()[:8], 16)
rng  = np.random.default_rng(seed)
vec  = rng.normal(0, 1, 1024)
vec  = vec / np.linalg.norm(vec)     # 归一化，保证余弦相似度语义正确
```

**Local 档（后续接入）**

- DeepSeek / 千问3.6（LLM）
- 实现方式：新增 adapter 类，填入公司内网地址，**不动业务代码**

### 7.4 ⚠️ 向量模型切换的强制机制（重要）

**维度相同 ≠ 向量空间相同。** 阿里 `text-embedding-v4` 与 bge-m3 同为 1024 维，但向量**完全不可比**。

强制机制：

1. `document_chunk.embedding_model` 记录生成向量的模型
2. `knowledge_base.embedding_model` 与 `embedding_dim` 绑定模型与维度
3. 切换 embedding 模型时：
   - 若维度不同 → **直接拒绝**，需先迁移
   - 若维度相同但模型不同 → **强制提示**"该知识库全部向量需重建"，并提供一键重建入口（异步任务）
4. 检索时校验 `embedding_model` 一致，不一致的切片**不参与检索**并告警

> 不做这套机制，将来切换模型会出现「检索结果莫名其妙全错」的隐蔽 bug。

### 7.5 API Key 安全

- **加密存储**：`api_key_hash` 只存哈希（bcrypt/argon2），明文**仅在创建时返回一次**
- **接口脱敏**：任何返回密钥的接口只回显 `sk-****abcd`
- **防越权**：禁止跨应用读取他人 Key
- **成本控制**：全真调用会真实扣费，必须有用量统计 + 日配额 + 上限告警

## 8. 元数据标签体系与治理

### 8.1 设计原则

1. 标签**先定义 schema**，上传时**从预设枚举中选择**，禁止自由输入（自有系统）
2. 标签打在文档上，入库时**冗余下沉到每个切片**（`document_chunk.tags`）
3. 过滤走 **pre-filter**：`WHERE kb_id=? AND is_retrievable=true AND tags @> '...'`

> 因为标签是预先划定的、选择性明确，直接 pre-filter 即可，**无需自适应的 pre/post-filter 切换**。

### 8.2 标签维度建议（可按业务调整）

| tag_key | 类型 | 可选值 |
|---|---|---|
| `dept` | enum | 研发 / 市场 / 财务 / HR |
| `doc_type` | enum | 制度 / 流程 / FAQ / 合同 / 技术文档 |
| `security_level` | enum | 公开 / 内部 / 机密 |
| `effective_date` | date | — |

### 8.3 ⚠️ "完全开放标签" 的 5 条治理机制（必须同时实现）

已确认对外 API 允许创建新标签维度，因此以下治理机制**必须落地**：

| # | 机制 | 防的问题 | 优先级 |
|---|---|---|---|
| 1 | **key 规范化**：trim、长度限制、小写归一、禁空 | `"Dept"` 与 `"dept"` 变成两个标签 | 必做 |
| 2 | **同义检测**：创建时与已有标签做编辑距离 / 拼音相似度比对，命中则提示"是否复用已有的 XX？" | `研发部`/`研发部门`/`yanfabu` 三胞胎 | 建议做 |
| 3 | **命名空间隔离**：外部系统创建的标签强制加前缀 `ext.` | 外部污染自有标签 | **必做** |
| 4 | **标签治理后台**：管理员可合并 / 重命名 / 废弃，废弃时文档数据可批量迁移 | 标签脏了却没法收拾 | **必做** |
| 5 | **独立权限点 + 审计留痕** | 出问题查不到来源 | 必做 |

> 第 3、4 条是兜底底线，即使缩减范围也不可省略。

## 9. 检索流程设计

### 9.1 执行顺序（不可调换）

```
① 权限过滤     →  只保留当前主体可见的切片
② 标签过滤     →  命中用户选择的标签条件
③ 向量召回     →  HNSW 近邻检索 + pg_bigm 全文召回（双路）
④ 融合         →  RRF 或加权融合两路结果
⑤ 版本压制     →  同一 root_id 的多版本，只保留最新
⑥ Rerank 精排  →  bge-rerank-m3 / gte-rerank-v2
⑦ Top-K 输出   →  带来源文件、版本号、生效日期、冲突标记
```

> **⑤ 必须在 ⑥ 之前**。否则会出现「旧版本分数高，把同一文档的新版本挤掉」，兜底策略失效。

### 9.2 混合检索的必要性

向量检索对**数值、日期、专有名词、条款编号**极不敏感，而这些**恰好是冲突最常发生的地方**（如"报销上限 500" vs "800"）。

因此必须做**双路召回**：

| 路 | 实现 | 擅长 |
|---|---|---|
| 语义路 | pgvector HNSW | 语义相似、表述不同 |
| 关键词路 | pg_bigm / tsvector | 精确数值、代号、专名 |

### 9.3 过滤查询示例

```sql
-- 主体权限 + 标签过滤 + 向量检索（pre-filter）
WITH visible AS (
    SELECT c.id, c.doc_id, c.content, c.embedding, c.tags
    FROM document_chunk c
    JOIN document d ON d.id = c.doc_id
    WHERE c.kb_id = ANY(:kb_ids)
      AND c.is_retrievable = true
      AND d.is_active = true
      AND NOT d.has_conflict                    -- 冲突挂起文档默认排除
      AND c.embedding_model = :current_model    -- 向量模型一致性校验
      AND c.doc_id IN (                         -- ⚠️ 后端强制注入的权限集
          SELECT doc_id FROM document_acl
          WHERE (subject_type='user' AND subject_id = :uid)
             OR (subject_type='role' AND subject_id = ANY(:role_ids))
      )
      AND c.tags @> :tag_filter                 -- 标签过滤
)
SELECT id, doc_id, content, tags,
       1 - (embedding <=> :query_vec) AS score
FROM visible
ORDER BY embedding <=> :query_vec
LIMIT :recall_k;
```

### 9.4 空结果兜底

标签过滤 + 权限过滤后可能为 0 条。**必须给出明确提示与建议**：

> 当前筛选条件下没有找到相关内容。全库在该知识库范围内有 N 条相关记录。是否放宽标签条件？

## 10. 冲突检测设计

### 10.1 定位

本系统的**核心差异化能力**。检测粒度：**切片级检测、文档级呈现**。

### 10.2 流水线

```
上传 → 解析 → 切片
   ↓
① 候选召回：新文档每个 chunk → 向量检索 Top-K(5~10)
             + pg_bigm 关键词召回（补数值/条款类冲突）
             ⚠️ 候选集限定在「上传者有权访问的文档」（严格方案）
   ↓
② 精排：bge-rerank-m3 / gte-rerank-v2 对 (新chunk, 库内chunk) 打分，取阈值以上
   ↓
③ LLM 判定：结构化输出关系分类
   ↓
④ 文档级聚合 → 生成冲突报告
   ↓
⑤ 分支处理：
     Web 上传  →  弹框人工决策（覆盖 / 保留旧版 / 并存 / 取消）
     API 上传  →  入库挂起 + 通知管理员（见 10.5）
```

### 10.3 关系分类（必须做 NLI，不能只看相似度）

| relation | 含义 | 处理 |
|---|---|---|
| `contradiction` | **真冲突**：数值/规则/事实矛盾 | 需人工决策 |
| `temporal` | 时效型：新文件取代旧文件 | 走版本升级，**不算冲突** |
| `duplication` | 重复：内容一致 | 可提示去重 |
| `unrelated` | 无关 | 忽略 |

### 10.4 ⚠️ 五个必须避开的坑

1. **绝不让 LLM 凭空判断冲突**
   LLM 只看新文档时不知道库里有什么，必然幻觉。**必须先检索、再判定**（Grounded）。

2. **冲突 ≠ 相似**
   相似度高可能只是"重复/一致"。必须做关系分类（NLI 任务）。

3. **复杂度必须控制**
   全量 N×M 对比会爆炸（100 chunk × 10 万 chunk）。必须只取 Top-K 候选，降到 **O(N×K)**。

4. **冲突类型要在 Prompt 中写死**
   明确告知 LLM 四类关系及其定义，并要求区分"时效型"与"真冲突"。

5. **LLM 输出必须结构化**
   JSON Schema / Function Calling + `temperature=0~0.2`，否则判定结果不稳定。

### 10.5 两个场景的冲突处理

| 场景 | 处理方式 |
|---|---|
| **Web 上传** | 弹框展示「新文件片段 vs 库内文件片段 + 文件名 + 冲突原因」，人工四选一 |
| **API 上传** | **入库挂起**：文档完成解析与向量化，打 `has_conflict=true`；**检索默认排除**；通知管理员处理 |

**API 场景细节**：
- 不阻塞调用方（否则对方系统容易直接放弃）
- 不丢文件（文档已入库，处理后可立即生效）
- `task` 状态返回 `conflict_pending`，调用方可据此感知
- 管理员在冲突处理台批量或逐条处理

### 10.6 权限边界（严格方案）

- 冲突检测候选集 = **上传者有权访问的文档**
- 受限文档**完全不参与**检测与提示，无侧信道泄露
- **补偿机制**：管理员可发起「全库一致性扫描」（仅 admin，操作进审计日志），避免受限文档与公开文档冲突无人发现的死角

## 11. 版本与兜底引用策略

### 11.1 版本链设计

```
document.root_id    同一份文档的版本族根
document.version_no 递增版本号
document.is_active  仅最新版为 true
```

**版本识别规则**：

| 情形 | 处理 |
|---|---|
| 同文件名 + 同 `content_hash` | 判为重复，**拒绝上传**并提示 |
| 同文件名 + 不同 hash | 判为**版本升级**，新版本 `version_no+1`，旧版 `is_active=false` |
| 不同文件名 + 内容冲突 | 判为**冲突**，走冲突处理流程（不自动覆盖） |

### 11.2 「优先引用最新」的五层实现

| 层 | 机制 | 说明 |
|---|---|---|
| **L2（主）** | **版本压制** | 检索结果中同 `root_id` 的多版本，**只保留最新版** |
| L1（辅） | 时间加权 | `score = α·相关度 + β·时间衰减`，β 取 0.1~0.2，**轻权重** |
| L3 | Prompt 注入 | 每个片段带「文件名 + 生效日期 + 版本号」，system prompt 明确冲突时优先采用最新的并说明理由 |
| L4 | 引用标注 | 命中存在冲突记录的片段，UI 打 ⚠ 标记并链接冲突详情 |
| L5 | 文档开关 | 被取代文档 `is_active=false`，默认不参与检索 |

> **只做 L1 时间加权是常见错误做法**——它会让"稍新但完全不相关"的文档污染答案。**L2 版本压制才是正确做法**。

## 13. 审计与限流

### 13.1 审计日志

**必须记录的字段**：操作主体（人/应用）、动作、资源、时间、来源 IP。

**必记动作清单**：

| 类别 | 动作 |
|---|---|
| 认证 | 登录、登录失败、API Key 鉴权失败 |
| 知识库 | 创建、修改、删除 |
| 文档 | 上传、删除、下载、版本切换、标签变更 |
| 权限 | 授权、回收、可见范围变更 |
| 检索 | ⚠️ **检索行为（必须含命中的文档 ID 列表）** |
| 冲突 | 冲突产生、冲突处理决策 |
| 标签治理 | 标签创建、合并、重命名、废弃 |
| 运维 | 全库一致性扫描、索引重建 |
| 管理 | 审计日志导出 |

> **重点**：检索日志必须记录 `hit_doc_ids`。否则当机密文档外泄时，无法追溯是"谁通过搜索看到了它"——这是企业级审计的核心留痕点。

### 13.2 限流与配额

| 维度 | 限制 |
|---|---|
| 单应用 QPS | 默认 5（`api_client.qps_limit`） |
| 单应用日配额 | 默认 10000 次（`api_client.daily_quota`） |
| 上传频率 | 单用户/单应用每分钟 N 次（防滥用） |
| 模型调用成本 | 按知识库统计 token 消耗，设日上限 + 告警 |

> 全真调用会**真实扣费**，配额即成本控制。

### 13.3 API Key 安全

- 只存哈希（bcrypt/argon2），明文仅创建时返回一次
- 接口回显一律脱敏 `sk-****abcd`
- 支持吊销与轮换
- 禁止跨应用读取

## 16. 分期实施计划

## 18. 风险清单与缓解措施

| # | 风险 | 影响 | 缓解措施 |
|---|---|---|---|
| 1 | **向量空间不兼容** | 切换 embedding 模型后检索结果全错 | `embedding_model` 字段 + 强制重建机制（7.4） |
| 2 | **标签失控** | 按标签过滤静默失效，最难排查 | 5 条治理机制，命名空间隔离 + 治理后台为底线（8.3） |
| 3 | **冲突检测幻觉** | 误报冲突，用户不信任 | 必须先检索再判定（Grounded）+ 结构化输出 + 低温度（10.4） |
| 4 | **全量对比性能爆炸** | 大文档上传卡死 | 只取 Top-K 候选，O(N×K)（10.4） |
| 5 | **权限越权** | 机密文档泄露 | 权限条件后端强制注入，单一出口函数，四处复用（6.3） |
| 6 | **API Key 泄露** | 全库数据泄露 | 只存哈希 + 脱敏回显 + 支持轮换吊销（13.3） |
| 7 | **模型成本失控** | 真实扣费超预算 | 配额 + 用量统计 + 日上限告警（13.2） |
| 8 | **对外 API 契约变更** | 打断调用方 | 版本化 + 兼容性承诺 + 破坏性变更走 v2（12.4） |
| 9 | **文档解析信息丢失** | 检索命中率低 | 保留标题路径，拼入 chunk 内容（10.2 / 15） |
| 10 | **异步任务积压** | 上传排队 | 任务优先级 + 并发度可配 + 状态可见 |

## 附录 A：关键技术决策速查

| 决策 | 结论 | 原因 |
|---|---|---|
| 向量库 | PostgreSQL + pgvector | 元数据过滤是核心需求，SQL 混合过滤能力最强，运维最简 |
| 全文检索 | pg_bigm / tsvector | 中文友好，免引入 ES |
| 权限模型 | RBAC + 文档级 ACL | 操作权限与内容可见性分离 |
| 标签过滤 | pre-filter | 标签选择性明确，无需自适应切换 |
| 冲突检测 | 切片级检测、文档级呈现 | 定位精确 vs 成本可接受的平衡 |
| 冲突权限 | 严格（只比对上上传者可见文档） | 无侧信道泄露，实现更简单 |
| 兜底引用 | 版本压制为主，时间加权为辅 | 时间加权会污染相关性 |
| API 认证 | API Key | 公司内部系统，简单够用 |
