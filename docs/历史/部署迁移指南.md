# 部署与迁移指南

> 面向运维/开发，说明本系统如何从"本机开发态"迁移到服务器运行。
> 覆盖：Docker 的角色、公网服务器迁移、内网服务器迁移、上线检查清单。

---

## 一、先回答：Docker 在这个项目里干了什么？

**一句话：Docker 只负责跑「数据库」，不跑应用程序。**

本项目的 `docker-compose.yml` 里只有 **两个基础设施容器**，没有任何应用容器：

| 容器名 | 镜像 | 宿主机端口 | 作用 |
|---|---|---|---|
| `kb-postgres` | `pgvector/pgvector:pg16` | **5433** → 容器 5432 | 数据库 + 向量检索（pgvector 扩展） |
| `kb-redis` | `redis:7-alpine` | **6380** → 容器 6379 | 缓存 / 任务队列（Celery 预留） |

**为什么用 Docker 跑数据库？** 因为 pgvector 是 PostgreSQL 的**扩展**，普通 `apt install postgresql` 装不出带向量能力的实例。用官方 `pgvector/pgvector` 镜像，一条命令就能得到一个带好扩展、编码是 UTF8、端口隔离好的数据库——不用在服务器上手工编译扩展、改配置、初始化。

**Docker 没做的事：**
- 后端 FastAPI（uvicorn）——**原生 Python 进程**，不在容器里跑
- 前端 React——`npm run build` 出静态文件，由 nginx 托管
- 上传的原始文件——存在宿主机 `data/uploads/`，**不在容器里**

**结论：Docker 是一个「开箱即用的数据库供应商」，不是部署方案本身。** 你完全可以不用 Docker（自己在服务器装带 pgvector 的 PG），只是那样更麻烦。

## 二、本项目的完整运行链路（三块）

系统由**三个独立进程**组成，缺一不可：

| # | 组件 | 启动方式 | 默认端口 | 对外暴露 |
|---|---|---|---|---|
| ① | PostgreSQL(pgvector) | `docker compose up -d` | 5433 | 否（仅本机） |
| ② | Redis | 同上（同一 compose） | 6380 | 否（仅本机） |
| ③ | 后端 FastAPI | `uvicorn app.main:app` | 8000 | 经 nginx 反代 |
| ④ | 前端静态文件 | nginx 托管 `web/dist` | 80/443 | 是 |

**请求流：** 浏览器 → nginx（80/443）→ 静态文件命中即返回；`/api/v1/*` 反代到 `127.0.0.1:8000` → FastAPI → 读写 PG(5433)/Redis(6380)。

**关键约定（迁移时必须对齐）：**

1. **前端 API 基址是相对路径 `/api/v1`**（见 `web/src/api/client.ts`）——生产环境**不会**硬编码某台机器地址，靠 nginx 同源反代即可，**前端无需改代码**。
2. **后端自动建表**：启动时 `app.main:lifespan` 会调 `db_init.init_database()`，幂等地建表 + 建扩展 + 写种子数据（权限点/角色/admin 账号），**无需手工执行 SQL**。
3. **`.env` 决定一切**：`server/app/core/config.py` 从 **项目根目录 `.env`** 或 `server/.env` 读取（前者优先）。端口、密钥、模型档位全在这里。
4. **上传目录**：`UPLOAD_DIR=./data/uploads` 是**相对项目根目录**的路径，迁移时要连同这个目录一起带走（历史文件）。

## 三、迁移到公网服务器（47.121.183.81）

### 3.1 服务器体检结果

| 项目 | 实测值 | 判断 |
|---|---|---|
| Docker | 26.1.3 | ✅ 可用 |
| Docker Compose | v2.27.0 | ✅ 可用 |
| pgvector 镜像 | `pgvector/pgvector:pg16` **已在本地** | ✅ 无需再拉 |
| nginx | 1.14.1，已在跑 `xibuyj.cn` / `xibuyj.com` | ✅ 可复用 |
| 端口占用 | 80、443、8200、6379(仅本机) | ✅ 8000 / 5433 / 6380 **空闲** |
| **磁盘** | 40G 总，**已用 38G，剩 2.9G（93%）** | 🔴 **严重不足** |
| **内存** | 7G 总，**可用仅 1G**（已用 6G） | 🟠 **偏紧** |
| **系统 Python** | **仅 3.9.6** | 🔴 **版本过低** |

### 3.2 三个必须先解决的问题

**🔴 问题一：磁盘只剩 2.9G。**
本系统上线大致要吃掉：pgvector 镜像 441MB（已有）+ redis 镜像约 40MB + Python 依赖约 600MB~800MB + Postgres 数据（随文档增长）+ 上传文件。**2.9G 基本不够**，尤其后续上传文档会持续增长。
→ 上线前**必须**先腾空间：`docker system prune -a`、清日志、找出占满磁盘的大文件；或扩容数据盘。
→ 把项目放到**大容量盘**（如 `/data`），别放 `/`。

**🔴 问题二：系统 Python 只有 3.9.6。**
本项目依赖 FastAPI/Pydantic v2/numpy 2.x 等，**Python 3.9 已无法满足**（numpy 2.x 要求 ≥3.10，部分依赖要求更高）。
→ 解决：**后端改用 Docker 容器跑**（推荐，见方案 B），或宿主机单独装 Python 3.11。

**🟠 问题三：可用内存只有 1G。**
先查清 **6G 内存被谁占了**（`ps aux --sort=-%mem | head`）。若已被其他业务占满，容器化三个服务会触发 OOM。
→ 缓解：限制容器内存、PG 调小 `shared_buffers`、Redis 设 `maxmemory`。

### 3.3 一个隐藏的严重冲突：nginx 的 `/api/`

现网 `nginx.conf` 里**已经存在**一条：

```
location /api/ { proxy_pass http://127.0.0.1:11999/; }
```

而**本系统的接口前缀也是 `/api/v1/*`**。如果不处理，你的前端请求会被**错误地转发到人家的 11999 服务**，表现是「前端能打开、一登录就报错」。
→ 处理办法（任选，推荐前者）：
1. **用独立域名**：新建 `conf.d/kb.xxx.com.conf`，绑定一个**新二级域名**，在新 server 块里做 `/api/v1` 反代，互不干扰。
2. **前缀避让**：给本系统换一个独占前缀，例如 nginx 里 `location /kbapi/ { proxy_pass http://127.0.0.1:8000/api/v1/; }`，前端 `baseURL` 相应改为 `/kbapi`。

### 3.4 两套落地方案

**方案 A｜混合部署（轻量，省资源）**

- Docker 只跑 PG + Redis（复用已有 pgvector 镜像）
- 宿主机装 **Python 3.11** 建 venv，`uvicorn` 跑后端，systemd 守护自启
- 前端**在本地 `npm run build`**，把 `web/dist` 上传，nginx 托管

优点：省内存/磁盘，复用现成 nginx。缺点：要在服务器上装对 Python 版本。

**方案 B｜后端也容器化（环境最干净，推荐）**

- 新增一个 `Dockerfile`（`python:3.11-slim` 装依赖）跑 FastAPI
- `docker-compose.prod.yml` 把 **PG + Redis + backend** 三个服务一起编排
- 前端仍在**本地构建**后交给 nginx（不在服务器装 Node）

优点：**彻底绕开服务器 Python 3.9 的问题**，环境可复现。缺点：构建时占内存（约需 1G 峰值），要先解决磁盘。
> 前端构建放本地做，是因为服务器装 Node + `node_modules` 会再吃掉几百 MB，没必要。

### 3.5 迁移步骤（以方案 B 为例）

```bash
# ── 0. 本地：准备部署产物 ────────────────────────────────
# 前端本地构建（服务器不装 Node）
cd web && npm install && npm run build        # 产出 web/dist

# 打包项目（排除 node_modules / .venv / __pycache__）
# 需要带上：server/  web/dist  docker/  docker-compose.prod.yml  .env  data/uploads(历史文件)

# ── 1. 服务器：腾空间、放代码 ────────────────────────────
docker system prune -a -f        # ⚠️ 会删未使用镜像，确认已无其他业务依赖再执行
mkdir -p /data/kb && cd /data/kb # 放到大容量盘
# 上传代码到 /data/kb

# ── 2. 配置 .env（务必改这三项）──────────────────────────
#   DATABASE_URL  指向容器服务名或 127.0.0.1:5433
#   JWT_SECRET    换成随机值：openssl rand -hex 32
#   CORS_ORIGINS  换成真实域名 https://kb.xxx.com
#   PROVIDER_MODE 公网可访问模型 API → online（端口 80/443 需能出网）

# ── 3. 起容器 ───────────────────────────────────────────
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps   # 三个都 healthy/running

# ── 4. 验证后端 ─────────────────────────────────────────
curl -m 10 http://127.0.0.1:8000/api/v1/system/health

# ── 5. nginx 托管前端 + 反代 API（新建独立域名配置）──────
#   见 3.6 示例；改完 nginx -t && systemctl reload nginx
```

### 3.6 nginx 配置示例（独立域名，避开 `/api/` 冲突）

```nginx
server {
    listen 80;
    server_name kb.xxx.com;              # ← 换成你的域名

    root /data/kb/web/dist;
    index index.html;

    # SPA 路由：刷新子页面不 404
    location / {
        try_files $uri $uri/ /index.html;
    }

    # API 反代到后端（比现网 /api/ 更长，优先级更高；但仍建议用独立域名彻底隔离）
    location /api/v1/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;          # 上传/冲突检测耗时较长
        client_max_body_size 100m;        # 与 MAX_UPLOAD_MB 对齐
    }
}
```
> 配 HTTPS 直接用 `certbot --nginx -d kb.xxx.com`（若服务器可出网），或手工贴证书。

### 3.7 数据迁移（把本机数据搬到服务器）

只搬**代码**是空的，要带上数据：

| 要搬的东西 | 位置 | 迁移方式 |
|---|---|---|
| 数据库 | Docker volume `kb_pgdata` | `docker exec kb-postgres pg_dump -U kb kb_system > kb.sql`，服务器上 `psql` 导入 |
| 上传的原始文件 | `data/uploads/` | 整目录打包上传 |
| 配置 | `.env` | 单独传，**改掉密钥与地址** |

> ⚠️ **`PROVIDER_MODE` 切换会导致向量空间失配**：若本机是 `mock`、服务器用 `online`，**旧向量全部作废**，导入后必须跑重建索引（`server/scripts/rechunk_documents.py`），否则检索返回空。

## 四、迁移到内网服务器

内网与公网最大的区别是 **"能不能出网"**，它决定了几乎所有步骤。

### 4.1 核心分叉：内网能不能访问外网？

| 场景 | 模型档位 | Docker 镜像 | Python/依赖 |
|---|---|---|---|
| **内网能出网** | `online`（走阿里云+DeepSeek）| `docker pull` 直接拉 | `pip install` 在线装 |
| **内网完全隔离** | `local`（内网自建模型）或 `mock`（演示）| **离线导入**（`docker save/load`）| **离线 wheel 包** |

**如果你的内网是"公司涉密内网、完全不通外网"，那 `online` 档直接作废**——它必须访问 `dashscope.aliyuncs.com` 和 `api.deepseek.com`。此时只有两条路：
- 有内网模型服务（bge-m3 / bge-rerank-m3 / DeepSeek / 千问3.6）→ 用 `PROVIDER_MODE=local`，这是**设计好的正式路径**（`server/app/providers/local_bge.py` 已实现，支持 OpenAI 兼容端点与 TEI 两种协议）
- 没有任何模型 → `PROVIDER_MODE=mock`，**仅能演示界面与链路，检索无真实语义**

### 4.2 内网部署前，需要向对方确认/准备的清单

**必问（缺一个方案就定不下）：**

| # | 问题 | 为什么必须知道 |
|---|---|---|
| 1 | 操作系统与版本（CentOS 7 / Ubuntu / 麒麟 / 统信UOS…） | 决定 Docker 能否装、包管理器、Python 怎么装 |
| 2 | 是否已装 Docker / 能否装 | 决定容器方案是否可行 |
| 3 | **能否出外网**（或有无内网 yum/apt 源、内网镜像仓库） | 决定在线装还是离线搬运 |
| 4 | CPU 架构（x86_64 / ARM64 / 龙芯） | 决定镜像与 wheel 架构 |
| 5 | 内存 / 磁盘（尤其数据盘剩余空间） | 决定能否跑、数据放哪 |
| 6 | 是否有内网模型服务？地址与协议？ | 决定 `PROVIDER_MODE=local` 能否用 |
| 7 | 端口占用情况（8000/5433/6380/80/443） | 避让冲突 |
| 8 | 是否有内网 nginx / 反向代理 / 统一网关 / 域名 | 决定前端怎么托管与访问入口 |
| 9 | 是否有 HTTPS 证书（内网 CA 或自签） | 决定访问方式 |
| 10 | 是否要对接公司用户库（`external_id`） | 决定认证是否改造 |
| 11 | 是否要求开机自启、由谁运维 | 决定 systemd / compose restart 策略 |

**离线环境要提前准备的物料：**

```bash
# 在「能上网的机器」上预先下载，再拷进内网：
docker pull pgvector/pgvector:pg16
docker pull redis:7-alpine
docker pull python:3.11-slim          # 若用容器跑后端
docker save pgvector/pgvector:pg16 redis:7-alpine python:3.11-slim -o kb-images.tar
# 内网里：docker load -i kb-images.tar

# Python 依赖离线包（版本要与内网 Python 一致，注意架构）
pip download -r server/requirements.txt -d wheels/ \
    --platform manylinux2014_x86_64 --only-binary=:all: --python-version 3.11
# 内网里：pip install --no-index --find-links=wheels/ -r requirements.txt

# 前端已在本地 npm run build 出 dist，直接拷进去即可（内网无需 Node）
```

### 4.3 内网落地步骤（以方案 B + 本地模型为例）

```bash
# 1. 导入离线镜像
docker load -i kb-images.tar

# 2. 配置 .env
#    PROVIDER_MODE=local
#    LOCAL_EMBEDDING_URL=http://<内网模型地址>/v1/embeddings
#    LOCAL_RERANK_URL=http://<内网模型地址>/v1/rerank
#    LOCAL_LLM_BASE_URL=http://<内网模型地址>/v1
#    LOCAL_LLM_API_KEY=<若需要>
#    JWT_SECRET=<随机值>

# 3. 起服务（镜像已在本地，加 --no-build 或直接 up）
docker compose -f docker-compose.prod.yml up -d

# 4. 健康检查 + 导入数据
curl -m 10 http://127.0.0.1:8000/api/v1/system/health
psql -h 127.0.0.1 -p 5433 -U kb kb_system < kb.sql   # 有历史数据才需要

# 5. nginx 托管 dist + 反代 /api/v1（同 3.6）
```

> ⚠️ **模型切换必重建索引**：`local`（bge-m3，1024 维）与 `online`（text-embedding-v4，1024 维）**维度相同但向量空间不兼容**。切换后旧向量全部失配，必须跑 `rechunk_documents.py` 重嵌。

## 五、上线前检查清单

- [ ] **磁盘**：目标盘剩余空间 ≥ 10G（公网那台当前只剩 2.9G，必须先清理/扩容）
- [ ] **内存**：确认可用内存 ≥ 2G，并为容器设内存上限
- [ ] **Python**：容器方案（推荐）或宿主机 ≥ 3.11
- [ ] **`.env` 三件套**：`JWT_SECRET` 换随机值、`CORS_ORIGINS` 换真实域名、`DATABASE_URL` 端口对齐
- [ ] **端口无冲突**：8000 / 5433 / 6380（公网那台 80/443/8200/6379 已被占，注意避让）
- [ ] **nginx**：`/api/v1` 反代未被现有 `/api/` 规则截胡；SPA 配 `try_files ... /index.html`
- [ ] **`client_max_body_size`** 与 `MAX_UPLOAD_MB`（默认 100m）对齐，否则大文件上传 413
- [ ] **数据已迁移**：PG 导出导入 + `data/uploads/` 整目录 + 旧向量已重建
- [ ] **模型连通性**：`online` 需服务器能出网到模型 API；`local` 需内网模型服务可达
- [ ] **自启**：systemd（方案 A）或 `restart: unless-stopped`（方案 B，compose 已含）
- [ ] **备份**：PG 定期 `pg_dump` + `data/uploads` 备份策略

## 六、安全提醒（上线前必读）

**⚠️ 当前 `.env` 里是真实密钥，且已明文存在项目目录中：**
- `ALIYUN_API_KEY`（阿里云百炼）
- `DEEPSEEK_API_KEY`（DeepSeek）

这两把 Key **绝不能**随代码提交到 Git、也不能随压缩包外发。建议：
1. 立刻到各控制台**轮换（重置）**这两把 Key；
2. `.gitignore` 中确认已忽略 `.env`；
3. 服务器上的 `.env` 权限设为 `600`；
4. 生产环境 `DEBUG=false`，避免异常堆栈把内部细节返回给前端。

**其他：**
- 初始管理员 `admin / admin123456` **首次登录后必须改密**；
- `JWT_SECRET` 必须换（默认值等于没有安全）；
- 数据库密码 `kb_dev_pwd` 仅为开发用，生产应改强密码并只监听本机。
