## 一、一句话结论

这是一个**功能相当完整、分层清晰的企业级 RAG 知识库**：后端 11 个路由模块共 **54 个接口**，
前端 11 个页面基本覆盖全部主流程，异步上传 + 冲突隔离 + 版本自愈都做得很扎实。

但它现在**跑不起来，而且档位配置是坏的**：

1. **全栈当前处于停止状态** —— 8000 / 5173 / 5433 / 6380 全部无监听，Docker 不可用。
2. **`.env` 写的是 `PROVIDER_MODE=online`，而代码里 online 档已被删除** ——
   会被静默降级成 `mock`。这意味着**本地现在只能跑伪向量**，之前用真实模型建的索引**全部失配**，检索会返回空。
3. 存在 **1 个必现功能性 bug**（用户管理页恒 403）和 **若干越权/数据泄漏隐患**。

这不是 bug，是配置漂移；但现象很像「检索坏了」。

```env

```
并确认 `LOCAL_EMBEDDING_URL` 等地址（`.env:52-58`）指向的模型服务真的在跑。
注意：切档后**必须重建索引**（`POST /kb/{id}/reindex`），否则旧向量永远失配。

## 五、前端是怎么调用后端的

### 5.1 调用架构（三层，很规范）

```
页面 pages/*.tsx
   ↓ 调用
api/index.ts        ← 按业务域分组导出 11 个 "api 对象"（kbApi/docApi/searchApi/...）
   ↓ 调用
api/client.ts       ← 唯一的 axios 实例（所有请求都从这里走）
   ↓
vite proxy: /api → http://127.0.0.1:8000
```

**`client.ts` 的三个关键设计**（`web/src/api/client.ts`）：

1. `baseURL: '/api/v1'`，超时 **180 秒**（`client.ts:24-26`）—— 因为上传/检测是慢接口。
2. **请求拦截器**自动加 `Authorization: Bearer <token>`，token 存在 `localStorage.kb_token`（`:28-34`）。
3. **响应拦截器**做两件事（`:42-75`）：
   - 成功时**直接返回 `res.data`**（解包一层）→ 所以 `api/index.ts` 里能写
     `http.get<any, KnowledgeBase>(...)` 泛型第二个参数就是返回类型；
   - 失败时把后端的统一错误体 `{detail:{code,message,required}}` 规范化成 `ApiError`，
     并**在 401 时清 token 跳登录页**（`:59-65`）。

**页面权限控制走 `store/auth.tsx`**：
登录后把 `user/roles/permissions` 同时写 React state 和 localStorage；
`has(...codes)` 用 `permissions.includes()` 判断（`auth.tsx:72-75`）；
路由层用 `<RequirePermission perm="xxx">` 包裹（`App.tsx:27-44`）。
刷新页面后会再拉一次 `/auth/me` 校正权限（`auth.tsx:59-70`）。

### 5.3 上传这条链路最能体现设计意图

```ts
// web/src/api/index.ts:328-375
docApi.upload()          // POST，只拿回 202 + task_id
docApi.uploadAndWait()   // 内部每 700ms 轮询 GET /tasks/{task_id}，直到 done/failed
                         // 10 分钟超时；结果从 task.result 里取 doc_id / conflict_count
```

> ⚠️ 这个封装**是必须的**：后端上传是异步受理，`doc_id` 和 `conflict_count` **不在 202 响应里**。
> 如果直接读上传响应里的 `conflict_count`，它**恒为 0** ⇒「检出冲突」的提示会**静默失效**。
> 前端已经正确规避了这个坑。

## 六、两大核心业务流（后端）

### 流 1：上传 → 入库

```
POST /kb/{id}/documents                     documents.py:141  (def，进线程池，不阻塞事件循环)
  ├─ 校验格式/大小（≤100MB）→ save_upload() 落盘
  ├─ create_task() 写 AsyncTask(pending) → db.commit()      ← 先落库
  ├─ ingest_document_task.delay(...)         ← 派发给 Celery
  └─ 返回 202 {task_id}

Celery worker (独立进程/独立 session)          tasks/__init__.py:51
  └─ ingest_document()                       ingestion/pipeline.py:142
       ├─ _detect_version()  判重/判版本（content_hash）
       ├─ parse_file()       解析（md/txt/docx/xls…）
       ├─ chunk_document()   切分
       ├─ embed_batch()      向量化 → 写 Document + DocumentChunk
       └─ detect_conflicts() 冲突检测 → 隔离冲突切片 → 写 task.result
```

### 流 2：检索（混合召回）

```
POST /search                                  services/retrieval/search.py:492
  ├─ recall_vector()    pgvector 余弦距离，且 embedding_model 必须 == 当前档位
  ├─ recall_keyword()   tsvector @@ to_tsquery_or（应用层中文二元组分词）
  ├─ RRF 融合           rrf_k=60，只看排名
  ├─ suppress_old_versions()  同一 root_id 只保留最大 version_no
  ├─ apply_rerank()     bge-rerank 精排（异常则 degraded=True 降级不报错）
  └─ _build_dynamic_parents() 检索时聚合父块（避免静态快照绕过冲突隔离）
```

**权限过滤的唯一出口**是 `permission.visible_document_filter()`：
`scope=search` → `公开 OR owner_id=自己`；`scope=manage` → 管理员全知。
服务端强制注入，调用方无法用参数绕过（这点做对了）。

## 七、缺陷清单（已逐条打开源码核对）

### 🔴 P0 —— 必现，直接影响功能

#### P0-1　「用户管理」页对所有人恒 403（含管理员）

- **证据**：`web/src/App.tsx:73-80` 用 `perm="role:read"` 守卫 `/permissions` 路由；
  但 `server/app/db_init.py:40-66` 的权限点字典里**根本没有 `role:read`**，
  与之相关的是 `user:read` / `user:manage`。
- **为什么必现**：`store/auth.tsx:73` 的 `has()` 是 `permissions.includes(code)`；
  管理员角色是 `["*"]`，在 `db_init.py:225` 展开成**全部 20 个真实权限码**，
  其中不含 `role:read` ⇒ `has("role:read")` 恒为 `false`。
- **后果**：前端渲染的是 `Result status="403"` 页面，**所有人都进不去用户管理**
  （后端 `GET /users` 其实只需要登录，接口是好的）。
- **修法**：把 `App.tsx:76` 的 `perm` 改成 `"user:manage"`（与 `roles.py:145` 的后端校验对齐）。

#### P0-2　档位配置漂移：`online` 被静默降级为 `mock`

见第二节。**不是代码 bug，但当前影响最大**：`.env` 不改，本地检索必然召回为空。

---

### 🟠 P1 —— 越权 / 数据一致性隐患

#### P1-1　`POST /conflicts/detect` 可对「他人的私有文档」触发检测

- **证据**：`api/v1/conflicts.py:182-189` 拿到 `doc = db.get(Document, payload.doc_id)` 后
  **只判空、不判可见性/归属**，直接调用 `detect_conflicts()`；
  而 `services/conflict/detector.py:312-338` 的 `detect_conflicts()` **只对「候选集」做权限过滤**，
  对**目标文档本身不做任何校验**。
- **触发条件**：普通用户也有 `conflict:resolve`（`db_init.py:92`），
  只要知道别人的 `doc_id` 就能调用。
- **后果**：检测会把该文档的冲突切片写成 `is_retrievable=False`（有写副作用），
  且返回体里带 `conflicts` 摘要 ⇒ 既是**越权写入**，也是**信息侧信道**。
  （对照 `resolve_conflict`：`conflicts.py:363` 是有 `can_edit_document` 校验的，说明这是漏写。）
- **修法**：`:182` 之后补 `_require_visible_doc(db, actor, payload.doc_id, scope=SCOPE_MANAGE)` 或 `can_edit_document` 校验。

#### P1-2　任务列表 / 任务详情没有归属隔离

- **证据**：`api/v1/tasks.py:19-36`、`:39-50` 只用 `get_current_actor`，
  `platform_service.list_tasks()` **没按 `created_by` 过滤**，`get_task()` 也不校验归属。
- **后果**：任意登录用户可枚举**全系统任务**，`task.result` 里含 `doc_id`、冲突数等；
  且 `AsyncTask` 的 UUID 可被遍历（虽然 UUID 难猜，但列表接口直接给出全部）。
- **修法**：非管理员按 `actor.user_id` 过滤 `created_by`。

#### P1-3　模型接口大部分没有后端权限校验（前端守卫可被绕过）

- **证据**：`models.py` 里 **只有 `POST /models/switch`（:161）** 带 `system:config`；
  `GET /models/config`（:53）、`POST /models/test`（:97）、`GET /models/usage`（:229）**都只要求登录**。
- **后果**：前端 `App.tsx:89-96` 的 `system:config` 守卫只是 UI 层；
  直接调 API，任意登录用户可读取模型配置，并触发 `/models/test`
  —— **该接口会用真实凭据向后端模型服务发探测请求**，等于把模型端点借给别人扫。
  同类问题还有 `GET /audit-logs/actions`（`audit.py:105-110` 漏了 `audit:read`）。

#### P1-4　上传派发失败会留下「孤儿任务 + 孤儿文件」

- **证据**：`documents.py:208-236` 顺序是
  `create_task()` → `db.commit()`（:215）→ `ingest_document_task.delay(...)`（:228），
  **`.delay()` 没有 try/except**。
- **触发条件**：Redis broker 不可达 / Celery 未起。
- **后果**：`.delay()` 抛异常 ⇒ 接口返回 500，但
  ① `AsyncTask` 已提交且**永远 pending**；② 文件已 `save_upload` 落盘，**永不清理**。
- **修法**：把 `.delay()` 包 try，失败时把任务标 `failed` 并 `_safe_unlink` 掉文件。

#### P1-5　版本历史会泄漏同一版本链上的受限版本元数据

- **证据**：`documents.py:459-474`，入口用 `_require_visible_doc()` 校验了可见性，
  但随后 `.where(Document.root_id == root)` 查询**整条版本链，未加 visibility 过滤**。
- **后果**：只要你可见其中一个版本，就能看到链上**全部版本**的
  `filename / content_hash / chunk_count / created_at`（仅元数据，不含正文）。
