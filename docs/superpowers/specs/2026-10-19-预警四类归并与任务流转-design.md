## 零 一句话

**预警从 11 类收成 4 类**（预算 / 项目全过程 / 穿透式复盘 / 指标）—— 收的不是判据，是**同一件事的三种切法**；
**再加一层任务流转**：预警不再是"推给人看的一句话"，而是**一条能下发、能回执、能按时限催办上报、能按数据自动核销的处置单**，全过程留痕。
**入口是对话**：点开任何一条预警，直接把它变成对话框里的一张卡片 —— AI 把详情、原因、建议一次说清，并问一句"要不要我帮你发起"。

> **v2 修订（2026-10-19 晚，按 Fred 反馈）**
> ① 复盘类按年/季推 → **确认**；② 升级改成**按职责线给对应的人**，市领导只收大方向、不接执行层 → 已改写 §4.5；
> ③ 自动核销 → **确认**（"7 天把指标降下来，降下来就自动完成"）；④ 预警**要有跳转**：点击 → 自动在对话框发一条 → 出详情（需前端配合）→ §4.10/§7；
> ⑤ AI **代替人思考**：给建议 → 问"要不要我帮你发起"（拟办）→ 执行侧同样给建议、代写/润色报告 → §4.11/§4.12。

## 一 现状与问题（实测，不是判断）

### 1.1 现在 11 类，同一个人最多收到 7 条，其中一半是同一件事

2026-10-19 用现网数据实跑 `alerts.daily()`（脚本见附录 B，原始输出 `output/probe_alerts_today.json`）：

| 账号 | 角色 | 范围 | 条数 | 收到的类型 |
|---|---|---|---|---|
| `sngdssz` | 所长 | 两水供电所 | **5** | budget_underspend · node_stay_overdue · approval_backlog · node_backlog · data_quality_amount |
| `xgscwb` | 县财务 | 曾都（7 所） | **5** | budget_underspend · approval_backlog · zero_execution · node_backlog · metric_deteriorated |
| `xgscwb003` | 县财务 | 广水（17 所） | **4** | budget_underspend · approval_backlog · zero_execution · node_backlog |
| `sgscwb` | 市财务 | 全市（47 所） | **7** | 上面 + extreme_amount · data_quality_amount · metric_deteriorated |
| `sgsld` | 市领导 | 全市 | **2** | budget_underspend · metric_deteriorated |

**重复的三组（同一事实，换了切法）**：

| 组 | 现在的两条/三条 | 为什么是同一件事 |
|---|---|---|
| 审批积压 | `node_stay_overdue`（9 个项目滞留超 90 天）+ `approval_backlog`（23 个待审批）+ `node_backlog`（10 个集中在内部审核） | 所长拿到 3 条，说的都是"我这儿有单子压着没批"；`node_backlog` 是 `approval_backlog` 按节点分组，`node_stay_overdue` 是同一批件按天数筛选 |
| 预算不动 | `budget_underspend`（预计年底剩余 37.87 万）+ `zero_execution`（6 个所尚未启动） | 零执行是"花不完"的最严重档，不是另一件事 |
| 数据质量 | `data_quality_amount`（2 个项目工程费或物资费为零）+ `extreme_amount`（1 个项目 4383 万） | 都是"这张单的金额填得不对"，该合并成一条"申报金额存疑，N 件" |

**结论：11 类不是 11 件事，是 4 件事被切了 11 刀。**

### 1.2 "审核种类太多"的根子

现有实现把**审批节点**（供电所内部审核 / 县运检 / 营销部 / 县财务 / 市财务 / 市领导）当成了预警的种类来源，
于是每个节点×每种统计口径都能长出一个类型。实测 130 件待处理审批任务的节点分布：

| 节点 | 待处理件数 | 最久进入节点 |
|---|---|---|
| 供电所内部审核 | 92 | 2026-04-18 |
| 营销部审核 | 18 | 2026-04-23 |
| 县公司财务部审核 | 13 | 2026-04-17 |
| 县公司运检部审核 | 6 | 2026-06-13 |
| 市公司财务部审核 | 1 | 2026-04-23 |

**到底哪个需要预警：只有一个 —— 「停在你这个节点、超过 90 天还没办」。**
节点不是预警种类，是**这条预警的属性**（卡在谁那儿）。所以：
- 按节点拆类型 → 6 个节点 6 个类型 → 收到的人一脸问号；
- 按"停留超期"一条类型 + `data.node` 列出节点分布 → 1 条，能办事。

### 1.3 真正的缺口不是预警，是"预警之后"

现在接口是**无状态现算**（设计原话："处理掉的就没了，不需要我们记状态"）。这条在"今天我该看什么"上成立，
但在"**领导点名让某所在 1 个月内把钱花完、3 天内给方案**"这类事上**完全不成立**：

| 缺口 | 现状 | 后果 |
|---|---|---|
| 谁办了 | 没有任务实体，没有承办人 | 第二天预警还在（数据没变），但没人知道领导已经批过要求 |
| 何时办完 | 只有"命中/不命中" | 1 个月后钱还是没花，也没有"逾期"这件事 |
| 往下压 | 没有下发链 | 所长只能自己在系统外打电话 |
| 催与上报 | 没有时限与升级 | 3 天没回执，没人知道，更不会上报 |
| 复盘 | 没有处置记录 | 同类问题年年重犯，无法复盘 |

**所以第二部分不是"加个功能"，是把预警从"通知"变成"工单"。**

| D6 | 处理人 | **规则推荐 → 发起人确认 → 可多人（主责/协办/抄送）** | ❌ 按 `assignee_id` 找人：130 件全 NULL；❌ 纯手工选人：每天几十条变手工活 |
| D7 | 上级是谁 | **职责线（配置）+ 发起人**，**不用 `t_department.manager_id`** | ❌ 用 manager_id：52 个部门 51 个是 NULL（只有 admin 挂着） |
| D8 | 闭环判定 | **两套并存**：可计算的自动核销 / 不可见的人工回执 | ❌ 只做人工回执：预算、指标这类明明能算；❌ 只做自动：项目类"方案好不好"算不出来 |
| D9 | 定时驱动 | **内部 asyncio 循环（默认 10 分钟）+ 外部 `tick` 接口** | ❌ 只靠外部 cron：内网部署不一定有；❌ 引入 APScheduler：多 worker 会重复跑 |
| D10 | 预警频率 | **按子判据分层：日 / 周 / 月 / 年** | ❌ 全部塞进每天 8 点：指标快照最新期是 202609，会连续几周推同一句 |
| D11 | AI 用在哪 | **9 个挂点，全部"只写话、不写数"**（数字来自 SQL，沿用 `_num_pool` 出处守卫） | ❌ 让模型现算标题：`report.py:219` 已有教训（每次数不一样） |
| D12 | 预警入口 | **点预警 = 进对话**（带 alert_id 的会话，先出卡片再出建议） | ❌ 只做列表/抽屉：用户还得自己组织问题；❌ 只做详情页：AI 没法接管 |
| D13 | AI 建议 | **建议必须带依据**（对象/数字/时效），并问"要不要我帮你发起"（拟办 → 人确认 → 才下发） | ❌ AI 直接下发：没人担责；❌ 只给结论不给依据：等于算命 |
| D14 | 升级对象 | **按职责线对应的人**；市领导只收汇总与大方向 | ❌ 统一升到市领导：职责混乱（Fred 明确否掉） |
| D15 | 状态流转 | 6 状态不变，补 OA 的**动作**：签收/转办/退回/催办/督办/撤办/归档/紧急 | ❌ 引入加签/会签/补签：收益不抵复杂度（§4.13） |
| D16 | 报告 | **代写 + 润色**（复用现有 docgen / 公文审校），不要求用户自己想 | ❌ 只给模板：用户还是不会写 |
| D17 | 提醒 | **提醒矩阵 + tick 去重**：下发/临期/超期/升级/待确认/到期/闭环/督办 | ❌ 全部实时推：等于没有提醒 |

## 三 四类预警

### 3.1 四类定义与边界

| 类 | code | 回答的问题 | 归谁办 | 数据底座 |
|---|---|---|---|---|
| **预算预警** | `budget` | 这笔钱**花得完吗**、会不会超 | 所长 → 县财务 → 市财务 → 市领导 | `t_power_company_budget_result` + `t_power_work_order` |
| **项目全过程管理预警** | `project` | 这张单**卡在哪一步、卡了多久** | 卡住的那个节点角色（所/县运检/营销/县财务/市财务） | `t_work_order_audit_task` + `t_power_work_order` + `t_power_work_order_status` |
| **穿透式复盘预警** | `review` | 钱花出去了，**有没有效果**、复盘了没有 | 县财务/市财务 → 市领导 | `t_governance_effectiveness` + 指标快照 + 复盘任务记录 |
| **指标预警** | `metric` | 这个数**变差了吗、越线了吗** | 对应层级业务角色 | `t_power_ai_metric_snapshot` + `t_power_ai_metric_comparison` |

**边界（防止两类打架，这是本次最容易做错的地方）**：

| 情形 | 归哪类 | 判据 |
|---|---|---|
| 预算执行率 5.87%、年底预计结余 1751 万 | 预算 | 钱 vs 时间 |
| 某所线损率 4.2%，超 3% 优秀线 | 指标 | 单指标 vs 阈值 |
| 某县投入 970 万、产出 38 万，投入产出比 0.04 | 复盘 | 钱 vs 效 |
| 某县投了钱，六项指标里 3 项反而恶化 | 复盘 | 投入方向 vs 结果 |
| 某项目完工 120 天，没做过复盘 | 复盘 | 流程欠账 |
| 某项目卡在营销部审核 175 天 | 项目 | 单子 vs 流程 |
| 某所 44 个项目未审批 | 项目 | 单子数量（不是预算） |

**关键取舍**：复盘看**钱-效关系**（跨表），指标看**单指标自身**（同表时序）。两者数据源不同、频率不同，不会重复推同一句话。

| 市公司财务部审核 | `sgscwb` | 市 |
| 市公司领导审批 | `master` | 市 |

> **节点是属性不是类型**：`alert_item.data.by_node = [{"node":"营销部审核","total":18,"overdue_90":18,"max_days":179}]`，
> 收到的人看到的是"你这儿压着 18 件，最久 179 天"，而不是 6 个类型各来一条。

### 3.4 频率分层

| 频率 | 谁 | 何时 | 内容 |
|---|---|---|---|
| **日** | 预算 2 + 项目 3（`acceptance_overdue` / `amount_structure` 默认关） | 每天 8:00（沿用上游定时任务调 `/api/alerts/daily`，内部再跑 scan） | 变化快、当天能动手的 |
| **周** | 项目 `amount_structure`（默认关） | 每周一 | 数据质量，不催人 |
| **月** | 指标 2~3 | 每月 5 日（等上月快照） | 指标恶化/越线 |
| **年/季** | 复盘 3 | 1 月（上年复盘）、7 月（中期） | 钱-效关系（✅ Fred 2026-10-19 确认按年/季） |

**同一条预警不重复吵人**：`alert_item` 一天只在列表里出现一次；数据没变化时 `days_open` 递增、`is_new_today=false`，
**不发第二条通知**（除非级别升档、或超过时限进入催办）。这是替换"每天重复推同一句"的关键。

### 3.5 一条预警一行（`dedupe_key` 口径）

```
dedupe_key = {alert_type}|{subtype}|{role_code}|{scope_key}|{object_key}
例：project|approval_stay|sz|42|node:供电所内部审核     （42 = 两水所的 t_power_company.id）
    budget|underspend|sgscwb|city|*
    metric|deteriorated|cto|3|tripCount              （3 = 曾都区 t_department.id）
```
- `scope_key`：所 = `t_power_company.id`；县 = `t_department.id`；市 = `city`
- `object_key`：工单 id / 节点名 / metric_code / `*`（单位级）
- 角色进 key：因为**同一事实在不同层级要说不同的话**（县财务要"7 个所 6 个零执行"，所长要"你所多少"），这是原设计 §3.1 的核心原则，不能因为合并而丢

### 3.6 文案与数字纪律（沿用原设计，不放松）

| 规矩 | 具体要求 |
|---|---|
| 一条一件事 | 预算花不完、审批积压是两件事 → 两条；合并只合并"同一件事的不同切法" |
| `title` ≤ 40 汉字 | 对象 + 事实 + 最多 2 个数；明细进 `data` |
| 数字一律来自 SQL | 模板填空，**不调模型写数字**；AI 只写"为什么/怎么办"，每个数字必须能指回 `data` 里的键 |
| 用业务说法 | "未审批 / 待审批 / 已通过"，不用"卡在审批""单子""卡住" |
| 说后果 | "预计年底结余 37.87 万"，不是"异常" |
| 花得完就不发 | 均川/府河/柳林这类按 pace 能达标的，一条都不发（实测生效） |

### 3.7 做不了 / 默认关闭（缺字段，不是设计取舍）

| 想做 | 实测缺什么 | 处置 |
|---|---|---|
| 超期未完工（按计划完工日） | `plan_end_time` 2026 年 **658/658 全空** | 不做；改用"停留"（`exec_stalled`） |
| 完工未上报（按进入状态时间） | 状态历史表 `work_status=7` 在 2026 年 3 单里 **0 行**；`update_time` 是同一天批量写的 | **默认关闭**；业务方补状态流转（或 `actual_end_time` 可用）后再开 |
| 钱花了没动 | `reality_total` 有值仅 **52 单 / 5311** | 不做（覆盖度不足）；等业务方补录 |
| 重复驳回 ≥2 次 | `approval_round` 2026 年只有 0 和 1 | 不做 |
| 待我审批（按人） | `assignee_id`、`assignee_name` 待处理 **130/130 全空** | 不做按人；按"节点角色+层级"路由 |
| 2026 投入产出 | `total_economic_benefit` 2026 全空 | 复盘类只算 2025，卡片标注"数据年度" |

## 四 任务流转（问题全过程追踪）

### 4.1 参与角色

| 角色 | 在系统里是谁 | 能做什么 |
|---|---|---|
| **发起人**（决策人） | 任何登录人（领导/县财务/所长） | 看预警 → 对话了解 → 下发 → 确认方案/核销 → 催办/撤回 |
| **主责**（承办人，可多人） | 系统推荐 + 发起人确认 | 接单/拒接 → 提方案 → 执行 → 回执 → 继续下发 |
| **协办**（可多人） | 发起人指定 | 收通知、提意见，不阻塞闭环 |
| **抄送** | 发起人指定 | 只读 + 收通知 |
| **上级**（升级接收人） | 按职责线算出 | 收到升级通知，可接管/改派 |
| **系统** | tick 任务 | 扫描、催办、升级、自动核销 |

### 4.2 主流程 —— 把领导那个例子走一遍

```
10-19 08:00  扫描命中：两水供电所 预算执行进度偏慢，预计年底剩余 37.87 万      → alert_item #1001
10-19 09:10  市领导打开预警，问"这钱为什么花不出去？"                        → 任务无关的对话，回答带明细
10-19 09:25  点「下发」→ 系统推荐：主责 sz@两水（1 人），抄送 cto@随县
              AI 生成任务要求草稿（可改）：
                目标：11-19 前把 2026 年预算执行率提到 80% 以上
                回执：3 天内（10-22 18:00 前）提交实施方案
                核销：自动（执行率 ≥80% 即闭环），不足则到期上报
10-19 09:30  确认下发 → dispatch_task #2001（open）→ 通知 sz、抄送 cto
10-19 15:40  所长接单（accepted→doing）
10-21 11:00  提交实施方案（plan owner_plan）→ 状态 doing（待方案确认）
10-21 14:00  领导确认方案 → 方案生效
10-22 08:00  tick：执行率 0% 未达 80%，但回执已交 → 不算逾期
...
11-19 08:00  tick：到期判定，执行率 62% < 80% → 任务 overdue → 升级 ×1
             通知：发起人 + 县财务（阶梯）→ 县财务可改派/追加要求
11-25 08:00  tick：执行率 80.4% → 自动核销 closed（auto_verified）→ 通知双方
11-25 08:05  自动生成处置小结（发现→闭环 37 天、3 次事件、1 次升级）→ 可导出
```

### 4.3 状态机（6 个状态 + 2 个标志）

```
 [draft] ──confirm──> [open] ──accept──> [doing] ──submit──> [verify] ──pass──> [closed]
    │                   │ ↺decline          │  ▲                │
    │                   │ 留 open + 升级     └──┼────────────────┘  fail 退回 doing
    │                   │                     （verify 不通过 / 发起人驳回）
    └──cancel──> [cancelled]  ←── cancel ──（open / doing / verify 均可，需发起人）

另有两个标志位（不是状态，避免状态爆炸）：
  escalate_level  0→1→2   超时未回执/到期未达标，每次 +1，写事件
  overdue_flag    0/1     是否已过 reply_due_at 或 due_at
```

| 状态 | 含义 | 谁能推进 |
|---|---|---|
| `draft` | 已填要求、还没下发（可在确认页改处理人/时限/核销方式） | 发起人 |
| `open` | 已下发，等接单 | 主责 |
| `doing` | 已接单，处理中（可提交方案/回执/子任务） | 主责 |
| `verify` | 已交回执/方案，等核销 | 发起人 / 系统（自动核销） |
| `closed` | 已闭环（`close_reason` = auto_verified / human_confirmed / cancelled） | — |
| `cancelled` | 撤回 | 发起人 |

**非法迁移一律拒绝并写 `dispatch_task_event`（action=reject_invalid），不静默改状态。**

### 4.4 处理人推荐与"确认下发"

**推荐算法（只读，不写库）**：

```
1) 起点 = alert_item.assignee_role + scope_key（或对话里提到的单位）
2) 层级定位：
     所级 → 该所的 `t_power_company.department_id`（**注意：这是部门 id，不是所 id**；两水：所 42 / 部门 56）
     县级 → 该所 `t_power_company.parent_id` 对应的县公司部门（广水 3 个县级账号挂关庙所的例外，沿用 `alert_scope` 的上溯规则）
     市级 → department_id = 1
3) 候选人 = 该部门下、该角色的有效账号（t_employee.deleted_flag=0 / disabled_flag=0）
4) 多人时排序：同名优先（如 sngdssz 这种实名账号）→ 最近登录（app_user 有记录）→ employee_id 小
5) 输出：[{login_name, name, dept, role, reason:"按 XX 节点应办角色推荐"}] + 备选（上级同角色、发起人）
6) 找不到人 → 不静默失败：返回空 + reason="该单位无 XX 角色账号"，推荐上级，UI 红色提示
```

**确认页必须让发起人看到并改这 6 项**（否则就是"系统替他拍板"）：

| 项 | 默认值 | 可改 |
|---|---|---|
| 主责（可多人） | 推荐第 1 人 | ✅ 增删 |
| 协办 / 抄送 | 空 | ✅ |
| 任务要求（AI 草稿） | 由预警 + 对话生成 | ✅ 必看 |
| 回执时限 `reply_due_at` | 按级别：高 24h / 中 3d / 低 7d | ✅ |
| 目标时限 `due_at` | 预算→年底/月末；项目→30 天 | ✅ |
| 核销方式 | 预警自带 `verify_hint` 预填（自动/人工） | ✅ |

**多人（联合办理）规则**（这是你说的"不一定是一个人"）：

| 情形 | 规则 |
|---|---|
| 多个主责 | **任一人回执即可进入核销**；其余主责收到"已由 X 回执"通知，核销前可补充 |
| 主责 + 协办 | 协办不阻塞；协办意见进时间线 |
| 主责全部拒接 | 任务回到 `open`，升级 ×1，通知发起人改派 |
| 主责离职/停用 | tick 检测到 `disabled_flag=1` → 自动转派给同部门同角色其他人；无人则升级 |

### 4.5 时限与升级

**两个时限，别混**：

| 时限 | 字段 | 管什么 | 到期后果 |
|---|---|---|---|
| 回执时限 | `reply_due_at` | "3 天内给方案/回执" | 未回执 → `urge` 通知 → 过了宽限期 → 升级 |
| 目标时限 | `due_at` | "1 个月内把钱花完" | 到期限未达标 → 自动核销判定；不通过 → `overdue` + 升级 |

**升级只在同一职责线内走，不跨线**（Fred 2026-10-19：对应预警给对应的人，市领导管大方向，职责划分清楚）：

| 类 | 一线（所 → 县） | 二线（县 → 市） | 再往上 |
|---|---|---|---|
| 预算 | `sz` → `xgscwb`（县财务） | `xgscwb` → `sgscwb`（市财务） | `sgscwb` → 发起人/管理员；**市领导只看周报汇总** |
| 项目·审批停留 | 按节点：所内→`sz`；县运检→`cto`；营销→`yxb`；县财务→`xgscwb`；市财务→`sgscwb` | 市财务节点已在市级 | 发起人/管理员 |
| 项目·已批未开工/停滞 | `sz` → `cto`（县运检） | 市公司**没有运检/营销角色** → 转发起人 + 管理员，标注"本级无对口角色，需人工指定" | 同上 |
| 项目·申报质量 | `sz` → `xgscwb` | `xgscwb` → `sgscwb` | 发起人/管理员 |
| 指标 | 按指标定责：线损/跳闸/停电时长/故障报修 → `cto`；售电量/意见工单 → `yxb`；所级先到 `sz` | 市级无对应业务角色 → 发起人 + 管理员 | 同上 |
| 复盘 | `xgscwb` → `sgscwb` | `sgscwb` → 发起人 | **市领导收年度复盘结论（大方向）** |

**四条规则**：

1. 升级只在同一职责线里找"上一级有账号的角色"；**找不到就不硬塞**——退回发起人 + 管理员，任务标"待指定"。
2. **市领导（`master`）不收执行层升级**（项目、审批、所级指标）；只收两类：① 预算全市通稿；② 年度复盘结论与跨县重大异常汇总。
3. 不用 `t_department.manager_id`：实测 52 个部门 51 个 NULL（只有 id=1 挂着 admin）。
4. 配置化：`dispatch_rules.DUTY_CHAIN`，按 `category`（项目再加 `node` / 指标再加 `metric_code`）查链条；**改职责只改这张表**。

**升级动作**（每次升级都写事件 + 通知，且可重复执行不重复通知）：
```
urge       : 回执到期前 4 小时提醒一次；到期未交 → 再提醒（每 24h 最多 1 次）
escalate+1 : 回执到期超过宽限（高 1d / 中 1d / 低 2d）→ 通知"发起人 + 阶梯上级"，escalate_level+1
escalate+2 : 再过一个宽限期仍无动静 → 通知再上一级 + admin，escalate_level+1
overdue    : 过了 due_at 且核销未通过 → overdue_flag=1 + 升级 ×1（与回执超时合并计算，不叠加刷屏）
```

### 4.6 两种回执方式（对应你说的"可见 / 不可见"）

| 模式 | 什么时候用 | 判定 | 闭环人 | 通知 |
|---|---|---|---|---|
| **自动核销（可见）** | 能算的：预算执行率、指标值、工单状态、审批待办数 | tick 每次跑规则 SQL，`measured` 写 `dispatch_check` | 系统 | 闭环后通知发起人 + 承办人；发起人可在 7 天内"重开" |
| **人工回执（不可见）** | 算不出的：方案质量、协调结果、现场情况 | 承办人提交 `content + 附件` → 发起人确认 | 发起人 | 提交/确认/驳回各一条 |

**核销规则（`verify_rule` JSON，可组合）**：

```json
{"kind":"budget_rate","station_ids":[42],"year":2026,"op":">=","target":0.8,"close_when_met":true}
{"kind":"work_status","work_order_ids":[9990001],"expect_not_in":["0","1","2","3","9"],"close_when_met":true}
{"kind":"audit_node","station_ids":[42],"node":"营销部审核","op":"<=","target":0,"close_when_met":true}
{"kind":"metric_value","scope_type":"station","scope_key":"42","metric_code":"lossRate","op":"<=","target":3.0}
{"kind":"task_tree","require_child_closed":true}
{"kind":"manual","evidence":"复盘报告"}
```

- `close_when_met=false` → 过程中只记录进度、显示"已达标"，到了 `due_at` 才闭环（用于"到期限才算完成"的场景）
- 规则跑不出数（SQL 无值/指标缺失）→ `passed=null` + `message="数据不可得"`，**不算通过、也不算失败**，转人工确认（不许静默闭环）

### 4.7 继续下发与问题链

- 承办人可「继续下发」→ 子任务（`parent_task_id` / `root_task_id`），要求由上一手写
- 一条问题 = 一棵树：`root_task_id` 相同；列表页默认按根任务聚合，展开看链条
- 父任务核销规则可设 `task_tree`（子任务全闭环才允许闭环）
- 链条上每一跳都有事件：谁在什么时候把什么事压给了谁（这就是"问题全过程追踪"的原始数据）

|---|---|---|
| `assign` | 下发/转派 | 主责、协办、抄送 |
| `urge` | 回执临期/超期 | 主责 |

### 4.9 AI 九个挂点

| # | 挂点 | 输入 | 输出 | 落库 | 失败兜底 |
|---|---|---|---|---|---|
| A1 | 预警根因分析 | 预警 `data` + 范围内明细（只读 SQL） | 3 条原因 + 每条的证据（SQL/数值） + 建议 | `alert_item.data.ai` | 回模板句 + `ai_unavailable` |
| A2 | 任务要求草稿 | 预警 + 发起人最近 3 轮对话 | 目标/回执要求/时限/核销建议/处理人建议 | 不落库（确认页展示） | 回模板 |
| A3 | 处置建议 | 任务要求 + 同类历史任务（已闭环的处置方式） | 3 条方案（动作/责任/时限/预期指标变化） | `dispatch_task_plan(ai_advice)` | 回 1 条通用建议 |
| A4 | 实施方案 | 任务要求 + 本单位数据 | 步骤/时间表/风险/需协调事项（执行人改后提交） | `dispatch_task_plan(owner_plan)` | 空草稿，可手写 |
| A5 | 上报报告 | 任务全过程事件 + 实测数字 | docx（事实/原因/措施/成效/下一步） | `dispatch_attachment` | 纯模板 docx |
| A6 | 核销说明 | `dispatch_check` 前后实测值 | "为什么算完成/为什么没完成" + 数字出处 | 事件 payload | 只给数字 |
| A7 | 预警对话 | 预警 `data` + 范围明细 | 卡片 + 首段话（为什么命中/影响/3 条建议） | 会话消息 + `alert_item.data.ai` | 只出卡片 + 模板句 |
| A8 | 拟办草案 | 用户选中的那条建议 | draft（要求/承办人/时限/核销规则/依据） | **不落库**，确认后才建 task | 回手填确认页 |
| A9 | 报告润色 | 用户上传/粘贴的稿子 | 修订版 + 问题清单 | 附件 / 事件 | 回原文 + 提示人工 |

```
   ├─ 前端：带 alert_id 打开 AgentChat（复用现有对话页，不新做详情页）

   │    ① 该用户 + 该预警没有会话 → 建会话（复用 `t_chat_session`，标题加【预警】前缀；不新增列）
   │    ② 写入一张卡片消息（role=assistant, type=card）：对象/级别/详情表/数字来源/首次与最近命中/已下发任务
   │    ③ 同一响应直接给 AI 的首段话：为什么命中、影响多大、3 条建议、要不要我帮你发起
   └─ 前端：渲染卡片 + 建议 chips（「帮我发起」「继续问」「看看别人怎么做」）
```

| 约束 | 说明 |
|---|---|
| 卡片数字只来自 `alert_item.data` | 模型只写解释与建议，不写数 |
| 同一预警重复点开 | 复用同一会话（按 `alert_id + employee_id` 找），不刷屏 |
| 列表页保留 | 列表用于批量浏览/筛选；**点击才进对话** |
| 会话可继续追问 | 复用 `/api/ask` 的历史与摘要能力，与预警上下文共存 |

### 4.11 AI 拟办：先给建议，再问"要不要我帮你发起"

> Fred：指标预警 → 哪个差 → 建议让下面出报告 → N 天内提升 → 问要不要发起；预算花不完 → 看别人怎么花完/能不能挪预算 → 给建议 → 发起。

**每条建议必须是三件套**：`动作` + `依据（对象/数字）` + `预期（指标/时限）`。**没有依据的建议不输出**（禁止"建议加强管理"这类空话）。

| 预警 | 建议长什么样（示例） | 依据从哪来（只读 SQL） |
|---|---|---|
| 指标·某所线损率 4.6%（>3%） | "让厉山所在 7 天内交降损报告；同县平均 2.96%，厉山高出 1.64 个百分点；先查 3 个高损台区" | snapshot 同级对比 + 台区线损 top N |
| 预算·某所年底预计结余 37.87 万 | "两条路：① 参照执行率 89.9% 的均川所，本月补 3 个储备项目；② 确无储备就向县财务申请把 20 万调给府河（73.0%）。两条我都能帮你拟成任务" | 各所执行率 + 立项节奏 + 同类项目单价中位数 |
| 项目·某单卡营销部 179 天 | "先让县营销部 3 天内出停留原因说明；材料缺失就退回补正——要不要我发起督办" | audit_task 停留 + 工单状态 + 节点角色 |

**"要不要我帮你发起"（OA 拟办的味道）**：

```
AI 3 条建议
  └─ 每条一个按钮「按这条发起」
       → POST /api/alerts/{id}/propose?option=1
       → 返回 draft（**不落库**）：标题/要求/承办人/回执时限/目标时限/核销规则/建议依据
       → 前端弹"下发确认页"（§4.4 那 6 项都能改）
       → 人点确认 = 真正下发（POST /api/alerts/{id}/dispatch）
```

**纪律：AI 不直接下发、不直接改数据；只有人点确认才算数。**

### 4.12 执行侧：怎么干、报告代写、润色

承办人打开任务，AI **先给"怎么干"**，不等他问：

- **实施建议（A4）**：步骤/时间表/风险/要协调谁，带本单位数据（同类项目周期、同所历史处置）
- **报告代写（A5）**：任务要求含"报材料"时生成 docx（事实/原因/措施/进展/下一步/需协调），**每个数字回指 alert/task 实测值**
- **润色（A9）**：复用现有 `pipeline_proofread`（错别字/标点/数字用法/层次序号 + 病句），返回修订版 + 问题清单
- **主动问一句**：任务详情页固定显示"要我帮你写报告 / 润色一下吗？"，不让用户自己想

### 4.13 对照成熟 OA 的状态流转（我们的取舍）

参考公开的政企 OA 能力清单（在线拟稿、多级审批、并行会签、移动签批、超期预警、电子归档；撤办、退回、加签、转办、紧急优先、缓办、补签、全流程跟踪）：

| OA 能力 | 做不做 | 落法 |
|---|---|---|
| 拟稿 | ✅ | `draft` + AI 拟办（§4.11） |
| 签收 | ✅ | `accept`（`open → doing`） |
| 转办 | ✅ | `transfer`（原主责降为协办，记事件） |
| 退回 | ✅ | `verify` 不通过 → `doing`（`plan_reject` / `verify_fail`） |
| 催办 | ✅ | `urge`（notice + 事件，支持手动催办） |
| 督办 | ✅ | `supervise`（上级/发起人发起，`notice_type=supervise`，**不改状态**） |
| 撤办 | ✅ | `cancel`（发起人，留痕） |
| 紧急优先 | ✅ | `level=high` 覆盖默认时限 |
| 归档 | ✅ | `archive`（closed 后可归档，`archived_flag=1`，列表默认不显示） |
| 加签 / 并行会签 / 补签 | ❌ | 本期不做：多人已用"多主责"表达；会签会引入审批树，收益不抵复杂度 |
| 缓办 | ❌ | 用"改期"（改 `due_at` + 事件留痕）代替，状态不再长一个 |
| 多级审批 | ❌ | 不是本系统职责（审批在业务系统，我们只督办） |

状态对照：OA 的"待办 / 办理中 / 待反馈 / 办结" = 我们的 `open / doing / verify / closed`，**6 状态不动**，只补动作与标志。

### 4.14 提醒矩阵（全程自动监控时间）

| 时点 | 提醒谁 | 内容 | 频次上限 |
|---|---|---|---|
| 下发 | 主责 / 协办 / 抄送 | 任务卡（要求 + 时限 + 一键接单） | 1 次 |
| 回执前 4h | 主责 | "还有 4 小时到回执时限" | 1 次 |
| 回执超期 | 主责 | "已超期 X 小时" | 每 24h 1 次 |
| 超期宽限后 | 发起人 + 职责线上一级 | "X 未回执，已升级" | 每级 1 次 |
| 方案/回执待确认 | 发起人 | "X 提交了方案/回执" | 每次提交 1 条 |
| 目标到期未达标 | 发起人 + 上级 | "到期未达标（实测 X vs 目标 Y）" | 1 次 + 升级 |
| 自动核销 | 全部参与人 | "已自动闭环（实测 X）" | 1 次 |
| 督办 | 被督办人 | 督办通知 | 手动触发 |

**"全程自动监控"就是 tick**：每 10 分钟跑一遍 —— ① 催办 ② 升级 ③ 自动核销判定 ④ 停用账号转派 ⑤ 提醒去重。

### 5.3 与业务库的关联键 —— 9 个已探到的坑（不处理就是"表建好了但不能用"）

| # | 坑 | 实测 | 处理 |
|---|---|---|---|
| K1 | 指标表 `scope_key` 一个县有 2~3 种写法 | 出现 6 种：`广水供电公司`/`广水市供电公司`、`高新区供电中心`/`高新区供电公司`、`曾都区供电公司`、`随县供电公司` | 建**归一函数**（6→4），并写测试断言；不以字面量 join |
| K2 | 工单表没有 `station_id` | 只有 `power_company_name`，且**存的是所名** | 告警生成阶段就用 `t_power_company` 映射成 `station_id`；任务侧只认 `scope_key=station_id` |
| K3 | 审批办理人全空 | `assignee_id` 130/130 NULL，`assignee_name` 也 130/130 空 | 不按人路由；按"节点角色 + 层级"（§4.4） |
| K4 | 部门负责人全空 | `t_department.manager_id` 51/52 NULL | 升级用职责线（§4.5），不读 manager_id |
| K5 | 状态历史有重复行 | 同一工单同状态同 sort 最多 **7 条** | 取 `MAX(create_time)` 且 `GROUP BY work_order_id,work_status`，不要直接 join 累加 |
| K6 | `deleted_flag` 类型不统一 | 工单表是 `varchar(2)`，要写 `'0'`；其他表是 `tinyint` | 生成的 SQL 按表区分；测试里对每张表断言过滤条件 |
| K7 | **部门 id ≠ 所 id** | 两水：`t_power_company.id=42`、`department_id=56`；账号挂部门 56 | `scope_key` 一律用 **`t_power_company.id`**；找部门树才用 `department_id`。测试断言 `t_power_company.id` 与 `department_id` 不同的所至少 1 个且映射正确 |
| K8 | **治理成效表含"全市行"** | `t_governance_effectiveness` 2025 年 5 行：4 个县 + 1 行 `county_company_id IS NULL`（全市 2536.73 万）；`SUM` 全表 = 5073.45 万（翻倍） | 按行取：县口径 `county_company_id IS NOT NULL`，市口径 `IS NULL`；测试断言全市投入 = 4 县之和 |
| K9 | **状态历史表覆盖不全** | `t_power_work_order_status` 有 0/1/2/4/8/9/10 的流转，但 2026 年状态 3 的 16 单、状态 7 的 3 单**一条都没有** | 不能把它当通用"进入状态时间"；状态 3 改用审批任务 `operate_time`（实测 16/16 都有），状态 7 判据默认关闭 |

### 5.4 一致性 / 幂等 / 事务

| 事项 | 做法 |
|---|---|
| 下发 | `task + assignees + notice + event` **同一事务**；`task_no` 唯一；接口带 `Idempotency-Key`，重放返回同一任务 |
| 扫描 | `run_key` 唯一；同一 `dedupe_key` 只 upsert；`found/new/resolved` 记进 `alert_scan_run` |
| tick | 可重复执行：每个动作先查"本轮是否已做过"（事件表 + notice `dedupe_key`），重复执行不产生重复通知 |
| 通知 | `dedupe_key = task:{id}|{type}|{receiver}|{round}`；部分唯一索引兜底 |
| 并发 | 状态迁移用 `UPDATE ... WHERE id=? AND status=?`（乐观），影响行数 0 → 409 |
| 时间 | PG `timestamptz`（UTC 存储）；业务日期 `today` 由调用方传，便于回放测试 |
| 保留 | `alert_item` 保留 400 天（closed 的 180 天）；任务与事件**不自动删**（审计需要）；清理脚本单独跑 |

### 5.5 怎么保证"建了就能用"（这是你问的第 3 点）

| 层 | 做法 | 验证 |
|---|---|---|
| 模型 | `server/app/models/dispatch.py`（9 个 ORM 类），在 `models/__init__.py` 导出 → `Base.metadata.create_all` 自动建表 | 空库启动后 9 张表存在 |
| 存量库 | `db_init.EXTRA_DDL` 登记幂等 DDL（`ADD COLUMN IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`） | 老库跑一次 `python -m app.db_init` 全绿 |
| 独立部署 | `db/dispatch_tables.sql`（上面 DDL 的整份，幂等） | 空 PG 库 `psql -f` 后表/索引/唯一键齐全 |
| 回归 | `server/tests/test_dispatch_schema.py`（表/列/索引/唯一键/默认值）、`test_dispatch_flow.py`（状态机/多人/超时/自动核销）、`test_dispatch_scope.py`（越权/失败关闸） | 全部 PASS，输出落 `output/test_results/` |
| 真数据回放 | 用 5 个账号 + 今天数据跑 scan，断言命中数与 `probe_alerts_today.json` 对得上（允许"合并导致的条数减少"，逐条给理由） | 差异清单为空或每条有理由 |
| 只读 | dispatch 模块只允许 `from app.secretary import tools_db` 调 `_exec`；`grep -r "INSERT INTO dlj_data"` 为空 | 测试里跑 grep |
| 观测 | `/health` 加 `dispatch` 段（表存在 / open 任务 / 逾期数 / 今日扫描）；`GET /api/dispatch/stats` | 健康检查一眼看到 |
| 回滚 | 全是新表 + 新路由；`DISPATCH_ON=0` 关路由；`DROP TABLE` 即回滚（不碰任何业务表） | 演练一次 |

## 十 风险与兜底

| 风险 | 影响 | 兜底 |
|---|---|---|
| 业务库身份表变动（账号/角色/部门） | 推荐不到人、范围解析失败 | 一律回 `unknown`/空推荐 + 原因，**绝不默认全市**；tick 检测停用账号自动转派 |
| `assignee_id` 一直不补 | 做不了"按人待办" | 本设计不依赖它；业务方补齐后可加 `project.approval_stay_by_person` |
| 指标/复盘数据只有年度 | 复盘预警"看起来没用" | 按年/季调度，卡片明确标"数据年度 2025"，不进日推 |
| 自动核销误判 | 任务假闭环 | 规则必须带 `close_when_met` + 数据不可得判 NULL；闭环 7 天内可重开；每次核销写 measured |
| 通知刷屏 | 用户不看 | 同任务同类型同轮 dedupe；同一条预警数据不变不重复通知 |
| AI 建议不着调、编对象 | 用户照着做错事 | 建议必须带 evidence；无依据不输出；**一键发起只是草稿**，最终由人确认；每轮建议留档可回查 |
| 状态流转越补越复杂 | 没人维护 | 只加"动作 + 事件"，不加状态（§4.13）；加签/会签明确不做 |
| PG 挂了 | 任务全停 | 预警查询（`/api/alerts/daily` 老路径）不依赖 PG，仍可用；`/health` 明确标 dispatch 不可用 |
| 多进程部署 | tick 重复跑 | tick 幂等 + `notice.dedupe_key` 唯一；部署文档写明"单进程或只让一个进程跑 tick" |
