## R1 删第③步「要不要预处理」（intent）

- **现象**：分流已经判到问数线，进入后还要跑一次模型判断"要不要预处理"。
- **是什么问题**：入口只分了「干活 vs 其他」（`router.route` 默认 `ask_db`，只有要文件/带文件/指文件才去 `office`），
  「闲聊、写材料」没有自己的线，于是问数线里又判一次。**同一件事判两遍**，一处判错就串。
- **改哪一层**：代码（`router.py` 加一条 chat 分支）+ 配置（删 `cfg.prompt_text.intent`）+ 代码（删 `preprocess.route` 的三布尔）。
  预处理（纠错 → 补问 → 补全表 → 问题确定）在问数线里无条件跑。
- **判据**：`cfg.prompt_text` 里没有 `intent`；`agent.ask` 的 trace 里预处理步骤固定出现；闲聊问句不再进查数循环。
- **影响面**：`preprocess.route`、`agent.ask` 的 `allow_refine`、工具子集（改为写死）、`agent_v2.system(with_rules=)`。
- **卡点**：闲聊去哪，见 Q1。

## R2 补全表要可编辑（不是只读）

- **现象**：影响面页把「补全表」标成只读。
- **是什么问题**：**我标错了**。后端 `GET/PUT /prompts/complete` 一直在，前端编辑器在 `/ask-data`（`SearchTest.tsx:202-249`，整表覆盖保存）。
  它在 PG 里（`cfg.complete_rule`），本来就是业务规则。
- **改哪一层**：页面（影响面页这一项给编辑入口，指向同一份数据）。
- **判据**：影响面页这一行点开能改、保存后下一轮生效；改的还是 `cfg.complete_rule` 同一张表。
- **影响面**：无（不动数据、不动链路）。

## R3 第⑦步装配 system（最大一块，拆成 8 条）

### R3.1 身份只写「你是谁」
- **现象**：`prompts_data.IDENTITY` 里现在是「三条分寸」（汇报口吻不寒暄 / 数字必须有出处 / 懂本地叫法）+ 非业务问题正常答。
- **是什么问题**：那是**纪律**，不是身份。身份该回答"我是谁、服务谁"；纪律属于业务层，应该只有一处——作答规则。
- **改哪一层**：配置（身份正文改成 2–3 句，无纪律无分寸）+ 代码（把现有三条分寸并入作答规则，或删）。
- **判据**：身份正文里没有"必须/不许/口吻"这类约束句；问数线的口吻/数字要求只来自作答规则一处。

### R3.2 L2 模式做法：删
- **是什么问题**：死代码。`agent.py` 固定 `_mode='general'`，`agent_v2.judge_mode` 全仓无人调用，`MODE_TEXTS` 的 data/doc/office 三段从不进提示词。
- **改哪一层**：代码（`prompt_stack` L2 层、`MODE_TEXTS`、`judge_mode`、`use_tools`）+ 配置（`prompt_text.modes` 键）。

### R3.3 S7「我的规则」：删
- **作用**：把个人资料库里 `doc_type='rule'` 的文档拼进 system（上限 1500 字），`agent.py:1530` 是唯一调用点。
- **是什么问题**：个人私有规则，当下一场会话也没用到；按"先看当下"删。
- **改哪一层**：代码（删 `personal_kb.personal_rules` 调用与 S7 层）。个人库文档**不动**，功能在文档里记「已下线」。

### R3.4 L4 会话人设：确认是文本框，删
- **事实**：`qa.t_chat_session.persona_name/persona_prompt`，是会话里员工自设的人设文字（现在 0 场在用）。
- **改哪一层**：代码（删注入与设置入口）。
- **注意**：如果前端还有「人设」输入框，一起删。

### R3.5 S0 红线 / S1 谁说了算：删
- **是什么问题**：两个框默认空；非空时又与作答规则重复，属于"同一个约束两处写"。
- **改哪一层**：代码（`prompt_stack` S0/S1）+ 配置（`prompt_text.redlines/priority` 两个键）。

### R3.6 「工具说明」段：删
- **是什么问题**：现在的工具说明在讲"先 list_metrics 再 run_sql、结果带 ref 就 read_result、能用结构化参数就别 run_code"——
  这些全是**工具怎么用**，属于工具 description 的职责，重复且会过期。
- **改哪一层**：代码（不注入 `prompt_text.tools`）+ 内容（该说的写进工具 schema）。

### R3.7 工具 schema 重写（按官方规范）
- **现象**：description 里塞了例子（`run_sql` 讲数组并发、`query_data` 讲三种用法、`make_deliverable` 讲 spec 形状）。
- **是什么问题**：示例、模式、调用套路混进 description，模型读到的是"散文"，参数定义反而空。
- **改哪一层**：代码（重写 schema）。
- **规范**（实现前按官方原文核对：[OpenAI Define tools](https://developers.openai.com/plugins/plan/tools)、[Anthropic Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)）：
  - 名字：`snake_case`，动词开头，一个动作一只工具。
  - description：≤3 句——做什么 / 什么时候用（以及什么时候别用）/ 返回什么。不写示例、不写调用流程。
  - 参数：每个都有 `description`；`required` 只放真正必填；可选值用 `enum`；多种形态用 `anyOf` 且每种各自有 description。
  - 默认值写在参数 description 里；示例若要给，放 few-shot 消息里，不塞 description。
- **判据**：`/prompts/tools` 返回的每一只工具，description 无示例句、每参数有 description、每字段类型与 enum 齐全。

### R3.8 工具集写死：只给查数用的
- **是什么问题**：现在按三个布尔切 15 只工具，还包含 `kb_search / kb_read / read_file / make_file / run_code / read_howto / get_rule / list_metrics / metric_query / describe_table / find_column / list_tables / read_result`。
  问数线只做一件事：按查数口径写 SQL、拿数据、回答。其余的都不该在。
- **改哪一层**：代码（固定工具表 = 查数那一只，见 Q2）。
- **配套**：口径说明里必须写全表名与字段（不再有 describe_table / 字典可查）。

## 目标形态（对齐用）

```
入口：闲聊 / 问数 / 干活  三分（R1）
问数入线：纠错 → 补问法 → 补全表 → 问题确定

循环   ：run_sql → 结果 → 再查 / 作答；无校验、无重贴、无进度、无对账
出线   ：正文 → 落库
```
