# 预算花不完 · 全链路验收（含按身份分级建议）

> 目标：一条「预算花不完」，从市里压下去、从所里报上来，两头都通；每一跳只有一张单；
> 每一级智能体给出的建议**符合他的身份**、**指向真实数据**、**能落地**。
> 不是测流程通不通，是测"这个智能体在这个位置上有没有用"。

## 口径（2026-10-21 Fred 定，未答的三条按推荐执行，可回退）

1. **严格相邻**：派活只能给直接下一级；上报只能给直接上一级；同级只能抄送。
   例外：本部门同岗位可换人；协办可相邻上下（请人配合不算派活）；抄送不限层级。
2. **一件事一个号**：一条业务预警 = 一件事 = 一个事项号 `C<日期>-<序号>`，整棵树共用。
3. **所级/县级算同一件事**（本次采用推荐 A）：县里点开看到的就是所里那单，只能补充，不能另发。
4. **往下压 = 同单长分支**（推荐 A）：县里给各所开子任务，事项号不变，市里看到的是一棵树。
5. **市里一条要求发给多个县 = 一张单多承办人**（推荐 A）。

## 三个身份各自该给什么（这就是要落成"规则文档"的东西）

| 身份 | 他关心什么 | 结论必须长这样 | 不许出现 |
|---|---|---|---|
| 市领导 master | 哪个县垫底、卡了多少钱、怎么让他们动 | 点名到县 + 百分比/金额 + 督办动作（限期、约谈、纳入考核） | 具体项目名、"新建项目""报审批""调线损"这类执行动作 |
| 县财务 xgscwb | 本县能不能自己了结 | 明确一句"本级能了结/必须往下压"；压下去要点名到所 + 各要完成多少 | 越位指挥所里报哪个项目；要求所里越级报市里 |
| 县运检/营销 cto/yxb | 专业侧能配合什么 | 本专业真实指标 + 具体配合动作 | 给别人派活（同级只能协办/抄送） |
| 所长 sz | 钱该花到哪个方向 | ≥1 个本所真实指标值 + ≥1 个具体项目动作（推已批未开工多少钱 / 新报哪类 / 清几单积压） | "要求下级限期汇报"这种当官话（他没有下级） |

## 六组 + 一组验收判据

| 组 | 测什么 | 怎么判 |
|---|---|---|
| 1 上面压下来 | 市领导 → 两个县财务 → 各所，四级贯通，最后数据达标自动闭环 | 事项号全程一个；每跳只到相邻一级；树在长；闭环原因 = auto_verified |
| 2 下面报上去 | 所 → 县 → 市，中间只能补充 | 上级看到的是下级处理意见；上级发不出第二张单 |
| 3 一件事一张单 | 第二个人进来必须拿到已有单 | 报 `CASE_EXISTS` + 已有单号 + "只能补充/改方案/写说明"；不同所各能开一张 |
| 4 身份建议分级 | 四个身份的建议各跑一遍 | 5 条硬判据（见下） |
| 5 要交方案这一路 | 要求交方案 → 主动提议代写 → 改 → 核数 → 上传 → 回执 → 上级审 | 代写内容基于本所真实数据；驳回必须带理由 |
| 6 不该发生的 | 越级、同级派活、跨组织、非参与人看任务 | 全部拦，且话术点明"该找谁" |
| 7 规则文档本身 | `ROLE_ADVICE` 四个身份齐全、字段不缺 | 缺一个身份/缺一个字段 → 失败 |

### 第4组的 5 条硬判据（口径先说死）

1. **有结论**：第一段就是"建议你怎么办"，不是背景铺陈。
2. **动作 ≥3 条且带依据**：不许出现"加强管理/高度重视/进一步提升"。
3. **数字 100% 可溯源**：建议里每个金额/百分比/天数/单数都能在业务库查到；编一个数字整组不过。
4. **身份不越界**：命中该身份的 `must_not` 词表即失败。
5. **指的东西真实存在**：点名的指标/项目/供电所，库里得有。

第 6 条机器判不了：每个身份贴一条原文给 Fred 抽检。
