# 实施：提示词页面里也能改「纠错词典 / 时间地点规则 / 数据表元数据」

日期：2026-11-02
要求：Fred「纠错词典 时间地点 数据表单这些 表也需要可以修改」→「在这个提示词页面可以修改」→「直接做」。

## 三样东西的位置（已核实，不是猜）

| 要改的 | 现在在哪 | 能不能直接改 |
|---|---|---|
| 纠错词典 `t_nc_typo/term/ambiguous/wordlist` | **本系统 PG**（ad_new）；typ 105 / term 75 / ambiguous 81 / wordlist 197 行 | 能。同一库，表都有 `id / deleted_flag / update_time` |
| `t_nc_catalog`(20183) / `t_nc_pinyin`(20922) | 同上 | **不开放**：离线编译产物，改一个字要重算全表 |
| 时间地点规则 `_MONTH_REL/_YEAR_REL/_YEAR_OFF/_WHOLE_CITY/_STRIP_HEAD/_STRIP_TAIL` | **代码常量**（time_scope.py），没有表 | 要搬成可覆盖项 |
| 数据表清单 / 字段说明 `ai_data.ai_table_metadata` 等 | **业务库 dlj_data**，我们的连接是只读（`run_sql` 只放 SELECT） | 用**覆盖层**：本系统 PG 存改过的值，读取时覆盖优先，不碰业务库 |

## 根因（为什么现在改不了）

这三样都是"规则"，但历史上分别写死在三个地方，改一次都要发版：

1. **纠错词典**虽然已经在 PG 表里（`t_nc_*`），但没有任何写入口 —— 只能手工连库改，
   而且改完还得知道"必须动 `update_time`"，否则 `name_fix` 的版本指纹探测不到、
   改了不生效（`name_fix.py` 里明写了这个坑）。
2. **时间地点规则**是 `time_scope.py` 的模块级常量（`_WHOLE_CITY` / `_STRIP_HEAD` …），
   连数据都不是，加一个"全市"的说法要改代码 + 重新部署。
3. **数据表元数据**在业务库（`dlj_data`），本系统的连接是**只读**的
   （`run_sql` 只放 SELECT，实测 `show tables` 都被拒）—— 想改只能绕开只读约束，
   而给只读系统开业务库写权限是另一件事，风险不对等。

## 做法

### ① 纠错词典（`server/app/secretary/lex_admin.py` + 接口 + 页面）

- 列白名单：每张表只开放业务列（`wrong/right_word/org/...`），其余列一律不接受。
- 增 / 改 / 删（**软删** `deleted_flag=1`）/ 查（分页 + 模糊搜索）。
- 每次写都 `update_time = now()` —— `name_fix._maybe_reload()` 每 60 秒比对
  `MAX(update_time)` 指纹来重建纠错引擎，不改这个字段就等于"改了不生效"。
- 标准词表新增时，拼音码/首字母留空则按 `t_nc_pinyin` 字表自动补（`py_full`=韵母串、
  `initials`=声母串，这是库里既有格式），补不出来就留空、不猜。

### ② 时间地点规则（复用 `prompt_text` 覆盖机制）

新增 6 个 key：`time_month_rel` / `time_year_rel` / `time_year_off` / `time_whole_city` /
`time_strip_head` / `time_strip_tail`，值是 JSON。`time_scope` 里改成
「读表有覆盖就用表、没有就用代码常量」，读不到的字段回落默认值。

**好处**：页面上已有的「代码提示词」抽屉按 key 列表渲染，加了 key 就自动出现，
不需要动前端；保存即生效（`prompt_text` 有 60 秒 TTL，保存时 clear_cache）。

只搬**数据**，不搬**逻辑**：正则、解析、比较这些仍留在代码里。

### ③ 数据表元数据覆盖层（`server/app/secretary/meta_admin.py` + 接口 + 页面）

- 新 PG 表 `data_meta_override(kind, table_name, column_name, field, value, updated_at)`；
  `kind` ∈ `table` / `column`，`field` ∈ `cn_name` / `desc` / `importance`。
- `semantic` 读业务库拿到元数据后，套一层覆盖值（本系统库，毫秒级）。
- 页面「数据表」标签页：列表 + 搜索 + 改中文名/说明；字段按表展开。
- **不写业务库**：业务库加了表，这边自动跟着有；这边只记"我改过什么"。

## 不改什么

- 不碰业务库写权限（这是"覆盖层"的全部意义）。
- 不开放 `t_nc_catalog` / `t_nc_pinyin` 手改。
- 不动纠错算法、不动时间解析逻辑、不动数据表读取逻辑（只加覆盖读取）。
- 不动提示词材料（prompt_material）那套。

## 验收判据

`server/tests/agent/test_page_admin.py`（本机临时 PG，不连业务库）：

1. 四张词表：列表分页 / 搜索 / 新增 / 改 / 软删，`deleted_flag` 与 `update_time` 都被正确更新。
2. 列白名单：传 `id`、`deleted_flag` 之类非白名单列 → 被忽略，不报错也不写。
3. 必填校验：`wrong` 空 → 拒绝；`term` 空 → 拒绝。
4. 标准词表新增时拼音码自动补（用假字表）。
5. 时间地点覆盖：写入 `time_whole_city` 后 `_says_whole_city` 立即认新词；
   `time_strip_head` 改了之后 `_strip_unit('随州环潭供电所')` 跟着变；
   覆盖值写成坏 JSON → 回落代码常量，不崩。
6. 数据表覆盖：`meta_admin` 写入后，`semantic` 组装时优先用覆盖值；删掉覆盖行 → 回退业务库原值。

线上核对：页面上改一条错别字 → 60 秒内提问能纠正；改时间地点词 → 立刻生效。
