## 0 结论

查数阶段没问题，问题在**收尾把证据换成了转述**：`agent.py:495-511` 扔掉整段工具对话，只给模型自己写的一份「〔口径〕=〔数值〕」清单（实测 q1：system 948 + 问题 91 + 清单 6,585 = 7,624 字，22,116 字的工具原文一句不在）。单位、统计期间、同比基期、好坏方向全在转述时丢失 → "查数是对的，回答是错的"。

修正总原则两条：

1. **取舍可以交给模型，数值和语义不许由模型搬运。**
2. **一个判断只在一个地方算一次，其它地方只能读结果。**

## 2 依据

### 2.1 最对口的一篇实证（直接决定本设计的两处取舍）

**Same Simulation, Different Evidence: Where Retrieved Tool Output Costs LLM Agents Accuracy**（arXiv 2610.26836，2026-10）
<https://arxiv.org/abs/2610.26836>

- 场景和我们一模一样：工具算对了，**回答却是错的**（"compute the right answer can still answer wrongly"）。
- 机制叫 **evidence substitution（证据替换）**：把工具输出移出上下文、改成"按需检索"后，模型算得照样对，但**回答时用的证据变了** —— 它会跳过权威报告，改用自己另存的高精度输出，然后在取整/口径上出错。GPT-5.1/5.2 因此掉 11.3 / 7.9 个百分点。
- 有效修法：**指名权威输出**（naming the authoritative output）→ 提升 6.3–7.9 点；**能放得下的输出直接内联**效果相当。
- **无效修法**：在提示词里要求"正确取整/正确抄写"—— 不管用。这与本项目实测一致（规则里写了"用 SUM 别自己加"，模型照旧自己加）。

对本案的三条直接含义：

1. 我们现在的"事实清单"就是**证据替换**：权威证据（SQL 结果）被换成了模型转述。
2. 收尾必须**内联权威证据**，并**指明哪份是权威**（表名 + 期间 + 字段 + 值 + `ref`）。
3. **别再指望靠提示词让它抄对**；抄对必须由"证据在手里"保证。

### 2.2 上下文管理

**LangChain《Context Management for Deep Agents》** <https://www.langchain.com/blog/context-management-for-deepagents>
大结果落盘 + 给路径 + 预览；超阈值时把旧工具调用换成指针；摘要替换历史但**原文完整落盘可回取**。

**Chroma《Context Rot》** <https://www.trychroma.com/research/context-rot>
18 个模型受控实验：输入越长表现越差且不单调；LongMemEval 里"只给相关部分的聚焦输入（约 300 token）"显著优于塞满无关内容的完整输入（约 113k token）。

**两条合起来**：聚焦输入更好，但"聚焦"必须是**从原文里选出来的原文**，不是让模型复述一遍。这与 2.1 的结论一致，也是本设计的分界线。

### 2.3 模式发现：工具化 vs 全量注入

**AutoLink（arXiv 2511.17190）** <https://browse-export.arxiv.org/pdf/2511.17190>：大规模库上不把整份 schema 塞进提示词，而是让模型**自主探查 schema** 再按需取。支持"表清单走工具、不注入"这条（Fred 已定）。

### 2.4 本项目内已有能力（不新造轮子）

`tools_result`（超限落盘 + ref + next_offset）、`tools_db._summarize`（合计/极值由库算）、`output/probe_trace_check.py`（回答里的数回指 SQL 结果）——三样直接复用。

## 3 设计

### 3.0 先立规矩：判断只写一处

同一条判断如果散在两处，必然出现"这里判了、下个地方又该回去了"。现状已经有重复（本次审查查出），先收口再谈新功能。

| 判断 | **唯一实现**（只此一处） | 输出 | 谁只能读、不许重算 |
|---|---|---|---|
| 表/字段是否合法 | `semantic.check_sql(sql)`（新建，包住现有 `unknown_tables` / `is_allowed` / `allowed_tables`） | `{'ok':bool,'bad_tables':[],'hint':''}` | `run_sql`、`describe_table`、`find_column`、`list_tables` |
| 这一轮 0 行算不算"没数据" | `tools_db.empty_verdict(table, period)` | 判定码 `ERROR_DICT/EMPTY_NOT_READY/PLACEHOLDER/EMPTY_OK` | `_one_sql` 只负责把它塞进结果；`gaps` 只按键值记缺口；提示词不许再判 |
| 某表"最新可用期间" | `semantic.period_facts(table)`（带 60s 缓存） | `{'period_col':'stat_month','max':'202610'}` | 空集判定、证据包、进度自检 |
| 本轮时间口径 | 第 5 步定稿（结构化字段） | `{'time': {'type':'month','key':'202610'}, ...}` | 证据包顶部、页面展示；**不再由 SQL 侧二次判断** |
| 这一轮给哪些工具 | `preprocess.route` 一处 | `{use_db, use_file, make_file}` | `agent.py` 只按它拼 `_want` |
| 上下文超限怎么压 | `ctxpack.fit(messages)` 一处 | 新 messages | 其它模块不许各自截断（P10 收口到此） |

现有的重复（要删掉的）：

- 表合法性：`run_sql` 调 `semantic.unknown_tables`、`describe_table` 调 `is_allowed`、`find_column` 自己拼 `allowed_tables` → 收成 `check_sql` 一个入口。
- 空集：`_one_sql` 注"空集提示"、`gaps.is_gap` 用词表判、提示词里又写"空集就是答案" → 只剩 `empty_verdict`，另外两处改成读码。
- 截断：`agent.py:1573` / `449` / `480` 各自 `[:N]` → 统一走 `ctxpack` 的"落盘 + 指针"。

**这条规矩怎么验**：加一个静态检查用例——`tests/` 里断言"判断函数只被允许的调用方引用"（用 `inspect` 扫调用点），防止以后又被绕过。

### 3.1 收尾：证据包内联 + 指名权威（P1 / P2 解，依据 §2.1）

新增 `server/app/secretary/evidence.py`，从本轮 `trace` **由代码**生成证据包（不经模型），收尾那次调用的用户消息 = 问题 + 证据包（**直接内联，不走检索**）：

```json
{
  "口径": {"时间": "2026年1—11月（yearToDate/202611）", "范围": "全市", "来源": "第5步定稿"},
  "权威证据": [
    {"id": "e1", "表": "t_power_ai_city_summary", "期间": "202611", "行数": 1, "ref": "r3f9a1c2d4e5",
     "字段": [
       {"列": "loss_rate", "名": "累计台区线损率", "单位": "%", "值": 2.61, "同比": "+1.16%", "同比基期": "202511", "方向": "越小越好"},
       {"列": "sales_volume", "名": "累计售电量", "单位": "kWh", "值": 3455072600, "同比": "-36.77%", "同比基期": "202511", "方向": "越大越好"}
     ]},
    {"id": "e2", "表": "t_power_ai_station_summary", "期间": "202611", "行数": 47, "ref": "r8b2c1",
     "汇总": {"trip_count": {"sum": 1089}, "loss_rate": {"mean": 2.93, "max": 3.69}},
     "缺": ["县公司层级 202611 无数据，最新可用 202610"]}
  ],
  "空集": [{"表": "t_power_ai_district_summary", "期间": "202611", "判定码": "EMPTY_NOT_READY", "最新可用": "202610"}]
}
```

规则：

- 值、期间、行数、合计/极值、判定码、`ref` **全部由代码填**；模型不许改数。
- 单位/方向：从字典取；取不到留空，并写明"缺单位照字段中文名写，**不许自己换算**"。
- 体积：q1 的 22,116 字上下文 → 证据包约 2 KB，**直接内联**（论文：能内联就内联，别让它去检索）。
- `read_result` 保留（Fred 已定试），但定位是**补充**：证据包里写明"完整明细见 ref=r…，需要某行再取"。它会成为观测指标——若模型频繁去取，说明证据包不够。

**事实清单的去留**：保留 `_collect_facts` 但降级为"选题索引"（这一问要答哪几方面、哪条证据对应哪方面），不再抄数值。

### 3.2 空集四码（P3 解，判定在 `tools_db.empty_verdict` 一处）

| 判定码 | 触发 | 应该怎么答 |
|---|---|---|
| `ERROR_DICT` | 表/字段不在字典 | 报"表/字段不成立"+可用表，**不是**没数据 |
| `EMPTY_NOT_READY` | 表有数据、请求期间无行（附最新可用期间） | 报"该期间未就绪，最近可用=YYYYMM" |
| `PLACEHOLDER` | 该期间有行但全 0/全 NULL | 报"占位行（更新于 …），不作结论" |
| `EMPTY_OK` | 以上都不是 | 才允许写"按某口径没有记录" |

实现在 `tools_db.empty_verdict`：0 行时用 `semantic.period_facts` 的缓存查一次最新可用期间（不额外打库）；`PLACEHOLDER` 需要数一次空值，同样缓存。`agent.py:692` 的"空集就是答案"只在 `EMPTY_OK` 注入；`gaps.is_gap` 改成读判定码。

### 3.3 表与字段：走工具，不注入（P4 / P5 解，Fred 已定）

不注入任何表清单。改成三条：

1. `find_column` 修 tuple（已改）+ 把字典中文名与**表名**纳入检索（现在字典命中只用于加注释，字典有、information_schema 没有的行会被整条丢掉，实测 `find_column("指标")` → 0 行）。
2. 新增工具 `list_tables(keyword)`（包 `tools_db.list_tables`，函数早就有，只是没有工具面），说明写"不确定表名先调它"。
3. `run_sql` 的表名报错保持现状（它已经能回"可用表清单"，q1 就是靠它找对表的）。

**你以后改哪里**：什么都不用改——这条路线不新增任何需要你维护的文本，表名和一句话说明全部来自 `ai_data.ai_table_metadata`（以及页面「数据表」抽屉的覆盖层 `data_meta_override`），与查数口径（`prompt_material.fetch`）互不重叠。

**如果实测还是不够**（模型连 `list_tables` 都不肯调，像 q2 那样 0 条 SQL），再谈注入；那时注入的内容**只能从字典生成**，不允许在任何页面另写一份同样的字。

### 3.4 循环内上下文：三档压缩（P6 / P10 解，统一在 `ctxpack`）

1. 单次结果（已有）：> 12,000 字 → 落盘 + 前 k 条 + `ref` + `next_offset`。
2. 轮间（新）：每轮结束，把**已消费**的结果换成一行指针（含 ref 与摘要值）；messages 总字数 > 30,000 时从最老一轮开始换。
3. 兜底（新）：仍 > 60,000 字时压一次历史，原文整段落盘、ref 保留可回取。

**注意 §2.1 的警告**：检索/离场会掉分，所以第 2 档只换"已经进了证据包的旧结果"，**当前轮结果与证据包内容永远在上下文里**。目标：单题上下文峰值 ≤ 30,000 字（现在 q1b 是 34,370）。

### 3.5 进度自检与打转判定（P7 / P8 解）

- 进度自检（`agent.py:1521`）：喂**证据包摘要**（每指标一行：表/期间/值/判定码），问题改成"还缺哪几方面"。不喂行数（喂行数模型只能说"无数据"，实测两次）。
- 打转判定（`agent.py:1428`）：错误结果不计指纹；连续两次 `ERROR_DICT` 时插一句"换表/换字段，先 list_tables / find_column"，**不收尾**；只有"两次成功且结果完全相同"才算打转。

### 3.6 信息补全：定稿结构化（P9 解，Fred 已定试）

`confirm` 框按固定四段输出，代码渲染成一句话 + 单独字段：

```
对象范围：全市 / 某县 / 某所
时间口径：202610（沿用上轮）/ 202611（用户指定）/ 未指定
要答的方面：主要指标完成情况、县公司对比
数据来源提示：六项指标 → 汇总表；工单 → t_power_ai_work_order
```

时间口径作为**字段**进证据包顶部，模型写 SQL 时看得见。**只注入事实、不拦截 SQL**（2026-11-03 删掉的守卫不恢复）。

## 5 验收：按环节看准确度丢在哪（依据 §2.1 的结论）

6 题 × 3 次 = 18 次，每题覆盖：全市情况、六项指标最好/最差、某所、指定月份、制度类、闲聊。每次落 `evidence.json` + `answer` + `trace`。

**四个环节分开判**（不能只看总分）：

| 环节 | 判据 | 怎么算 |
|---|---|---|
| 选表 | SQL 里的表名 100% 在业务字典内 | 扫 trace 里的 SQL；`check_sql` 结果 |
| 选期间 | SQL 的期间 = 定稿的时间口径 | 正则抽 SQL 期间字段 vs 定稿字段 |
| 抄数值 | 回答里每个数字都能在证据包里找到（列-期间-值） | `output/probe_trace_check.py`，允许 0 条对不上 |
| 出结论 | 最好/最差必须带方向依据（`方向` 字段） | 断言结论句引用了 `方向` |

另加两条硬指标：

- 同题 3 次的"期间 + 表 + 各指标值"完全一致（措辞可不同）。
- 18 次里 `AttributeError` 计数 0；上下文峰值 ≤ 30,000 字。

**改错了怎么发现**：每批改动都在开关后（`SECRETARY_EVIDENCE`、`SECRETARY_CTX_BUDGET`、`SECRETARY_CONFIRM_STRUCT`），跑同一套 18 次；哪一环节掉分就关回去，并把掉分写进证据目录。第 2 批必须先跑"改动前基线"，两批数据同时留档，否则不能说变好。
