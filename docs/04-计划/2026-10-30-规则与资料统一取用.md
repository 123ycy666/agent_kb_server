# 计划：一个检索，文档不分类

> 2026-10-30。上一版还留着「查规则 / 查资料」两个工具 —— 那就是标签换了个皮，作废。

## 0. 结论

1. **文档不分类**。用户上传什么都不用选类型，规则文档和制度原文也没有区别，都是文档。
2. **只有一个动作：检索**。没有"全量读取"这条路。
3. **检索范围 = 这个人能看见的全部文档**（公司共享库 + 本人库）。不是"规则文档 + 我的库"。
4. **"每轮必须生效"的东西不是文档**：红线、分析方法、个人口径、输出格式，都在代码或设置里，不靠上传。
5. **覆盖式约定（公司说三天、我只能请两天）靠检索保证不了**，必须显式声明覆盖（§4.5）。

---

## 1. 用户上传的文档有哪些，要不要分类

能上传的就是这些：制度、办法、规程、报告、案例、方案、外单位材料、自己的工作材料、Excel 台账说明。

**都不分类。** 因为它们对 agent 的用法是同一个：需要时找到相关段落，引用它作答。

唯一的例外不是"某一类文档"，而是"一句话约定"——比如"说线损就是台区线损"。这种东西：
- 短、且必须**每轮无条件生效**；
- 靠检索永远捡不回来（问题里没有这句话的字面，相似度算不出来）。

所以它不进知识库，进"个人口径"设置（§4）。这不是给文档分类，是把"一句话"和"一份文档"分开存。

---

## 2. 检索：只有一个入口

### 2.1 范围

| 库 | 谁能检索 |
|---|---|
| 公司共享库（制度、规则、办法、历史材料） | 所有人 |
| 本人库（我上传的） | 只有我 |
| 别人的库 | 谁都不能（管理员前台也不行） |

**检索面 = 上面两个库的并集**。不按文档类型挑，不按"是不是规则"挑。规则文档是共享库里的普通文档；我上传的文档是我库里的普通文档。

所以 agent 检索时不是"只能检索规则文档 + 我这个 id"，而是"检索我看得见的全部文档"。

### 2.2 怎么检索

```
输入：改写后的问题（口径已替换、名称已归一、时间已补全）
范围：可见库并集
召回：关键词腿（标题 + 别名 + 正文）＋ 向量腿，RRF 融合，取前 8 片
返回：
  - 同一节命中 2 片以上 → 折叠成该节**整节**（保证判据里的数字、口径、字段都完整）
  - 只命中单票 → 返回片段
  - 每段都带：哪个库、哪个文件、哪一节（章节路径）
  - 一片都没有 → 明确说「没找到」，并给出用过的检索词
```

关键点：

- **"整节"不是另一种读取方式**，是命中后的返回粒度。判据（如"超过 80 天算预期"）能完整拿到，是因为它本来就在一节里，且这一节通常会被命中 2 片以上。
- 让命中靠得住的办法是**把章节标题和别名写进可检索字段**，而不是另开一条"精确取"的通道。
- 判据必须能在同一节里写全：判据、口径、字段、别名。字段这行是硬要求，模型拿到就能写条件。

### 2.3 主题元数据（切片必须带，用来跨文档聚合）

切片入库时固定带一个 `主题`（可由标题自动抽，也可在正文里用 `主题：审批停留` 声明）：

- 一个主题可以**跨多个切片、跨多份文档**（分档、例外、字段说明分开放也照样聚得起来）；
- 取用时按 `主题` 聚合，返回该主题**全部切片**，与文档怎么分层、分几节无关；
- 内容是会长、会换形状的（以后加表格、案例、附件），但只要主题标对了，取用方式不变。

这条是为了不把设计绑死在"一节一条"上：文档结构以后怎么变，聚合口径不变。

### 2.4 体量闸：常驻还是取，由代码按体积自动决定

不写死"永远检索"，也不写死"永远常驻"：

| 规则库总量 | 系统怎么做 |
|---|---|
| ≤ 阈值（默认 30,000 字，可配） | **全量常驻**，不检索、不要目录 —— 省一次召回，也不会漏 |
| > 阈值 | 自动切：常驻**主题清单**（一行一主题）+ 按主题取该主题全部切片 |

- 阈值可配、有测试钉住两种形态都能跑（同一份数据，改阈值即可切换）；
- 阈值不是拍脑袋：先按"全文常驻的成本"定，再看实测 token 与响应时间调；
- 这个闸只在**规则库**上；制度资料永远走检索，不参与。

这样以后内容涨十倍也只改一个数，不改机制。

### 2.5 工具

只留一个：`查资料(问题)`。删掉 `查规则(主题)` —— 那是上一版留下的标签。

模型的纪律（写进提示词，不是工具）：**要做判定之前必须先检索**；检索不到就说「没有这条标准」，不许自己编。

## 3. 目录（常驻那段）

- 来源：可见库里有章节标题的节点，按库分组：`公司` / `我的`。
- 每行：`主题 ｜ 一句话`。
- 上限：公司 ≤40 行、我的 ≤20 行；超了按更新时间倒序，末尾写「另有 N 个主题未列出，问具体名词再查」。

---

## 4. 什么不是文档（放设置，不靠检索）

| 内容 | 例子 | 放哪 | 生效方式 |
|---|---|---|---|
| 术语口径 | 说线损就是台区线损 | 个人口径表 | 预处理阶段按最长匹配替换，确定性 |
| 回答角度 | 只报问题不报成绩 | 个人偏好 | 常驻 ≤300 字 |
| 输出格式 | 汇报骨架、字体字号 | 文档模板 | 出文档时加载 |
| 会话口吻 | 这场用局长口吻 | 会话人设 | 单场会话 |

口径优先级：个人口径 > 公司默认口径；但它不改判据，判据只有公司那一份。

---

### 4.5 覆盖式约定：唯一需要"保证"的东西

场景：公司规则写「请假三天」，个人库里配一条「我现在只能请两天」。两份都在库里、都走检索 —— **单靠检索保证不了**：

1. 两份语义几乎一样，公司那份更长、词更全，相关度常常更高；
2. top_k 会截断，个人那份排到后面就看不到；
3. 最常见的失败：用户问「我下周请假三天行不行」，问题里没有"几天"这个主题词，个人那份根本不会被召回；
4. 就算两份都召回，模型也没有理由选个人那条 —— 除非明确告诉它"这是本人约定"。

所以覆盖必须**显式登记**，不靠相似度：

```markdown
## 我的请假约定
覆盖：请假天数
约定：我现在请假最多两天，超过两天要部门负责人特批。
```

入库时把「覆盖：请假天数」这行抽出来，登记成一条**个人覆盖**（本人 + 主题 + 内容 + 来源文档）。生效规则：

| 时机 | 行为 |
|---|---|
| 检索到该主题（如问"请假几天"） | 公司那条与个人覆盖一起给，并标明「本人约定，优先于公司规则」 |
| 判定类问题涉及该主题（如"我下周请三天行不行"） | 强制带上个人覆盖，不依赖召回 |
| 回答 | 写清「按你的约定 2 天（公司制度 3 天）」，可核对 |
| 作用域 | 只对本人生效，别人不受影响 |

这样"不分类"仍然成立：**不按文档类型分类，只认"这一节有没有写覆盖声明"**。没写的是普通资料（检索到就参考，不保证）；写了的是约定（一定生效，且压过公司同主题那条）。

代价：需要按这一行格式写。不写就得接受"可能被引用、不保证生效"——这一点要在界面上说明，不能让人以为传上去就等于改规则。
