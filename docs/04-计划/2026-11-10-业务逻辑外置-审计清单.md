# 2026-11-10 · 业务逻辑外置审计：代码里还写死着什么

> 判据来自 Fred：「业务相关的逻辑都要在页面上能改，代码里不能写死业务相关的问题。」
> 本文只做审计与改造方案，不含测试方案（见 `2026-11-10-问答回归-测试方案.md`）。

## 0 什么算"业务逻辑写死"

算：

1. **模型看到的话里有业务内容** —— 业务名词、口径、单位换算、默认月份。它不是机制，是业务。
2. **代码替模型做业务判断** —— 哪张表算范围、什么算"没数据"、哪个月可用、哪几个字算"业务问题"。
3. **部署后才定、改它要发版的业务事实** —— 单位名、部门 id、县公司清单。

不算（属于机制，留在代码）：

- 工具协议、消息结构、并发、落盘与缓存、事务、只读与禁分号；
- 判断的**实现**（比如"空集怎么分类"这个算法），但它的**阈值与话术**必须可配。

## 5 改造方案

原则：**代码只留机制；文本一律可配；判断只留一处实现，其阈值/话术可配。**

**新增两个可配面（不新增"第二个判断"）**

1. `prompt_text` 新 key `lines`：每轮固定发的那几句话（今天这行、收尾兜底、进度自检要求、空集话术模板）。代码只填变量（日期、最新可用期间、判定码）。→ 覆盖 A 类 5 处中的 3 处。
2. `prompt_material` 新 slot `finalize`：收尾清单/正文的口径与格式（替代 `_FACTS_RULE`）。→ 覆盖 A 类 1 处。

**动作清单**

| 动作 | 影响 |
|---|---|
| 工具 `description` 里业务举例换成中性表述；删掉"system 里只有表名清单"这句过期话 | A 类工具描述 |
| 补问法词表挪进**现成的** `prompt_text.keywords`（不新增 key） | A 类补问法 |
| `gaps` 改读空集判定码（与设计文档 §3.2 同一处） | B 类 |
| 删除 C 类全部死代码；单位换算只保留在字典说明里（字典是可维护的） | C 类 |
| `project.py` 的 `DEPARTMENT`/`DEFAULT_STATION` 搬到配置文件（`config/site.yml` 或 DB），代码只读 | B 类 |
| 加静态断言：`secretary/*.py` 里不出现业务词（白名单：`skills/`、`tests/`、`prompts_data.py` 作为默认值） | 防回归 |

## 6 验收（怎么证明"页面上改了就生效"）

1. **静态**：`grep` 断言通过——除白名单外，`app/secretary/*.py` 不出现 `售电|线损|台区|工单|千瓦时|供电所` 等业务词。
2. **动态 A**：在页面把 `lines` 里的一句话改一个字 → 下一次提问的 system/user 里必须出现那个字。
3. **动态 B**：把 `prompt_text.modes` 里"空集就是答案"改成相反说法 → 0 行时回答必须改口（证明不是代码写死）。
4. **动态 C**：把 `prompt_material.finalize` 改一处格式 → 收尾那次调用的消息里必须变。

第 2/3/4 条是真正的判据：**改页面、看模型收到的东西变了没有**。只改代码不改页面，等于没外置。
