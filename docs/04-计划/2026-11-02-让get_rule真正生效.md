# 实施：让 get_rule 真正生效（清单给代号 / 代号精确命中 / 收尾阶段开放这一个工具）

日期：2026-11-02
设计：`docs/03-设计/2026-11-02-非必带规则改按题型自动带.md` 里"自动路由"那一版**作废**
（Fred 否掉：问句和规则匹配不上、维护成本高）。这份按"修到 get_rule 能用"重写。

## 目标

非必带规则（24 条）在实战中必须真的被取到一次——不靠猜、不靠触发语。

## 根因（服务器实测）

1. **时机错位**：循环阶段 system 里只有 `fetch+judge` 的 6 条清单，工具可用；
   收尾前换成 `answer+check` 的 19 条清单，**紧接着 `_final_answer()` 是 `use_tools=False`**
   —— 清单在、工具关了。那 19 条从来没被读过。
2. **定位不准**：清单里的标题 40 字带括号举例，模型不肯抄，凭印象编短名
   （「预算执行达标判据」「十七、资金合理性」）→ `get` 报"没有这条规则"，白跑一次。

## 改法

### ① 清单给「代号 + 短名」

代号从标题前缀自动解析，**不需要人维护**：
`20.2 审批待办 / 任批积压类（「…」）` → `20.2`；`六、缺陷类型…` → `六`；`0.6 拿到问题先拆…` → `0.6`。
清单一律写成 `- 20.2 ｜ 审批待办 / 审批积压类`（短名去括号、截 18 字）。

### ② `get_rule` 认代号

匹配顺序：**代号精确 → 全名精确 → 子串 → 二元组打分（≥0.34）**；
都没中 → 返回 5 条候选代号（不再丢一堆长标题），让它用代号重试。

### ③ 收尾阶段只开放 `get_rule` 一个工具

`_final_answer` 先带「仅 get_rule」的工具表发一次；模型若调了 `get_rule`，
执行后回填结果再要正文（**最多一轮工具，防死循环**）。没有 `run_sql`/`kb_search`，
物理上不可能借机查数。

### ④ 清单两阶段都给全

查数阶段的 system 里，清单按四份算（25 条短代号，约 300 字），
这样它知道自己这题该按哪类答，可以提前取；收尾时工具也在，双保险。

## 不改什么

- 不加触发语、不做"用户问句 → 规则"的匹配（上一版就死在这）。
- 不改"必带"语义、不改规则正文、不改表结构、不改页面。
- 不动地点解析与核实闸。

## 验收（多角度，能写成断言）

`server/tests/agent/test_rule_take.py`：

| 角度 | 断言 |
|---|---|
| 代号解析 | `20.2 x`→`20.2`、`六、x`→`六`、`十九、x`→`十九`、`0.6 x`→`0.6`、`无代号标题`→'' |
| 清单 | 含代号；不含 40 字长标题；25 条；总字数 < 500 |
| 取规则 | `get('20.2')` 命中；`get('审批待办')` 命中同一节；`get('能不能达标')` 打分命中 20.11；`get('瞎编')` → error + 5 条候选且带代号 |
| 收尾工具 | 假模型：先调 `get_rule('20.2')` → 回填 → 再出正文；不调 → 一次出正文；连调两次 → 最多一轮，不死循环 |
| 越权 | 收尾阶段工具表里**只有** `get_rule`（没有 `run_sql`） |
| 循环注入 | 循环阶段 system 含 answer 的非必带代号 |

线上核对：三题重跑，trace 里出现 `get_rule` 且 topic 命中 `20.6` / `20.11` / `20.2`。
