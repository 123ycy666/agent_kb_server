# 骨架交付：账号怎么建 + 怎么接进来 + 接口文档（2026-11-18）

## 目标

把「问数骨架」交到另一个项目手上，他们不需要碰我们的代码就能跑起来：

1. 自己建账号、登进来；
2. 在页面上换自己的业务库；
3. 在页面上配查数口径、作答规则；
4. 按文档调问数接口与 agent 接口。

本机已在 `127.0.0.1:8210` + 空库 `skeleton` 上验证过：库里 0 条业务规则，只配 3 节口径（1054 字），
「两水供电所的线损率」「全市的六项指标情况」两问都出了结果（证据 `output/test_results/2026-11-18-骨架本机验证/`）。

## 根因（登录这件事）

**复现**：在骨架服务上用 `admin` 登录 → 401 `BAD_CREDENTIALS`，`base.audit_log` 留下 `auth.login_failed`。
**证据**：`dlj_data.t_employee` 里 `admin` 的 `login_pwd` 是 `$argon2id$…`，认证路径 `employee.authenticate()` 只查这一列。
**为什么**：登录的权威源是 HR 的 `t_employee`，骨架交出去时对方没有这本表 —— 只认 argon2id 就一个人都进不去。
不是密码错，是「骨架缺一条不依赖 HR 的登录通道」。
**根因修正**：`LOCAL_LOGIN_ENABLED`（默认关）+ `app_user.password_hash` 那条本地口令分支；
账号的增删改再由脚本 `server/scripts/make_user.py` 落到同一个列上。线上不开开关，行为不变。

## 根因（换库后仍查旧库）

**复现**：页面把业务库从 `dlj_data` 换成 `yc_dlj_data`，`runtime/test` 立刻返回新库；紧接着提问，
答案里的数还是旧库的（意见工单 226 = 旧库值，新库是 223）；等 8 秒再问才换成新库的数。

**证据**：同一轮 trace 的 `run_sql` 结果 `feedback_work_order=20`（旧库当月值，新库是 17）。

**为什么**：`tools_db.py` 用 `threading.local()` 按线程缓存业务库连接，
`runtime_cfg.refresh()` 里的 `_drop_conn()` 只关了「处理这次保存请求的那个线程」的连接；
`run_sql` 跑在另一个工作线程，它缓存的连接仍然连着旧库，`ping(reconnect=True)` 又探得通，
所以永远不重连 —— 旧库一直生效，直到那条连接自己断掉才被动重建。

**根因修正**：连接跟着配置走 —— 缓存里同时记下建这条连接用的 (host, port, db, user)，
每次取连接先比一次，配置变了就主动重建。不靠线程生命周期、不靠连接自己断。

## 验收判据

1. 用 `server/scripts/make_user.py` 建出的账号能登录，密码错返回 401；
2. `LOCAL_LOGIN_ENABLED` 未设时，登录行为与改之前一致（只认 HR）；
3. 文档里每条命令都能照抄执行：建账号、换库、配口径、问数、查会话；
4. 文档不依赖本机路径，对方在自己的机器上照做能起；
5. 问数接口的字段与 `docs/01-接口/2026-11-17-问数接口-定稿.md` 一致，不另起一套说法。
