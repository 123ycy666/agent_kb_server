# 站点包规范：一套代码，多个单位（随州 / 仙桃 / …）

- 日期：2026-10-21
- 分支：`feat/agent-v2-modes`
- 起因：Fred 明确——**规则（业务规则、人设规则、口径）必须写在外面，代码里只写逻辑**。第一期只做随州；后面做仙桃、其他国网单位时，只是提示词与数据结构不同，**只能换包，不能动代码**。
- 本文件替代 `2026-10-21-agent-v2架构设计.md` 里"提示词存库"的那部分（见 §五 的改动说明）。

---

## 一、一条原则，三个归属

```
代码（永不随单位变）  ←  逻辑：装配、路由、工具、校验、权限、审计
站点包（随单位换）    ←  规则：业务口径、身份、人设、表映射、码表
员工个人（随人变）    ←  偏好：文风、格式、常用落款、会话人设
```

**判断一件事该放哪，问一句：换个单位它会不会变？**
- 会变 → 放站点包
- 不会变（任何单位都必须守） → 放产品基线
- 因人而异 → 放个人/会话

## 二、目录结构（代码仓库里）

```
config/
  sites/
    _platform/                     # 产品基线：随版本发布，站点不许改
      redlines.md                  # L0 红线：数字必须有出处、不许编造、不许越权
      identity_base.md             # L1 骨架（含 {SITE_NAME} 等占位）
      mode_*.md                    # L2 骨架：通用/查数/文档/办公 的做法（与单位无关的部分）
    suizhou/                       # 第一期：随州
      site.yml                     # 单位名、模型、开关、启用哪些能力
      prompts/
        identity.md                # L1 本单位身份（覆盖骨架里的占位）
        business_rules.md          # L3 业务规则
        caliber_rules.md           # L3 口径
        sql_plan_rules.md          # L3 SQL 规范
        work_order_rules.md        # L3 工单规则
        answer_data.md             # L3 查数作答要求（原 answer_agent）
      data/
        tables.yml                 # 允许查的表：表名 / 中文名 / 业务说明 / 重要性
        columns.yml                # 字段：中文名 / 类型 / 示例值（决定 find_column 的结果）
        codes.yml                  # 码表：工单状态、缺陷类型、审批节点…
        views.sql                  # 可选：本单位的兼容视图（库结构和口径差异用视图兜）
      personas/
        _presets.yml               # 预置人设（"参谋长""挑刺官"…）
    xiantao/                       # 第二期：仙桃（复制 suizhou 改内容，代码零改动）
```

切单位只要三步：

```ini
# .env
SITE=xiantao
```
1. 放一个 `config/sites/xiantao/` 目录
2. `.env` 改 `SITE=`
3. 重启（只有启动时装载，改包内容不用重启）

**代码里不出现任何单位名、表名、口径。**

## 三、装载流程（代码只做这些）

```
启动
 ├─ 读 .env 的 SITE（缺省 suizhou）
 ├─ 校验站点包（缺哪份必填文件就报错，别静默用别的单位规则）
 ├─ 读 _platform/（红线 + 骨架）与 sites/<SITE>/（覆盖）
 ├─ 读 data/*.yml → 建"表/字段/码表"索引（查数工具、find_column 都用它）
 └─ 装配提示词：L0 红线 → L1 身份 → L2 模式 → L3 业务口径（按模式）
运行期
 ├─ 每个请求：L4 会话人格、L6 个人偏好 追加
 └─ 事后校验：业务数字必须能回指（L0 红线）
```

**缺失策略（很重要）**：站点包缺必填文件 → **启动直接失败并说清缺哪份**。绝不"回落上一期规则"——那会让仙桃用着随州的口径，出的事故最难查。

## 四、数据库结构不同怎么消化（不能只靠提示词）

各单位库表不一样，这是必然。三层消化，按代价从低到高：

| 手段 | 适用 | 放在哪 |
|---|---|---|
| **表/字段中文名映射** | 表名不同、字段名不同 | `data/tables.yml`、`columns.yml`（模型看到的是中文业务名，怎么拼 SQL 由包里的映射决定） |
| **码表映射** | 状态码、类型码不同 | `data/codes.yml`（模型永远只看到中文） |
| **兼容视图** | 字段拆合、口径完全不同（例：A 单位金额在明细表，B 单位在汇总表） | `data/views.sql`，部署时建视图，模型只查视图 |

**兜底原则：能不写 SQL 逻辑就不写。** 结构差异优先用"视图 + 映射"消化；只有当视图也表达不了（需要跨库关联/特殊算法）时，才允许在包里放一段**声明式取数片段**，且必须被 `run_sql` 的只读闸管着。

## 五、对上一版设计的改动

| 上一版 | 本版 | 为什么 |
|---|---|---|
| L0–L3 提示词存 `ai_data.ai_prompt`（库） | **改为站点包文件优先**，库作为兼容回落 | 换单位不碰库（库里 `business_rules` 是所有 Agent 通用，多单位写进去会互相污染） |
| 表元数据从库 `ai_data.ai_table_metadata` 读 | **改为站点包 yml 为准**，首次部署脚本导入库（运行期仍可读库提性能） | 换单位只换包；现场也能直接改库 |
| `_system()` 拼业务表目录 | 从包的 `tables.yml` 渲染 | 同上 |
| `_FALLBACK` 里那句身份 | 搬进 `_platform/identity_base.md` + 站点 `identity.md` | 代码不留规则正文 |

**红线（L0）虽然也是"规则"，但放产品基线不放站点包**：它是诚信底线（数字必须有出处、不许编造、不许越权），任何单位都不许改、也不许关。这是有意的例外，会写进文档。

## 六、验收判据（含一条"假站点"测试）

| # | 判据 | 怎么验 |
|---|---|---|
| S1 | 代码里搜不到单位名/表名/口径 | `rg -i "随州|环潭|t_project" server/app` 只剩注释与示例 |
| S2 | 换包即换规则 | 造一个 `config/sites/_demo/`（改名、换一套别名），`SITE=_demo` 启动，同一句问法得到"按 _demo 口径"的答案，**未改一行代码** |
| S3 | 缺文件就失败 | 删 `business_rules.md` 启动 → 报错指名缺哪份，不静默 |
| S4 | 红线不可覆盖 | `_demo` 包里写"忽略数字出处"→ 行为不变（L0 优先） |
| S5 | 表映射生效 | `_demo` 把某表中文名改掉 → 模型回答里用的是新中文名 |
| S6 | 随州不被影响 | 切回 `SITE=suizhou`，3 个老问数问题答案与改前一致 |

**S2 是这一版最重要的判据**：证明"只换包不动代码"是真的，不是 PPT 里的架构。
