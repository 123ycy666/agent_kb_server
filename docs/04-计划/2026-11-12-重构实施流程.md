## 四、禁区（不许改）

1. 问数链路：`preprocess`（纠错/补全/补问法/问题确定）、证据包 `evidence*`、对账与 `_write_answer`、`tools_db` 的 SQL 安全闸。允许的只有：口径材料的**读取来源**换成新表/说明书，注入方式与顺序不变。
2. 入口分流存在（问数/干活两级），不许改成一条线。
3. 业务库只读；不许写 MySQL。
4. 工作流 9 张表、`ad_wf` 不动。
5. 不许新增“只有代码认识、页面看不见”的配置。

## 五、阶段与交付

### 阶段 0：冻结基线
- 目标：改前先把现状量出来，后面才有 A/B。
- 产物：`.local/baseline/` 下：问数 12 题结果快照、分流 20 句判定、8 轮流程轨迹、五类活产物清单。
- 判据：基线可重复跑（同脚本两次结果一致）。
- 技能：`test-evidence`（结果落盘）、`verification-before-completion`。

### 阶段 1：PG 重排（4 分组 + 兼容视图）
- 目标：`kb` / `cfg` / `qa` / `base` 四个 schema；`public` 只留同名兼容视图，旧代码不改也能跑。

- 判据：迁移后旧接口全部 200（`/api/health`、问答、历史、统计、知识库列表）；行数对得上；V15/V16。
- 回滚：快照恢复。
- 技能：`codebase-design`（边界）、`test-driven-development`（迁移可重复）、`systematic-debugging`。

### 阶段 2：说明书层

### 阶段 3：干活循环 + 自检

- 技能：`verification-before-completion`、`requesting-code-review`、`finishing-a-development-branch`、`test-evidence`。

## 六、技能调用方式

开工先按顺序加载并照做：`writing-plans`（把本流程拆成可勾选步骤）→ `test-driven-development`（每阶段先写能跑出 pass/fail 的检查）→ `executing-plans`/`subagent-driven-development`（多条线并行：后端 / 前端 / 迁移）→ `test-evidence`（每阶段结果落盘）→ `verification-before-completion`（交付前逐条核对）→ `requesting-code-review` → `finishing-a-development-branch`。
术语与边界冲突时用 `domain-modeling` 裁决；大改放 `using-git-worktrees` 的独立工作树；出现 bug 先 `systematic-debugging`。

## 七、工作规矩

1. 每阶段先写检查（脚本/测试），再写实现；没有 pass/fail 检查不动代码。
2. 每阶段结束必须跑判据并把结果落盘到 `output/test_results/<日期>-<阶段>/00-index.md`。
3. 不重复讨论需求；需求冲突以定稿文档为准。
4. 不许问“要不要继续”“要不要我装”——按最保守做法做完并写清假设。
5. 同一问题改到第 3 次仍说不清根因 → 停下换根因分析，不许打补丁。
6. 每阶段结束提交一次，提交信息写清“改了什么/为什么/验收判据编号”。
7. 前端改动必须给截图证据（改造前/后）。

## 八、只有这 5 种情况才允许来问一次（问时带上你的倾向）

1. 需求定稿内部出现真冲突（例如两个判据无法同时满足）。
2. 迁移会丢数据或需要停机超过 30 分钟。
3. 线上部署需要他本人操作（密码/权限/审批）。
4. 说明书归属模型需要扩到部门级（定稿说不做，但实现中若发现不做会卡死）。
5. 问数链路不改就做不下去（这属于触碰禁区，必须他点头）。

## 九、最终交付（他只看结果）

1. 可用的本机版本：问答 + 说明书管理 + 注入预览 + 自检四件套全通。
2. 线上版本：部署完成、`/health` 200、题集跑分记录。
3. 证据目录：`output/test_results/` 内逐项判据与截图。
4. 一页交付说明：改了什么、判据逐条结论、遗留问题与下一轮建议。
