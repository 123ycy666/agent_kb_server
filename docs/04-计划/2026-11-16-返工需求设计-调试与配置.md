# 返工需求设计：调试、配置、库结构（把写死的东西交还给人）

- 日期：2026-11-16
- 状态：待 Fred 审，未开工
- 适用范围：问答页、提示词页、库结构页、配置作用域、写死业务逻辑迁移；知识库存取另见 `2026-11-16-知识库需求设计.md`

## 0 三条原则

- **先全景，再下钻**：每个页面先给"整体长什么样"，再给单条细节。库结构页是库的全景，提示词页是这一轮发给模型的东西的全景，问答页是一轮对话的全景。
- **每一块都得有说明**：表要有一句话用途、字段要有一句含义、提示词每一段要知道它从哪来。没有说明的标「未登记」，不留空。
- **改不动的要能指出在哪改**：只读项不删，展开给原文，旁边写文件位置。

一句话：这一轮不是补页面，是让「业务规则住在库里、页面上能改、改完能当场验」。

## 1 调试：一趟问答要能倒查到"哪一步判断错了"

现在答错时看不到原因：模型收到什么、调了哪只工具、SQL 是谁放行的，全在日志里翻不到。定稿 H15.2 原本就有「运行步骤可展开」，上一轮把它连同四件套一起撤了。

**问答页**：每轮答案下面一行摘要（依据 · 自检 · 数字来源 ▾），点开是本轮运行步骤。每一步一行，展开后必须给出：

| 步骤类型 | 必须能看到 |
|---|---|
| 分流 | 判成问数还是干活、命中哪条判据（判据原文 + 来自全局还是个人） |
| 检索 | 检索词、命中文档名、目录、相关度；个人池与通用池各命中几条 |
| 调工具 | 工具名、参数、返回原文、耗时 |
| 跑 SQL | SQL 原文、命中了哪张契约表、口径有没有管到它、返回行数、**被哪道闸放行** |
| 自检 | 逐条结论 + 依据 |

「被哪道闸放行」是这条的关键：审计查明 `run_sql` 不校验表名，`semantic.allowed_tables()` 又把整库并进白名单，所以模型查了口径外的表也没人拦。页面直接写「未经口径校验，由 ALLOWED_TABLES 放行」，问题一眼可见，不用等人去读代码。

**判据 D1**：任取一轮问答，三次点击内能指到出错的那一步，并看到该步完整输入输出。

## 2 提示词页：看的是"这一轮发出去的东西整体长什么样"

页名「提示词」，两个页签「干活线 / 问数线」。页面不按"我们一共有几段文本"排，按**装配顺序**纵向排——顺序就是 `inject.ORDER` 那 8 段，页面上不许另排一份。

```
① 身份              库·可改        301 字
② 纪律（红线+优先级+数字）  库·可改      0 字，三小段都空
③ 说明书目录行        自动生成        5 篇 306 字（最多 30 篇）
④ 会话摘要           自动生成        0 字
⑤ 前几轮             自动生成        3 轮 1,240 字（超限先压这段）
⑥ 会话文件清单        自动生成        0 个
⑦ 本轮命中的说明正文    自动生成        命中《公文处理办法》2,180 字  ← 只注命中那一篇
⑧ 工具说明           代码兜底        621 字
────────────────────────────────────────────
合计 4,648 字 / 上限 6,000 字              ▓▓▓▓▓▓▓░░ 77%
```

- 每段右侧三个动作：`展开原文` · `看来源` · `改`。可改的是 ①②⑧ 这种库里的；只读的给文件位置。
- **字数在这里才有意义**：不是"库里存了多少"，是"这一轮吃掉多少、还剩多少"。超限时的压缩顺序是"先压前几轮、再压目录"，压掉了什么、多少字，要写在那一段下面。
- 目录行始终在，正文只有命中那一篇，这就是"按需取"；不是把 5 篇全塞进去。
- 资料不在这一段：检索结果是工具的返回值，落在问答页的运行步骤里。
- 只读段照样展开看原文：7 只工具的定义与参数 schema、`KIND_HINT`、`DEFAULT_CHECK`、`spec.FOUR`、问数系统提示词、安全闸。
- `改` 保存后弹「用同一句重跑」，左旧右新并排。

**判据 D2**：改动任一段 → 下一轮合计与占比跟着变；同一句重跑能并排对比。
**判据 D3**：页面上 8 段的名称、顺序、来源，与 `inject.ORDER` 和 `inject.LABEL` 一致，由代码生成，不在前端写第二份；改动顺序后页面跟着变才算通过。

## 3 配置的作用域：全局一套，个人可覆盖

**不同的人配自己的问数。** 只有两级，不做层级、不做角色。

一张表：`作用域类型`（`global` / `user`）+ `作用域值`（用户 id，global 为空）+ `键` + `值` + `改的人` + `改的时间`。
生效：同一个键有个人取个人，没有取全局。

首批开放的键：身份（口吻、自称、详略都写在里面）、红线、优先级、工具说明、数字纪律、口径材料、预处理规则、补全规则。口吻不单开一段——个人写自己的身份，就得到自己的口吻。

不动的：纠错词典 6 张表、指标口径、字典覆盖层、安全闸、可查表清单——要么是大表，要么是安全约束，保持全局或代码。以后要扩，是往 `作用域类型` 加一个值，不改代码。

页面上每行显示「来源：全局（被个人覆盖）」，并给「恢复继承」。

**判据 D4**：个人改「身份」只影响他自己；管理员改全局，没被覆盖的人下一轮跟着变。
**判据 D5**：作用域只出现在上面那 9 个键上，别的配置表没有作用域列。

## 4 库结构页：把整个库摊开给调试的人看

一级页「库结构」，读 `information_schema` 与 PG 注释，不读配置文件。打开就是**全库全景**，不用先选表。

**全景区**（默认展开，可折叠）：四组 `kb / cfg / qa / base`，组内列出全部表，每张表一行：

| 列 | 内容 |
|---|---|
| 表名 · 中文名 | `kb.document` · 文档 |
| 一句话用途 | 存的是什么、谁在写它 |
| 字段数 · 行数 | 18 · 19 |
| 页面入口 | `有 → 知识库`；没有的标红 |
| 关系 | 被 `document_chunk` / `kb.spec` 按 `doc_id` 引用 |

**字段区**（表展开后）：字段名 · 类型 · 可空 · 默认 · **含义** · 示例值。

**说明从哪来**：页面上的「含义」可直接编辑，保存时写 `COMMENT ON COLUMN`。写进库里，psql、代码、页面看到的是同一句，不存在第二份说明。

**判据 D6**：四组全部表都在页面上；每张表有一句话用途，每个字段有一句含义（没有的标「未登记」并可现场补）；无页面入口的表数量为 0。
