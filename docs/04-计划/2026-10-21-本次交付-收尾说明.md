## 一、一句话

把"只会查数的一个业务秘书"，改成**一套代码 + 单位规则包 + 四模式**的办公助手：
业务规则全部搬到 `config/sites/<单位>/`，代码只留产品骨架与红线；同时补齐了一批办公能力（PPT/公文/比对/Excel/PDF/看图/批量/定时），并修掉一个会漂数字的**口径问题**。

## 二、架构层面改了什么（本次的核心）

| 改动 | 改前 | 改后 |
|---|---|---|
| 提示词装配 | 5 道 key 无条件全塞进 system | **七层装配**：L0 红线（代码，不可覆盖）→ L1 身份 → L2 模式 → L3 业务口径（仅 data/doc）→ L6 个人偏好 → L4 会话人设 → L5 技能 |
| 模式 | 只有一个"业务秘书" | **general / data / doc / office**；general 不挂工具、不塞业务表目录 |
| 强制查数 | 查数轮强制调工具 | 该查就查、不该查直接答；数字靠**结果校验**守 |
| 业务规则位置 | 散在 11 个 py 文件（部门锚点、判据、词表、格式…） | **站点包** `config/sites/<SITE>/**`（md/yml），代码只读结构 |
| 换单位 | 改代码 | **换包**：放目录 + `.env SITE=xiantao` + 重启 |
| 口径 | 模型每轮自己拼 SQL | 核心指标**固定 SQL + 预热**（`metrics.py`），模型只传参与措辞 |
| 个人 | 无 | **个人资料库**（复用 kb，按 created_by 隔离）+ **个人文风**（三级覆盖）+ 会话人设 |

红线：`tool_choice` 不再强制；但 L0 与数字出处校验对**所有模式**都生效（人设/偏好/技能一律压不住）。

## 五、修掉的两个真问题（都是实测暴露的）

1. **口径漂移**：同一问题三次分别得 22.79% / 0.00%——都"有 SQL 出处"，守卫拦不住。
   修法：口径写死（状态 3/6/7、`create_time`、当年年初至统计日）+ 工具化 + **代码预热**。改后三次 `run_sql 次数=0`、执行率均 0.00%。
2. **个人库建库失败**：`knowledge_base` 的 `embedding_model/dim/chunk_*` 是 NOT NULL，必须沿用系统当前 embedding（否则与公司库不在同一向量空间）；另 `pgdb` 兼容层会给 INSERT 追加 `RETURNING id`，故 `t_user_pref` 需 `id bigserial`。
