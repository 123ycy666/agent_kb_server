# 问数线：口径是唯一来源（设计）

- 日期：2026-11-16
- 状态：待 Fred 审
- 走的是 brainstorming 流程：用户故事 → 现状证据 → 方案对比 → 推荐 → 判据。代码没动。

---

## 1 用户故事

**正常**：秘书问「上个月全市欠费多少」。分流判成问数 → 口径材料（`cfg.prompt_material` 的 `fetch / 表字段说明`，17862 字，每轮注入）告诉模型有哪些表、每个字段什么意思 → 模型据此写 SQL → `run_sql` 执行 → 答数 → 数字来源落库。

**出错**：秘书问「哪个所欠费最多」。口径里只有总额，没有按所分组的说法 → 模型手上没有可用的表名 → 它去调工具现取表清单 → 工具把整库 500 张表递过去 → 它挑了张备份表 → 跑出个数 → 答了。

出错那一步的根子不是「缺一道闸」，是**表名有两个来源**：一个是你写的口径材料，一个是工具临时去库里翻。两个来源不一致时，模型当然挑省事的那个。

---

## 2 现状证据（这一节是纠错，我上一条说错了）

**问数线（老链路 `agent.py`）根本没给那两个工具。** `agent.py:1568-1577` 按分流结果给工具子集，`use_db` 时只给六只：

```
kb_search · list_metrics · metric_query · run_sql · read_result · finish
```

不含 `list_tables` / `describe_table` / `find_column`。

**给了的是干活线**：

- `loop.py:23` 的 `query_data` 一只手里塞了 `list_tables` / `find_column` 两个开关（`loop.py:68-69`），执行时落到 `tools_db.list_tables`（`loop.py:452-455`）。
- `agent_office.py:21` 的 `OFFICE_TOOLS` 直接含 `describe_table` / `find_column` / `list_tables`。

**这两处返回的是整库**：`semantic.py:234-251` 的 `allowed_tables()` 是「字典 ∪ 库内实况」，注释自己写着这是 2026-11-16 的功能回退——因为只认字典那 10 张时，真实问题「今年各供电所工单数量」答不出数。

**口径材料里还压着 12 行重复**：`fetch` 槽位共 13 行，只有 1 行启用（表字段说明 17862 字），另 12 行同内容停用副本（字段说明 4 份、表说明 4 份、字典说明 4 份）。

## 3 三个方案

| | 做法 | 代价 |
|---|---|---|
| **A 什么都不加** | 维持现状：问数线只用口径 + `run_sql`；干活线的工具照样列整库 | 干活线里模型仍能从整库挑表；这次的现象会再出现 |
| **B 表名只从口径来**（推荐） | 干活线那两只手不再读 `information_schema`，改成读口径材料里登记的表：问「有哪些表」时回口径里的表；问「这张表什么字段」时回口径里这段；口径里没有就回「口径里没有这张表」。`run_sql` 不加任何校验 | 需要能解析出口径材料里的表名（它本来就是按「表说明 / 字段说明」分段写的），解析失败时退回只回表名列表 |
| **C 加白名单表** | 新建 `cfg.allowed_table`，`run_sql` 按它校验 | 已否决：白名单是第二份真身，跟口径必然打架，且会再撞一次 2026-11-16 那次回退 |

---

## 4 推荐 B 的理由

1. 不加新表、不加新闸，只是把「表名从哪来」收敛成一处。
2. 问数线本来就没给这些手，改的是干活线，风险面小。
3. 口径是你在页面上能改的东西，改口径就等于改模型能看到什么——这符合「业务规则住在库里」。

配套两条（都不是新需求，是清账）：

- 口径页要能看见那 12 行停用副本，并标出「内容与启用行相同」——重复真身是上一次改版的残留。
- 运行步骤里记一笔：本轮有没有用到口径外的表。不拦，只留痕。

## 6 明确不做

- 不做可查表白名单，`run_sql` 不校验表名。
- 不做常驻字数上限的调整项（那个旋钮删掉，压缩发生时只显示「被压掉 X 字」）。
- 不动问数线的工具集（已经是对的，六只手里没有能翻整库的）。
