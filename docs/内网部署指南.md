# 内网部署指南

面向**离线内网**部署「统一知识库与智能问数平台」。全文按"照做即可"的顺序写。

---

## 0. 部署形态

| 项 | 值 |
|---|---|
| 形态 | **单进程 / 单端口**（默认 **8200**）/ 单内容库 / 单用户表 |
| 拓扑 | 浏览器 → 后端(8200) → ①PostgreSQL(内容库) ②MySQL(员工+业务库，只读) ③模型服务(内网 HTTP) |
| 无依赖 | **不需要 Redis、不需要 Celery**；文档入库用进程内 BackgroundTasks |

⚠️ 三条**内网特有**的硬约束，先记住：

1. **模型必须是 HTTP 服务**。内网 vLLM / Xinference / Ollama 都通过 HTTP 暴露 OpenAI 兼容接口，`MODEL_CHANNEL=local` 只是把地址换到内网，**协议不变**。
2. **`EMBEDDING_DIM` 在建表时写死**（向量列长度）。内网 embedding 模型产出的维度必须与它一致，否则向量写入直接报错。
3. **切通道 / 换 embedding 模型后必须重建索引**，否则检索结果错乱。

## 1. 环境要求

| 组件 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Windows Server 2016+ / Linux (x86_64) | 文档以 Windows 为主，Linux 差异处单独标注 |
| Python | **≥ 3.11**（推荐 3.13） | 后端运行环境 |
| PostgreSQL | **16**，且带 **pgvector** 扩展 | 建议直接用镜像 `pgvector/pgvector:pg16` |
| MySQL | 能连通现有 HR / 业务库 | 只读；本系统不建表 |
| 内网模型服务 | LLM + Embedding（+ 可选 Rerank），OpenAI 兼容 | 例：vLLM `:8000/v1`、Xinference `:9997/v1` |
| 磁盘 | 内容库 + `data/uploads` 原件 | 按文档量估算，建议 ≥ 50GB |
| 内存 | **≥ 8GB** | 向量检索与文档解析吃内存 |

**端口占用**

| 端口 | 用途 |
|---|---|
| **8200** | 唯一入口（前端 + 全部 API） |
| 5433 | PostgreSQL（宿主机映射；容器内 5432） |
| — | 模型服务端口（由内网模型方提供） |

## 2. 部署总览

```text
① 装 PostgreSQL + pgvector        → 建库 ad_new / 账号 kb
② 配置 MySQL 只读账号             → 能读 t_employee、dlj_data、ai_data
③ 配置 .env                       → MODEL_CHANNEL=local + 模型地址 + LOCAL_MODELS
④ 装 Python 依赖（离线 wheel）
⑤ 放置前端构建产物 web/dist
⑥ 初始化数据库 + 启动后端 :8200
⑦ 按「验证清单」逐项确认
⑧ 配常驻运行（NSSM / systemd）+ 可选 nginx
```

## 3. 第一步：PostgreSQL + pgvector

### 方式 A：Docker（推荐）

项目自带编排，**库名是 `ad_new`**：

```bash
docker compose up -d          # 只拉起 PostgreSQL，映射到宿主机 5433
docker compose logs -f postgres
```

编排关键参数（`docker-compose.yml`）：

| 参数 | 值 |
|---|---|
| 镜像 | `pgvector/pgvector:pg16` |
| 用户 / 密码 | `kb` / `kb_dev_pwd`（**生产请改**，并同步改 `.env`） |
| 库名 | `ad_new` |
| 端口 | 宿主机 `5433` → 容器 `5432` |
| 初始化脚本 | `docker/initdb/01-extensions.sql`（自动 `CREATE EXTENSION vector`） |

> ⚠️ **库名必须与 `.env` 的 `DATABASE_URL` 一致**。开发用编排原写的是 `kb_system`，
> 与 `.env` 不符会导致全新部署连不上库，**2026-10-16 已修正为 `ad_new`**。老环境若已建过 `kb_system`，需手工 `CREATE DATABASE ad_new;`。

### 方式 B：内网已有 PostgreSQL

若能出网/有内网源：

```sql
CREATE EXTENSION IF NOT EXISTS vector;      -- 必须成功，否则向量检索不可用
CREATE DATABASE ad_new OWNER kb;
```

`pg_bigm`（中文全文检索）**可选**：不装会自动降级为 `tsvector + ILIKE` 模糊匹配，功能可用、召回略降。

### 验证

```bash
psql "postgresql://kb:kb_dev_pwd@127.0.0.1:5433/ad_new" -c "SELECT extname FROM pg_extension;"
# 期望至少看到 vector
```

## 4. 第二步：MySQL 只读账号

本系统**只读**以下三个库（不建表、不写数据）：

| 库 | 用途 |
|---|---|
| `dlj_data` | 员工表 `t_employee`（**登录认证权威源**）+ 业务数据 |
| `ai_data` | 业务字典与系统提示词 |
| `agent_data` | ⚠️ **已废弃**（早期对话记录库，现全部在 PG）；配着无害，不配也行 |

**权限**：给应用一个只读账号即可，不要用 root。

```sql
CREATE USER 'kb_ro'@'%' IDENTIFIED BY '<强密码>';
GRANT SELECT ON dlj_data.*  TO 'kb_ro'@'%';
GRANT SELECT ON ai_data.*   TO 'kb_ro'@'%';
FLUSH PRIVILEGES;
```

> 说明：`t_employee` 的密码是 **argon2id**，且**原文不是裸明文**，而是
> `明文 + "_" + UID大写 + "_" + UID小写`（HR 系统规则）。本系统已按此实现，**无需部署方额外处理**。

## 5. 第三步：配置 `.env`

复制模板后修改：`copy .env.example .env`

### 内网必改项（`MODEL_CHANNEL=local`）

```ini
MODEL_CHANNEL=local

# ── 内网模型服务（OpenAI 兼容端点）──
LOCAL_LLM_BASE_URL=http://<内网LLM地址>:8000/v1
LOCAL_LLM_MODEL=<内网部署的模型名，如 deepseek-chat>
LOCAL_LLM_API_KEY=                 # 内网 vLLM/Ollama 一般留空

LOCAL_EMBEDDING_URL=http://<内网embedding地址>:9997/v1/embeddings
LOCAL_EMBEDDING_MODEL=bge-m3
LOCAL_EMBEDDING_API_KEY=

LOCAL_RERANK_URL=http://<内网rerank地址>:9997/v1/rerank
LOCAL_RERANK_MODEL=bge-rerank-m3
LOCAL_RERANK_API_KEY=

# 可选 Rerank 不可用时，把重排关掉（检索仍可用，只是不精排）
# （见 app/core/config.py 的对应开关）

# ⭐ 内网「可选模型」清单（逗号分隔）——问答页下拉框只显示这里列出的
LOCAL_MODELS=deepseek-chat,Qwen3-32B

# ⚠️ 必须与内网 embedding 模型的实际维度一致，且**建库前**就要定好
EMBEDDING_DIM=1024
```

### 其余必改项

```ini
DATABASE_URL=postgresql+psycopg://kb:<PG密码>@127.0.0.1:5433/ad_new

MYSQL_HOST=<MySQL地址>
MYSQL_PORT=3306
MYSQL_USER=kb_ro
MYSQL_PASSWORD=<只读账号密码>

JWT_SECRET=<openssl rand -hex 32 生成，务必替换>
APP_ENV=production
DEBUG=false
```

### 说明

| 项 | 说明 |
|---|---|
| `.env` 是**唯一配置源**，且**不入库** | 换机器只需带走 `.env` |
| `MODEL_CHANNEL` 同时管 LLM 与 embedding/rerank | 切档后向量空间不兼容 |
| `LOCAL_MODELS` 不配也能跑 | 但下拉框只有 `LOCAL_LLM_MODEL` 一个可选 |
| `SECRETARY_KB_IDS` | 问数默认检索的知识库 ID；留空 = 用「参与智能问答」标记的库 |

## 6. 第四步：Python 依赖（离线安装）

内网无法 `pip install` 时，在**能出网的同类机器**上先下好 wheel：

```bash
# 出网机器（Python 版本、系统、位数要与目标机一致）
pip download -r server/requirements.txt -d wheels/
```

把 `wheels/` 一起带进内网，然后：

```bash
# 内网目标机
python -m venv .venv
.venv\Scripts\activate                # Linux: source .venv/bin/activate
pip install --no-index --find-links=wheels -r server/requirements.txt
```

**离线包仓库缺失时的替代**：让内网方提供 PyPI 镜像（`pip config set global.index-url <内网源>`）。

## 7. 第五步：前端构建产物

后端会托管 `web/dist/`（**没有它首页会白屏**）。

- **推荐**：直接使用交付包里的 `web/dist/`（已构建）。
- 需要重新构建时（出网机器）：

```bash
cd web
npm ci
npm run build          # 产物输出到 web/dist
```

> `web/node_modules/` **不需要**打包进内网（体积大且是源码依赖）。

## 8. 第六步：初始化数据库 + 启动

```bash
cd server
python -m uvicorn app.main:app --host 0.0.0.0 --port 8200
```

**首次启动会自动完成**（幂等，可重复启动）：

1. 建扩展（pgvector）
2. 建表
3. 增量补列（新增字段）
4. 写入/同步种子管理员（从 `t_employee` 同步）

启动日志应看到：

```text
统一知识库与智能问数平台 启动中
模型通道 MODEL_CHANNEL = local
数据库就绪 | 扩展=['vector'] | ... | 管理员同步={'synced': N, 'source': 't_employee'}
```

> ⚠️ 若出现「数据库初始化失败」，**先看括号里的异常类型**（日志已带类型名），
> 不要默认是 PG 没启动。服务会继续启动，但建表/迁移**都没做**。

**Windows 一键启动**（交付包含）：双击 `启动全部.bat`。

## 10. 常驻运行

**Windows（NSSM）**

```bat
nssm install KbBackend "<交付目录>\.venv\Scripts\python.exe" ^
  "-m" "uvicorn" "app.main:app" "--host" "0.0.0.0" "--port" "8200"
nssm set KbBackend AppDirectory "<交付目录>\server"
nssm set KbBackend AppStdout "<交付目录>\logs\backend.log"
nssm set KbBackend AppStderr "<交付目录>\logs\backend.err.log"
nssm start KbBackend
```

**Linux（systemd）** `/etc/systemd/system/kb-backend.service`

```ini
[Unit]
Description=KB Backend
After=network.target

[Service]
WorkingDirectory=/opt/kb/server
ExecStart=/opt/kb/.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8200
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

> ⚠️ **保持单进程**：不要加 `--workers`。本系统的进程内缓存、ContextVar 检索身份、
> BackgroundTasks 队列都建立在"单进程"这个前提上（这是合并时的设计决定）。
> ⚠️ **不要加 `--reload`**（那是开发用的，会重复起进程）。

## 11. 反向代理（可选）

若需要域名 / 80 端口 / HTTPS，把 `deploy/nginx/kb.conf` 拷到 nginx 配置目录并改 `server_name`。
**要点**：整站反代到 `127.0.0.1:8200` 一个端口即可（前端已由后端托管），并注意：

```nginx
client_max_body_size 100m;        # 与 MAX_UPLOAD_MB 对齐
proxy_read_timeout 300s;          # 问数与解析耗时长
proxy_buffering off;              # 问数流式输出必须关闭缓冲
```

## 12. 升级与回滚

```text
升级：停服务 → 备份 PG（pg_dump ad_new）与 data/ → 覆盖代码 → 启服务
      → 首次启动会自动执行增量迁移（db_init 幂等）
回滚：停服务 → 换回旧代码 → 启服务
      ⚠️ 增量迁移只加不删，回滚旧代码不会报错
```

**备份命令**

```bash
pg_dump "postgresql://kb:<密码>@127.0.0.1:5433/ad_new" -Fc -f ad_new_$(date +%F).dump
```

> `data/uploads/` 是**用户上传的原件**，删了「下载原文件」会 404，**务必一起备份**。

## 13. 故障排查

| 现象 | 排查顺序 |
|---|---|
| 服务起不来 | 看启动日志的**异常类型**；再确认 `.env` 的 `DATABASE_URL` / `MYSQL_*` |
| 数据库初始化失败 | `psql ... -c "SELECT extname FROM pg_extension"` 确认 `vector` 存在；确认库名是 `ad_new` |
| 登录总失败 | 确认 `t_employee` 可读、账号未被停用；`MYSQL_PASSWORD` 正确 |
| 首页白屏 | `web/dist/index.html` 是否存在；`Ctrl+Shift+R` 强刷 |
| **改了配置不生效** | 启动命令**没有 `--reload`**，必须**重启后端** |
| 提问报「模型不可用」 | 该模型未在内网部署；`GET /api/models` 应只列出 `LOCAL_MODELS` |
| 提问报「无法连接模型服务」 | 内网模型地址/端口不通，或 vLLM 未启动 |
| **问答没有历史记录** | ① 历史页**不会自动刷新**，点「刷新」；② 响应里 `qa_id` 是否为 `null`；③ 看后端日志 `[qa_log] 落库失败` |
| 检索结果很差/报维度错 | `EMBEDDING_DIM` 与内网 embedding 模型不一致；或换过模型**没重建索引** |
| 上传一直 running | 后端进程被重启会丢未完成任务；对文档执行「重建索引」重跑 |
| 端口被占 / 行为随机 | `netstat -ano \| findstr :8200`，**只应有一个 PID**，重启服务 |

## 附录：三个最容易踩的坑

1. **库名不一致** —— 编排建 `kb_system`、应用连 `ad_new`（已修正，但老环境要手工建库）。
2. **模型清单没配** —— 内网不配 `LOCAL_MODELS`，下拉框只有一个模型；若清单里混进公网模型名，选一个报错一个。
3. **换 embedding 模型没重建索引** —— 向量空间不兼容，检索结果会莫名其妙。
