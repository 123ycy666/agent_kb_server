# 办公文档能力 —— 接口设计（v1）

> 对应用户要求：「我们做接口，实际前端怎么接到他们来调用，按正常流程设计」。
> 设计参照主流开源实现（Dify / Open WebUI / RAGFlow）的通行做法：**文件先落地拿 id，消息再引用 id**；同时提供**一步到位**的写法给"只想调一次"的外部系统。
> 兼容原则：`/api/ask` 现有 JSON 调用**一行不改**仍可用，新字段全部可选。

---

## 1. 三条调用路径（覆盖所有场景）

| 场景 | 调用顺序 | 为什么这么设计 |
|---|---|---|
| **A. 新对话，文件 + 问题一起发**（豆包式） | `POST /api/ask` 一次 multipart（`question` + `files`） | 调用方一次搞定；服务端内部先落地再解析 |
| **B. 对话中发文件 / 多轮追问同一份文件** | 先 `POST /api/files` 拿 `file_id` → 后续每轮 `POST /api/ask` 带 `file_ids` | 文件不重复上传、可预览可删除、解析失败不影响提问 |
| **C. 文档任务（速读/纠错/审查/生成文件）** | `POST /api/files` → `POST /api/docs/jobs` → 轮询 `GET /api/docs/jobs/{id}` → 下载 `outputs[].url` | 20 页要几十秒到几分钟，同步请求必超时 |

**短问答同步返回，长任务一律 job 化**——这条界线别混：单次问答几十秒可以同步，抽 20 页 + 生成 docx 必须异步。

## 2. 接口清单

### 2.1 文件

#### `POST /api/files` 上传
`Content-Type: multipart/form-data`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `file` | 文件 | 是 | 单个文件。多文件就调多次 |
| `purpose` | string | 否 | `chat`（默认）/ `task`，只影响保留策略 |

```json
{
  "file_id": "f_8f3c2a1b9d4e",
  "name": "关于开展2026年配网缺陷治理的通知.docx",
  "ext": "docx",
  "size": 184320,
  "sha256": "9c1f…",
  "parsed": {
    "ok": true,
    "chars": 21408,
    "blocks": 143,
    "headings": 26,
    "tables": 3,
    "preview": "关于开展2026年配网缺陷治理的通知\n公司各单位：\n为…"
  },
  "created_at": "2026-10-19T15:02:11+08:00"
}
```

- 解析**同步**做（小文件 <1 秒；`.doc`/`.wps` 走 WPS COM 转换，慢，见 §6）。
- 解析失败**仍然返回 file_id**（`parsed.ok=false` + `error`），用户可以先聊、稍后重试；不要让上传失败挡路。
- 上限：`settings.max_upload_mb`（沿用现有配置）；超了报 `FILE_TOO_LARGE`。

#### `GET /api/files` 我的文件列表
`?page=1&page_size=20` → `{ items: [文件对象], total }`

#### `GET /api/files/{file_id}` 元信息 · `GET /api/files/{file_id}/download` 原件 · `DELETE /api/files/{file_id}`

#### `GET /api/files/{file_id}/blocks` （按需查看解析结果）
`?from=0&limit=50` → 段落/表格块（带 `heading_path`、`para_no`），供前端做"跳到原文"。**这是"可追溯"的接口**，纠错和速读都要用到。

### 2.2 问答（扩展，向后兼容）

#### `POST /api/ask`

**三种请求形态，同一个 URL：**

1. **纯 JSON**（现状，不变）
```json
{ "question": "今年预算执行怎么样", "session_id": "s_xxx", "model": "…", "kb_ids": [3] }
```

2. **JSON + 文件引用**（对话中发文件）
```json
{ "question": "这份文件要求我们什么时候上报、报什么材料？",
  "session_id": "s_xxx",
  "file_ids": ["f_8f3c2a1b9d4e"] }
```

3. **multipart 一步到位**（新对话，文件+问题一起发）
```
question: 这份文件要求我们什么时候上报、报什么材料？
files:    <二进制，可多个>
session_id: 可空（空则新建）
```
服务端判断 `Content-Type` 是否 `multipart/form-data`，是则内部拆成"先落地 → 再走 2"。

**响应**：在现有字段（`answer` / `trace` / `session_id` / `qa_id` / `elapsed_ms` …）基础上**只增不改**：

```json
{
  "answer": "……（正文，含出处章节）",
  "session_id": "s_xxx",
  "files": [
    { "file_id": "f_8f3c…", "name": "…docx", "used_chars": 12000,
      "truncated": false, "cited_sections": ["二、主要任务 > （三）时限要求"] }
  ],
  "trace": [ … ]
}
```

**带文件时的上下文策略（关键，别写成"把全文塞进去"）：**
- 文件 ≤ 6000 字：整篇进上下文；
- 文件 > 6000 字：**按问题召回相关段落**（标题路径 + 段落级关键词/向量粗排，取 top 8 段 + 全文目录），并在回答里带 `章节路径`；
- 一律在系统提示里声明：**只依据文件内容回答，文件里没有的写"文件中未提及"，不要用外部常识补**。

### 2.3 文档任务（异步）

#### `POST /api/docs/jobs` 建任务
```json
{ "task": "digest",
  "file_ids": ["f_8f3c…"],
  "options": { "role": "供电所所长", "want_docx": true, "want_xlsx": true } }
```
| `task` | 说明 | 产出 |
|---|---|---|
| `digest` | 长文速读：一页纸摘要 + 要点清单 + 与我相关 + 高风险 | Markdown + docx + xlsx |
| `proofread` | 公文纠错 + 格式合规 | 问题清单 docx + 修订版 docx |
| `table_audit` | 表格审查（空值/重复/合计不平/单位混写/异常值） | 问题清单 xlsx + 清洗后 xlsx |
| `report` | 按模板生成报告 | docx |
| `pptx` | 长文转汇报提纲 | pptx |

返回 `202`：
```json
{ "job_id": "j_2b7d…", "status": "queued", "task": "digest", "created_at": "…" }
```

#### `GET /api/docs/jobs/{job_id}` 轮询
```json
{ "job_id": "j_2b7d…",
  "status": "running",          // queued | running | done | failed
  "progress": 45,                // 0-100，按"块"推进
  "stage": "抽取 5/12 段",
  "task": "digest",
  "result": {
    "answer_markdown": "……",
    "evidence": [ {"claim":"10月31日前上报","section":"二、主要任务 > （三）时限要求","para_no":42,"quote":"请于10月31日前…"} ],
    "warnings": ["第 3 页有表格未识别，已跳过"]
  },
  "outputs": [ {"name":"速读_通知.docx","url":"/api/docs/jobs/j_2b7d…/download?name=…"} ],
  "error": null
}
```
- `done` 之后 `outputs` 才有值；`failed` 时 `error` 给一句人话（"文件是扫描件，没有文字层"）。
- 轮询建议 1–2 秒一次；前端也可以在 `GET /api/docs/jobs/{id}/stream`（SSE，P1 再上）拿增量。

#### `GET /api/docs/jobs` 我的任务列表 · `POST /api/docs/jobs/{job_id}/cancel`

## 3. 统一约定

| 项 | 约定 |
|---|---|
| 鉴权 | 沿用 `Authorization: Bearer <JWT>`（与知识库同一套登录）；系统间定时调用用 `X-Internal-Token`（与 `/api/alerts/daily` 一致） |
| 错误 | `HTTPException(detail={"code":"…","message":"…"})`，与现有 `documents.py` 一致 |
| 时间 | ISO8601 带时区 |
| 分页 | `{ items, total, page, page_size }` |
| 文件可见性 | **私有**：只有上传者本人与管理员能读；问答/任务只能引用自己的文件（服务端校验，不信任入参） |
| 保留期 | 默认 30 天（`DOC_FILE_TTL_DAYS`），到期清理原件与成果；被任务引用的保留至任务结束 |
| 幂等 | 同 `sha256` 同用户重复上传 → 复用已有 `file_id`，不重复落盘 |

**错误码**

| code | HTTP | 含义 / 处理 |
|---|---|---|
| `UNSUPPORTED_FORMAT` | 400 | 格式不支持，按 `SUPPORTED_EXTENSIONS` 改 |
| `FILE_TOO_LARGE` | 400 | 超上限 |
| `FILE_NOT_FOUND` | 404 | file_id 不存在或不属于当前用户 |
| `PARSE_FAILED` | 422 | 解析失败（扫描件 / 加密 / 损坏），带 `message` |
| `JOB_NOT_FOUND` | 404 | job_id 不存在 |
| `JOB_BUSY` | 429 | 同一用户并发任务超限（默认 3） |
| `MODEL_UNAVAILABLE` | 503 | 内网模型未就绪，提示换模型 |

## 4. 调用示例

**A. 一步到位（curl）**
```bash
curl -X POST http://10.0.0.8:8200/api/ask \
  -H "Authorization: Bearer $TOKEN" \
  -F "question=这份文件要求什么时候上报？要报什么材料？" \
  -F "files=@通知.docx"
```

**B. 两段式（前端推荐）**
```javascript
const fd = new FormData(); fd.append('file', fileObj)
const up = await fetch('/api/files', { method:'POST', headers:{Authorization:`Bearer ${tk}`}, body: fd }).then(r=>r.json())

const ans = await fetch('/api/ask', {
  method:'POST',
  headers:{ 'Content-Type':'application/json', Authorization:`Bearer ${tk}` },
  body: JSON.stringify({ question:'要报什么材料？', session_id, file_ids:[up.file_id] })
}).then(r=>r.json())
```

**C. 任务 + 轮询**
```javascript
const job = await fetch('/api/docs/jobs', { method:'POST', headers:{'Content-Type':'application/json', Authorization:`Bearer ${tk}`},
  body: JSON.stringify({ task:'digest', file_ids:[up.file_id] }) }).then(r=>r.json())

let s
do { await new Promise(r=>setTimeout(r,1500))
     s = await fetch(`/api/docs/jobs/${job.job_id}`, {headers:{Authorization:`Bearer ${tk}`}}).then(r=>r.json())
} while (s.status==='running' || s.status==='queued')
// s.outputs[0].url 直接 <a download> 即可
```

## 5. 前端最小接入（"能正常生成就行"）

不做独立工作台也行，在现有 `/agent/` 问答页加三样东西就够用：
1. 输入框左边一个 📎：选文件 → 立即 `POST /api/files` → 气泡里显示"文件名 · 2.1万字 · 已解析"；
2. 发送时把已传文件的 `file_ids` 一起带上（第 2.3 种请求）；
3. 任务类（速读/纠错/审查）走一个下拉选择 → 调 `/api/docs/jobs` → 顶部细进度条 + 完成后在气泡里给下载按钮。

## 6. 已知边界（别指望接口能兜住）

| 边界 | 接口表现 | 处理 |
|---|---|---|
| `.doc` / `.wps` 旧格式 | 解析慢（走 WPS COM），未装 WPS 则 `PARSE_FAILED` | 提示"请另存为 .docx"；内网机器确认有 WPS 后再开 |
| 扫描件 PDF（无文字层） | `chars≈0` → `PARSE_FAILED: 未提取到文字` | 明说"需要 OCR，当前版本不支持" |
| 超长文件（>200 页） | 任务能跑但慢 | 任务接口给 `progress`，前端别用同步问答硬扛 |
| 图片/图表内容 | 解析不到（只取文字层与表格） | 摘要里标注"含 N 处图片，未解析" |

## 7. 与开源实现的对照（为什么这么设计）

| 项目 | 做法 | 我们对应 |
|---|---|---|
| Dify | `POST /v1/files/upload` 先拿 `id`，再 `POST /v1/chat-messages` 的 `files[].upload_file_id` 引用 | `/api/files` + `/api/ask` 的 `file_ids` |
| Open WebUI | 文件表 + 消息上挂 `files`，检索走 RAG | 同一套（`t_doc_file` + `file_ids`） |
| RAGFlow | 上传 → 解析（带进度）→ 会话引用 | `/api/docs/jobs` 的 `progress`/`stage` |

参考：[Dify files 与 chat-messages 的 upload_file_id 语义](https://github.com/langgenius/dify/issues/19112)、[同一问题的复现讨论](https://github.com/langgenius/dify/issues/28982)。它们的"两段式"是主流，也是唯一能支持多轮复用同一文件的形态；一步式只是给外部系统减少一次调用，内部仍走同一条路径。

## 8. 实现状态（2026-10-19 收口，**对接方按这张表写代码**）

| 接口 | 状态 | 说明 |
|---|---|---|
| `POST /api/files` | ✅ 已实现 | 上传即解析；解析失败也返回 file_id（`parsed.ok=false`） |
| `GET /api/files` / `{id}` / `{id}/blocks` / `{id}/text` / `{id}/download` / `DELETE` | ✅ 已实现 | 全部校验归属，别人的 id 一律 404 |
| `POST /api/ask`（JSON + `file_ids`） | ✅ 已实现 | 与现有问答完全兼容，不传文件行为不变 |
| `POST /api/ask`（multipart 一步式） | ✅ 已实现 | 同一 URL 按 `Content-Type` 区分 |
| `POST /api/docs/jobs` | ✅ 已实现 | `task` 目前支持 `digest` / `proofread` / `table_audit` |
| `GET /api/docs/jobs/{id}`、`GET /api/docs/jobs`、`{id}/download`、`{id}/cancel` | ✅ 已实现 | 轮询建议 1.5 秒一次 |
| `GET /api/docs/jobs/{id}/stream`（SSE 增量） | ⬜ 未实现 | 轮询够用；前端要做"打字机感"再补 |
| `task=report`（按模板生成报告） | ⬜ 未实现 | 等真实报告模板 |
| `task=pptx`（长文转汇报提纲） | ⬜ 未实现 | 等真实 PPT 模板 |
| `.doc` / `.wps` 旧格式 | ⬜ 不支持 | 报 `UNSUPPORTED_FORMAT`，提示另存为 `.docx` |
| 扫描件 PDF（无文字层） | ⬜ 不支持 | `parsed.ok=false`，`error` 写明"未提取到文字" |

**响应字段补充**（实现比设计稿多出来的，对接方可直接用）：
- `POST /api/ask` 的 `files[]` 里除 `used_chars/truncated/cited_sections` 外，还有 `mode`（"全文" / "节选 1/8 段"）与 `chars`（全文总字数）；
- `GET /api/docs/jobs/{id}` 的 `result` 里：`answer_markdown`（聊天里直接显示）、`items`（结构化清单）、`evidence`（每条主张的原文与位置）、`warnings`（未核实、跳过段落等）；
- `POST /api/files` 的 `parsed.warnings`：例如"含 3 个图表，图表里的数字未解析"。

**已实现的错误码**：`UNSUPPORTED_FORMAT`、`FILE_TOO_LARGE`、`EMPTY_FILE`、`BAD_CONTENT`、`FILE_NOT_FOUND`、`JOB_NOT_FOUND`、`JOB_BUSY`(429)、`UNSUPPORTED_TASK`、`NO_FILE`、`BAD_JSON`、`OUTPUT_NOT_FOUND`。
