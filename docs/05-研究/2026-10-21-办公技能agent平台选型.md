# 内置办公技能（Word/PPT/Excel/公文）的开源 AI Agent 平台选型调研

- 调研日期：2026-10-21（以下 star / commit 数据均为该日抓取快照）
- 调研对象：一个已有的企业内网系统（Python FastAPI :8200 + React，自写 agent 主循环，OpenAI 兼容 function calling，核心能力「自然语言问数」+ 多重硬守卫）
- 目标：判断能否引入某个平台承载「内置办公技能」，以及现有问数能力以什么形式接入、代价多大
- 标注约定：
  - **【事实·来源】**：本次实际抓取到的页面/源码/许可证原文，附 URL
  - **【推断】**：基于事实或工程经验的判断，未被官方文档逐字确认
  - **未核实**：想核实但抓取失败（限流/页面 404/JS 渲染）或没有一手来源

## 0. 结论速览（先看这 6 条）

1. **没有任何一个候选平台能直接替换现有 agent 主循环而不伤问数能力。** 卡点不在"能不能挂工具"，而在**没有一个平台提供"每次工具调用前后执行项目自定义守卫"的钩子**——Dify / FastGPT / Coze / MaxKB / BISHENG 的主循环都在各自的服务里（Agent 节点、对话 Agent、单智能体、应用），守卫（时间范围、权限、单位、数字必须来自工具输出）无法插进去，只能改源码或在平台外再包一层。【推断，依据各平台扩展文档能力边界】
2. **"内置办公技能"这一条，12 个候选里只有 BISHENG 毕昇是真内置**：源码里有 `bisheng-docx` / `bisheng-pptx` / `bisheng-xlsx` 三个内置技能目录（含 SKILL.md + scripts）。【事实·[源码目录](https://github.com/dataelement/bisheng/tree/main/src/backend/bisheng/linsight/builtin_skills)】
3. 其余全部是"**靠代码解释器写 python-docx**"或"**靠第三方插件/社区节点**"：Dify 靠社区插件 `markdown-exporter`（DOCX/PPTX/XLSX，Apache-2.0）；FastGPT 的代码节点**根本 import 不到 python-docx/openpyxl**（白名单只有 numpy/pandas/matplotlib）；Coze / MaxKB / Open WebUI / OpenManus / n8n 同理或更弱。【事实·见各节证据】
4. 许可证有两类坑必须先过法务：**Dify（改版 Apache-2.0：多租户需授权、不得改 LOGO）**、**FastGPT（同为改版 Apache-2.0）**、**Open WebUI（BSD-3 + 品牌条款：>50 人必须保留 Open WebUI 标识）**、**n8n（Sustainable Use License，非 OSI 开源）**、**MaxKB（GPL-3.0，v2 主分支）**。【事实·LICENSE 原文】
5. 离线可行性：Dify / FastGPT / MaxKB / BISHENG / Open WebUI / n8n 都能纯内网 Docker 跑；**Coze Studio 最差**（官方插件必须连 coze.cn 配鉴权 + 需要 MySQL/Redis/ES/Milvus/MinIO 五件套），**Qwen-Agent 的 code interpreter 是阿里云托管服务**，纯内网不可用。【事实+推断，见各节】
6. **推荐路线：不动主循环。** 把"办公技能"做成现有 FastAPI 里的一组 function tools（模板驱动的 python-docx / python-pptx / openpyxl + 一个 `office_render` 服务），问数守卫一条代码都不用改；只有当领导明确要求"可视化编排/工作台"时，再用 Dify 装离线插件包当"办公前台"，并把问数**整体封装成一个黑盒工具 `ask_data(question)`** 回调现有 FastAPI。【建议，见第 5、6 章】

## 3. 逐项详述

### 3.1 Dify

1. **仓库/活跃度**：https://github.com/langgenius/dify ，159,073★，`pushed_at` 2026-10-21，最新 release **v1.17.1（2026-09-10）**。【事实·[REST API](https://api.github.com/repos/langgenius/dify)、[releases](https://github.com/langgenius/dify/releases)】
2. **许可证**：GitHub 识别为 `NOASSERTION`。LICENSE 原文标题是 "Open Source License"：基于 **Apache-2.0 的修改版**，附加 **2 条硬约束**——(a) 未经书面授权不得用其源码运营**多租户**环境（原文把 tenant 定义为 workspace）；(b) 使用其前端（`web/` 目录或 web 镜像）时**不得移除/修改 LOGO 与版权信息**；末尾另注"交互设计受外观专利保护"。内部单租户自用不触发 (a)。【事实·[LICENSE](https://github.com/langgenius/dify/blob/main/LICENSE)】
3. **内置办公技能**：**没有原生 docx/pptx/xlsx 生成能力**，实际路径有两条：
   - 插件市场：`markdown-exporter`（`bowenliang123/markdown-exporter`，274★，Apache-2.0，2026-08-13 有提交），官方描述即"transform Markdown to files of **DOCX, PPTX, XLSX**, PNG, PDF, HTML, MD, CSV, JSON, XML"，市场页 https://marketplace.dify.ai/plugins/bowenliang123/md_exporter 。Dify 官方文档另有一篇"开发 md-exporter 插件"的 walkthrough（教程性质，非该仓库官方文档）。【事实·[仓库](https://github.com/bowenliang123/markdown-exporter)、[Dify 文档](https://docs.dify.ai/en/develop-plugin/dev-guides-and-walkthroughs/develop-md-exporter)】
   - 代码执行节点（dify-sandbox）：默认**不带**第三方库，社区反复问"怎么装 bs4"（discussion #37580），还有人专门做了 `dify-sandbox-python-requirements-download` 来离线备依赖。→ 想在代码节点里 `import docx`，必须先自定义 sandbox 镜像。【事实·[discussion](https://github.com/langgenius/dify/discussions/37580)、[离线依赖工具](https://github.com/yodhcn/dify-sandbox-python-requirements-download)；镜像内是否预装 docx/openpyxl = 未核实】
4. **离线**：compose 全栈可离线，但要注意 (a) 插件市场默认要外网 → 需打成本地包安装（官方文档标题即 "Package as Local File and Share"，页面本次抓取失败）；(b) sandbox 依赖；(c) 1.17.1 起 Weaviate 换到 `cr.weaviate.io` 且要求分阶段升级（release notes 明确警告）。【事实·[release notes 1.17.1](https://github.com/langgenius/dify/releases/tag/1.17.1)、[Dify 文档](https://docs.dify.ai/en/develop-plugin/publishing/marketplace-listing/release-by-file)】
5. **扩展工具**：自定义工具（粘 OpenAPI schema）/ HTTP 请求节点 / 插件（Python SDK）/ MCP。**把已有 Python 函数变成工具**：最省事是给 FastAPI 加一个 OpenAPI 端点，在 Dify 里"自定义工具"粘 schema 即可 —— 代码量≈0（后端加 1 个路由），配置量≈1 张表单。【推断，Dify 官方扩展文档未逐条抓取】
6. **多租户/审计**：workspace + 成员角色 + 应用级 API Key；1.17.1 新增"按知识库绑定的 API Key"（越权返回 403），说明其 API 权限粒度在补。【事实·release notes 同上】
7. **缺陷**：① 许可证多租户条款；② 插件市场/沙箱/镜像源三处外网依赖；③ 平台自己接管 Agent 循环 → 守卫无法插入；④ 版本升级破坏性大（Weaviate 跨 12 个 minor）。【事实+推断】

### 3.2 Coze Studio（字节扣子开源版）

1. **仓库/活跃度**：https://github.com/coze-dev/coze-studio ，21,735★，`pushed_at` **2026-07-29**，最新 release **v0.5.1（2026-02-05）**。→ 近 8 个月没有 release，最后提交停在 7 月底。【事实·[REST API](https://api.github.com/repos/coze-dev/coze-studio)、[releases](https://github.com/coze-dev/coze-studio/releases)】
2. **许可证**：**Apache-2.0**（README 的 License 段指向 `LICENSE-APACHE`）。没有额外商用限制条款被点名。【事实·[README](https://github.com/coze-dev/coze-studio/blob/main/README.md)】
3. **内置办公技能**：**无**。README 的能力表只有 模型服务 / 建智能体 / 建应用 / 建工作流 / 插件·知识库·数据库·Prompt / OpenAPI·Chat SDK。文档节点只能靠：(a) **插件商店的官方插件**——README 明确"要使用插件商店的官方插件，必须先配置插件并填写第三方服务鉴权 key"，v0.5.0-beta 的 release notes 也写明"支持接入 Coze.cn 官方插件"；(b) **代码节点**——release notes 显示已从 `eyurtsev/pyodide-sandbox` 切到 `langchain/pyodide-sandbox`，即 **Pyodide(WASM) 沙箱**，没有原生 wheel 的环境里 `python-docx` 不可用。【事实·README + [v0.5.1 release](https://github.com/coze-dev/coze-studio/releases/tag/v0.5.1) 的 PR #2498；Pyodide 不能装原生扩展包属技术常识=推断】
4. **离线**：**最差**。Go 微服务 + MySQL + Redis + Elasticsearch + Milvus + MinIO；官方插件要连 coze.cn；README 甚至自带 WARNING 列出公网部署风险："代码节点的 Python 执行环境、SSRF、部分 API 的横向越权"。社区 issue #488 专门讨论"开源版与商业版插件生态联动及过渡方案"，侧面说明开源版插件生态不完整。本地代码节点报沙箱错也是常见问题（社区多篇）。【事实·README、[issue #488](https://github.com/coze-dev/coze-studio/issues/488)；本地报错细节见社区帖 = 弱证据】
5. **扩展工具**：自定义插件（HTTP + OpenAPI schema）、工作流节点、OpenAPI/Chat SDK。把一个 Python 函数接进来 ≈ 写一份 OpenAPI JSON。【推断，官方 wiki「Plugin Configuration」未逐条抓取】
6. **多租户/审计**：有 workspace/账号体系与 OpenAPI PAT；细化权限与审计日志能力 未核实。
7. **缺陷**：活跃度下滑（8 个月无 release）、服务组件最重、代码节点沙箱在离线环境易失败、官方插件依赖外网鉴权、官方自曝若干安全问题。

### 3.3 FastGPT

1. **仓库/活跃度**：https://github.com/labring/FastGPT ，29,884★，`pushed_at` 2026-10-20，活跃。【事实·REST API】
2. **许可证**：**Apache-2.0 + 附加条款**（`NOASSERTION`）：a. 多租户 SaaS 需书面授权；b. 不得移除/修改控制台 LOGO 与版权；末尾注明"交互设计受外观专利保护"。允许商业化、允许作为 BaaS。【事实·[LICENSE](https://github.com/labring/FastGPT/blob/main/LICENSE)】
3. **内置办公技能**：**无原生节点**，而且有一条硬限制足以否掉"用代码节点写 docx"这条路——
   - 官方"代码运行"文档（4.14.8+）：Python **白名单模块**只到 `numpy / pandas / matplotlib` + 标准库，**没有 python-docx / openpyxl / python-pptx**；禁止 `os/subprocess/requests`；**无法访问文件系统**；**自动拦截内网 IP**（127/10/172.16/192.168 段）；私有化必须单独部署 `fastgpt-sandbox` 镜像并配 `CODE_SANDBOX_URL`。【事实·[代码运行节点文档](https://doc.fastgpt.cn/zh-CN/guide/build/workflow/nodes/sandbox-v2)】
   - 官方"企业报告自动生成"方案页写"文档交付输出：Markdown、**docx 输出**，客户可下载"——注意这是**方案/模板**，不是内置节点，实际必须由外部 HTTP 服务产出 docx。【事实·[方案页](https://solutions.fastgpt.cn/customers/solution/enterprise-report-auto-generation/markdown)】
4. **离线**：可（compose + sandbox 镜像）；无外网也能跑，插件/工具是自建的 HTTP。
5. **扩展工具**：HTTP 请求节点、工具调用节点、自定义工具（OpenAPI）；沙箱 `SystemHelper.httpRequest` 也提供受限 HTTP，但**拦内网 IP** → 想从代码节点回调内网 FastAPI 会被拦，必须走 HTTP 请求节点（其内网策略 未核实）。把 Python 函数变成工具 ≈ 起一个 HTTP 端点 + 填 OpenAPI。【事实（拦截规则）+ 推断（落地方式）】
6. **多租户/审计**：团队/成员、知识库文件级权限、SSO、管理员后台、调用日志（商业版更全）。【事实·文档目录可见 [团队管理/SSO/文件级权限](https://doc.fastgpt.cn/zh-CN/guide/dataset/collection_permission)】

## 4. 「办公技能」这件事的真实成本（比选平台更重要）

无论选哪个平台，落到"领导能签字"的公文/PPT，真正的成本在这三处（**均是工程事实，不是平台能力**）：

1. **版式来自模板，不来自提示词。** 公文（GB/T 9704-2012）要求特定的字号字体（如标题小标宋二号、正文仿宋_GB2312 三号）、行距（28–30 磅）、页边距、版记。正解是**准备 .docx/.pptx 母版模板**，用 python-docx / python-pptx 做"占位符替换 + 表格填充"，而不是让模型生成全文再转格式。【推断+工程经验；GB/T 规范可参考 [official_document](https://github.com/xiaoshi7915/official_document)】
2. **中文字体必须打进镜像。** 容器里没有 `SimSun/FangSong_GB2312/仿宋` 时，docx 里写中文字体名会在别的机器上 fallback；pptx 的"字数自适应/行距"在缺字体时排版崩。→ 镜像预置字体文件 + `fc-cache`。【推断，常见坑】
3. **Excel 不是"生成文件"，是"填对表格"。** 业务要的是带公式、带数据校验、带冻结窗格的工作簿；openpyxl 能做到，但要求输入是**结构化数据**——这正好是你问数能力的下游。这条反而是你的优势：问数 → 结构化 → openpyxl 出表，比任何平台都顺。

结论：**"生成 docx/pptx/xlsx"这段代码只有 200–500 行，真正的价值在模板与数据契约。** 把它做成现有 FastAPI 的一组内部函数，成本远低于引入任何平台。

## 5. 现有「问数」接入四种形态与代价

前提：问数必须保持**黑盒**。一旦把 `run_sql / find_column / kb_search` 拆给平台去编排，四类守卫（时间范围、权限、单位、数字必须有工具出处）就失去拦截点——因为守卫的生效位置是"**每次工具调用返回后、模型下一次生成前**"，这属于主循环内部，而平台不开放这个钩子。【推断，基于各平台扩展文档的能力边界】

| 接入形态 | 适用平台 | 做法 | 代码量 | 守卫是否保留 | 代价 |
|---|---|---|---|---|---|
| **A. HTTP/OpenAPI 工具（黑盒 `ask(question)`）** | Dify、FastGPT、Coze、MaxKB、Open WebUI、n8n、BISHENG | FastAPI 加一个 `/agent/ask` 路由（已有则直接复用），把 OpenAPI 3 schema 贴进平台"自定义工具" | 后端 ~30 行；平台侧填表 | ✅ 完整保留（守卫留在 FastAPI 内） | **0.5–2 人日** |
| **B. MCP Server** | Dify（MCP 客户端）、Open WebUI、MaxKB、AgentScope、BISHENG（MCP 支持程度 未核实） | 用 fastmcp 把 `ask` 包成 MCP tool，stdio 或 sse | ~60 行 | ✅ 保留 | **1–2 人日** |
| **C. 外部 API 节点（工作流里当一步）** | FastGPT、Dify、n8n、BISHENG | 工作流里排 [用户输入]→[HTTP 调 ask]→[出报告]，不做多轮 | 0（平台配置） | ✅ 保留但丢失多轮追问 | **0.5 人日** |
| **D. 把工具拆给平台、由平台跑 ReAct** | Dify/FastGPT/Coze 的 Agent 节点 | 把 run_sql 等注册为平台工具，平台负责循环 | 中 | ❌ **守卫全废**（无法在工具返回后插校验） | 不建议 |

**关键判断**：A/B/C 三种都是"平台只当壳，问数还是自己的引擎"——那么引入平台的收益就只剩"可视化编排 + 现成会话 UI + 用户/权限管理"，而代价是多一套服务、多一份许可证审查、多一条离线运维链路。**这笔账只有在"要给领导演示工作台/要给多个部门开应用"时才划算。**

## 6. 推荐路线（分三层，按需启用）

**第 0 层（默认，强烈推荐）：不引入平台，扩展现有 FastAPI**

- 新增 `office/` 模块：`docx_from_template(template_id, fields)`、`pptx_from_outline(template_id, slides)`、`xlsx_from_dataset(dataset_ref)`，依赖 python-docx / python-pptx / openpyxl（都是 MIT/BSD，离线 wheel 可控）。
- 以 function tool 形式注册进现有主循环 → 守卫、审计、数字出处全部天然复用。
- 公文规范做成"模板 + 字段 schema"，不让模型碰版式。
- 工作量：**3–6 人日**（含 2 套模板 + 中文字体 + 出文件接口）；比任何平台接入都便宜，且零许可风险。

**第 1 层（可选，办公零件复用）**

- 直接引 `markdown-exporter`（Apache-2.0）当"Markdown → DOCX/PPTX"转换器，避免自己写转换层；它的 SKILL.md 形态也能直接当 agent skill 用。

**第 2 层（只在需要"平台化交付"时）：Dify 或 BISHENG 当办公前台**

- **Dify**：离线安装 `markdown-exporter` 插件包；把问数封装成单个自定义工具（形态 A）；守卫留在 FastAPI。**必须接受**：Dify 会接管对话/编排，问数的多轮追问体验要在 Dify 侧重新设计（否则用户感知变差）。
- **BISHENG**：唯一有原生 docx/pptx/xlsx 技能的，且是 Python 栈；但它把技能放在 `linsight` 智能体下，**要先做一次 PoC 验证"技能能否被普通助手调用"**（这是我这次没核实的最大空白）。
- **不要选**：Coze Studio（8 个月无 release + 五件套中间件 + 官方插件要外网）、Qwen-Agent（云端 code interpreter）、OpenManus（无权限无审计）、n8n 当主平台（非 OSI 许可 + 不是 agent 平台）、LangGraph/AutoGen（要重写主循环）。

3. **Coze Studio**：代码节点 Pyodide 是否可加载 docx 类包；自定义插件的鉴权与内网地址策略；审计日志能力。

5. **MaxKB**：函数库的依赖安装方式（能否 pip 装 python-docx）、MCP 支持、审计日志；《飞致云社区软件许可协议》是否在 GPL-3.0 之上叠加限制。
6. **SQLBot** 的确切许可证与"问数守卫"设计（字段权限/口径/审计）——建议单独做一次竞品拆解。
7. 所有平台的"多租户 + 审计日志"我只核到目录/功能名，**没有逐条读文档**；给领导交付前必须逐项验证（尤其：谁能看谁的会话、操作留痕保留多久、能否导出）。
8. `gongwen-draft` 无 LICENSE 文件；`official_document` 只有 5★；`onlyoffice-mcp-server` 只有 1★ —— 都不能作为生产依赖。
9. 本次 GitHub REST API 在后续请求中被限流（60 次/小时/IP），因此 langgraph/autogen/agentscope 等我只核到 `pushed_at` 与 license，**"最近一次 release tag 时间"只核到 Dify(v1.17.1, 2026-09-10)、Coze(v0.5.1, 2026-02-05) 两个**，其余以 commit 时间代表活跃度。
10. 网络可用性：`web_fetch` 可用（GitHub API / jsdelivr / 官方文档均可）；`raw.githubusercontent.com` 与部分文档站（docs.dify.ai、docs.fit2cloud.com 子路径）不可达或 404；容器内 `curl`/`Invoke-RestMethod` 因 schannel 凭证问题无法直连外网，故全部事实均经 `web_fetch` 取得。

---

## 8. 一句话结论

**这批平台里没有任何一个能"直接替换"现有 agent 主循环而不伤问数能力**——卡点不是挂工具（HTTP/OpenAPI/MCP 都能挂，0.5–2 人日），而是**平台把 ReAct 循环锁在自己服务里，不提供"每次工具调用后、模型再生成前"的钩子**，而你的时间范围/权限/单位/数字出处四类守卫必须长在这个位置；同时"内置办公技能"绝大多数只是代码解释器或第三方插件（FastGPT 的代码沙箱甚至 import 不到 python-docx），唯一天生带 docx/pptx/xlsx 技能的是 BISHENG，但它的技能可用范围仍有待 PoC 验证。**因此正解是：主循环不动，办公技能做成 FastAPI 内的模板化工具集；只有在"必须交付可视化工作台"时才上 Dify 或 BISHENG 当壳，并把问数整体封装成一个黑盒工具回调进来。**
