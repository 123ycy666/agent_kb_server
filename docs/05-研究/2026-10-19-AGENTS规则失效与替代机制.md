# AGENTS.md 类规则文件：为何失效、以及替代机制（一手来源调研）

调研日期：2026-10-19｜范围：仅回答 6 组问题｜全部结论标注证据等级并附可核查链接。

**证据等级图例**：`[论文]` 同行评审/arXiv 预印本实验；`[官方]` 厂商文档、规范、官方工程博客（含其自建数据分析）；`[博客]` 实践者/二手教程；`[推断]` 本报告在没有直接证据时的推论，明确标记。

## 结论摘要

1. 注入的指令越多、越密，单条遵从率确实下降；但"长"只是表层，真正致命的是**不可验证、互相冲突、重复强调**。证据等级：`[论文]`+`[官方]`（实体实验 + 官方维护建议，最强一档）。
2. AGENTS.md 里**该写的**是可验证的具体事实与边界；**该删的**是仓库综述、目录结构、泛泛原则——两篇 2026 年的对照实验显示这类内容不提升成功率，还多花 20% token。证据等级：`[论文]`（最强，但仅两篇、任务集有限）。
3. 凡是"必须在某个时刻发生"的事，写进提示词只是**建议**，必须改成 hook / 权限 / lint / CI 才算**强制**；Anthropic、OpenAI、Cursor 三家文档都用这个二分法。证据等级：`[官方]`（设计论证 + 机制存在性，无对照实验）。
4. 长会话漂移靠**落盘的目标 + 进度表 + 压缩后重注入**解决，不靠某句"记住原始目标"的提醒；有论文支持"提醒能压住漂移"。证据等级：`[论文]`+`[官方]`。
5. 删规则的证据链最硬，也最反直觉：官方原文是"啰嗦的 CLAUDE.md 会让 Claude **忽略你真正的指令**"。证据等级：`[官方]`（厂商经验，未公开数据）。

## 1. 长指令文件会不会让遵从度下降？

**1.1 位置效应有稳定的实验证据：开头和结尾好，中间差。**
`[论文]` Lost in the Middle 在 multi-document QA 与 key-value retrieval 上发现：相关信息出现在**开头或结尾**时表现最好，被迫从**中间**取信息时显著退化，即使模型标称长上下文也一样。
来源：https://arxiv.org/abs/2307.03172

**1.2 指令密度上升 → 遵从率下降，且偏向"靠前的指令"。**
`[论文]` IFScale 用 500 条关键词包含指令压测 20 个前沿模型：**最好的模型在 500 条满密度下只有 68%**，并观察到"3 种不同的退化曲线"和**对靠前指令的偏好（bias towards earlier instructions）**。
来源：https://arxiv.org/abs/2507.11538

**1.3 退化发生在远低于宣称上限的地方，而且与"任务难度"无关。**
`[论文]` 同任务加不同长度/类型/位置的 padding：推理性能在**远短于技术上限**时就开始明显退化，且每种变体都出现退化趋势。
来源：https://arxiv.org/abs/2402.14848

**1.4 Chroma 的 context rot：18 个模型、任务复杂度受控，输入变长性能就掉；干扰项（distractors）比无关内容更伤。**
`[论文/技术报告]` 关键细节：把 needle 固定在 11 个不同位置时**没发现明显位置差异**（NIAH 这个特定任务）；但"复述长序列"任务里，**唯一词越靠前越准**；LongMemEval 上"只给相关片段（约 300 token）"远好于"全量 113k token"。
来源：https://trychroma.com/research/context-rot

**1.5 Anthropic 官方把这件事讲成"注意力预算"，并给了"最小高信号 token 集"的原则。**
`[官方]` "context rot：随着上下文 token 数增加，模型从上下文中准确回忆信息的能力下降……上下文必须被当作有限资源，边际收益递减"。同一文还给出反例："团队常把一长串 edge case 塞进 prompt……**我们不建议这样做**"，并建议用少量典型示例代替规则堆砌。
来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

**1.6 Anthropic 官方对 CLAUDE.md 篇幅的明确建议：目标 200 行以内，超了会降低遵从。**
`[官方]` "Size: target under 200 lines per CLAUDE.md file. **Longer files consume more context and reduce adherence.**"；另一处："Files over 200 lines consume more context and may reduce adherence."；并且 @import 只是组织结构，**不会降低上下文成本**（导入文件同样在启动时加载）。
来源：https://code.claude.com/docs/en/memory

**1.7 官方最狠的一句（本条是本报告"加规则反而更差"的总纲）：啰嗦的规则文件会让模型忽略你真正的指令。**
`[官方]` "Keep it concise. For each line, ask: *'Would removing this cause Claude to make mistakes?'* If not, cut it. **Bloated CLAUDE.md files cause Claude to ignore your actual instructions!**"；另一处把它列为典型反模式："The over-specified CLAUDE.md. If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise."
来源：https://code.claude.com/docs/en/best-practices

**1.8 官方对"写什么/不写什么"给了正反清单（可直接当裁剪标准）。**
`[官方]` 该写：Claude 猜不到的 bash 命令、与默认不同的代码风格、测试指令与 test runner、仓库礼仪（分支/PR 约定）、项目特有的架构决策、开发环境怪癖、非自明的坑。不该写：读代码就能知道的、语言标准约定、详细 API 文档（给链接）、**经常变化的信息**、长解释/教程、逐文件的代码库描述、以及"写干净代码"这种自明实践。
来源：https://code.claude.com/docs/en/best-practices

**1.9 需要注意的证据边界：我没有找到"针对 CLAUDE.md/AGENTS.md 单条指令遵从率 vs 文件长度"的直接实验。**
`[推断]` 现有证据是三条间接链：①长上下文召回退化（1.1/1.3/1.4）；②指令密度 → 遵从退化（1.2）；③厂商基于内部观察的经验结论（1.6/1.7，无公开数据）。因此"文件越长，某一条越不被遵守"目前是**合理外推，不是已发表结论**。

## 2. AGENTS.md 的官方规范与社区最佳实践

**2.1 AGENTS.md 是开放格式，规范极简：纯 Markdown，无必填字段；嵌套时"最近的赢"，且用户对话里的显式指令覆盖一切。**
`[官方]` FAQ 原文："The closest AGENTS.md to the edited file wins; **explicit user chat prompts override everything**."；大 monorepo 用嵌套文件（"at time of writing the main OpenAI repo has 88 AGENTS.md files"）；站点称已有 60k+ 开源项目使用。推荐章节：项目概览、构建与测试命令、代码风格、测试说明、安全注意事项。
来源：https://agents.md/

**2.2 OpenAI Codex 的发现与优先级规则是可执行的（不是建议）：全局 `~/.codex/AGENTS.md` → 从项目根逐级下到 cwd，每级取 `AGENTS.override.md` 或 `AGENTS.md`（每目录至多一个），按"根在前、近的在后"拼接，故**近的覆盖远的**；空文件跳过；合并体积到 `project_doc_max_bytes`（默认 **32 KiB**）就**停止添加并截断**。**
`[官方]` 含义：规则文件不是"想加多少加多少"，超限是**静默丢弃后面内容**。
来源：https://learn.chatgpt.com/docs/agent-configuration/agents-md

**2.3 Codex 官方对规则写法的要求：短、说清要拦的行为 + 安全路径/例外，格式与 lint 交给 CI。**
`[官方]` "Keep rules concise, explain the behavior to flag and any safe path or exception, and **reserve formatting and lint checks for CI**."
来源：https://learn.chatgpt.com/docs/agent-configuration/agents-md

**2.4 大规模内容统计（厂商自建分析，2,500+ 仓库）：写得好的文件有共同结构——命令放前面、给真实代码示例、明确边界、说清技术栈版本；覆盖 6 个核心区的属头部。**
`[官方]`（GitHub 官方博客，数据为其自有分析）"Put commands early"、"Code examples over explanations: one real code snippet beats three paragraphs"、"Set clear boundaries… **'Never commit secrets' was the most common helpful constraint**"、"Cover six core areas: commands, testing, project structure, code style, git workflow, and boundaries"；边界建议用三层："Always do / Ask first / Never do"；并强调"文件是靠迭代长大的，不是靠提前规划"。
来源：https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/

**2.5 反直觉的实证结论：上下文文件总体上并不提升任务成功率，却平均多花 20% 以上推理成本。**
`[论文]` 覆盖 SWE-bench 任务（LLM 生成的上下文文件）与含开发者提交上下文文件的真实仓库：**context files 一般并不提高成功率，而推理成本平均上升 20%+**；跨模型、跨 agent、两类文件都成立。
来源：https://arxiv.org/abs/2602.11988

**2.6 同一篇进一步定位了"哪部分没用"：指令本身被很好地遵守了，没用的是"仓库综述"。**
`[论文]` "instructions in the context files **are well followed** by coding agents, **repository overviews**, although popular and recommended by model providers, **are not helpful**. … context files are useful for specifying non-standard coding practices". 即：**非标准约定有效，厂商推荐的"项目概览/架构说明"被数据否掉**。
来源：https://arxiv.org/abs/2602.11988

**2.7 更严格的对照实验（Claude Code vs Codex，17 任务、288 次运行、gold-test 评测）：注入策略对正确率没有可测影响（等价检验上界 ≤10–15pp）。**
`[论文]` 原因分析："agents fail on **implementation skill**—feature design, pattern selection, exact wiring—**not missing repository knowledge** that a context file could supply"；并做了 manipulation probe 验证"给了真实上下文也没把 near-miss 变通过"。
来源：https://arxiv.org/abs/2607.27250

**2.8 因此 2.5–2.7 与 2.1–2.4 的官方建议之间存在**真实张力**，不是我不一致。**
`[推断]` 合理解读：官方推荐来自"大量失败案例的经验归纳"，两篇论文测的是"平均任务成功率"这一窄口径（且任务集中在成熟开源仓库，agent 本身可从代码里恢复知识）。两者共同支持的结论是：**上下文文件的价值只在"代码里读不出来的约定"，其余部分是净成本**。

**2.9 社区/二手清单**：`[博客]` 这类"该写/不该写"清单在二手教程里大量存在，但内容与 1.8 / 2.4 高度重合，未提供额外一手证据，本报告不单独采信。

## 3. 散文式规则 vs 确定性执行（谁真的管用）

**3.1 Anthropic 官方把二分法写死了：CLAUDE.md 是"上下文"，不是"强制配置"；要拦动作必须用 PreToolUse hook。**
`[官方]` "Claude treats them as context, **not enforced configuration**. **To block an action regardless of what Claude decides, use a PreToolUse hook instead.** The more specific and concise your instructions, the more consistently Claude follows them."
来源：https://code.claude.com/docs/en/memory

**3.2 同一页直接承认提示词无法保证严格遵从。**
`[官方]` "CLAUDE.md content is delivered as a user message after the system prompt … Claude reads it and tries to follow it, but **there's no guarantee of strict compliance**, especially for vague or conflicting instructions."
来源：https://code.claude.com/docs/en/memory

**3.3 官方给出的替换规则很机械：凡是"必须在某时发生"的，写成 hook。**
`[官方]` "If the instruction is something that **must run at a specific point**, such as before every commit or after each file edit, **write it as a hook instead**. Hooks execute as shell commands at fixed lifecycle events and **apply regardless of what Claude decides to do**."；"Use hooks for actions that **must happen every time with zero exceptions**."
来源：https://code.claude.com/docs/en/memory ｜ https://code.claude.com/docs/en/best-practices

**3.4 官方对 hook 的定义就是"确定性控制"。**
`[官方]` "Hooks are user-defined shell commands … which gives you **deterministic control**: certain actions always happen **rather than relying on the LLM to choose to run them**. Use hooks to enforce project rules…"；另一处对照句："**Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens.**"
来源：https://code.claude.com/docs/en/hooks-guide ｜ https://code.claude.com/docs/en/best-practices

**3.5 还有第三层：不是所有拦截都该用 hook，硬允许/硬拒绝要用权限系统。**
`[官方]` "Because the `if` filter is best-effort, **use the permission system rather than a hook** to enforce a hard allow or deny."；同页对照表把"阻断特定工具/命令/路径"指向 `permissions.deny`，"行为指令"指向 CLAUDE.md。
来源：https://code.claude.com/docs/en/hooks ｜ https://code.claude.com/docs/en/memory

**3.6 产品已把"完成标准"做成机制：TaskCompleted hook 用于"关闭任务前必须过测试/lint"，官方给了跑测试失败就阻止完成的示例；Stop hook 可以阻止 agent 收尾（有 8 次连续续跑上限防死循环）。**
`[官方]` "Use this to **enforce completion criteria** like passing tests or lint checks before a task can close."；Stop hook 的 `decision: "block"` "prevents Claude from stopping"；另有 `stop_hook_active` 与 8 连击上限。注意：`async: true` 的 hook **不能**拦截（"Async hooks can't block or control Claude's behavior"）。
来源：https://code.claude.com/docs/en/hooks

**3.7 Cursor 提供同一套生命周期面（会话开始/结束、工具前后、shell 前后、提交前、压缩前、stop），并明确"可以观察、阻断、修改行为"，还能直接加载 Claude Code 的 hook。**
`[官方]` "They run before or after defined stages of the agent loop and **can observe, block, or modify behavior**"；hook 列表含 `sessionStart`、`preToolUse`、`beforeShellExecution`、`beforeSubmitPrompt`、`preCompact`、`stop` 等；"Cursor supports loading hooks from third-party tools like Claude Code."
来源：https://cursor.com/docs/hooks

**3.8 实践者结论（这一条我必须诚实标注）：我没有找到"流程写提示词 vs 用 hook/CI 强制"的对照实验。**
`[论文]` 缺位。现有最硬的证据是厂商文档的确定性论证（3.1/3.4）+ 机制存在性（3.6/3.7），属于**设计论证 + 产品事实**，不是受控实验。
`[推断]` "必须先写计划"这类**时序约束**用 hook 更可靠，机制上的理由很朴素：hook 在模型动作发生前执行并可以直接阻断（exit 2 / `permissionDecision: deny`），而提示词只能改变"模型愿意做什么"的概率分布。

## 4. 长会话中的目标漂移（goal drift）

**4.1 有论文把"context drift"形式化，并给出乐观结论：漂移是有界均衡，不是必然崩坏；**简单提醒干预能可靠降低偏离**。**
`[论文]` 把漂移定义为"测试模型与目标一致的参考模型之间逐轮 KL 散度"，在合成长程改写与 τ-Bench 类用户-代理模拟上测量："stable, noise-limited equilibria rather than runaway degradation"，且"simple **reminder** interventions reliably reduce divergence"。
来源：https://arxiv.org/abs/2510.07777

**4.2 Anthropic 官方给长任务三件套：压缩（compaction）、结构化笔记、子代理；并明确"待办列表/NOTES.md"就是最小成本的目标持久化。**
`[官方]` "Like Claude Code creating a to-do list, or your custom agent maintaining a **NOTES.md** file, this simple pattern allows the agent to track progress across complex tasks"；压缩要"保留架构决策、未解决 bug、实现细节"，丢弃冗余工具输出；"overly aggressive compaction can result in the loss of subtle but critical context"。
来源：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

**4.3 压缩会把"对话里的临时指令"抹掉，但**从磁盘重注入的东西会活下来**——这就是官方的 re-anchor 机制。**
`[官方]` 压缩后仍存活：项目根 CLAUDE.md 与无路径作用域的 rules（**从磁盘重注入**）、auto memory（重注入）、**plan mode 里写的计划（从磁盘重注入）**、最近改过的至多 5 个文件（重读）、已调用技能的正文（有 token 上限）、匹配 `compact` 来源的 **SessionStart hook（其输出被加入压缩后上下文）**。
来源：https://code.claude.com/docs/en/context-window ｜ https://code.claude.com/docs/en/memory

**4.4 官方给的诊断句：压缩后某条指令消失，说明它当初只存在于对话里，或在不一定会重载的嵌套文件中。**
`[官方]` "If an instruction disappeared after compaction, it was given only in conversation, lives in a nested CLAUDE.md that hasn't reloaded yet, or is a path-scoped rule that hasn't matched a file since. **Add conversation-only instructions to CLAUDE.md to make them persist.**"
来源：https://code.claude.com/docs/en/memory

**4.5 压缩行为本身可以用一条规则来约束（这是少数"该写进提示词"的规则）。**
`[官方]` 示例："When compacting, always preserve the full list of modified files and any test commands"。
来源：https://code.claude.com/docs/en/best-practices

**4.6 OpenAI 的做法最具体：AGENTS.md 只留一句指针，真正的目标状态放进 `PLANS.md`（ExecPlan），并把"不要问下一步、直接推进到下一个里程碑"写进流程。**
`[官方]` AGENTS.md 里只有："When writing complex features or significant refactors, use an ExecPlan (as described in .agent/PLANS.md) from design to implementation."；PLANS.md 要求"**do not prompt the user for 'next steps'; simply proceed to the next milestone**"、"it should always be possible to **restart from _only_ the ExecPlan** and no other work"；必备章节含 `Progress`（带时间戳的勾选清单）、`Surprises & Discoveries`、`Decision Log`、`Outcomes & Retrospective`；该文件"enabled Codex to work for more than seven hours from a single prompt"。
来源：https://learn.chatgpt.com/cookbook/articles/codex_exec_plans

**4.7 Codex 侧还有一个容易踩的坑：自定义术语不会被模型自动理解，必须在 AGENTS.md 里定义。**
`[官方]` "Here, we call it an 'ExecPlan'. **Note that this is an arbitrary term, Codex has not been trained on it.**"
来源：https://learn.chatgpt.com/cookbook/articles/codex_exec_plans

## 5. "一直打补丁不找根因"与"硬编码常量逐步膨胀"

**5.1 两个现象在软件工程里都有名有姓。**
`[官方]`（Fowler 站点一手页）**Code Smell**："A code smell is a surface indication that usually corresponds to a deeper problem in the system."
来源：https://martinfowler.com/bliki/CodeSmell.html
`[官方]` **Replace Magic Number with Symbolic Constant**（魔法数字 → 命名常量），官方示例即把 `9.81` 换成 `STANDARD_GRAVITY`。
来源：https://refactoring.com/catalog/replaceMagicNumberWithSymbolicConstant.html
`[官方]` **YAGNI**："some capability we presume our software needs in the future should not be built now"。
来源：https://martinfowler.com/bliki/Yagni.html

**5.2 Shotgun Surgery / Primitive Obsession 这两个命名，我没找到一手可直链页面。**
`[博客]` 只有二手站点给出定义（Shotgun Surgery = "a single change is made to multiple classes simultaneously"；Primitive Obsession 属同一 smell 目录）。原始出处是 Fowler《Refactoring》书中的 smell 目录，其官方页面未列出该词条，故按二手采信。
来源：https://refactoring.guru/smells/shotgun-surgery ｜ https://refactoring.guru/smells/primitive-obsession
`[未找到一手来源]` **5 Whys**：未找到 Toyota 或原作者的一手页面，本报告不把它当论据使用。

**5.3 官方对 agent 的"先复现再修"是明确指令，不是原则。**
`[官方]` 提示词范例："users report that login fails after session timeout … **write a failing test that reproduces the issue, then fix it**"；另一条："**address the root cause, don't suppress the error**"。
来源：https://code.claude.com/docs/en/best-practices

**5.4 OpenAI 把"失败测试转通过"写成计划里的验收措辞。**
`[官方]` "the new test <name> **fails before the change and passes after**"；"Every ExecPlan must produce a demonstrably working behavior, not merely code changes to 'meet a definition'"；验收要"phrased as behavior a human can verify"。
来源：https://learn.chatgpt.com/cookbook/articles/codex_exec_plans

**5.5 "打补丁不找根因"可以被做成机制，而不是写成守则：把完成/收尾事件绑定测试。**
`[官方]` TaskCompleted hook 的用途就是"关闭任务前必须过测试/lint"，官方示例直接跑测试并在失败时阻止标记完成；Stop hook 同理。也就是说**"你说完成但测试没过"这件事可以被工具拒绝**，不需要靠"不要说谎"的规则。
来源：https://code.claude.com/docs/en/hooks

**5.6 常量膨胀这类事最适合交给 linter，而不是交给提示词。**
`[官方]` ESLint 有 `no-magic-numbers` 规则可确定性执行。
来源：https://eslint.org/docs/latest/rules/no-magic-numbers
`[推断]` 推论：凡是"能被静态检查表达的规则"，写进 AGENTS.md 只是把确定性问题降级成概率问题；正确做法是写进 lint 配置（并能被 CI 跑）。

## 6. 反面证据：规则本身的副作用

**6.1 规则互相冲突时，模型不是报错，而是随便挑一个。**
`[官方]` "**if two instructions contradict each other, Claude may pick one arbitrarily.** Review your CLAUDE.md files, nested CLAUDE.md files … periodically to remove outdated or conflicting instructions."；故障排查页重复："If two files give different guidance for the same behavior, Claude may pick one arbitrarily."
来源：https://code.claude.com/docs/en/memory

**6.2 重复强调会互相抵消——这条直接对应"每轮都强调一遍"的做法。**
`[官方]` "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. **If you emphasize many lines, none of them stands out.**"
来源：https://code.claude.com/docs/en/best-practices

**6.3 "加了规则还是犯同样的错"被官方直接解释为"文件太长，规则被埋了"。**
`[官方]` "**If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost.** If Claude asks you questions that are answered in CLAUDE.md, the phrasing might be ambiguous."
来源：https://code.claude.com/docs/en/best-practices

**6.4 官方把"规则要像代码一样被测试和删除"写成了明确流程。**
`[官方]` "**Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts.**"；并有自动化审计入口：`/doctor prompt-audit` 会找出"为旧模型写的指令、引用了不存在的文件/命令、文件之间互相矛盾"的问题，且**默认只给报告不改文件**；`/doctor` 还会建议删掉"Claude 能从代码库自行推导"的内容（目录结构、依赖清单、架构综述），保留坑、理由、与非默认约定。
来源：https://code.claude.com/docs/en/best-practices ｜ https://code.claude.com/docs/en/memory

**6.5 规则的成本是可量化的：不提升成功率，+20% 推理成本。**
`[论文]` 见 2.5。另一篇对照实验在等价检验下"没有可测影响"。这说明"多加一条"的期望收益经常是 **0 或负**。
来源：https://arxiv.org/abs/2602.11988 ｜ https://arxiv.org/abs/2607.27250

**6.6 "为了满足规则而做无关的事"（例如为满足"要写文档"而产出无关文档）：我没有找到直接实证。**
`[未找到一手来源]` 这是本报告唯一被明确问及但**没有直接证据**的因果链。
`[推断]` 支持它成立的间接材料有三条：①规则饱和会让单条规则"不突出"（6.2）；②指令越多单条遵从越低、且偏向靠前（1.2）；③上下文文件平均只增加成本（6.5）。因此"把'别写无关文档'当又一条规则加进去"属于**同层级加规则**，预期收益接近 0；把它降级为"只允许写到指定目录 + 由检查脚本比对产物清单"才是换层级。

**6.7 自指规则（"不要写无关文档"本身是一条文档）不是文字游戏，而是可观测的机制问题。**
`[推断]` 依据 2.2：Codex 的合并上限（默认 32 KiB）会**静默截断**——自指条目消耗的是与真规则同一个预算；依据 3.3：它不会被任何机制执行，只增加一条待遵从项。

## 对 DeepSeek Harness 的可用落点

### 先给三个本机实测事实（不是估算）

| 事实 | 数值 | 怎么测的 |
|---|---|---|
| 当前 `~/.dsh/AGENTS.md` 规模 | 6,608 字节 / 37 行（约 2,200 汉字） | `Get-Item` + 按行切分 |
| 历史备份 | 20,728 → 13,019 → 6,608 字节（10/10 → 10/13 → 10/19） | `Get-ChildItem ~/.dsh/AGENTS.md*` |
| 宿主是否支持 Claude Code 式生命周期 hook | **未在打包产物中找到 `PreToolUse`/`SessionStart`/`beforeToolCall` 等字符串** | 对 `app.asar`（161 MB）做 `Select-String -SimpleMatch` 探测 |

结论：**文件已经在正确的收缩方向上了（20.7 KB → 13.0 KB → 6.6 KB，三次备份实测），当前长度远低于官方 200 行上限**——所以"再砍一半"的理由不该是"超长"，而该是下面三条：每行是否**可验证**、是否**与技能重复**、是否本该是**机制**。

同时，"DSH 没有 hook"这条意味着：Claude Code 那套"把时序约束搬出提示词"的最强手段**在本机不可用**，只能用次优替代（工具/脚本/CI/权限），不要用"更重的措辞"假装解决了——那正好落进 6.2 的坑。

### 该保留什么（建议压到 15 行以内 + 3 张小表）

| 保留 | 理由 | 风险 |
|---|---|---|
| §0 技能默认调用表（现状保留，可再压） | 这是**指针**而非规则：把"何时用哪个能力"从散文里转成可查表，符合 4.6 的"AGENTS.md 只放指针"模式 | 表越长越像文档；若技能描述本身够清楚，部分行可删（技能目录里 `description` 已可见） |
| §1 五条判据中**能一眼判真假**的两条（"不假报完成"、"数字先定口径"） | 1.8 明确"具体到可验证"才有效；这两条有客观判据 | 与"verification-before-completion / test-evidence"技能重复的部分，应只留指针 |
| §5 环境事实（代理、镜像、路径、成本口径） | 属于 1.8 的"Claude 猜不到的事实"，且是**只读参考**，不参与行为竞争 | 会随环境腐化，需带日期；`/doctor prompt-audit` 类审计在本机没有，得手动复核 |
| §4 记忆分层（`~/.dsh/memory` vs `.dsh/memory`） | 这是**机制**（落盘位置），不是态度要求 | 索引文件 `MEMORY.md` 会膨胀，需要和 4.2 的压缩纪律一起管 |

### 该改成机制/工具强制什么

| 现在写成规则的 | 改成 | 理由 | 风险 |
|---|---|---|---|
| "说完成/通过必须贴本轮真实输出" | 已有 `verification-before-completion` + `test-evidence` 技能：把"落盘位置 + 字段"写死在技能里，AGENTS.md 只留一句"命中即调" | 3.4/3.5：能被工具判定的，不要靠自觉；这是本机最接近 hook 的替代面（技能 = 可复用的确定性流程） | 技能仍需模型主动调用；若模型跳过调用，效果等价于没写。**这是本机最大的机制缺口** |
| "不过分设计"、"解释只说重点"、"不用选择题代替思考" | **删掉**，或降级为 `karpathy-guidelines` / `brainstorming` 技能内的检查项 | 6.1/6.2：形容词式规则不可判定，且互相竞争注意力；1.8 把"写干净代码"这类列为明确不该写 | 删后短期可能更啰嗦；用"交付前自检清单"落在技能里补偿 |
| "先写会失败的测试" | 保留一句指针，执行细节交给 `test-driven-development` 技能；可验证部分改为"贴出 failing→passing 的两段输出" | 5.3/5.4 官方都是这个结构：规则只定义**可观测证据**，流程在别处 | 无真实测试框架时无法执行，需接受"人工贴输出"的弱化版 |
| "≥2 文件/≥3 步先落计划"（已删）与跨会话交接 | 用 **ExecPlan 式计划文件**：路径固定（如 `docs/04-计划/<date>-<slug>.md`），含 `Progress`（带时间戳勾选）/`Decision Log`/`Outcomes` | 4.6 是目前唯一有"7 小时单 prompt"实证的官方做法；且压缩后能从磁盘重注入（4.3） | 计划文件自己会膨胀；需规定"完成即归档、只保留当前一份" |
| "常量不要硬编码/别打补丁" | **lint 规则**（`no-magic-numbers` 一类）+ CI；DSH 场景下至少要求"新增魔法数必须写进同一常量文件" | 5.6：静态可判定的问题不该用概率手段解决 | DSH 侧要真的跑 lint，否则只是换了个地方写愿望 |
| 长会话漂移 | 每轮/每次压缩后**重读计划文件的 `Progress` 段**（而不是重读 AGENTS.md） | 4.3：AGENTS.md 与计划文件在压缩后都从磁盘重注入，但计划文件承载"本次目标"，AGENTS.md 承载"永久偏好"——两者混用会让目标信息被永久规则稀释 | 没有自动 compaction hook 可用时，需人工在轮次边界触发 |

### 该干脆删掉什么

| 删 | 理由 | 风险 |
|---|---|---|
| §2 "已删的仪式"整节 | 它是**元信息**（记录曾经删过什么），每轮注入只消耗注意力，不改变行为；属于 6.7 的自指条目 | 失去"别再走回头路"的提醒；可移到 `~/.dsh/memory/` 的一条 feedback memory（不注入每轮） |
| 任何"IMPORTANT/必须/一定"堆叠 | 6.2 原文：强调太多条 = 没有一条突出 | 短期会感觉"没那么强调了" |
| 与技能正文重复的流程细节（如记忆 YAML 字段、四段汇报格式） | 1.8 不该写"读代码/文档就能知道的"；技能正文已有一份，两份必然漂移，最终触发 6.1 的"随便挑一个" | 需要在技能里补全，否则丢知识 |

### 一次可执行的最小改法（按收益排序）

1. **把"每轮注入的东西"和"本次任务的东西"物理分开**：AGENTS.md 只留永久偏好与指针（目标 ≤15 行），本次目标写进计划文件。（依据 4.3/4.6）
2. **把所有"时序类"要求改成"可观测证据"**：不写"先写计划"，写"交付时贴出计划文件路径 + Progress 前后两段"。（依据 3.3/5.3，且绕开本机无 hook 的限制）
3. **引入一条自动审计**：本机没有 `/doctor prompt-audit`，等价物是"每周跑一次：AGENTS.md 每行能否举出一个它防住的具体错误，举不出的删"——把 6.4 的官方流程手工化。（依据 6.4）

### 我不建议做的事

- **不要**因为"DSH 没有 hook"就退回去加更严厉的措辞：证据（3.1/3.2/6.2）显示这条路的期望收益接近 0，成本是真实的注意力预算。
- **不要**把 AGENTS.md 当知识库用：2.6 的实证是"仓库综述类内容不提升成功率"，2.5 是"+20% 成本"。知识该落 `memory/` 或技能，不该落每轮注入的文件。
- **不要**指望从 AGENTS.md 里删掉条目就能修好"实现能力不足"：2.7 的结论是 agent 失败在 **implementation skill**（特性设计、模式选择、接线），而那部分只能靠"可验收的规格 + 失败测试"补，不靠规则。
