# 本地小模型 + 多工具 + 复杂 schema 下的 function calling 可靠性：公开证据盘点

抓取时间：2026-10-21（+08:00）。标注约定：**【实测】= 来源里给出的测量数字**；**【观点】= 来源作者的判断/建议**。所有 URL 均为本次实际抓取过的页面。

## A. BFCL（Berkeley Function Calling Leaderboard）当前版本与分项口径

1. **当前榜单版本是 V4，不是 v3。** 榜单页标题为 "Berkeley Function Calling Leaderboard (BFCL) V4"，页面标注 `Last Updated: 2026-04-12`，评测用 commit `f7cf735`，复现方式 `pip install bfcl-eval==2025.12.17`。来源性质：官方榜单页 — https://gorilla.cs.berkeley.edu/leaderboard.html

2. **V4 总分权重（官方给的百分比加权，我照抄）**：`Overall = Agentic×40% + Multi-Turn×30% + Live×10% + Non-Live×10% + Hallucination×10%`。各主类样本数：Agentic 665（Web Search 200 + Memory 465）、Multi-Turn 800、Live 1351、Non-Live 1150、Hallucination 1122。来源性质：官方 blog（BFCL V4 Part-1）— https://gorilla.cs.berkeley.edu/blogs/15_bfcl_v4_web_search.html

3. **你问的三个子项，在 V4 里的官方条目数与样本数**（这决定分项数字的噪声大小）：
   - 多函数（Multiple）：非 live 200 条；live 1053 条。
   - 并行调用（Parallel）：非 live 200 条；**live 只有 16 条**。
   - 并行+多函数（Parallel Multiple）：非 live 200 条；**live 只有 24 条**。
   - Irrelevance detection：非 live 240 条 + live 882 条（Hallucination Measurement 主类共 1122 条）。
   来源性质：官方 blog（同上）+ 官方榜单页 — https://gorilla.cs.berkeley.edu/blogs/15_bfcl_v4_web_search.html

4. **【推断，非实测】live parallel 只有 16/24 条样本，意味着单个用例 = 6.25 / 4.17 个百分点**。所以拿 live parallel 的分项分差（例如 7B 与 GPT-4o 差 20 分）去论证"并行能力差一截"，统计上非常脆弱；要比较并行调用应优先看非 live 的 parallel(200) / parallel_multiple(200)，或用 live multiple(1053) 当多函数代理指标。这个结论是我从官方样本数推出来的，不是榜单作者说的。

5. **BFCL 的论文出处**：ICML 2025，PMLR 267:48371-48392，标题 "The Berkeley Function Calling Leaderboard (BFCL): From Tool Use to Agentic Evaluation of Large Language Models"（Patil, Mao, Yan, Ji, Suresh, Stoica, Gonzalez）。**该论文没有 arXiv 版本**（arXiv:2502.18971 是同名不同文的行星科学论文，已核）。来源性质：会议论文集 — https://proceedings.mlr.press/v267/patil25a.html

6. **榜单表格是前端 JS 渲染的，静态抓取拿不到分数**：`leaderboard.html` 的 HTML 里只有表头说明（"Click on column header to sort"），没有任何模型-分数行。所以任何声称"从 BFCL 官网抄到某模型 parallel 子项 89.5"的说法，都需要给出可复核的二次入口（截图/导出 CSV/bfcl-eval 自跑）。来源性质：官方榜单页实测 — https://gorilla.cs.berkeley.edu/leaderboard.html

7. **BFCL 论文 PDF 在本环境的可达性**：PMLR 页面的 PDF 链接指向 `raw.githubusercontent.com/mlresearch/v267/main/assets/patil25a/patil25a.pdf`，该域名在本会话 DNS 解析失败；OpenReview PDF 有反爬验证页。**因此论文表格数字本轮未取到**（详见文末「未核实」）。来源性质：论文集页面 — https://proceedings.mlr.press/v267/patil25a.html

8. **BFCL 官方对"格式敏感度"的口径**：Format Sensitivity（5200 条 = 26 种配置 × 200 用例）只对 **prompt（非 FC）模型**计分，不计入 FC 模型总分。含义：本地小模型如果靠 vLLM/EvalScope 以"prompt 模式"接进去，它在 BFCL 上被衡量的是另一套东西，与 OpenAI 兼容端点上的 tool_calls 行为不可直接比。来源性质：官方榜单页 — https://gorilla.cs.berkeley.edu/leaderboard.html

9. **EvalScope 的 BFCL-v4 复现口径（可用于自己跑小模型分项分）**：dataset id 指向 gorilla 仓库的 `berkeley-function-call-leaderboard`，总样本 5,106，按 subset 给全了（`irrelevance` 240、`live_irrelevance` 884、`live_multiple` 1053、`live_parallel` 16、`live_parallel_multiple` 24、`multiple` 200、`parallel` 200、`parallel_multiple` 200、`memory_kv/rec_sum/vector` 各 155、`multi_turn_*` 各 200、`web_search_base/no_snippet` 各 100），并支持 `is_fc_model` 开关。来源性质：第三方评测工具官方文档（ModelScope EvalScope），**不是榜单本身** — https://evalscope.readthedocs.io/en/v1.6.0/benchmarks/bfcl_v4.html

10. **结论（就你 A 节最关心的问题）**：BFCL 官方**没有**公布"7B~14B 模型 vs GPT-4o/Claude"的分项差值摘要；榜单是逐模型一行，且表格动态渲染。要做这个对比只有两条路：① 在 BFCL 站点上人工读数并截图；② 用 `bfcl-eval` 本地跑同一 commit 自测。本轮两条都没能产出可引用的数字，故**不给任何小模型 BFCL 分项分数**。

## B. 工具数量增加导致准确率下降：公开的量化证据

1. **RAG-MCP（arXiv:2505.03275）——本轮找到的最直接的"工具多→选错"量化实验。** 设计：给模型 N 个 MCP schema，其中 1 个正确、N−1 个干扰项，N 从 1 扫到上千（论文写作"1 to 1 100 in 26 intervals"，LaTeX 渲染有粘连），干扰项来自 4,400+ 个公开 MCP server 池。选型准确率：**RAG（检索后只喂 top-1）= 43.13%，关键词匹配 = 18.20%，全量塞入（Blank）= 13.62%**；prompt token 1084 / 1646 / 2133.84。【实测】来源性质：论文 — https://arxiv.org/html/2505.03275v1 （abs：https://arxiv.org/abs/2505.03275 ）

2. **同一篇里"性能随工具池增大而崩"的读图结论（原文措辞）**：位置 < 30 时"success rates above 90%"；31–70 区间开始成片失败；"Beyond position ~100, purple dominates"。注意这是**按检索命中位置的逐次成功率热图**，不是"N 从 10 到 100 准确率线性掉 X%"的干净曲线。【实测+作者读图】来源性质：论文 — https://arxiv.org/html/2505.03275v1

3. **RAG-MCP 的局限（据其自述）**：base LLM 是 `qwen-max-0125`（云端大模型，不是 7B 本地模型），评测集是 MCPBench 的 web-search 子集，每 baseline 20 次试验、>10 对算通过，判分用 DeepSeek-v3 + Llama judge。**把它当"小模型也会这样"的证据是不成立的**，只能说方向一致。【事实】来源性质：论文 — https://arxiv.org/html/2505.03275v1

4. **Anthropic "advanced tool use"（Tool Search Tool 原始数字，本轮已核实原文）**：内部 MCP 评测上，**Opus 4 从 49% → 74%**，**Opus 4.5 从 79.5% → 88.1%**（开启 Tool Search Tool）。注意主语是 Claude 自家模型，不是小模型。【实测，厂商内部测试】来源性质：厂商工程/研究博客 — https://www.anthropic.com/research/advanced-tool-use

5. **同一篇给出"工具定义占多少 token"的实测账**：5 个 MCP server = GitHub 35 tools (~26K tok) + Slack 11 (~21K) + Sentry 5 (~3K) + Grafana 5 (~3K) + Splunk 2 (~2K) ≈ **58 tools / 55K tokens**；再加 Jira（单独 ~17K）逼近 100K+；"At Anthropic, we've seen tool definitions consume 134K tokens before optimization"。Tool Search Tool 后：**上下文占用 ~77K → ~8.7K tokens，保留 95% 上下文，token 降 85%**（191,300 vs 122,800）。【实测，厂商内部】来源性质：厂商博客 — https://www.anthropic.com/research/advanced-tool-use

6. **Anthropic 对失败模式的定性（这是【观点】，不是数字）**："The most common failures are wrong tool selection and incorrect parameters, especially when tools have similar names like `notification-send-user` vs. `notification-send-channel`." 并且明确给了启用阈值：**">10 tools"** 或 tool 定义 >10K tokens 时收益最大，**"<10 tools"** 收益小。—— 这条正好对上你报告里">10 个工具"的边界。【观点】来源性质：厂商博客 — https://www.anthropic.com/research/advanced-tool-use

7. **Anthropic "Tool Use Examples"（复杂参数处理的量化）**：内部测试中，给 3 个 `input_examples` 后准确率 **72% → 90%**；理由是 JSON Schema 只能表达"结构合法"，无法表达"什么时候填哪个可选字段、日期用 YYYY-MM-DD 还是 Nov 6"。这条直接对应你说的"复杂 JSON schema"。【实测，厂商内部】来源性质：厂商博客 — https://www.anthropic.com/research/advanced-tool-use

8. **Anthropic Programmatic Tool Calling（减少 tool 往返的量化）**：平均 token 43,588 → 27,297（−37%）；内部 knowledge retrieval 25.6% → 28.5%；GIA 46.5% → 51.2%。【实测，厂商内部】来源性质：厂商博客 — https://www.anthropic.com/research/advanced-tool-use

9. **Anthropic "Code execution with MCP"（code mode 的原始数字）**：把 MCP server 摊成文件树、由模型读文件按需加载，token 从 **150,000 → 2,000（−98.7%）**；并给出中间结果污染的例子：2 小时会议 transcript 在 context 里流两遍、多 50,000 tokens。同族还有 **Cloudflare "Code Mode"**（本文存在、URL 可访问，Anthropic 博客点名"published similar findings"，但页面正文被导航墙挤占，**本轮未取到它的数字**）。【实测，厂商口径】来源性质：厂商工程博客 — https://www.anthropic.com/research/code-execution-with-mcp 、 https://blog.cloudflare.com/code-mode/

10. **你清单里的 MCP-Bench 与 MCPEval：都存在，但都不是"工具膨胀"证据。** MCP-Bench（arXiv:2508.20453）规模口径是"28 representative live MCP servers spanning **250 tools**"、评 **20 个 LLM**，摘要只说 "persistent challenges"，**没有**工具数→准确率曲线；MCPEval（arXiv:2507.12806）是 Salesforce 的 MCP 端到端自动评测框架（5 个领域），摘要无工具数-性能数字。【规模事实】来源：论文 — https://arxiv.org/abs/2508.20453 、 https://arxiv.org/abs/2507.12806

11. **"Less is More: Optimizing Function Calling for LLM Execution on Edge Devices"**：确实存在（IEEE 文档号 10992798），主题是边缘设备上的 function calling 优化，与你"本地小模型"的场景最贴近。**本轮只核到题录与 IEEE 页面，正文与数字未取到**（付费墙）。来源性质：论文（IEEE） — https://xplorestaging.ieee.org/document/10992798

12. **业界应对架构（可写进报告的三种，均有官方来源）**：
    - **工具检索前置（RAG-MCP 式）**：只把 top-k 工具 schema 塞进 prompt。数字见第 1 条。
    - **按需加载 / 渐进披露（Anthropic Tool Search Tool + `defer_loading`）**：工具定义不进初始 prompt，模型先调 `tool_search_tool_regex_20251119` 再展开。数字见第 4、5 条。
    - **代码即工具（code mode / programmatic tool calling）**：MCP server 变文件树或 Python 函数，中间结果不进 context。数字见第 8、9 条。
    来源性质：厂商博客 + 论文（同上各条 URL）。

6. **是否"原样透传 JSON Schema"？—— 基本是，但恰恰因此撞上"合法 JSON Schema ⊄ OpenAI 接受子集"。** 已核实的失真：
   - 参数名被改写：`config`/`run_manager`/`callbacks` 这类与 LangChain `StructuredTool` 形参撞名的 MCP 参数会被改成 `name__mcp_arg` — https://github.com/langchain-ai/langchain-mcp-adapters/pull/566 ；用户侧症状见 issue #277（schema 里 `resourceType`，发出去 `resource_type`，服务端按 schema 解析失败）— https://github.com/langchain-ai/langchain-mcp-adapters/issues/277
   - 空对象 schema 缺 `properties: {}` 被 OpenAI 兼容端点 400：PR #343 — https://github.com/langchain-ai/langchain-mcp-adapters/pull/343 ，跟进 PR #406（复现场景正是 `MultiServerMCPClient` + Azure OpenAI gpt-4.1）— https://github.com/langchain-ai/langchain-mcp-adapters/pull/406
   - `outputSchema` 直接丢：issue #308 — https://github.com/langchain-ai/langchain-mcp-adapters/issues/308
   - mcpo 丢 `enum`：issue #245 — https://github.com/open-webui/mcpo/issues/245 ；`items` 为数组（合法 JSON Schema）时整条路由挂载崩溃：issue #296 — https://github.com/open-webui/mcpo/issues/296

7. **`$ref` / `$defs` / `additionalProperties` 的已知问题（openai-agents-python 是最集中的一处）**：
   - issue #4353：`strict_schema` 的 `$ref` sibling 合并是 parent-wins（静默反转接受集），且 `convert_schemas_to_strict` 在 17 种不可转换形状里**只有 2 种正确回落**（`uniqueItems`、`prefixItems`、tuple-form `items`、`additionalItems`、`patternProperties`、`propertyNames`、`unevaluatedProperties`、`not`、`if/then`、`contains`、`minProperties`、`dependentRequired`、嵌套 `$id`、多成员 `allOf`、`allOf:[{$ref},{$ref}]`、无 items 的 array 等）— https://github.com/openai/openai-agents-python/issues/4353 ；修复 PR #4354 — https://github.com/openai/openai-agents-python/pull/4354
   - `additionalProperties` 判定错（strict 要求 `false`）：issue #4114 — https://github.com/openai/openai-agents-python/issues/4114 ；PR #3927（`additionalProperties: {}` 因 `{}` falsy 漏检）— https://github.com/openai/openai-agents-python/pull/3927 ；PR #4277（无 properties 也无 additionalProperties 的 object 被补成 `false`，参数被锁死只能传 `{}`）— https://github.com/openai/openai-agents-python/pull/4277 ；PR #4151（inputSchema 根非 object 被当 strict 发出 → 上游 400）— https://github.com/openai/openai-agents-python/pull/4151

8. **strict 模式的 schema 约束（本轮核到的最硬的一手条文，来自 vLLM 官方文档而非 OpenAI 文档）**：vLLM 文档明写"define tool parameter schemas in the OpenAI strict-schema style"——① 每个 object 的 `parameters` 里 `additionalProperties` 设 `false`；② `properties` 里所有字段都标 required；③ 可选字段用 `{"type":["string","null"]}` 表达。另有一条关键警告：**"Most OpenAI-compatible clients and agent frameworks never set `strict` on their tools, so with `tool_choice="auto"` the model generates tool calls without any grammar and malformed markup can leak into the response."** 来源性质：推理引擎官方文档 — https://docs.vllm.ai/en/latest/features/tool_calling/

9. **选型结论（【我的判断】，非来源原文）**：想在 OpenAI 兼容端点（非 OpenAI 官方、非 Anthropic）上接 MCP，四个候选里只有 **mcp-use** 与 **openai-agents-python** 仍在活跃维护且真正走 `tools[].function` 路线；**langchain-mcp-adapters 已归档**（可继续用，但别指望修 issue）；**mcpo 的两次转译必然丢字段**；**FastMCP 的官方 OpenAI 路径在兼容端点上不可用**。所有方案都需要自己加一层"schema 降级 + 校验"，因为 MCP 的 `inputSchema` 允许的 JSON Schema 特性比 OpenAI 接受的多。

## D. vLLM / Ollama / Xinference 的官方要求与已知坑

### D1 vLLM（正文已逐段核对）

1. **两个 flag 的官方定义**：`--enable-auto-tool-choice` 是 **mandatory**（"Auto tool choice. It tells vLLM that you want to enable the model to generate its own tool calls when it deems appropriate."）；`--tool-call-parser` 选 parser；`--chat-template` 在 auto 下**可选**，指向能处理 `tool` role 与含历史 tool call 的 assistant 消息的模板（Hermes/Mistral/Llama 的 `tokenizer_config.json` 自带）。来源性质：官方文档 — https://docs.vllm.ai/en/latest/features/tool_calling/

2. **还支持自定义 parser**：`--tool-parser-plugin`（可选）注册用户 parser，注册名（`ToolParserManager.register_lazy_module(name=...)`）才是 `--tool-call-parser` 的取值，类名不参与。来源性质：官方文档（同页 "How to Write a Tool Parser Plugin"）— https://docs.vllm.ai/en/latest/features/tool_calling/

3. **⚠️ 对你清单的更正：`qwen25` 这个 parser 不存在。** 官方文档 Qwen 段落原文是"For Qwen2.5, the chat template in tokenizer_config.json has already included support for the Hermes-style tool use. Therefore, you can use the `hermes` parser"，即 `Qwen/Qwen2.5-*` 与 `QwQ-32B` 都用 `--tool-call-parser hermes`。同理 `functionary` 在当前 main 的文档与源码注册表里都不存在。来源性质：官方文档 — https://docs.vllm.ai/en/latest/features/tool_calling/

4. **文档里确实存在的 parser 名（按文档章节，共 32 个，节选与你相关的）**：`hermes`、`mistral`、`llama3_json`、`llama4_pythonic`、`pythonic`、`granite`、`granite4`、`granite-20b-fc`、`internlm`、`jamba`、`xlam`、`deepseek_v3`、`deepseek_v31`、`openai`(gpt-oss)、`kimi_k2`、`hunyuan_a13b`、`cohere_command3`、`cohere_command4`、`longcat`、`glm45`、`glm47`、`functiongemma`、`qwen3_xml`(Qwen3-Coder)、`mimo`、`step3p5`、`olmo3`、`gigachat3`、`apertus`、`muse`、`hf`、`beam`。源码注册表另有别名/未上文档项（如 `qwen3_json` 是 `hermes` 的 alias，源码注释说"TODO 给 Qwen2.5/QwQ/Qwen3 做独立 JSON parser"）。来源性质：官方文档 + 源码 `vllm/tool_parsers/__init__.py` — https://github.com/vllm-project/vllm/blob/main/vllm/tool_parsers/__init__.py

5. **文档自己写明的坑（可直接引用，含"参数被截断/丢弃"类）**：
   - 无 structural tag 生效时："vLLM extracts tool calls from raw text, so **arguments may occasionally be malformed or violate the function's parameter schema**"。
   - Llama 3.1/3.2：**"Parallel tool calls are not supported for Llama 3"**；且"the model can generate parameters in an incorrect format, such as generating an array serialized as string instead of an array"。
   - Mistral：**"Mistral 7B struggles to generate parallel tool calls correctly"**；官方格式要求 tool call ID 恰好 9 位（Transformers tokenizer 后端会直接抛异常），须用 `examples/tool_chat_template_mistral.jinja`（ID 截断到后 9 位）或 `_parallel.jinja`。
   - `pythonic`："模型不能在同一次生成里同时输出文本和 tool call"；**"Llama's smaller models frequently fail to emit tool calls in the correct format"**。
   - `hf` parser：只解析不约束，且"rejects requests for strict tools, required or named tool choice, or `parallel_tool_calls=false`"；不能与其他 reasoning/tool parser 组合。
   来源性质：官方文档 — https://docs.vllm.ai/en/latest/features/tool_calling/

6. **vLLM 的服务端兜底开关（对"客户端不设 strict"的现实很有用）**：`--tool-strict-level {auto|function|parameter}`（`parameter` 相当于把所有工具当 `strict:true` 处理），环境变量 `VLLM_ENFORCE_STRICT_TOOL_CALLING`（默认 `true`），`--exclude-tools-when-tool-choice-none`。默认 level：`glm47` 为 `function`，其他 parser 为 `auto`。来源性质：官方文档 — https://docs.vllm.ai/en/latest/features/tool_calling/

### D2 Ollama

7. **官方博客口径（2024-07-25）**：通过 `tools` 字段传工具、模型回 `tool_calls`、结果以 `role:"tool"` 回灌；当时列的支持模型是 `llama3.1`、`mistral-nemo`、`firefunction-v2`、`command-r-plus`，OpenAI 兼容端点同样支持 `tools`。**"Future improvements" 明确写了当时还没有的两项：Streaming tool calls 与 Tool choice（"force a model to use a tool"）** —— 这是"早期不支持流式/不能强制工具"的一手证据。来源性质：官方博客 — https://ollama.com/blog/tool-support

8. **当前文档已覆盖并行与流式**：页面章节含 Parallel tool calling / Multi-turn tool calling (Agent loop) / Tool calling with streaming；唯一保守表述是 Python 示例注释 "only recommended for models which only return a single tool call"。**"模型模板必须含 tool 支持"这句话在官方文档与博客里都找不到明文**（只有模型名单 + Tools 分类）。来源性质：官方文档 — https://docs.ollama.com/capabilities/tool-calling

### D4 真实 issue/PR：模型输出格式与 parser 不匹配 → 调用失败/参数丢失/静默吞掉

11. **vLLM PR #62368（open）** — 模型写出没有 `<tool_call>` 包裹的 `<function=...>` 时，parser 认它、语法不认它，结果被解析成 `get_weather({})`，**参数全丢**。 https://github.com/vllm-project/vllm/pull/62368
    **vLLM PR #60770（open）** — `hermes` + `tool_choice="required"` 时 structural tag 不允许并行调用之间的换行，贪心解码在第一个调用后就 EOS：**要 2~3 个调用只返回 1 个**（Qwen3-0.6B / Qwen2.5-1.5B 复现）。 https://github.com/vllm-project/vllm/pull/60770
    **vLLM PR #60842（open，Fixes #60703）** — `glm47` parser 遇到正文里一个游离 `<tool_call>` 会把后续整段流**静默吞掉**，返回 200 + `finish_reason="stop"` + `tool_calls` 为空。 https://github.com/vllm-project/vllm/pull/60842

12. **llama.cpp issue #30118（open）** — 模型省略 `<tool_call>` 开头时，`--jinja` 下整段调用**漏进 `message.content`**、`tool_calls` 为空；作者实测 100 次请求里 15 次解析成功、9 次泄漏。 https://github.com/ggml-org/llama.cpp/issues/30118
    **Ollama issue #17778（open）** — 多轮 tool 循环（tool 结果回灌后）流式报 500 `no user query found in messages`，单次 tool call 不触发。 https://github.com/ollama/ollama/issues/17778
    **Ollama issue #12187（open）** — "GPT-OSS not completing tool calls"：调用起头后几秒就"完成"、模型什么也没做。 https://github.com/ollama/ollama/issues/12187
