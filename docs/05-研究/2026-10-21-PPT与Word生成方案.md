# 2026-10-21 PPT 与 Word 生成方案选型调研

> **调研对象**：企业内网系统（FastAPI 主服务 + 内网 vLLM 的 OpenAI 兼容接口），纯离线，Linux/Windows Server 容器。
> **交付物**：中文汇报 PPT（.pptx，党委会/经营分析会风格，能套企业模板）+ 中文公文 Word（仿宋_GB2312 三号 / 28 磅行距 / 方正小标宋标题）。
> **取证方法**：GitHub API（`api.github.com`）取 star / pushed_at / license；README / package.json / 官方文档（jsdelivr 镜像 `cdn.jsdelivr.net/gh/...`，本机 `raw.githubusercontent.com` 不可达）；标注约定：**【事实】** = 有源可点，**【推断】** = 我基于事实的判断，**【待证】** = 本次未取到证据，需 POC。
> **星级/时间口径**：均为 2026-10-21 当日 GitHub API 读数。

## 0. 一句话结论

**PPT 主方案选「python-pptx + 企业母版占位符」的模板引擎路线**（Python 原生、MIT、进程内调用、输出 100% 真 .pptx 且与企业模板同一份母版）；**备选两个**：**LandPPT**（Apache-2.0、FastAPI 同栈、中文原生、模板包可"从 PPTX 创建"，但**可编辑输出需 Apryse 商业许可**）与 **Presenton**（11k★、唯一开箱即用的离线 HTTP 微服务，`LLM=custom` 可指内网 vLLM，但模板是英文 HTML/Tailwind）；**PPTAgent 是"套模板"思路最正确但运维最重的学术方案，不做生产主路径**；**PPTist 因 AGPL-3.0 + 商业授权限制出局**；**HTML 截图塞 pptx 出局（不可编辑）**；**AiPPT 系（含 veasion/AiPPT）是伪开源，出局**。
**Word 主方案选「docxtpl（Jinja2 套 .docx 模板）+ python-docx 做版记/页码后处理」**，格式正确性靠模板作者在 Word 里调好样式承载，而不是靠代码拼 XML。**LibreOffice 只用于 docx→pdf 的兜底转换，不进主链路**（分页与 Word 不一致，公文页码/版记会错位）。

## 2. PPT 生成路线

### 2.1 Presenton（开源 AI 演示文稿生成器）

- **仓库**：https://github.com/presenton/presenton
- **许可**：【事实】Apache-2.0（API `license.spdx_id`）。
- **规模/活跃度**：【事实】11,244 star、1,710 fork、2026-10-19 最后 push，主语言 TypeScript（API）。
- **部署**：【事实】单容器 `docker run -it --name presenton -p 5001:80 -v "./app_data:/app_data" ghcr.io/presenton/presenton:latest`；另有 Electron 桌面版（README「Option 1: Electron」）。内部是 Next.js（UI）+ FastAPI（`servers/fastapi`）双进程，容器内以 80 端口对外。
- **是否必须公网 LLM**：**不必须**【事实】。README 提供 `LLM=custom` 通道：
  `CUSTOM_LLM_URL`（OpenAI 兼容 base URL，**必须实现 `POST /v1/chat/completions`**）+ `CUSTOM_LLM_API_KEY` + `CUSTOM_MODEL`；另有 `litellm` / `lmstudio` / `ollama` 通道，以及 `DEEPSEEK_BASE_URL` 之类可覆盖的 base URL。
- **离线加固必须做的 3 件事**【事实，README「Air-gapped deployments」+ 遥测段】：
  1. `PRESENTON_COMMUNITY_ENABLED=false` —— 否则后台会向 community 服务请求模板/设计参考（官方明确点名这是 air-gap 必关项）；
  2. `DISABLE_ANONYMOUS_TRACKING=true` —— 关匿名遥测；
  3. `MEM0_ENABLED=false`（或改 `MEM0_LLM_BASE_URL`）—— 记忆模块默认指向 Ollama 端点，嵌入模型是 `BAAI/bge-small-en-v1.5`（**英文**嵌入），对中文场景既无益又多一条外呼/依赖。
- **中文/模板支持**：【事实】模板体系是 **HTML + Tailwind CSS**（README「Custom Templates & Themes」），并提供「AI Template Generation — 从已有 PowerPoint 文件生成模板」。**【推断】这意味着"套企业模板"= 把你公司的 .pptx 一次性"翻译"成一份 HTML 模板，之后每页都由 HTML 渲染，再转 pptx；还原度取决于翻译质量，与你公司母版不是同一份文件。**
- **中文字体**：【待证】镜像是否预装 CJK 字体未取到证据（`Dockerfile` 在 jsdelivr 上被当作 octet-stream 拒绝取文本）。POC 第一条命令就该是容器内 `fc-list :lang=zh | wc -l`。
- **输出**：【事实-厂商标称】"Fully editable PPTX export"；API `export_as: pptx|pdf`。**【推断】导出链路在 FastAPI 侧（`servers/nextjs/package.json` 中无 pptxgenjs / playwright 依赖），是 HTML 结构 → pptx 形状的映射，文字可编辑但字号/行距/字体名会漂移；不是"保留母版占位符"式的可编辑。** 需 POC 验证：导出的 pptx 里文字是真文本框还是图片。
- **质量证据**：README 内嵌真实产品 GIF（drag-and-edit、banner）与 6 套模板预览页（https://presenton.ai/explore/momentum 等），属"可见但未量化"级别。【推断】内置模板是**英文商务风**（Momentum / Executive / Dynamic / General / Modern / Standard），与党委会"红头+稳重"风格不同源，需要自建。
- **接入成本**：**最低**。独立 HTTP 服务，接口语义清楚：`POST /api/v1/ppt/presentation/generate`（`content` / `slides_markdown` / `n_slides` / `template` / `language` / `export_as`），返回 `presentation_id` + `path` + `edit_path`；鉴权用管理员签发的 `sk-presenton-...` API key；还内置 MCP server（`/mcp`，Streamable HTTP）。
- **失败模式**：① 版本还在 0.x（文档站标 `v0.9.7-beta`），API/env 名会变，升级即破坏；② 中文排版不可控（断行、避头尾、字重）；③ HTML→pptx 的还原度是黑盒；④ Mem0/社区/遥测三类外呼若漏关，在内网表现为超时卡顿而不是报错——**最阴的坑**。

### 2.2 PPTAgent（中科院系，生成 + 评测）

- **仓库**：https://github.com/icip-cas/PPTAgent
- **许可**：【事实】MIT。**规模**：5,136 star、601 fork、2026-10-19 最后 push，Python。
- **学术背书**【事实】：EMNLP 2025 主会（arXiv [2501.03936](https://arxiv.org/abs/2501.03936)）；DeepPresenter 被 ACL 2026 接收（arXiv [2602.22839](https://arxiv.org/abs/2602.22839)）；自带评测框架 **PPTEval**（Content / Design / Coherence 三维）。
- **思路（与本需求最契合的一点）**【事实，论文摘要 + README】：**两阶段、基于"编辑"的生成** —— 先分析**参考 PPT**，抽取每页的功能类型（封面/目录/要点/图表…）与内容 schema；再基于选中的参考页**生成编辑动作**来产出新页。**这就是"套企业模板"的正确抽象**：它以真实 .pptx 为母体，而不是从零画色块。
- **是否必须公网 LLM**：**可改内网**【事实-部分】。README 的 skill 配置样例即为 OpenAI 兼容端点：
  ```yaml
  visual:
    base_url: "<OpenAI-compatible API base URL>"
    model: "deepseek-v4-flash-vision"
    api_key_env: VISUAL_API_KEY
  ```
  【事实】2026/01 更新日志明确：「Freeform & template generation now support PPTX export and **offline mode**」。【待证】主框架（`pptagent/DOC.md` / DeepPresenter）对接 vLLM 的具体配置键未逐行核实，需 POC。
- **部署依赖**【事实，README「Install PPTAgent Skill」】：`uv` + Python 3.12 + `npm` + **LibreOffice（`soffice` 必须在 PATH）** + `playwright install chromium`（macOS 还要 Chrome）。**镜像重、冷启动慢**是硬伤。
- **接入形态**【事实】：它不是"一个 REST 服务"，而是 **coding agent 的 skill**（Claude Code / Codex CLI / OpenCode 驱动），或 v1.1.37 起的 **MCP server**。要塞进现有 FastAPI 架构，需要自己包一层 HTTP wrapper，或让 agent 走 MCP。
- **中文**：作者团队是中文语境（中科院软件所/复旦/人大），中文模板与中文文本路径在论文实验中覆盖。【待证】README 未单列"中文字体安装"步骤——LibreOffice + 容器若无 CJK 字体，渲染环回会出方块，直接毁掉视觉自检环节。
- **质量证据**：**本清单里唯一有量化评测的**（PPTEval + 两张顶会论文 + demo GIF `resource/pptagent-demo.gif`）。
- **失败模式**：① 一次生成 = 一次多轮 agent 循环（**分钟级**），不适合"点一下按钮等 5 秒"的产品形态；② 不确定性高，可能改坏参考页版式；③ LibreOffice + Chromium + Node 三件套让容器从 300MB 变 2GB+；④ 迭代极快（月更），无 API 兼容承诺；⑤ 需要视觉模型（多模态）做 review，vLLM 上得额外部署一个 VLM。

### 2.3 PPTist（在线 PPT 编辑器，含 AIPPT）

- **仓库**：https://github.com/pipipi-pikachu/PPTist （注意：`pipipi/PPTist` 是 404，正确 owner 是 `pipipi-pikachu`）
- **许可**：【事实】**AGPL-3.0**。README 中文段明确「**禁止闭源商用**」，并给出付费路径：独立商业授权 **2,999 元/年、5,999 元/永久**；另有一个 2022 年 5 月停更的 Apache-2.0 旧快照可下载。
- **规模/活跃度**：【事实】9,409 star、1,774 fork、2026-10-10 最后 push，Vue3 + TypeScript，Node ≥ 20。
- **定位（作者原话）**【事实】："Web Slide Editing/Presentation Application"；对"AI PPT 生成工具"只给 ⭐⭐ 推荐，明说「PPTist 更适合作为承接/编辑/再加工结构化生成结果的基础，而不是开箱即用的 AIPPT 商业方案」。
- **输出**：【事实】`pptxgenjs ^3.12.0` 导出 pptx（README 称整体保真 ~95%+），`pptxtojson ^2.2.0` 导入（~85%）。**是真正的原生形状，可编辑**——这是它最强的地方。
- **中文**：中文原生项目，文本/字体按中文习惯处理；文本编辑用 ProseMirror，支持首行缩进、字间距、行高。
- **接入成本**：**最高**。它是纯前端（`private: true`，无后端），要自己接模型、资产、模板库，还要处理 AGPL 传染性（内网对外提供服务也要给使用者源码）。
- **结论**：**不选**。理由两条：许可（AGPL + 作者明确商业授权收费）与形态（编辑器不是生成服务）。但**若未来要"生成后在线微调"**，它是国内最成熟的可编辑底座，值得单独评估付费授权。

### 2.4 python-pptx + 企业模板（模板引擎 / 占位符替换路线）

- **仓库**：https://github.com/scanny/python-pptx ——【事实】MIT、3,560 star、741 fork、最后 push **2024-08-07**、541 个 open issue。
- **活跃度判断**【推断】：**低频但稳定**。这类"Open XML 读写库"的成熟度不靠高频提交；541 个 open issue 说明维护不积极，但接口稳定、生态最大，遇到问题基本都能搜到答案。
- **做法**（这是本次推荐的路线）：
  1. 在 PowerPoint 里做一份**企业母版模板 .pptx**：定义"封面 / 目录 / 章节页 / 要点页 / 表格页 / 图表页"6~8 个**版式（Slide Layout）**，每个版式里的占位符命名清晰（`title`、`subtitle`、`body`、`tableXXX`）。
  2. 服务端 `Presentation("企业模板.pptx")` 打开 → `slides.add_slide(layout)` → 按占位符名填文本 / `add_table` / `add_chart` / `insert_picture`。
  3. **LLM 只输出结构化 JSON**（每页类型 + 标题 + 要点 + 表格数据 + 图表序列），渲染完全由代码决定。
- **关键约束**【事实，库的设计边界】：python-pptx **不能新建版式/母版**，只能在编辑里预先做好的 layout 上填；也不支持动画、SmartArt 的创建。→ **版式必须先在 PowerPoint 里做好，这是好事**：等于把设计权交给设计人员，而不是交给模型。
- **中文**：**完全可控**。字体写在 `a:rPr` 的 `<a:latin>/<a:ea>/<a:cs>` 三处（中文必须设 `<a:ea>`，否则中文会退回主题字体）；字号、行距（`a:lnSpc`）、字间距（`a:spc`）都能精确指定 `微软雅黑 / 思源黑体 / 方正兰亭`。**【推断】这是唯一能保证"领导电脑上打开与设计稿一致"的路线**（只要目标机装了同名字体，或用嵌入字体）。
- **输出**：**100% 真 .pptx，与企业模板同一份母版**，文本框/表格/图表都可继续编辑，无转换漂移。
- **质量证据**：本路线无开源 demo（是自研），**质量下限由模板决定、上限也由模板决定**。可验证方式见 §5 POC：拿公司真实模板做 3 页，让办公室同事盲评。
- **接入成本**：**中**。零新增容器（就装在现有 FastAPI 里），但**首期要写 6~8 个版式的渲染代码 + 文本溢出预算逻辑，约 1~2 周**。
- **失败模式**：① **文本溢出**——python-pptx 写的框不会自动缩排，中文长标题必须自己算「字数 × 字号 ≤ 框宽」，否则字跑到框外（最丑的失败）；② 版式硬编码，新增一种页型就要改代码；③ 图表样式弱（复杂组合图要先在模板里做样例再克隆）；④ 没有"自由设计"，超出模板的创意需求做不了。

### 2.5 HTML→pptx / Markdown→slides 路线

**这条路有三个变体，必须先分清楚，否则会踩"交上去才发现不可编辑"的坑。**

| 变体 | 代表 | 视觉保真 | 可编辑 | 判断 |
|---|---|---|---|---|
| Chromium 截图，每页图片塞 pptx | 自写 Playwright + python-pptx | ★★★★★ | ❌ 完全不可编辑 | 只适合"定稿发 PDF"，不适合"要改" |
| Markdown → 图片式 pptx | Slidev `--format pptx` / Marp | ★★★★★ | ❌ | 同上 |
| Markdown → 原生形状 pptx | Slidev `--format pptx-editable`（新） | ★★★☆ | ✅ | 可用，但受限于"浏览器量测 vs PowerPoint 排版"差异 |
| DOM → 原生形状库 | PptxGenJS 自己写量测转换 | ★★★☆ | ✅ | 等于自研 html2pptx，工程量不小 |

- **Slidev**：https://github.com/slidevjs/slidev ——【事实】MIT、**49,154 star**、2026-10-18 最后 push。官方文档两处说法必须对齐：
  - `slidev export --format pptx`：**「all the slides in the PPTX file will be exported as images, so the text will not be selectable」**（[docs/guide/exporting.md](https://cdn.jsdelivr.net/gh/slidevjs/slidev@main/docs/guide/exporting.md)）。
  - 新增 `slidev export --format pptx-editable`：**先在浏览器里量测、再用原生 PowerPoint 形状重建**，文字可选中可编辑；但 **SVG（含 Mermaid/图标）、`<canvas>`、`<iframe>`、视频、KaTeX 公式、CSS 渐变/滤镜/`clip-path` 一律退化为图片**，且**无法安全重建的页会整页回退成图片**并打印原因。还有一句很关键：**「A `.pptx` names fonts, it does not embed them」**——中文场景下这句话就是"到领导机器上字体被替换"的同义词。
- **PptxGenJS**：https://github.com/gitbrent/PptxGenJS ——【事实】MIT、6,294 star、2025-11-28 最后 push，项目 topics 里直接有 `html-to-powerpoint`。它是"往 pptx 里画原生形状"的最成熟 JS 库（PPTist 的导出就是它）。
- **结论**：截图式**出局**（不满足可编辑）。`pptx-editable` 式可作为"设计自由度"的补充通道（比如要做一页特别炫的图），但**不作为主方案**：字体不嵌入 + 浏览器与 PowerPoint 断行不一致，中文长标题必翻车。

### 2.7 中文场景的四个硬坑（跨方案共性，必须在 POC 里逐条验证）

1. **中文字体三件套**：pptx 里中文走 `<a:ea>`，只设 `<a:latin>` 会导致"英文是雅黑、中文是宋体"。渲染侧（Presenton/PPTAgent/Slidev）则依赖容器内 `fc-list :lang=zh` 有字体，否则出方块。
2. **断行与避头尾**：中文不能按空格断行，标点不能出现在行首。浏览器（CSS `line-break`）与 PowerPoint 的规则不同 → HTML 路线必然出现"多一行/少一行"。
3. **字体不嵌入**：`.pptx` 只存字体名。要保证领导机器上一致，只能（a）约定全公司装同一套字体，或（b）在 pptx 里嵌入字体（PowerPoint 支持"嵌入字体"，但 python-pptx 无 API，需手工改 XML）。
4. **母版 vs 模板的语义差别**：企业 .pptx 模板的价值在 **Slide Layout + 占位符 + 主题字体/配色**。任何"把 pptx 翻译成 HTML"的方案（Presenton 的 AI Template Generation）都会丢掉这层语义，只留下视觉近似。

## 3. Word 公文生成

### 3.1 docxtpl（Jinja2 套 .docx 模板）—— 主方案载体

- **仓库/许可**：【事实】https://github.com/elapouya/python-docx-template ，2,725 star、2026-07-07 最后 push、**LGPL-2.1**；文档 v0.20.x（https://docxtpl.readthedocs.io/en/latest/ ）。
- **许可判断**【推断】：LGPL-2.1 下"以库的形式 import 使用"不要求你的业务代码开源；只有你**修改库本体并分发**时才需开源修改。内网部署连"分发"都不构成。**这点需要法务复核一次**（清单见 §6）。
- **工作模式**【事实，官方文档 Introduction】："先用 Word 做一份你想要的文档（图、页眉页脚、表格、变量随便加），在 Word 里插入 jinja2 标签，另存为 .docx 模板"，再由代码 `doc.render(context)` 填值。**这正好契合公文：版式由人调一次，代码只管填内容。**
- **中文/公文相关的关键能力**【事实，官方文档】：
  - `{{r var}}` + `RichText('测试', font='eastAsia:仿宋_GB2312')` —— **中文字体必须带 `eastAsia:` 前缀**，否则只作用于西文字体。这一条直接决定"仿宋_GB2312 / 方正小标宋"能不能生效。
  - 块级标签 `{%p ... %}`（段落）/ `{%tr ... %}`（表格行）/ `{%tc ... %}`（单元格）/ `{%r ... %}`（run）：会**连同承载标签的段落/行一起删除**，适合"有无附件""列不列抄送"这类可选块。
  - 表格：`{% colspan n %}`、`{% hm %}`（横向合并）、`{% vm %}`（纵向合并）、`{% cellbg %}`（单元格底色）。
  - `tpl.replace_pic('dummy.jpg', 'real.jpg')` **可替换页眉/页脚中的图片** → 红头、印章、单位 LOGO 走这条；【事实】但**不能动态新增**页眉页脚图片，只能替换。
  - `{{ var|e }}` / `render(autoescape=True)` / `Listing()`：正文里出现 `<`、`>`、`&` 会破坏 XML，必须转义。
- **已知坑**【事实，官方文档】：
  1. 普通 jinja2 标签**只能在同一个 run 内**，而 Word 会因为加粗/字体变化把一段文字拆成多个 run → 录标签时必须"纯文本粘贴"，且 `{%p`/`{%tr` **独占一行**、不能在同一个段落里出现两次；
  2. `{{r }}` 会清掉当前字符样式，且 **RichText 不兼容 jinja 过滤器**（`{{r var|lower}}` 无效，只能在 Python 侧处理）；
  3. Word 2016 会吞掉 `\t` 和前导空格，要用 `RichText(5*'\t')` 兜；
  4. `replace_media/replace_embedded` 要求模板目录里保留原始占位文件（要算 CRC）。
- **接入成本**：低。`pip install docxtpl`，一个函数：`DocxTemplate(模板).render(json).save(路径)`。可直接作为 FastAPI 里的工具函数，或独立微服务。

### 3.2 python-docx（纯代码 / 后处理）

- 【事实】https://github.com/python-openxml/python-docx ，5,746 star、MIT、2026-08-01 最后 push。
- **必须手工处理的四件事**（这是"为什么不能只用 python-docx 拼公文"的答案）：
  1. **中文字体**：`run.font.name` 只写 `w:rFonts/@w:ascii`，中文不会变。必须补 `<w:eastAsia w:val="仿宋_GB2312"/>`（`run._element.rPr.rFonts.set(qn('w:eastAsia'), ...)`）。
  2. **行距**：`paragraph_format.line_spacing = Pt(28)` + `line_spacing_rule = EXACTLY` → OOXML 里是 `w:spacing w:line="560" w:lineRule="exact"`（28pt × 20 = 560 twips）。
  3. **首行缩进 2 字符**：要用 `w:ind @w:firstLineChars="200"`，不能用 `first_line_indent=Pt(32)`——后者按磅算，字号一变就错位。python-docx 没有 `firstLineChars` 的 API，要手写 XML。
  4. **页码域**：python-docx **没有域（field）API**，`PAGE` 域要自己拼 `w:fldSimple` 或 `w:instrText`，且要分奇偶页两个页脚（`evenAndOddHeaders`）。
- **结论**【推断】：**docxtpl 渲染 + python-docx 后处理**是最优组合——复杂版式交给模板，动态内容交给 docxtpl，页码域/版记补写/落款位置这类"最后一段逻辑"交给 python-docx 改 XML。

| **Windows 自带 宋体/仿宋/楷体（simfang/simkai）** | 「不可再分发、不可转换格式」；文档内嵌入（Word/PDF）按 font 的 `fsType` 允许、含嵌入字体的文档一般可分发；**但明令不得嵌入游戏/应用/设备** —— [Microsoft Typography FAQ](https://learn.microsoft.com/en-us/typography/fonts/font-faq) | ❌ 不行（容器=应用/设备） |
| **思源宋体 / 思源黑体** | **SIL OFL 1.1**，可捆绑、嵌入、随软件分发（受保留字体名限制）—— [LICENSE](https://github.com/adobe-fonts/source-han-serif/blob/master/LICENSE.txt) | ✅ **可以** |
| **Fandol（Song/Hei/Kai/Fang，TeX Live 收录）** | GPL + GPL font exception —— [CTAN](https://ctan.org/pkg/fandol) | ✅ 可以 |

**最关键的一条合规结论**【事实 + 推断】：**GB/T 9704-2012 原文只写"仿宋体字""小标宋体字"，不指定厂商**（7.3.1 / 7.3.3）。所以用思源宋体/思源黑体替代，**不违反标准原文**——违反的只是"单位内部细则/领导观感"。

**两条交付形态，两条结论：**
- **交付 `.docx`**（推荐）：文件里只存字体名，机关电脑通常已装 → **风险最低**。渲染发生在接收方的 Word 里，不构成"随软件分发字体"。
- **容器内渲染 PDF**：必须把 TTF 装进镜像 → 对商业字体属"嵌入软件"（方正明确禁止）→ **不可行**；只能用 OFL/GPL 字体，而它们与"仿宋_GB2312"字形有差异，公文内行一眼看得出。
- **所以**：主链路只产 `.docx`；需要 PDF 时走"Windows Server + Word COM / OnlyOffice"，或让用户在本地 Word 导出。**不要在 Linux 容器里渲染正式公文。**

### 3.6 LibreOffice headless + 容器中文字体

- **字体从哪来 / 多大**【事实，Debian packages】：`fonts-noto-cjk`（bookworm 1:20220127）**包 55.2 MB，安装后 91.0 MB**，含 Noto Sans/Serif CJK SC/TC/JP/KR 的 regular+bold。更轻的替代是 `fonts-wqy-zenhei` / `fonts-wqy-microhei`（同页"Similar packages"列出）。
- **微软字体包不含中文**【事实】：`ttf-mscorefonts-installer` 只装 Andale/Arial/Comic/Courier/Georgia/Impact/Times/Verdana/Webdings 等西文字体，**不含任何 CJK**——指望它解决中文是常见误解。
- **并发坑**【事实，docling issue #3819 标题：「LibreOffice DOCX/PPTX/XLSX conversions have no timeout and share a colliding user profile」】：多个 `soffice --headless` 同时跑会争同一个 user profile 而互相锁死/崩溃。修法是每次调用带独立 profile：
  `soffice --headless -env:UserInstallation=file:///tmp/lo-$RANDOM --convert-to pdf in.docx --outdir out/`，并加超时与 `kill`（docling 的 PR #3820 就是干这个）。
- **最致命的坑（决策依据）**【推断，但机制明确】：LibreOffice 与 MS Word 的**断行/分页算法不同**，同一 .docx 转出的 PDF 页数、页码位置、版记所在页会与 Word 不一致。公文恰恰是"页码和版记必须在确定位置"的文档 → **容器渲染的公文 PDF 不能当交付物**。
- **结论**：LibreOffice 只用于三件事：① 生成缩略图/预览；② 内部流转的"不准正式版"PDF；③ 版面溢出自检（把 pptx/docx 转图，用视觉模型或像素比对看有没有溢出）。**正式交付 = .docx**。

## 4. 决策

### 4.1 如果只能选一条路做 PPT 主方案：**python-pptx + 企业母版占位符（自研模板引擎，跑在现有 FastAPI 里）**

**六条理由，每条都可当场验证：**

1. **它是唯一同时满足"真可编辑 + 与公司母版同一份文件"的路线。**
   - 截图式 → 不可编辑（致命）；
   - Presenton / LandPPT → 模板是 **HTML/Tailwind**，你的 .pptx 母版只能被"翻译"成网页，丢掉的正是 Layout/占位符/主题字体这层语义；
   - LandPPT 的可编辑输出要 **Apryse 商业许可**；
   - 自研路线直接 `Presentation('企业模板.pptx')`，导出的 pptx 打开就是你的母版。
2. **零新增运行时依赖。** 不需要 Node、Chromium、LibreOffice、字体包的组合拳；镜像不变大、离线最干净、安全审计面最小（对内网项目，这条的隐性成本最高）。
3. **质量由设计决定，不由模型运气决定。** 同一份 JSON 永远渲染出同一页；每次领导看到的版式是稳定的。任何"AI 自己选版式/自己排版"的方案，同一主题生成两次结果不同，且改一页可能连带改坏别的页。
4. **许可干净**：MIT，无 copyleft、无商业授权、无"禁商用"。
5. **与现有架构成同构**：工具调用就是一个 Python 函数（`build_deck(json) -> path`），连微服务都不用起；要隔离再包一层 FastAPI。
6. **把 LLM 的职责压缩到它最擅长的部分**：只写结构化内容 JSON（页型 + 标题 + 要点 + 表格 + 图表序列）。这一段的正确性可以用 JSON Schema + 单测卡死，是内网 vLLM 最容易评测的一环。

**必须承认的代价（这也是它的失败模式）：**
- 需要有人先做模板：6~8 个版式（封面/目录/章节/要点/表格/图表/结尾），约 2~3 天设计工作量。
- 需要 1~2 周写渲染器 + **文本溢出预算**（字数 × 字号 ≤ 框宽/框高，中文还要按字宽而不是按空格估）。
- **做不了自由设计**：所有页型必须预先定义。
- 长表格/长标题会溢出到框外——这是最丑的失败，必须用"渲染→转图→像素/视觉自检"闭环兜住。

### 4.2 备选（按推荐顺序）

| 备选 | 什么时候用 | 它的失败模式 |
|---|---|---|
| **LandPPT** | 需要"今天就出一版草稿"、或要中文 UI + 中文模板包；Apache-2.0、FastAPI 同栈、`OPENAI_BASE_URL` 直连 vLLM | 可编辑输出要 **Apryse 商业许可**，否则只能出图片型 pptx（页内元素不可编辑）→ 领导要改一个字就得重生成 |
| **Presenton** | 英文/通用商务场景，或作为对照评测基线；生态最活（11k★） | 中文模板要自建；HTML→pptx 还原度黑盒；0.x 版本 API 会变；漏关 Mem0/社区/遥测会在内网表现为"卡住"而非报错 |
| **PPTAgent** | 只有当你愿意接受"分钟级 + 2GB 镜像 + 多模态 VLM"时；或用于离线评测集建设 | 不是稳定 REST 服务（agent skill / MCP），一次生成是一次多轮 agent 循环；依赖 LibreOffice+Chromium+Node；无 API 兼容承诺 |
| **Slidev `pptx-editable`** | 主方案做不出的"单页炫技"（时间轴、架构图） | 字体不嵌入；浏览器量测与 PowerPoint 排版不一致，中文必翻车；SVG/公式/渐变退化为图片 |

**PPTist 出局**（AGPL-3.0 + 作者明确"禁止闭源商用"，独立授权 2,999 元/年、5,999 元/永久）；**GordenPPTSkill 出局**（README 明禁商用与二次分发，哪怕它 17 套中文模板最像国企汇报）——**但它的架构（LLM 只产 edits.json，本地 python-pptx 确定性排版）与本方案一致，可以读、不能抄代码。**

### 4.3 Word 主方案：**docxtpl + 公文 .docx 模板 + python-docx 后处理 + 自建规则审校**

- **为什么**：GB/T 9704 的正确性本质是**版式正确性**（版心、字号、行距、页码一字线、版记横线位置）。这些在 Word 里由人调一次就永久正确；用代码拼 XML 则每一条都要重新实现且难以验收。docxtpl 让"填内容"和"定版式"彻底分开。
- **分工**：模板作者（懂 Word 样式的人）负责版式；`docxtpl` 负责可选块与表格行循环；`python-docx` 只做三件事——补 `PAGE` 奇偶页域、写版记、调落款位置。
- **失败模式**：① Jinja 标签被 Word 的 run 拆分（最高频故障，表现为"标签没被替换，原样出现在文档里"）；② 模板维护强依赖特定一个人（他休假就没人能改）；③ 长标题/超长表格撑破 22 行版心，需要预留"标题换行降级"规则；④ 正式 PDF 若用 LibreOffice 渲染，页码与版记会错位（**所以正式交付物只给 .docx**）。

### 4.4 一句话给决策者

> **PPT**：花两周自研"模板引擎"，换来的是一份永远像公司自己做的、可以继续改的 pptx；买/用任何"AI 自动排版"产品，换来的是省两周、但每次生成都要重新审一遍的网页转 pptx。
> **Word**：不要写代码画版式，让 Word 做 Word 该做的事（做模板），代码只填字。

## 5. 落地路线（4 周 POC，每周有验收判据）

| 周 | 交付 | 验收判据（可当场判真假） |
|---|---|---|
| W1 | 企业 PPT 模板改造（6~8 个版式，占位符命名规范）+ 公文 .docx 模板（通知/请示/报告 3 文种）+ 字体盘点表 | PowerPoint/Word 里手动改字能改；模板里的页码、版记、横线位置正确 |
| W2 | PPT 渲染器最小闭环：封面 / 目录 / 章节 / 要点 4 类 + 文本溢出预算 | 给定 JSON 生成 10 页，**零文字溢出**（LibreOffice 转图 + 像素/视觉比对）；改 JSON 重跑，版式不变 |
| W3 | 表格页 + 图表页 + 接 vLLM（`json_schema` 强约束） | 一句需求 → 12 页 pptx；3 人盲评 ≥4/5；同一 prompt 跑 3 次，版式稳定性 100% |
| W4 | 公文链路（docxtpl + 页码域 + 10 条规则审校）+ 注册成 agent 工具 | 3 文种各 1 份，Word 打开后**零手工调整**；规则审校用例集全绿 |

**POC 必做 8 条硬验证**（对任何候选方案都适用，别只看 demo）：

1. **可编辑性解包检查**：`unzip -p out.pptx ppt/slides/slide1.xml`，数 `<p:sp`（形状/文本框）与 `<p:pic`（图片）的比例。`<p:pic` 占绝大多数 = 图片拼页。
2. **容器中文字体**：`fc-list :lang=zh | wc -l`，必须 > 0；再 `fc-match "仿宋_GB2312"` 看落到哪个字体。
3. **字体替换检查**：把生成的 pptx 拷到没装公司字体的机器打开，看是否变形。
4. **中文长标题 30 字**是否溢出；标点是否跑到行首（避头尾）。
5. **docx 页数/页码/版记位置**与设计一致（在真实 Word 里，不是在 LibreOffice 里）。
6. **LibreOffice 转出的 PDF 页数** vs Word 导出的 PDF 页数（不一致就说明该链路不可用于公文）。
7. **断网跑通**：`docker run --network none`，看有没有隐藏外呼（Presenton 必须设 `PRESENTON_COMMUNITY_ENABLED=false`、`DISABLE_ANONYMOUS_TRACKING=true`、`MEM0_ENABLED=false`）。
8. **成本与延迟**：vLLM 下 P95 时延、每份 PPT 的 token 数（决定要不要缓存大纲）。
