## 问题 1：挂 12~20 个工具，7B~32B 内网模型的工具选择准确率会明显下降吗？

**一句话结论（【推断】，但有三条一手证据支撑方向）**：会明显下降，尤其是"工具名近义 + schema 长"的时候；不过"下降多少"不由工具总数单独决定——公开证据支持"候选池超过约 10 个后选错率显著上升，把候选裁到 5~7 个能拿回大部分准确率"，所以缓解方式是**意图路由 + 工具集分片 + 检索式短名单 + 子 agent**，不是硬扛 20 个工具。

### A. 你点名的那篇论文找不到（【未核实】，疑似标题串台）

- 按题名检索不到 "Less is More: On the Over-Globalizing Tool Representations"。同题名家族只有两篇：
  - `Less is More: on the Over-Globalizing Problem in **Graph Transformers**`（arXiv:2405.01102，图神经网络，与工具选择无关）— https://ar5iv.labs.arxiv.org/html/2405.01102
  - `Less is More: Optimizing Function Calling for LLM Execution on **Edge Devices**`（IEEE 文档号 10992798，付费墙，正文数字未取到）— https://xplorestaging.ieee.org/document/10992798
- 结论：报告里**不要**引用 "Less is More: On the Over-Globalizing Tool Representations" 这个标题，它核不到。

### B. 一手证据一：短名单长度实验（本轮【抓取】）

arXiv:2605.24660 *How Many Tools Should an LLM Agent See? A Chance-Corrected Answer*（Repantis 等，2026-05-23 提交，v2 2026-06-07）— https://arxiv.org/abs/2605.24660

- 摘要原文："**Show too many tools and the model struggles to choose. Show too few and the correct tool may not appear.**"
- 实验规模：三个工具选择 benchmark，registry 从 **20 到 3,251 个工具**。
- BFCL（**370 tools**）上：学到的"每次查询自适应深度"策略平均只展示 **7 个**工具，覆盖率 **90.3%**；固定展示 **50 个**是 **90.8%** —— 即"少给 43 个工具，覆盖率只差 0.5 个点"。
- ToolBench（**3,251 tools**）：固定短名单 5 个的聚合覆盖率 **64.7%**（优于 61.9%），但在"正确工具排在第 6–20 位"的难查询上一个都找不到（0）；自适应策略在这些难查询上找到 **16.7%**。
- 下游真模型选型验证（Claude Sonnet 4.6）：短自适应列表 **93.1%** vs 固定 5 个 **87.1%**；在"正确工具在列表里但不在第一"的中等难度查询上扩大到 **76.8% vs 60.9%**。
- 读法提醒【推断】：这篇的自变量是"**检索短名单长度**"，不是"prompt 里直接塞 N 个 schema"。它证明的是"**让模型看到更多候选 ≠ 选得更准，常常更差**"，以及"固定一刀切的 N 是错的，要按查询调深度"。

### C. 一手证据二：厂商官方文档的明确警告（本轮【抓取】）

Anthropic 工程博文 *Writing effective tools for agents* — https://www.anthropic.com/research/writing-tools-for-agents

- 原文："**More tools don't always lead to better outcomes.**"
- 原文："**Too many tools or overlapping tools can also distract agents from pursuing efficient strategies.**"
- 原文（同名不同功能的工具是主要失败源）："When tools overlap in function or have a vague purpose, agents can get confused about which ones to use."
- 官方缓解手段就是 namespacing（前缀分组），理由是它会 "reduce the number of tools and tool descriptions loaded into the agent's context"。

### D. 更贴"12~20 个工具"的量化数字（【转录】，本文未重抓）

- **RAG-MCP（arXiv:2505.03275）**：1 个正确工具 + N−1 个干扰项，N 扫到上千。选型准确率：检索 top-1 **43.13%**、关键词匹配 **18.20%**、**全量塞入 13.62%**。→ "工具池大而不筛选"的代价约是 **−30 个百分点**（43.13 → 13.62）。https://arxiv.org/abs/2505.03275
- 同一篇的局限（别过度外推）：base model 是 `qwen-max-0125`（云端），不是 7B 本地模型。→ 只能说明方向，不能直接搬成"7B 会掉 30 点"。【转录】
- **Anthropic "advanced tool use"**：官方给出的启用阈值是 "**>10 tools**" 或 tool 定义 >10K tokens 时收益最大，"<10 tools" 时收益小；失败模式原文："The most common failures are wrong tool selection and incorrect parameters, especially when tools have similar names like `notification-send-user` vs. `notification-send-channel`."；Tool Search Tool 开启后 Opus 4 内部评测 49% → **74%**。https://www.anthropic.com/research/advanced-tool-use

### E. vLLM / Qwen 官方有没有关于工具数量的说明

- **【未核实】本轮没取到任何 vLLM/Qwen 官方关于"工具数量/长 system prompt 影响选型"的公开结论。** 已知它们的文档口径是**机制性**的：vLLM 讲 `--enable-auto-tool-choice` + `--tool-call-parser`（解析与 chat template 匹配），Qwen 讲 `tools` 参数格式与 tool 定义写法，两者都不讨论"最多几个工具"。
- 因此：**"vLLM 官方说工具不能超过 N 个"这类话不要写进报告**。要写只能写"官方文档未涉及"，或自己跑 A/B 出数。

### F. 落到你场景的【推断】

12~20 个 Word/PPT/Excel/检索/SQL 工具，功能其实不重叠，掉分主要来自三件事：
1. **上下文挤压**：长 system prompt + 长 schema（每个工具 200–400 token）在 7B 上会挤掉有效推理空间；
2. **近义动词互干扰**：`search` / `sql_query` / `excel_read` / `query_doc` 这类"读数据"工具是重灾区；
3. **双向错**：既会"选错"，也会"少调/不调"（该用时不用）。

建议做法（都有一手证据支撑）：先做**意图路由**（4~5 个粗类），每轮只暴露 **5~7 个**工具；重名工具加**命名空间前缀**（`doc_` / `sheet_` / `sql_`）；跨域任务用**子 agent**（每个子 agent 只带 3~5 个工具），不要在单轮里堆 20 个。

## 问题 2：AGPL-3.0 / GPL-3.0 企业内部自用不分发，要不要开源自有代码？

**一句话结论**：**不要**。GPL-3.0 只在 **convey**（把副本交给别的法人）时才要求整体按 GPL 授权并提供对应源码；AGPL-3.0 只在"**你修改了程序** + 用户通过网络远程与它交互"时，才要求把**你这一版**的对应源码提供给这些用户（原文对象是 "**all users**"，不是 "the public"）——内部自用本身不产生"对外开源"义务。

### 原文一：§0 对 "convey" 的定义（"内网用不算分发"的锚点；GPLv3 与 AGPL 同文）

> To "convey" a work means any kind of propagation that enables other parties to make or receive copies. **Mere interaction with a user through a computer network, with no transfer of a copy, is not conveying.**

### 原文二：§2 Basic Permissions（跑了但不 convey = 无附加条件）

> You may make, run and propagate covered works that you do not convey, **without conditions** so long as your license otherwise remains in force.

### 原文三：§13 Remote Network Interaction（AGPL 唯一"网络即触发"条款，且前提是 **if you modify the Program**）

> Notwithstanding any other provision of this License, **if you modify the Program**, your modified version must prominently offer all users interacting with it remotely through a computer network (if your version supports such interaction) an opportunity to receive the Corresponding Source of your version by providing access to the Corresponding Source from a network server at no charge, through some standard or customary means of facilitating copying of software.

**URL（本轮【抓取】）**：https://spdx.org/licenses/AGPL-3.0-only.html （SPDX 页面自注：`gnu.org/licenses/agpl.txt` 与 `opensource.org` 的对应链接 "no longer live"）。许可本体：https://www.gnu.org/licenses/agpl-3.0.html

### 没拿到的那部分：GNU 官方 FAQ 原文（【未核实】）

- 本轮对 gnu.org 的 3 次抓取全部 `TypeError: fetch failed`：`/licenses/gpl-faq.html`、`/licenses/gpl-faq.en.html`、`/licenses/agpl-3.0.en.html`。**因此 "internal use / private use / ASP loophole" 那几段 FAQ 无法直引原文。**
- 处理建议：报告里只写"FAQ 地址：https://www.gnu.org/licenses/gpl-faq.html（本环境网络不可达，正文待内网可通环境自核）"，**不要凭记忆引 FAQ 字句**。同目录 `2026-10-21-MCP与内网工程约束.md` 已记录过同一限制。

### 三条落到你项目的【推断】

1. **只装不改 + 内部自用** → 不触发任何源码提供义务（依据 §0 `convey` 定义 + §2）。
2. **改了 AGPL 组件又在内网给员工用** → §13 字面上要求把"你改的那版源码"提供给"远程交互的用户"（也就是你的员工）；满足方式是在内网放一个源码获取点，**不是**向社会公开。
3. **真正的雷是法人边界**：把系统交付到**甲方机房（甲方≠你）**，这一跳在许可证语境里构成 convey，GPL/AGPL 全部义务被触发（整体 GPL 授权 + 提供对应源码 + 允许再分发）。先定清"我方与部署方是否同一法人"。
4. GPL-3.0 与 AGPL-3.0 的 §0/§2 文字一致，**差别只在 §13 这一段**（AGPL 多出网络交互义务）——所以上面三条引用对 GPLv3 同样成立。

## 问题 3：仿宋_GB2312 / 楷体_GB2312 / 方正小标宋简体的版权处理

**一句话结论**：**方正小标宋简体是方正的商业字体**（属"基础字体"，且"嵌入软件/电子产品"须另签内置授权，价格表明确不含嵌入）；**仿宋_GB2312 / 楷体_GB2312 在公开一手来源里查不到权利人许可**，绝不能当"免费"用；**Windows/Office 自带版本不可随产品分发、也不可装进容器当内置字体**；而 **GB/T 9704-2012 原文只写"仿宋体字""小标宋体字"，不点名 GB2312、也不点名方正** —— 所以用 OFL 字体替代**不违反标准原文**。

### A. 方正官方授权政策（本轮【抓取】，原文）

来源：https://www.foundertype.com/index.php/About/bookAuth/key/my_grfs.htm （北京北大方正电子有限公司《方正字库"商业发布"授权价格说明》2016-02 起施行 + 《方正字库家庭版用户许可协议》）

- 三种使用方式，原文分得很清楚：
  > "1.内部使用：指个人或单位在其内部使用的终端设备上安装并使用字库的行为。该使用行为包括在屏幕上显示和临时从打印机上输出两种。
  > 2.内置使用：指将字库文件整体或部分、直接或格式转换后，以嵌入的方式应用到网站、计算机程序或带有可视化显示功能的电子产品中的行为。
  > 3.商业发布：指以直接营利或者间接营利为目的，将字体作为视觉设计要素，进行复制、发行、展览、放映、信息网络传播、广播等使用字体的行为。"
- **容器/服务端渲染 = 内置使用**，须单独授权。原文再次排除：
  > "上述价格不包括将被许可字库对应的电子文件整体或部分直接或格式转换后，以嵌入的方式应用到网站、计算机程序或带有可视化显示功能的电子产品中的使用方式。"
- 免费四款（关键，别记错）：
  > "**免费字体：包括四种字体：方正黑体、方正书宋、方正仿宋、方正楷体。** 针对'商业发布'这种使用方式免费。"
- 收费清单里点名了它：
  > "**基础字体**：包括二十二种字体：……方正大标宋体、**方正小标宋体**……"（基础字体商业发布 0.7 万元/年/款起，且嵌入另计）

→ **事实**：方正小标宋简体 = 商业字体（基础字体），**不在**方正免费四款内，且"随镜像/嵌入产品"禁止。
→ **【推断】容易混的一点**："方正仿宋、方正楷体"免费，指的是**方正自有**的这两款；它们**不等于** Windows 里那个 `仿宋_GB2312` / `楷体_GB2312`。别拿"方正仿宋免费"去给 `仿宋_GB2312` 背书。

### B. Windows / Office 自带版本

- MS Typography 官方 FAQ 口径（【转录】，本文该站本轮 30s 超时未重抓）：**不可再分发、不可转换格式**；含嵌入字体的文档一般可分发（受 `fsType` 限制），但**明令不得嵌入游戏/应用/设备**。https://learn.microsoft.com/en-us/typography/fonts/font-faq
- 【推断】容器镜像预装 `simfang.ttf` / `simkai.ttf` = 把字体嵌入"应用/设备"，同时是"再分发"（镜像会流到别人机器上）→ 两条都踩，**不可行**。
- Office 自带字体（含"方正小标宋简体"随某些中文 Office 模板下发的场合）同理由微软 EULA 约束，**不因字体文件被复制而转移授权**。【推断】

### C. 标准到底要求哪款字（"必须是仿宋_GB2312"还是"仿宋类即可"）

- 【转录】GB/T 9704-2012 原文只写 "**3 号仿宋体字**"（正文）、"**2 号小标宋体字**"（标题）；**没有** "_GB2312"、**没有** "方正"、**没有** "加粗"；"28 磅行距"也不在原文（原文是每面 22 行、每行 28 字）。见 `2026-10-21-PPT与Word生成方案.md` 的"必须纠正的三个流传误差"一节（该节引用原文 5.2.2 / 7.3.1 / 7.3.3）。
- 【未核实】标准本体本轮**未直连抓国标原文**（openstd 只有题录、无正文）。所以只能说"多份转录一致指向'仿宋体字/小标宋体字'"，不能说"我核了国标 PDF"。
- 【推断】因此 "**必须是仿宋_GB2312**" 是**基层规范 / 单位细则 / 领导观感**的用词，不是国标强制项。这是"仿宋类即可"的**唯一支点**，且支点强度取决于本单位有没有把 GB2312 写进内部细则。
