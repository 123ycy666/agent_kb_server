# 长 system prompt 对指令遵循的影响、工具目录该放哪、收尾该怎么切上下文：一手来源调研

抓取时间：2026-11-05（+08:00）。所有链接均为本轮实际抓取过的页面，引号内为原文摘录（英文原文照抄，不翻译的部分保留原文以避免失真）。

**证据等级**
- 【实测数字】= 来源里给出的可复现测量结果（模型名、样本量、分数）。
- 【厂商建议】= 厂商官方文档/工程博客给出的做法与判断，通常无公开对照数据。
- 【论文结论】= 论文作者基于其实验得出的结论（不含我加的解读）。
- 【我的推断】= 本轮没有任何来源直接说，由我据前几项推出，明确标明。

**一句话结论**：有大量证据说明「上下文变长 → 召回与指令遵从变差」，也有厂商明文说「规则文件太长会降低遵从」；但**没有**任何公开研究做过「同一组规则放在 18k 字符 system 里 vs 放在 427 字 system 里，单条遵从率对比」这个实验。这条空白在 §6 明确写出。

## 结论摘要

1. **位置效应有硬数据，且"中间"能差到不如不给**：Lost in the Middle 里 GPT-3.5-Turbo 把答案放到多文档上下文的中间时，准确率**低于完全不给文档的闭卷水平（56.1%）**。【论文结论】§1.1
2. **指令密度上升 → 遵从率单调下降，且最前沿模型也扛不住**：IFScale 20 个模型，claude-3.7-sonnet 从 10 条指令的 100% 掉到 500 条的 52.7%；最好的模型在 500 条时只有 68%，失败形态以"整条遗漏"为主。【实测数字】§1.2
3. **输入变长本身就会降性能，与任务难度无关**：Chroma 用 18 个模型、固定任务难度只改输入长度，性能一致下降；LongMemEval 上"只给相关片段（~300 token）"远好于"全量 113k token"。【实测数字】§1.3
4. **工具目录常驻的反面证据很硬（但只在大工具集）**：Anthropic 内部测得 tool definitions 占过 134K token；开 Tool Search Tool 后 Opus 4 工具选择准确率 49%→74%。**同时官方明说 <10 个工具时收益很小**——所以这条不能直接搬到 5–9 个工具的场景。【实测数字】+【厂商建议】§2
5. **大块静态知识的官方推荐是"混合"而非二选一**：Anthropic 明确写「先塞进上下文的（CLAUDE.md）+ 运行期按需取（glob/grep）」这套混合法更适合"内容不常变的领域，比如法律、金融"。【厂商建议】§3.2
5b. **缓存的硬约束决定"能怎么改"**：缓存顺序是 `tools` → `system` → `messages`，三者串联，"**modifying `tools` invalidates the `system` and `messages` caches**"；最小 checkpoint 因模型而异 **512–4,096 token**，TTL 5 分钟（每次命中重置）或 1 小时。【厂商建议】§3.1
6. **收尾的"浓缩 + 分工"是 Anthropic 的明文做法**：sub-agent "returns only a condensed, distilled summary of its work (**often 1,000-2,000 tokens**)"，lead "focuses on synthesizing and analyzing the results"；Anthropic 另有明文"each consideration handled by a separate LLM call"更好。【厂商建议】§4.1、§4.2b
7. **但"最终答案只吃压缩后的上下文"没有任何厂商给过字面表述**——这是**未找到**，不是我说它错。【事实】§4.3、§4.4
8. **可测**：IFEval（25 类可验证指令、~500 prompts、官方代码）和 IFScale（关键词包含、可自建）都能直接改成"回答是否守格式"的自动判分。【论文结论】§5

## 1. 长 system prompt 对指令遵循的影响：实测证据

### 1.1 Lost in the Middle：位置效应，且中间比"不给"更差

来源：Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*，TACL 2023 — https://arxiv.org/abs/2307.03172 （HTML 全文：https://arxiv.org/html/2307.03172v3 ）

- 【论文结论】摘要原文："we observe that performance is often highest when relevant information occurs at the beginning or end of the input context, and **significantly degrades when models must access relevant information in the middle of long contexts, even for explicitly long-context models**."
- 【实测数字·最狠的一条】正文 §1："when relevant information is placed in the middle of its input context, **GPT-3.5-Turbo's performance on the multi-document question task is lower than its performance when predicting without any documents** (i.e., the closed-book setting; **56.1%**)."
- 【实测数字】表 1：GPT-3.5-Turbo **闭卷 56.1% / oracle 88.3%**。
- 【实测数字】合成 key-value 检索任务里，"without query-aware contextualization, the **worst-case performance is 45.6%**"；而把 query 同时放在数据前后（query-aware contextualization）能让 300 对键值下接近满分。
- 【实测数字·边界条件】"the U-shaped performance curve **only appears in sufficiently large language models** … the **7B Llama-2 models are solely recency biased**, while the 13B and 70B models exhibit a U-shaped performance curve." —— 小模型不是"中间最差"，而是**只认最后面**。这条对我们的 7B 级内网模型尤其重要：**放在 system 末尾的内容反而更容易被吃进去，放在 system 中间的会被丢**。
- 【实测数字】检索文档加量无效："Using more than 20 retrieved documents only marginally improves reader performance (**~1.5% for GPT-3.5-Turbo and ~1% for Claude-1.3**)"。
- 【实测数字】编码器-解码器模型在训练长度内很稳："**1.9% absolute difference** between best- and worst-case performance"（Flan-UL2，2048 token 以内）；超出训练长度才出现 U 形。

**与第 1.3 节的冲突要摆明**：Chroma 在它自己的 NIAH 变体上"测试了 11 个 needle 位置，没有发现明显位置差异"。所以位置效应**不是普遍规律，是任务相关的**；但"输入越长越差"是两边都成立的。

### 1.2 IFScale：指令越多，遵从率越低（20 个模型，含前沿模型）

来源：Jaroslawicz et al., *How Many Instructions Can LLMs Follow at Once?* — https://arxiv.org/abs/2507.11538 （HTML：https://arxiv.org/html/2507.11538v1 ，榜单/数据：https://distylai.github.io/IFScale ）

- 【实测数字】摘要："we evaluate 20 state-of-the-art models across seven major providers and find that **even the best frontier models only achieve 68% accuracy at the max density of 500 instructions**."
- 【实测数字·可直接引用的曲线】附录 A 表 1（密度 10 / 50 / 100 / 250 / 500 条指令的准确率）：
  - claude-3.7-sonnet：**100.0% → 99.6% → 94.8% → 72.9% → 52.7%**
  - claude-opus-4：**100.0% → 100.0% → 94.6% → 67.9% → 44.6%**
  - claude-3.5-haiku：**98.0% → 78.0% → 43.4% → 16.6% → 8.5%**
  - 单模型极端值：grok-3 61.9%、o3 62.8%、deepseek-r1 30.9%、qwen3 26.9%（均在 500 条时）
- 【实测数字】三种退化形状："threshold decay"（gemini-2.5-pro、o3，"maintaining near-perfect performance through **150 or more instructions** before declining"）、"linear decay"（gpt-4.1、claude-3.7-sonnet）、"exponential decay"（claude-3.5-haiku、llama-4-scout，"level off around similar accuracy floors (**7-15%**)"）。
- 【实测数字·与"规则放前面"直接相关】首因效应（primacy effect = 末三分之错误率 / 首三分之错误率）：**在 150–200 条指令区间达到峰值，然后回落**。原文 §4.6："at extreme densities (300+ instructions), primacy effects uniformly diminish across all models, with most ratios converging toward **1.0–1.5**"；结论是"**packing more important instructions towards the beginning of a prompt may help, but it becomes a less effective strategy once extreme densities are reached**"。
- 【实测数字·失败形态】"Models overwhelmingly err toward **omission** errors as instruction density increases"（claude-3.5-haiku 的 omission:modification 比从 0.00 → 31.69）。**这正好对上"规则被整条无视"而不是"做了一半"的现象。**

**这条证据的边界（重要）**：IFScale 测的是**同一任务里并列的约束条数**（500 条 "Include the exact word X"），不是"system prompt 字符数"。它证明的是"约束一多就会整条丢"，不能直接换算成"18,400 字符的 system 会让某条规则失效"。

### 1.3 Context Rot（Chroma）：固定任务难度、只加长度，性能也掉

来源：Hong, Troynikov, Huber, *Context Rot: How Increasing Input Tokens Impacts LLM Performance*，Chroma Technical Report，2025-07-14 — https://www.trychroma.com/research/context-rot （代码：https://github.com/chroma-core/context-rot ）

- 【实测数字】规模：**18 个模型**（含 GPT-4.1、Claude 4、Gemini 2.5、Qwen3）；每个组合测 **8 个输入长度 × 11 个 needle 位置**；判分用对齐过的 GPT-4.1 judge。全量 194,480 次调用。
- 【实测数字·核心结论】"**Across all experiments, model performance consistently degrades with increasing input length.**" 实验设计的关键在于"hold task complexity constant while varying only the input length"。
- 【实测数字·最贴近"整份注入 vs 只给相关"的一条】LongMemEval：**聚焦输入平均 ~300 token，全量输入平均 ~113k token**；"Across all models, we see **significantly higher performance on focused prompts compared to full prompts**." 作者的解释是：全量输入等于让模型同时做"检索 + 推理"两件事。
- 【实测数字】干扰项（distractors，话题相关但不回答问题的内容）比无关内容更伤："**Even a single distractor reduces performance relative to the baseline** (needle only), and adding four distractors compounds this degradation further."
- 【实测数字·反直觉】"**models perform better on shuffled haystacks than on logically structured ones**" —— 逻辑连贯的长文比打乱句序的长文更难。
- 【实测数字·位置效应在此任务上不显著】"Testing across 11 needle positions, we find **no notable variation in performance** for this specific NIAH task."

### 1.4 厂商官方对"规则文件长度"的明文（无公开数据，但措辞确定）

来源：Claude Code 官方文档 *How Claude remembers your project* — https://code.claude.com/docs/en/memory （可直接抓 `.md` 版：https://code.claude.com/docs/en/memory.md ）

- 【厂商建议】"**Size**: target under 200 lines per CLAUDE.md file. **Longer files consume more context and reduce adherence.**"
- 【厂商建议】故障排查一节："**Files over 200 lines consume more context and may reduce adherence.**"
- 【厂商建议·冲突规则的后果】"if two instructions contradict each other, **Claude may pick one arbitrarily**."
- 【厂商建议·提示词不是强制】"Claude treats them as context, **not enforced configuration**. To block an action regardless of what Claude decides, use a PreToolUse hook instead."
- 【厂商建议·硬机制（这条是行为保证，不是建议）】按需加载的文件超过每文件字符上限时，模型**只收到开头**："When a subdirectory `CLAUDE.md` or a rules file that loads on demand is over a per-file size limit, **Claude receives only the start of it**. That part ends with a note telling Claude to read the rest with the Read tool"（200K 上下文窗口：**40,000 字符**；1M 上下文窗口：Opus 4.6 / Sonnet 4.6 为 **200,000 字符**，后续模型 150,000 字符）。

### 1.5 Anthropic 官方把机制讲成"注意力预算"

来源：Anthropic 工程博客 *Effective context engineering for AI agents* — https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

- 【厂商建议】"Studies on needle-in-a-haystack style benchmarking have uncovered the concept of **context rot**: as the number of tokens in the context window increases, **the model's ability to accurately recall information from that context decreases**."（注意：这句是 Anthropic **转述 Chroma 的实验**，不是它自己测的。真正的原始测量在 §1.3。）
- 【厂商建议】"Context, therefore, must be treated as a **finite resource with diminishing marginal returns** … LLMs have an '**attention budget**' that they draw on when parsing large volumes of context. **Every new token introduced depletes this budget by some amount**."
- 【厂商建议·直接对上"把边界 case 全塞进去"的做法】"teams will often **stuff a laundry list of edge cases into a prompt** in an attempt to articulate every possible rule the LLM should follow for a particular task. **We do not recommend this.**"
- 【厂商建议·但别过度删】"you should be striving for the minimal set of information that fully outlines your expected behavior. (Note that **minimal does not necessarily mean short**; you still need to give the agent sufficient information up front…)"
- 【厂商建议·规则要给"正确的抽象层级"】system prompt 要落在"right altitude"：一端是"hardcoding complex, brittle logic in their prompts"，另一端是"vague, high-level guidance"，两者都错。

### 1.6 这一节必须承认的证据缺口

- **未找到**：任何把「同一组回答规则分别放进长 system prompt 与短 system prompt，测单条遵从率」的公开对照实验。现有证据全是三条间接链：①长上下文召回退化（§1.1/§1.3）；②约束条数增加→整条遗漏（§1.2）；③厂商基于内部观察的经验结论（§1.4/§1.5，无公开数字）。
- 所以「规则埋在 19k 字符的 system 末尾会被忽略」在文献里是**合理外推，不是已发表结论**。【我的推断】

## 2. 工具定义该不该常驻 system

### 2.1 Anthropic Tool Search Tool：厂商内部实测（唯一有前后对比的一手数字）

来源：Anthropic 工程博客 *Introducing advanced tool use for Claude* — https://www.anthropic.com/engineering/advanced-tool-use

- 【实测数字·工具定义的 token 账】5 个 MCP server：GitHub 35 tools（**~26K tokens**）+ Slack 11（**~21K**）+ Sentry 5（~3K）+ Grafana 5（~3K）+ Splunk 2（~2K）= **58 tools / 约 55K tokens**；"Add more servers like Jira (which alone uses ~17K tokens) and you're quickly approaching 100K+ token overhead. **At Anthropic, we've seen tool definitions consume 134K tokens before optimization.**"
- 【实测数字·开启后的收益】"Tool Search Tool preserves **191,300 tokens of context compared to 122,800** with Claude's traditional approach"；上下文占用 **~77K → ~8.7K**，"preserving **95%** of context window"，"an **85% reduction** in token usage"。
- 【实测数字·准确率（最硬的一条）】"Internal testing showed significant accuracy improvements on MCP evaluations when working with large tool libraries. **Opus 4 improved from 49% to 74%**, and **Opus 4.5 improved from 79.5% to 88.1%** with Tool Search Tool enabled."（主语是 Anthropic 自家模型 + 内部 MCP 评测，不是小模型。）
- 【厂商建议·失败模式定性】"The most common failures are **wrong tool selection and incorrect parameters**, especially when tools have similar names like `notification-send-user` vs. `notification-send-channel`."
- 【厂商建议·启用阈值（决定这条能不能搬给我们）】**Use it when**: "Tool definitions consuming **>10K tokens**"、"10+ tools available"；**Less beneficial when**: "Small tool library (**<10 tools**)"、"Tool definitions are compact"。
- 【厂商建议·与 prompt caching 的关系（对我们最关键的一句）】"**Prompt caching note:** Tool Search Tool doesn't break prompt caching because deferred tools are excluded from the initial prompt entirely. They're only added to context after Claude searches for them, so your system prompt and core tool definitions remain cacheable." 机制是给工具打 `defer_loading: true`。"Keep your **three to five most-used tools always loaded**, defer the rest."

### 2.2 RAG-MCP：工具池越大，选错越严重（论文，有数字）

来源：Gan & Sun, *RAG-MCP: Mitigating Prompt Bloat in LLM Tool Selection via Retrieval-Augmented Generation* — https://arxiv.org/abs/2505.03275

- 【实测数字】摘要："RAG-MCP significantly cuts prompt tokens (e.g., by **over 50%**) and **more than triples tool selection accuracy (43.13% vs 13.62% baseline)** on benchmark tasks."
- 【论文结论】问题定义直接就是我们要问的："LLMs struggle to effectively utilize a growing number of external tools … due to **prompt bloat and selection complexity**."
- 边界（据其正文，见本仓库既有调研 `2026-10-21-工具调用可靠性与工具膨胀证据.md` 第 B 节）：base LLM 是云端 `qwen-max-0125`，评测集是 MCPBench 的 web-search 子集，**不是小模型实验**。

### 2.3 代码即工具（progressive disclosure 的极端形态）

来源：Anthropic 工程博客 *Code execution with MCP: Building more efficient agents* — https://www.anthropic.com/engineering/code-execution-with-mcp

- 【实测数字】把 MCP server 摊成文件树、模型按需读文件："This reduces the token usage from **150,000 tokens to 2,000 tokens**—a time and cost saving of **98.7%**."
- 【实测数字·中间结果污染的账】"the full call transcript flows through **twice**. For a 2-hour sales meeting, that could mean processing an additional **50,000 tokens**."
- 【厂商建议·渐进披露的两种实现】"Presenting tools as code on a filesystem allows models to read tool definitions on-demand"；或者给 `search_tools` 加 `detail level` 参数（"name only, name and description, or the full definition with schemas"）。

### 2.4 结论：这条对我们**不适用**，理由在来源里

- 【我的推断】Anthropic 官方把「<10 tools / 定义紧凑」列为"收益不大"的情形；本项目 5–9 个工具，工具 schema 也远不到 10K token，**所以 tool search / defer_loading 不是我们要解决的问题**。真正对标的是 §3（知识放哪），不是 §2。
- 【我的推断】唯一值得从这节搬走的原则是 `defer_loading` 背后的分层：**核心工具常驻 + 冷门工具按需展开**，且展开动作不能破坏稳定前缀（见 §3.1 的缓存契约）。

## 3. 大块业务知识（表结构、字段字典、口径）放哪

### 3.1 prompt caching 对"稳定前缀"的硬要求

**DeepSeek（对本项目最相关：走 OpenAI 兼容网关）** — 来源：https://api-docs.deepseek.com/guides/kv_cache

- 【厂商建议】默认开启、按前缀精确匹配："The DeepSeek API Context Caching on Disk Technology is **enabled by default** for all users… If subsequent requests have **overlapping prefixes** with previous requests, the overlapping part will only be fetched from the cache, which counts as a 'cache hit'."
- 【厂商建议·命中条件】"A subsequent request can only hit the cache if it **fully matches** a **cache prefix unit**." 缓存单元的落点有三种：请求边界（用户输入末尾、模型输出末尾）、跨请求的公共前缀、以及"**at fixed token intervals**"（长输入/长输出会被切块，避免永远等不到边界）。
- 【实测数字·官方 Example 2】同一个知识块、三种问法：第 1、2 次请求**都没有命中**；系统随后把 "`system` message + <financial report content>" 识别为 cache prefix unit 持久化；第 3 次请求**完全匹配它，命中**。→ 命中率最高的形状是"**稳定 system + 稳定知识块 + 只有末尾 user 轮变化**"。
- 【厂商建议·可观测、但有前提】usage 里有 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`；"The cache system works on a '**best-effort**' basis and **does not guarantee a 100% cache hit rate**"；缓存"usually within a few hours to a few days"后自动清理；"Cache construction takes **seconds**"。

**Anthropic 侧（经 Amazon Bedrock 官方文档核实；Anthropic 自家 caching 文档本轮抓不到，见 §6）**

来源：Amazon Bedrock User Guide, *Prompt caching for faster model inference* — https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html

- 【厂商建议·**改 tools 会不会连带作废**（本题最想要的一条）】"Cache checkpoints are processed in this order: **`tools` → `system` → `messages`**. The minimum cache size is evaluated against the cumulative tokens across all three sections combined, not each section individually. Because the sections are **chained, changing content in an earlier section invalidates the cache for later sections** (for example, **modifying `tools` invalidates the `system` and `messages` caches**)."
- 【厂商建议·最小长度不是固定值】"Cache checkpoints have a minimum and maximum number of tokens, depending on the model … **Minimums currently range from 512 to 4,096 tokens per cache checkpoint**." 表里逐模型：Claude Sonnet 4.6 / Opus 4.8 **1,024**；Claude Opus 4.5 / Opus 4.6 / Opus 4.7 / Haiku 4.5 **4,096**；Claude Sonnet/Haiku/Opus 5.5 与 Fable/Mythos **512**；每请求**最多 4 个** checkpoint。
- 【厂商建议·最小长度按"前缀累计"算，含 tools 与 system】"The minimum applies **cumulatively to the entire prompt prefix before each checkpoint**, including, where applicable, content in the `tools`, `system`, and `messages` fields."
- 【厂商建议·TTL】"The cache has a Time To Live (TTL), which **resets with each successful cache hit** … **Many models support a 5-minute TTL**"；可选 `"ttl": "1h"`；官方建议"system prompts that are used more frequently than every 5 minutes"就继续用 5 分钟档。
- 【厂商建议·"把 checkpoint 放在哪"的官方写法，正好是我们要的形状】"place one checkpoint after your **tool definitions**, one after your **system prompt**, and one after a **reference document**. When only the document changes, the tool definitions and system prompt are still read from cache."；并提醒回看只查约 **20 个 content block**。
- 【实测数字·计价（来自 Anthropic 产品页）】"**Writing to the cache costs 25% more** … while **using cached content** … costing only **10% of the base input token price**." 来源：https://claude.com/resources/articles/prompt-caching
- 【实测数字·官方三行基准，"10 轮长 system 多轮对话"就是我们现在的形状】"Multi-turn conversation (**10-turn convo with a long system prompt**)"：首 token 延迟 **~10s → ~2.5s（-75%）**，成本 **-53%**；"Chat with a book (**100,000 token cached prompt**)"：**11.5s → 2.4s（-79%）**，成本 **-90%**；"Many-shot prompting (10,000 token prompt)"：1.6s → 1.1s（-31%），**-86%**。（同 URL）
- 【厂商建议·与工具目录的交互（解释了为什么"延迟加载工具"不破坏缓存）】"Tool Search Tool doesn't break prompt caching because **deferred tools are excluded from the initial prompt entirely**. They're only added to context after Claude searches for them, so your system prompt and core tool definitions remain cacheable."（§2.1 URL）

**OpenAI 侧**（`platform.openai.com` / `developers.openai.com` / `cookbook.openai.com` 本轮全部 **403**；以下取自 AWS Bedrock 文档对 OpenAI 模型的实现说明）

- 【厂商建议·隐式缓存的最小前缀】"For OpenAI models prior to GPT-5.6 … Implicit Prompt Caching is automatic … The system automatically attempts to cache eligible prompt prefixes of **1,024 tokens or longer**."（同 AWS URL）
- 【厂商建议·显式断点 + TTL】"**Minimum prefix length** — 1,024 tokens per breakpoint"、"**30-minute minimum TTL**"、"Cache write billing — Tokens written to cache are billed at **1.25×** the uncached input token rate"；`usage` 里给 `cached_tokens` / `cache_write_tokens`。
- 【厂商建议·与本题直接对齐的一条】"Place breakpoints after stable content — Put content that doesn't change between calls, such as **system instructions, tool definitions, and reference documents**, before the breakpoint. **Content after the breakpoint can change without affecting the cache**."

### 3.1b 缓存视角的结论

- 【我的推断·在 system 后追加】旧前缀完整匹配，前半段照样命中，**但"长 system"的问题一条没解决**。
- 【我的推断·把 system 整段换掉】那一次是新前缀，**必付一次全量 miss**。所以"收尾换 system"的代价是**一次可预算的 miss**，不是"破坏缓存导致整体变慢"；换来的是短上下文 + 规则在更高优先级槽位。
- 【我的推断·改工具集要单独算账】因为 `tools` → `system` → `messages` 是串联的，**收尾那一步若连工具集一起精简，会额外作废 `system` 缓存**（§3.1 第一条）。要省 token 时，这两个动作别混在同一次改动里评估。

### 3.2 常驻 vs 按需取：官方推荐的是"混合"，且给了领域判据

来源：Anthropic *Effective context engineering for AI agents*（同 §1.5 URL）

- 【厂商建议·just-in-time 的定义】"Rather than pre-processing all relevant data up front, agents built with the 'just in time' approach **maintain lightweight identifiers** (file paths, stored queries, web links, etc.) and use these references to **dynamically load data into context at runtime** using tools."
- 【厂商建议·progressive disclosure 的定义】"allows agents to **incrementally discover relevant context through exploration** … Agents can assemble understanding layer by layer, maintaining only what's necessary in working memory."
- 【厂商建议·按需取的代价（必须承认）】"there's a trade-off: **runtime exploration is slower than retrieving pre-computed data**. Not only that, but opinionated and thoughtful engineering is required to ensure that an LLM has the right tools and heuristics…"
- 【厂商建议·混合法 + 领域判据（直接对上我们的场景）】"**The hybrid strategy might be better suited for contexts with less dynamic content, such as legal or finance work.**" 官方举的例子正是 Claude Code："CLAUDE.md files are naively **dropped into context up front**, while primitives like **glob and grep** allow it to navigate its environment and retrieve files just-in-time"。
- 【厂商建议·规则的另一种分层实现（官方产品机制）】Claude Code 的 `.claude/rules/` 支持按路径懒加载："Rules can also be **scoped to specific file paths**, so they only load into context when Claude works with matching files, **reducing noise and saving context space**."（https://code.claude.com/docs/en/memory ）

### 3.3 取舍怎么算（有出处的部分）

- 【论文结论】"当上下文无关内容增多时，模型被迫同时做检索和推理" —— Chroma 对 LongMemEval 的解释："Adding irrelevant context adds the additional step of identifying what is relevant, **forcing the model to perform two tasks simultaneously**."（§1.3 URL）
- 【我的推断】对"查数口径"这类**几乎每轮都要用、内容又不常变**的知识，官方混合法给的答案不是"删掉"，而是：**常驻一份"索引/指引 + 最常用子集"，其余按需取**（对应 Anthropic 的 3–5 个常驻工具 + 其余 defer；Claude Code 的 CLAUDE.md + grep）。若按需取的比例高，"运行期更慢"这个代价要单独付。
- 【我的推断·缓存视角的反向约束】把知识从 system 移走会**缩短稳定前缀**，DeepSeek 是按前缀匹配的，前缀变短不改变"命中同一前缀"这件事，但会让**每次调用都要多一次取知识的往返**（多一步 = 多一次 round trip）。

## 4. 收尾 / 合成步骤的最小上下文做法

### 4.1 Anthropic 有明文：sub-agent 只回"浓缩摘要"，量级 1,000–2,000 token

来源：Anthropic *Effective context engineering for AI agents*（同 §1.5 URL）

- 【厂商建议·最直接的证据】"Each subagent might explore extensively, using tens of thousands of tokens or more, but **returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)**. This approach achieves a **clear separation of concerns**—the detailed search context remains isolated within sub-agents, while **the lead agent focuses on synthesizing and analyzing the results**."
- 【厂商建议·compaction 的官方定义】"Compaction is the practice of taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary."
- 【厂商建议·最轻的一种压缩，正是"丢掉工具原始结果"】"An example of low-hanging superfluous content is **clearing tool calls and results** – once a tool has been called deep in the message history, why would the agent need to see the raw result again? One of the safest lightest touch forms of compaction is **tool result clearing**, most recently launched as a feature on the Claude Developer Platform."
- 【厂商建议·structured note-taking】"the agent regularly writes notes persisted to memory outside of the context window. These notes get pulled back into the context window at later times."

### 4.2 指令层级：为什么"收尾单开一次调用"在机制上更可靠

来源：Wallace et al., *The Instruction Hierarchy: Training LLMs to Prioritize Privileged Instructions*（OpenAI）— https://arxiv.org/abs/2404.13208

- 【论文结论】"one of the primary vulnerabilities … is that LLMs often consider **system prompts** (e.g., text from an application developer) **to be the same priority as text from untrusted users and third parties**." 论文提出的方案是训练模型"**selectively ignore lower-privileged instructions**"。
- 【我的推断】这条**不能**证明"短 system 更有效"，但它证明"system 槽位的指令与 user 槽位的指令在模型看来优先级应当不同"。所以"把回答规则从 system 末尾挪到**独立一次调用的 system 位**"不只是缩短上下文，还是把它放到优先级更高的槽位。

### 4.2b "把考虑点拆成不同调用"这条在 Anthropic 有明文

来源：Anthropic *Building effective agents* — https://www.anthropic.com/engineering/building-effective-agents （现 302 到 https://www.anthropic.com/research/building-effective-agents ，正文同）

- 【厂商建议·最接近"另一次调用专管输出"的一句】"**For complex tasks with multiple considerations, LLMs generally perform better when each consideration is handled by a separate LLM call**, allowing focused attention on each specific aspect."
- 【厂商建议·同一篇文章里的实证类比（拆调用比合调用好）】"Implementing guardrails where **one model instance processes user queries while another screens them** for inappropriate content or requests. **This tends to perform better than having the same LLM call handle both guardrails and the core response.**"
- 【厂商建议·prompt chaining 的定义】"Prompt chaining decomposes a task into a sequence of steps, where each LLM call processes the output of the previous one. You can add programmatic checks … on any intermediate steps"；适用场景是"the task can be easily and cleanly decomposed into fixed subtasks … trade off latency for higher accuracy, by making each LLM call an easier task."
- 【厂商建议·三步式例子，结构与"查数→核对→写答案"同形】"Writing an outline of a document, **checking that the outline meets certain criteria**, then writing the document based on the outline."
- 【厂商建议·orchestrator 的定位】"In the orchestrator-workers workflow, a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and **synthesizes their results**."

### 4.3 OpenAI 与 Google 的一手说法

**OpenAI**（`platform.openai.com` / `developers.openai.com` / `cdn.openai.com` 的 PDF 本轮全部 403 或被拦，故只能引 Agents SDK 文档站）

- 【厂商建议·"由谁产出最终答案"是可配置项】https://openai.github.io/openai-agents-python/multi_agent/ ：Agents-as-tools 模式的适用场景原文 "**You want one agent to own the final answer, combine outputs from multiple specialists**, or enforce shared SDK guardrails in one place."；机制是 "A manager agent keeps control of the conversation and calls specialist agents through `Agent.as_tool()`."
- 【厂商建议·阶段串联的顺序（研究在前、写作在后）】同页："Chaining multiple agents by transforming the output of one into the input of the next. You can decompose a task like writing a blog post into a series of steps - **do research, write an outline, write the blog post, critique it, and then improve it**."
- 【厂商建议·守卫只挂在"产出最终输出"的那个 agent 上】https://openai.github.io/openai-agents-python/guardrails/ ："Input guardrails run only for the first agent in the chain." / "**Output guardrails run only for the agent that produces the final output.**"；并且"you can run a guardrail with a fast/cheap model … Blocking execution guarantees that the expensive model does not start"。
- **未找到**：OpenAI 文档里"把压缩后的上下文传给最终生成步"的字面表述。

**Google（ADK）**

- 【厂商建议·"并行取数 + 后续 agent 汇总"是官方 pattern】https://adk.dev/workflows/patterns/index.md ："A `ParallelAgent` runs multiple `sub_agents` concurrently, **often followed by a later agent (in a `SequentialAgent`) that aggregates results**."；"Execute independent tasks simultaneously to reduce latency, then **combine their outputs**."
- 【厂商建议·汇总 prompt 只吃已结构化好的结果】官方示例：`synthesizer = LlmAgent(name="Synthesizer", instruction="Combine results from {api1_data} and {api2_data}.")`，注释说明前者并发跑完"**saving to state**"、`synthesizer` 之后"**reading state['api1_data'] and state['api2_data']**"。
- 【厂商建议·步间通信只传结果不传全量历史】"**Communication:** Primarily uses **Shared Session State**. Earlier agents write results (often via `output_key`), later agents read those results from `context.state`."（同页）；另一页："**The output from each sub-agent is passed to the next by storing them in state via [Output Key]**"（https://adk.dev/agents/workflow-agents/sequential-agents/index.md ）
- 【厂商建议·官方也做上下文压缩】"ADK Context Compaction feature is designed to **reduce the size of context** as an agent is running by summarizing older session history—including instructions, inputs, and model responses."（https://adk.dev/context/compaction/index.md ）
- **未找到**：Google 官方"最终答案必须由缩减后的上下文单独生成"的字面表述；`cloud.google.com` 与 Kaggle 上的《Agents》白皮书本轮抓不到正文。

### 4.4 一条要小心引用的更正

- 【事实】本仓库既有笔记与不少二手文章把"subagent 只回传 **1,000–2,000 tokens**"挂在 Anthropic 那篇 multi-agent research system 上。**该文没有这个数字**（本轮逐段核过）。这个数量级只出现在 *Effective context engineering for AI agents*（§4.1）。multi-agent 那篇的对应表述是定性的："The essence of search is compression: distilling insights from a vast corpus."（https://www.anthropic.com/engineering/multi-agent-research-system ）另有一句是"传轻量引用而不是原文"："Subagents call tools to store their work in external systems, then **pass lightweight references back to the coordinator**. This prevents information loss … and reduces token overhead from copying large outputs through conversation history."
- 【实测数字】同一篇给出的成本量级："agents typically use about **4× more tokens** than chat interactions, and multi-agent systems use about **15× more tokens** than chats"；以及上下文超限即截断："if the context window exceeds **200,000 tokens it will be truncated** and it is important to retain the plan"。
- 【厂商建议·最贴近"独立收尾环节"的产品化描述】"Once sufficient information is gathered, the system exits the research loop and **passes all findings to a CitationAgent**, which processes the documents and research report to identify specific locations for citations." —— 这是"最后一步是另一个专职环节"，但仍不是"喂给它的只有压缩上下文"。

## 5. 可测量的判据：公开、可复现的评测方法

### 5.1 IFEval：可验证指令 + 官方代码，最省事的模板

来源：Zhou et al., *Instruction-Following Evaluation for Large Language Models*（Google）— https://arxiv.org/abs/2311.07911

- 【论文结论】"IFEval is a straightforward and **easy-to-reproduce** evaluation benchmark. It focuses on a set of '**verifiable instructions**' such as '**write in more than 400 words**' and '**mention the keyword of AI at least 3 times**'. We identified **25 types** of those verifiable instructions and constructed **around 500 prompts**, with each prompt containing one or more verifiable instructions."
- 【可复现性】代码与数据：https://github.com/google-research/google-research/tree/master/instruction_following_eval
- 【我的推断】IFEval 的两条示例恰好覆盖我们要测的两件事：**长度约束**（"more than 400 words"→ 对应"回答别啰嗦"）和**关键词/格式约束**（"at least 3 times"→ 对应"必须出现某几段结构"）。可以照抄它的判分思路（正则/计数，不用 LLM judge）自建 20–50 条。

### 5.2 IFScale：把"约束条数"做成自变量（可自建的最小实验）

来源：https://arxiv.org/abs/2507.11538

- 【论文结论】任务本身极简且自动判分："Each instruction is a constraint to include a specific keyword in the generated report. This allows us to easily **scale instruction density from 10 to 500 instructions with a step size of 10** and automatically grade performance by **keyword inclusion**."
- 【实测数字】每档 5 个随机种子；判分用"wildcard-enabled regex matching"。方差、首因效应、omission:modification 比都被量化（§1.2）。
- 【我的推断】照这个骨架，"缩短 system 是否更守规则"可以做成一个**对照实验而非感觉**：同一批问题 × 两个版本（长 system / 短 system）× N 次，判分用固定正则集合，报告"规则命中条数"与方差。

### 5.3 多轮一致性：Multi-IF

来源：He et al., *Multi-IF: Benchmarking LLMs on Multi-Turn and Multilingual Instructions Following*（Meta）— https://arxiv.org/abs/2410.15553

- 【实测数字】"**All the models tested showed a higher rate of failure in executing instructions correctly with each additional turn.** For example, **o1-preview drops from 0.877 at the first turn to 0.707 at the third turn** in terms of average accuracy over all languages."
- 【规模】基于 IFEval 扩成多轮："resulting in a dataset of **4,501 multilingual conversations, where each has three turns**"，代码与 prompts 开源。
- 【我的推断】这条对应我们最关心的"第 N 步才收尾"的场景：**同一套规则，轮次越多越不守**。它给了一个现成的量化口径（第 1 轮 vs 第 3 轮的准确率差），可以拿来当"收尾轮次是否吃亏"的基准。

### 5.4 长上下文退化本身也能测

- 【实测数字】Chroma 的做法可直接借用：固定任务难度，只改输入长度，测 8 个长度档（§1.3），代码在 https://github.com/chroma-core/context-rot 。

## 7. 对我们的直接含义

> 只列有出处支撑的条目，且每条只写"该做什么"。

1. **收尾那次调用必须真的换掉 system，而不是在后面追加**。依据：Lost in the Middle 与 IFScale 都显示"靠后 / 密度高"的内容更容易整条丢（§1.1、§1.2），追加只是把规则留在 19k 前缀的末尾；而"换掉 system"在缓存上的代价是**可算的一次性 miss**——DeepSeek 按完整前缀匹配（§3.1），换 system 等于换新前缀，那一次不会命中，但换来的是"短上下文 + 规则在最高优先级槽位"，这正是 Anthropic 描述的分工："the detailed search context remains isolated within sub-agents, while the lead agent focuses on synthesizing and analyzing the results"（§4.1）。反过来，若只在原 system 后追加，前缀仍能命中，但"长 system"的问题一条没解决。
2. **把"事实清单"做成收尾调用的唯一输入，口径文档不进那次调用**。依据：Chroma 在 LongMemEval 上实测"只给相关片段（~300 token）显著优于全量 113k"（§1.3）；Anthropic 官方对 context rot 的处置就是"find the smallest set of high-signal tokens"（§1.5）。
3. **不要为了"少注入"去上工具检索/tool search——我们把问题归错了类**。依据：Anthropic 明说工具库 **<10 个**时 Tool Search Tool 收益很小（§2.1），本项目 5–9 个工具；真正的 token 大头是口径知识，应按 §3.2 的"混合法"处理。附带一条硬约束：**缓存顺序是 `tools` → `system` → `messages`，改 `tools` 会连带作废 `system` 与消息的缓存**（§3.1），所以"收尾时顺手精简工具集"这个动作会在缓存上双重付费。
4. **口径知识若要拆，优先按"是否每轮都用"分层，而不是按"表/字段/字典"分层**。依据：官方混合法的判据是内容动态性（"less dynamic content, such as legal or finance work"适用先塞进去），并把"每轮都用"的部分常驻、其余按需取（§3.2）；Claude Code 的产品化实现就是"常驻 CLAUDE.md + 按需 glob/grep / path-scoped rules"。
5. **验证方式照抄现成评测，不要自创主观标准**：用 IFEval 式的**可验证约束**（字数上限、必须出现的段落标题、必须出现的数字）做正则判分（§5.1），跑"长 system / 短 system"两组对照 + 至少 3 次取方差，用 Multi-IF 的"第 1 轮 vs 第 N 轮"口径看收尾轮是否系统性更差（§5.3）。
