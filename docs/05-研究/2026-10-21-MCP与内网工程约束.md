## 1. MCP 协议现状

### 1.1 版本与传输（事实）

| 项目 | 2026-10-21 的状态 | 来源 |
|---|---|---|
| 最新规范版本 | **`2026-07-28`**（站点标注 "Version 2026-07-28 (latest)"） | [spec 入口](https://modelcontextprotocol.io/specification/2026-07-28) |

**结论（事实）：stdio 与 Streamable HTTP 是当下唯一两个标准绑定；SSE 传输已进入官方弃用登记，新实现不要采用。**

### 1.2 `2026-07-28` 的九条重大变化（都是自建客户端会踩的）

来源：[Key Changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog)（每条都标注了对应 SEP/PR）

1. **去会话**：Streamable HTTP 删掉 `Mcp-Session-Id` 头；`tools/list` / `resources/list` / `prompts/list` 不再随连接变化（SEP-2567）。需要跨调用状态的 server 改用"服务端发放的显式句柄"当普通工具参数传。
2. **无状态化**：删掉 `initialize` / `notifications/initialized` 握手；每个请求在 `_meta` 里带 `io.modelcontextprotocol/protocolVersion` 与 `clientCapabilities`，版本不匹配返回 `UnsupportedProtocolVersionError`（SEP-2575）。
3. **新增 `server/discover`**：server **MUST** 实现，用来声明支持的版本、能力、身份（SEP-2575）。
4. **订阅改造**：删掉 HTTP GET 端点与 `resources/subscribe`/`resources/unsubscribe`，改用 `subscriptions/listen` 长连（SEP-2575）。
5. **删掉 `ping`、`logging/setLevel`、`notifications/roots/list_changed`**；日志级别改为请求级 `_meta.io.modelcontextprotocol/logLevel`。
6. **tasks 移出核心**，变成官方扩展 `io.modelcontextprotocol/tasks`（`tasks/get` 轮询 + `tasks/update`，删除 `tasks/list`）（SEP-2663）。
7. **MRTR（多轮往返）** 取代"服务端主动发请求"（roots/sampling/elicitation）：server 返回 `resultType: "input_required"` + `inputRequests`，客户端带 `inputResponses` 重发原请求（SEP-2322）。
8. **所有结果新增必填 `resultType`**（`"complete"` / `"input_required"`）；老 server 不返回时客户端 **MUST** 当 `"complete"` 处理。
9. **删掉 SSE 断线重传**（`Last-Event-ID`、SSE event id）：流断了就当请求丢失，客户端 **MUST** 用新 request id 重发。

另有两条与"工具膨胀"直接相关的次要变化：

- **`tools/list` 等结果必须带 `ttlMs` 与 `cacheScope`**（CacheableResult，SEP-2549）——客户端可以缓存工具表，不必每次重拉。
- **server SHOULD 以确定性顺序返回 `tools/list`**，目的是"enable client-side caching and improve LLM prompt cache hit rates"。即：**官方自己承认工具表会进提示词、且吃缓存**（呼应 §4）。

### 1.3 授权机制（事实）

来源：[Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)（原文为 `.md` 版，内容更完整）

- **授权是 OPTIONAL**。原文："Authorization is **OPTIONAL** for MCP implementations."
- 用 HTTP 传输的 **SHOULD** 遵循；用 **stdio 的 SHOULD NOT** 遵循，改为"从环境变量取凭据"。
- 机制是 **OAuth 2.1（draft-ietf-oauth-v2-1-13）的子集**，叠加 RFC 6750 / 8414 / 7591 / **8707（Resource Indicators）** / **9728（Protected Resource Metadata）** / 9207（iss）与 OAuth Client ID Metadata Documents。
- 硬要求：MCP server（资源服务器）**MUST** 实现 RFC 9728 PRM 并在 `WWW-Authenticate` 里给出 `resource_metadata`；客户端 **MUST** 用 PRM 做授权服务器发现；**MUST** 在授权与令牌请求里带 `resource`（RFC 8707）；令牌只放 `Authorization: Bearer`，**MUST NOT** 放 query。
- **动态客户端注册（DCR, RFC 7591）已弃用**，保留兼容；推荐 Client ID Metadata Documents。

**结论（事实 + 推断）：单租户内网自建场景可以直接跳过整套 OAuth——规范本身写的是 OPTIONAL，stdio 又明确 SHOULD NOT 走它。内网若用 Streamable HTTP，用一份静态 Bearer（如 excel-mcp-server 的 `EXCEL_MCP_AUTH_TOKEN`）就够，不必为 MCP 引入 OAuth 服务器。**

### 1.4 兼容性（推断，标注依据）

规范给了"旧版互操作"的检测与回退矩阵（[Versioning / Backward Compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning#backward-compatibility-with-initialization-based-versions)），所以"新客户端连旧 server"在协议层是被照顾的。但**第三方 server 与 SDK 是否已跟进 `2026-07-28`，本次未逐个核实**——从 §2 的盘点看，办公类 server 绝大多数停在 `2025-06-18`/`2025-11-25` 一代（`mcp[cli]`、`fastmcp` 老版本、README 写 Claude Desktop 配置）。

### 2.2 逐个判定：Linux 无 Office 环境下能不能跑

**(1) Word —— 能跑，但别用它的 `convert_to_pdf`**

- 依赖来自仓库 `requirements.txt`：`fastmcp / python-docx / msoffcrypto-tool / **docx2pdf** / python-dotenv`。
- 阻断点在 `docx2pdf`：PyPI 页面标题即 "Convert `docx` to `pdf` on Windows or macOS directly using Microsoft Word (**must be installed**)"，实现方式 "On Windows, this is implemented via `win32com` while on macOS this is implemented via JXA"（[PyPI](https://pypi.org/project/docx2pdf/)）。**Linux 上无法用。**
- 其余工具（建文档、加标题/表格/图片、脚注、批注、保护、格式）都是 python-docx 的纯 Python 操作，跨平台。
- 结论（事实）：**除 PDF 导出外可用；PDF 导出要换成 LibreOffice。**

**(2) PowerPoint —— 能跑**

- 依赖：`mcp[cli] / python-pptx / Pillow / fonttools`，无 COM、无 Office。
- python-pptx 官方首页写明 "runs on any Python capable platform, including macOS and Linux, and **does not require the PowerPoint application to be installed or licensed**"（[python-pptx 文档](https://python-pptx.readthedocs.io/en/latest/)）。
- 坑（推断，来自仓库体积与做法）：仓库 69,663 KB，主要是预置模板资产；这些模板里的字体名（如 `思源黑体`、`微软雅黑`）在 Linux 容器里**只写进 XML、不落地渲染**，所以生成不失败；但一旦要缩略图/PDF 预览就必须在容器里装中文字体（见 §6.3）。

**(3) Excel —— 用 `haris-musa/excel-mcp-server`，是目前这一族里唯一"活着的"**

- README 明写："built on `openpyxl`, needs **no Microsoft Excel**, and runs on Windows, macOS and Linux"；支持 `.xlsx/.xlsm/.xltx/.xltm`，自带约 260 个函数的计算引擎，能算 Excel 从未打开过的文件里的公式值。
- 支持 **stdio 与 Streamable HTTP**（`uvx excel-mcp-server streamable-http --allow-dir /srv/workbooks`，localhost:8017 + `Authorization: Bearer`）。
- **它自己把"工具表占上下文"当一等问题**：提供 `--tools` 按区域裁剪，并在 README 里列出每区域的字符数（"Every tool costs context in every request … at about 3.5 characters per token"）。全量约 **60,700 字符 ≈ 1.7 万 token**（我按其表格逐项相加：core 8,900 + workbooks 2,600 + csv 2,200 + sheets 2,000 + data 6,700 + formulas 1,300 + formatting 14,000 + tables 1,900 + charts 9,900 + pivots 4,600 + slicers 2,500 + names 900 + notes 500 + images 800 + vba 1,900）。

**(4) `mcp-server-office`（npm，mindstone）—— 不能跑，且许可证不是开源**

- npm registry 元数据：`"description": "Microsoft Office (Word, Excel, PowerPoint) MCP server … **Bundles the stdio MCP server, the Office add-in sidecar, and the add-in task pane assets**"`，`"license": "FSL-1.1-MIT"`，deps 含 `office-addin-dev-certs`、`@types/office-js`。
- 即：它的工作原理是**在装有 Microsoft Office 的桌面端插一个 add-in**，MCP server 只是和 sidecar 通信。**Linux 无 Office 场景直接不成立。**
- `FSL-1.1-MIT` 是 Fair Source License（源可用、非 OSI 开源），通常带"年营收超阈值需商业授权"之类限制——**具体条款本次未核实**，但足以判定：不能当成 MIT/Apache 一样随便内嵌交付。

**(5) PDF —— MCP 生态里没有可靠的"生成 PDF"server**

- 现有的是**读取/转换**向：markitdown（PDF→Markdown）、pdfplumber（本项目已用）。
- 生成 PDF 的现实路子只有两条：**LibreOffice `--convert-to pdf`**（§6.4），或 Python 侧 reportlab/WeasyPrint（后者依赖系统库，离线装更麻烦，未核实）。

**结论（加粗给决策用）：**
**能在 Linux 无 Office 环境跑：Excel（haris-musa/excel-mcp-server，MIT，活跃）、Word（GongRzhe/Office-Word-MCP-Server，MIT，已归档，除 PDF 导出）、PPT（GongRzhe/Office-PowerPoint-MCP-Server，MIT，已归档）。**
**不能跑：任何依赖 Office COM / Office add-in 的方案——`@mindstone-engineering/mcp-server-office`、Word server 的 `docx2pdf` 导出、以及任何"服务端调 Word/WPS"的变体（微软对此有明文，见 §6.4）。**
**共同风险：两个最有名的 Word/PPT server 已归档（2025-12-31 后零提交），fork 全是 1 星。选 MCP 等于选"接手一份没人维护的代码"。**

## 3. 在 OpenAI 兼容（非 Claude）模型上接 MCP 的现实做法

### 3.1 核心事实：MCP 与 OpenAI function calling 之间没有任何协议层"桥"，必须自己写一层翻译

- **MCP 的 `tools/list` 返回的是 JSON Schema 的 `inputSchema`；OpenAI 的 `tools[].function.parameters` 也是 JSON Schema。** 两者形状高度重合，所以"搬过去"这一步几乎是恒等映射（字段名 `name` / `description` / `parameters` 一一对应）。依据：[MCP Server/Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)（工具定义含 `inputSchema`）、OpenAI function calling 的 `tools` 数组结构（本项目 `agent.py:35-70` 就是手写的 Open-AI 形 tools，可直接对照）。
- **真正的翻译工作在"调用"与"结果"两端**：
  - 模型返回 `tool_calls[].function.name/arguments` → 你要找出发起它的那个 MCP server → 发 `tools/call`（`name` + `arguments`）→ 拿 `content` 数组（多段 `text`/`image`…）→ 拍平成一条 `role="tool"` 的字符串 → 回填进 messages。
  - **OpenAI 协议要求 `assistant(tool_calls)` 后必须紧跟对应的 `tool` 消息**，否则 400。本项目已经为此写了一整套 `_sanitize_messages()`（`agent.py:122-192`，注释里记录了"insufficient tool messages following tool_calls message"这个真实 400）。**接 MCP 会让这条约束更容易被踩**：MCP 一侧一个工具调用可能返回多段 content、也可能是 `isError=true`，都必须在回填前对齐成"一条 tool 消息"。
- **没有"官方"的 OpenAI×MCP 参考实现**：OpenAI 自己的 Agents SDK 是 MCP 客户端，但它面向的是 OpenAI 自家 Responses/Chat Completions 端点，**不是给"任意 OpenAI 兼容端点"准备的适配层**——这一段本次未深入核实具体代码，标记为未核实。

### 3.2 现成的客户端适配层（事实）

| 项目 | 定位 | 状态（2026-10-21） | 与"OpenAI 兼容端点"的关系 |
|---|---|---|---|
| [langchain-ai/langchain-mcp-adapters](https://github.com/langchain-ai/langchain-mcp-adapters) | 把 MCP 工具转成 LangChain tool（再 `bind_tools` 给任意 chat model） | **README 置顶："This repository is no longer actively maintained"，MCP 支持已并入 `langchain[mcp]`（`langchain.mcp` 命名空间）** | 能用：`MultiServerMCPClient` + `model.bind_tools(tools)`；只要模型客户端是 OpenAI 兼容的即可 |
| `langchain[mcp]`（官方继任者） | 同上，进主仓 | 活跃（据 README 迁移说明） | 同上，但要求 langchain ≥ 1.x，**依赖树很重** |
| `mcp`（官方 Python SDK）的 `ClientSession` / `stdio_client` / `streamablehttp_client` | 底层客户端；自己拿 `list_tools()` 再自己拼 OpenAI tools JSON | 活跃 | **最贴合本项目**（零框架），代价是翻译层自己写 |

关键警告 —— 这句话来自 langchain-mcp-adapters README 的代码注释，是本次调研里**最直接反对"在 Web 服务里用 stdio MCP"的一手证据**：

> "ATTENTION: MCP's stdio transport was designed primarily to support applications running on a user's machine. Before using stdio in a web server context, evaluate whether there's a more appropriate solution. For example, **do you actually need MCP? or can you get away with a simple `@tool`?**"

### 3.3 代际错位（事实 + 推断）

- 上述库的示例代码至今仍是 `await session.initialize()` 起的**握手时代**（对应 `2025-06-18` / `2025-11-25`），而 `2026-07-28` 已经**删掉了 `initialize`**（见 §1.2）。
- 推断：内网落地时，"新 SDK 客户端 + 老第三方 server"是最可能的组合。规范给了兼容矩阵，但**这条路径没人替你测**，属于自担风险。

## 4. 提示词 / 工具膨胀风险

### 4.1 三个互相独立的效应（机制层面）

1. **工具定义本身占上下文**。绝大多数 MCP 客户端把**全部**工具定义一次性塞进上下文。
2. **选择歧义**：工具越多、名字与描述越接近，模型选错工具的概率越高（下节给数据）。
3. **本项目特有的放大器**：查数轮强制 `tool_choice='required'`（`agent.py:212-215`）——**模型没有"不调工具"这个选项**。工具表里只要有 1 个不该在这轮出现的工具，被选中就是流程性错误，而不是"答得差一点"。

### 4.2 公开数据（有出处的）

**(a) Anthropic 官方工程博客直接量了这件事** —— [Code execution with MCP for efficient agents](https://www.anthropic.com/research/code-execution-with-mcp)：

> "Most MCP clients load all tool definitions upfront directly into context, exposing them to the model using a direct tool-calling syntax."
> "Tool descriptions occupy more context window space, increasing response time and costs. In cases where agents are connected to thousands of tools, they'll need to process **hundreds of thousands of tokens** before reading a request."

同一篇给出的改造效果（**这是本篇唯一的硬数字**）：

> "This reduces the token usage **from 150,000 tokens to 2,000 tokens**—a time and cost saving of **98.7%**."

**(b) 厂商自己在 README 里把"工具表成本"列成了预算表** —— [excel-mcp-server README](https://github.com/haris-musa/excel-mcp-server)：

> "Every tool costs context in every request."（按"约 3.5 字符/token"折算）

它给出 15 个工具区域的字符数，全量合计 **≈60,700 字符 ≈ 17,000 token**（core 8,900 / formatting 14,000 / charts 9,900 / data 6,700 / pivots 4,600 …）。所以它提供 `--tools` 参数，只暴露 core + 指定区域。

**(c) 规范作者也在为"工具表进提示词"做优化** —— `2026-07-28` 要求 `tools/list` 结果带 `ttlMs`/`cacheScope`，并要求 server **SHOULD** 以确定性顺序返回工具列表，理由写明是 "improve LLM prompt cache hit rates"（[Key Changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog)）。**工具表属提示词的一部分，这是官方口径。**

**(d) 本项目自己的量级（实测）**：`agent.py:35-70` 的 `TOOLS` 字面量共 **2,039 字符**（其中中文 520 字），折算约 600–1,000 token。**把 excel-mcp-server 全量工具箱挂进来，工具表会放大 ~20–30 倍。**

### 4.3 业界推荐的替代架构（都有出处，不是我的发明）

| 架构 | 做法 | 出处 |
|---|---|---|
| **渐进式披露（progressive disclosure）** | 工具定义不进上下文，改成"按需读"：把每个工具写成一个文件，模型先列目录、再读它需要的那一个；或提供 `search_tools` 工具，支持 `detail level`（只有名字 / 名字+描述 / 完整 schema） | [Anthropic: Code execution with MCP](https://www.anthropic.com/research/code-execution-with-mcp) |
| **Code Mode / 代码执行调工具** | 把 MCP server 暴露成**代码 API**，模型写代码调工具、在沙箱里过滤/聚合结果，只把结果摘要带回上下文 | 同上；[Cloudflare: Code Mode](https://blog.cloudflare.com/code-mode/)（Anthropic 文中称之为 "Code Mode"） |
| **工具集裁剪 / 分区** | 服务端只暴露当前任务需要的那一簇工具 | excel-mcp-server 的 `--tools`（[README](https://github.com/haris-musa/excel-mcp-server)） |
| **按意图分工具集 / 子 agent** | 主循环只带"路由工具"，命中意图后再把对应工具集交给下一跳（子 agent 或第二轮） | 与上方 progressive disclosure 同源思路；**本项目现有 `ask()` 的"查数轮 vs 正文轮"两段式已经是这个形状**（`tool_choice='required'` 只用于查数轮） |

**结论（推断，但依据充分）：在 7B~32B 的自建模型上，"一次挂 10+ 个工具"不是最优解。** 现实做法是**按意图把工具集切成小份**（每份 3–8 个），或干脆**不给模型工具、让系统代码去调**（路线 A/§7 正是这个形状）。

### 4.4 对本项目的直接含义

- 现有 4 个工具（`kb_search`/`find_column`/`run_sql`/`finish`）已经接近"一个 7B~32B 模型能同时稳住"的上限；再加 10 个办公工具，最先坏掉的不是"答数准确率"，而是**查数轮的工具选择**。
- 因此**办公文档能力不要走 tool_calling 通道**，走 `job` 接口（`/api/docs/jobs`，本已存在）。这就是"按意图分工具集"的落地版：意图=生成文件 → 直接进 job 流水线，不进模型工具表。

## 5. 许可合规

> 证据等级说明：本节条文引用来自**许可证原文**（SPDX 官方文本镜像 + Apache 基金会官方文本 + SIL 官方站点）。
> **重要限制**：`gnu.org` 在本调研环境**网络不可达**（多次 `fetch failed`，SPDX 页面还标注 gnu 的 AGPL/RFC 链接 "no longer live"），因此 **GNU GPL FAQ 的问答原文本次无法直接引用**——凡依赖 FAQ 的判断，一律标为**推断**。
> 本节不构成法律意见；涉及"交付给外部客户"的情形必须走法务。

### 5.1 四种许可证在"企业内网自用"下的义务（结论表）

| 许可证 | 要不要把自己写的代码开源出去？ | 实际义务（内网自用） | 触发点 |
|---|---|---|---|
| **MIT** | **不需要** | 分发时保留版权声明与许可声明 | 分发（convey/transfer） |
| **Apache-2.0** | **不需要** | (a) 给接收方许可副本；(b) 改过的文件加显著修改说明；(c) 保留版权/专利/商标/归属声明；(d) 若原件带 `NOTICE`，衍生分发需带上其归属声明。专利授权随"发起专利诉讼"**自动终止** | 分发 |
| **GPL-3.0** | **不需要**（对内部使用而言） | 只在 **convey（向他人转移副本）** 时触发：整体以 GPL-3.0 授权、提供 Corresponding Source。"纯粹跑、不 convey"没有条件 | 分发 / 员工间交付副本 |
| **AGPL-3.0** | **不需要对社会开源**，但**要向"通过网络使用它的用户"提供源码** | 除 GPL 全部义务外，§13 追加：改了它，就必须向"**所有通过网络远程与它交互的用户**"提供你这一版的 Corresponding Source（可以从一台网络服务器提供，不收费） | 网络提供服务 + 你做了修改 |

### 5.2 条文原文（这是本节最硬的部分）

**AGPL-3.0 §0（"convey" 的定义，决定了"内网自用不算分发"）** —— 原文（[SPDX 全文镜像](https://spdx.org/licenses/AGPL-3.0-or-later.html)，许可文本本体见 [gnu.org/licenses/agpl-3.0](https://www.gnu.org/licenses/agpl-3.0.html)，本次不可达）：

> "To 'convey' a work means any kind of propagation that enables other parties to make or receive copies. **Mere interaction with a user through a computer network, with no transfer of a copy, is not conveying.**"

**AGPL-3.0 §2（"跑了但没 convey 就不受条件约束"）** —— 原文：

> "You may make, run and propagate covered works that you do not convey, **without conditions** so long as your license otherwise remains in force."

**AGPL-3.0 §13（唯一的"网络即触发"条款，注意它的对象是 "all users"，不是 "the public"）** —— 原文：

> "Notwithstanding any other provision of this License, **if you modify the Program**, your modified version must prominently offer **all users interacting with it remotely through a computer network** (if your version supports such interaction) an opportunity to receive the Corresponding Source of your version by providing access to the Corresponding Source from a network server at no charge, through some standard or customary means of facilitating copying of software."

**GPL-3.0** 与 AGPL-3.0 的 §0/§2 条款文字一致，**区别只在 §13 这一段**（AGPL 多出来）。因此上面对 §0/§2 的引用同时解释了 GPLv3。

**Apache-2.0 §3（专利终止）** —— 原文（[apache.org/licenses/LICENSE-2.0.txt](https://www.apache.org/licenses/LICENSE-2.0.txt)）：

> "If You institute patent litigation against any entity (including a cross-claim or counterclaim in a lawsuit) alleging that the Work or a Contribution incorporated within the Work constitutes direct or contributory patent infringement, then any patent licenses granted to You under this License for that Work **shall terminate as of the date such litigation is filed**."

**Apache-2.0 §4（分发的四个条件）** —— 原文摘要：`(a)` 给接收方许可副本；`(b)` 修改过的文件"carry prominent notices stating that You changed the files"；`(c)` 保留源形式的版权/专利/商标/归属声明；`(d)` 若 Work 含 `NOTICE` 文件，"any Derivative Works that You distribute must include a readable copy of the attribution notices contained within such NOTICE file"，可放在自己的 NOTICE、源码/文档、或生成的展示里（三者之一）。

### 5.3 落到本项目的判断

**(1) 只 import 开源库、内部自用 → Apache/MIT 组件零负担（保留声明即可）。**

**(2) 用了 GPL-3.0 组件（如某些 Office 转换工具）：内部自用、不把二进制/代码交给别人 → 不触发。** 依据是 §2 原文（"do not convey … without conditions"）。**推断**：把软件装在公司自己的服务器上、员工通过浏览器用，属于"convey 给同一法人内部"还是"没 convey"，FSF 的 FAQ 通常认为**同一法人内部**的传递不构成分发；但这条本次**无法引原文**（gnu.org 不可达），标记为**推断，建议法务确认**。

**(3) 用了 AGPL-3.0 组件（如 Ghostscript、部分 PDF/转换工具、某些 MCP server）：即使只在公司内网，只要"员工通过网络与它交互"，§13 就可能要求你把**你修改后的版本源码**提供给这些员工。**
- 注意区分**两件事**：① "不需要向社会公开" ✅（§13 只要求给"interacting users"）；② "不需要给自己的员工" ❌（员工就是 users）。
- 实操上这条几乎零成本：把改过的源码放在内网 Git/共享目录，并在系统"关于/版本"页放一句"源码可向内网 Git 仓库索取"，即满足"prominently offer … opportunity to receive"。
- **真正的雷**：如果你的"内网系统"是**交付给外部客户**（部署在甲方机房、甲方是另一个法人），那么"你 → 甲方"这一跳在许可证语境里是**分发**，GPL/AGPL 的全部义务被触发（要给源码、要允许再分发）。**这是本项目最需要法务确认的一条**：我方与部署方是否同一法人主体。

**(4) 边界：`import` 一个 GPL 库 vs 用 `subprocess` / HTTP 调一个 GPL 程序**

| 形态 | 传染风险（推断） | 说明 |
|---|---|---|
| `import gplpkg` 进主 FastAPI 进程 | **高** | FSF 长期立场：与 GPL 代码链接/紧密集成的作品是衍生作品，需整体 GPL。**FAQ 原文本次不可引**，标为推断 |
| `subprocess.run(["ghostscript", ...])` 调独立程序 | **低** | 两个独立程序通过命令行/文件交互，通常视为"聚合"而非衍生作品；**但**若你**修改**了该程序并在网络服务里用，AGPL §13 仍会要求向 users 提供**你改的那部分**源码 |
| 独立进程 + 自有 HTTP/stdio 协议（MCP server 就是这个形态） | **低** | 这也是"用 AGPL 的 MCP server 不一定传染你的 agent"的依据；代价是要接受 §13 的源码提供义务 |

**(5) 本次盘点里三种"非标准"许可，单独点名：**
- `FSL-1.1-MIT`（`@mindstone-engineering/mcp-server-office`）：**不是 OSI 开源许可**，通常带营收/竞品限制；**条款原文本次未核实**。→ **结论：不当作 MIT 用，不能直接内嵌交付。**
- **无 LICENSE 文件**（`NeekChaw/mcp-server-okppt`）：默认**保留所有权利**，连"内部复制进代码库"都缺授权。→ **结论：不能用。**
- **仓库 `archived: true`**（GongRzhe 的 Word / PPT server）：许可仍是 MIT，可 fork 自维护；但"没人维护"是工程风险不是许可风险。

## 6. 内网离线工程细节

### 6.1 pip 离线：wheelhouse，别做私有 PyPI

官方给了标准做法（[pip User Guide · Installing from local packages](https://pip.pypa.io/en/stable/user_guide/#installing-from-local-packages)）：

```bash
# 联网机（与目标机同 OS/同 Python 小版本时最简单）
pip download -r requirements.txt -d wheels/
# 内网机
pip install --no-index --find-links=wheels -r requirements.txt
```

跨平台/跨 Python 版本下载（例如在 Linux 构建机上给 Windows Server 备料）必须**同时**给全约束，否则会把"当前解释器匹配但目标机不匹配"的包一起拉下来：

```bash
pip download -r requirements.txt -d wheels/ \
  --only-binary=:all: --platform win_amd64 --python-version 3.11 --implementation cp --abi cp311
```

依据：[`pip download` 文档](https://pip.pypa.io/en/stable/cli/pip_download/) 原文——"`pip download` with the `--platform`, `--python-version`, `--implementation`, and `--abi` options provides the ability to fetch dependencies for an interpreter and system other than the ones that pip is running on. `--only-binary=:all:` or `--no-deps` is required when using any of these options."

实务坑（推断，基于上面的官方说明）：

- **纯 sdist 的包在离线机安装要编译**（C 扩展/需 Rust、需 MSVC 或 gcc）。对策：`--only-binary=:all:` 先筛一遍，装不上的（如某些包只发 sdist）单独在联网机 `pip wheel` 出 `.whl` 后再放进 wheelhouse。
- **本项目现状**（已核实）：`server/requirements.txt` 里 `psycopg[binary]`、`cryptography`、`numpy`、`lxml`（python-docx 传递依赖）这些都有平台轮子；`docker/requirements.txt` + `docker/requirements.lock.txt` 已存在，说明按 lock 定版即可复现。
- 私有 PyPI（devpi/pypiserver）**不是必需**：一次性交付用 `--find-links` 目录就够；只有"内网长期持续装包"才值得上。

### 6.2 npm 离线：本项目运行时根本不需要 Node

- 已核实：`web/dist` 是预构建产物、由后端托管（见 `docs/02-部署/内网打包清单.md`），运行时不跑 node。
- 所以 npm 离线只在**选 Node 版 MCP server** 时才成为问题（例如 §2 的 `@mindstone-engineering/mcp-server-office` 明确 `engines: node>=20`）。
- 三种对策，按代价从低到高（推断）：
  1. **不选 Node 实现**（首选）。办公类需求全都有 Python 实现，见 §2。
  2. **整包 node_modules 过网**：离线最省事、最可复现，缺点是体积与"不知道装了什么"。
  3. **Verdaccio**（内网私有 npm registry）：官方定位是 "lightweight private npm proxy registry"、"cache all dependencies on demand"（[verdaccio.org](https://www.verdaccio.org/docs/what-is-verdaccio/)）。它本身是 Node.js 应用——为了离线装 Node 包，你得先离线装上 Verdaccio，属于**只有在长期维护时才划算**。

### 6.3 中文字体：docx/xlsx 生成不需要字体，转 PDF/缩略图才需要

这是本次最容易搞错的一条，分开说：

- **生成 `.docx/.xlsx/.pptx` 不需要服务器装字体。** 这些是 OOXML 声明式格式，字体只是写进 XML 的一个名字（本项目 `server/app/secretary/docgen.py` 第 17–22 行就是把 `仿宋_GB2312`/`方正小标宋简体` 写进样式），打开文档的客户端有字体就行。
- **一旦要"转 PDF / 出缩略图 / 服务端预览"，就必须有字体文件**，否则 LibreOffice 会替换或画方块。
- 容器/离线机装什么：**Noto CJK（SIL OFL 1.1）或思源黑体/思源宋体**——许可最干净（见 §5 第二块）。`fonts-noto-cjk` 一类系统包即可；不要从网上下"仿宋_GB2312.ttf"散装文件塞进镜像（版权问题见 §5）。
- 名称映射：如果生成的 docx 里写的是 `仿宋_GB2312`，而容器里只有 Noto Serif CJK，**不影响 docx 生成**；只在转 PDF 时被替换字体，外观会变。要么在模板里统一用可自由分发的字体名，要么在转 PDF 的机器上补齐授权字体（这属于"用字体渲染"的授权问题，见 §5）。
- Windows 侧的对应事实：服务器装了 Office 时，Office 自带的中易字体能否被服务端进程使用——见 §5 第二块的结论（含许可判断）。

### 6.4 Windows Server 部署的坑（本项目已经踩过一半）

**(a) python-docx / python-pptx / openpyxl 都是纯 Python，不需要 Office。** 已核实：本项目 `server/requirements.txt` 有 `python-docx>=1.1.2`、`openpyxl>=3.1.5`、`xlrd>=2.0.1`、`pdfplumber>=0.11.4`，`docs/02-部署/内网打包清单.md` 也写明"Word/Excel 用已有的 python-docx / openpyxl，PDF 用 pdfplumber，PPT 用标准库 zipfile+XML 解析（不装 python-pptx）"。

**(b) 中文 eastAsia 字体是真实老坑，本项目已处理。** `docgen.py` 第 43–47 行注释与代码：`style.font.name = DOC_FONT_FALLBACK` 之后还必须 `style.element.rPr.rFonts.set(qn("w:eastAsia"), DOC_FONT)`——只设 `font.name` 中文不生效。做 PPT 时同理，python-pptx 要设 `run.font.name` 的同时写 `ea` 类型字体（推断：与 docx 同源问题，未在 python-pptx 上实测）。

**(c) 文件被占用 → PermissionError。** Windows 上用户开着 Word 打开同一路径时，`doc.save()` 会抛权限错误（推断，非本文档验证）。对策：写到临时文件再 `os.replace()` 原子替换，失败重试；本项目 `doc_jobs.py` 已经是"生成到 job 目录再给下载链接"的形态，天然规避。

**(d) LibreOffice 转 PDF 的两个硬约束（Windows / Linux 都一样）**

- 命令形态：`soffice --headless --convert-to pdf --outdir <目录> <文件>`（[LibreOffice 启动参数文档](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html)）。
- **profile 目录必须可写**：官方原文 "LibreOffice requires write access to its user profile directory"；容器里无 HOME / 服务账号无 profile 时必须 `-env:UserInstallation=file:///可写路径`（同一文档里 `-env:VAR[=VALUE]` 的定义）。
- **并发要各自独立的 profile**（推断，业界通行做法）：多个进程共用一个 profile 会撞单实例锁，表现为第二个转换挂住或直接失败。给每个并发槽一个独立 `UserInstallation` 目录即可。

**(e) 绝对不要走 Office COM / `docx2pdf` / WPS COM 做服务端转换**

微软官方文章（[Considerations for server-side Automation of Office](https://support.microsoft.com/en-us/visio/considerations-for-server-side-automation-of-office)）原文：

> "Microsoft does not currently recommend, and does not support, Automation of Microsoft Office applications from any unattended, non-interactive client application or component (including ASP, ASP.NET, DCOM, and NT Services), because Office may exhibit unstable behavior and/or deadlock when Office is run in this environment."

以及许可层面的明文：

> "Current licensing guidelines prevent Office applications from being used on a server to service client requests, unless those clients themselves have licensed copies of Office."

**结论（事实）：服务端自动化 Office 既不被支持，也有许可风险。** 这条同时否掉了 §2 里 `docx2pdf` 的 PDF 导出和 `mcp-server-office` 的 add-in 方案，也给 `docs/03-设计/办公文档能力-接口设计.md` §6 里".doc/.wps 走 WPS COM 转换"打了个问号——**WPS 的 EULA 是否允许服务端无人值守调用，本次未核实**，但架构风险与 Office COM 同类（服务账号无交互桌面、进程常驻、并发不稳定）。

### 6.5 体积与进程（部分未核实）

- **已核实**：新增 `python-pptx` 只多一个纯 Python 轮子（它依赖 `lxml`、`Pillow`、`XlsxWriter`，其中 `lxml`/`Pillow` 大概率已在依赖树里，本项目已用 `lxml` 于 python-docx）。
- **未核实**：LibreOffice 安装包的具体体积（常见说法数百 MB 级），以及本内网服务器是否已有 LibreOffice。**这一项是"要不要 PDF 预览"的直接成本，建议现场 `where soffice` 确认后再决策。**

| **没有 pptx 生成**；PPT 只有"解析"（标准库 zipfile+XML） | `server/app/services/ingestion/parsers/pptx_parser.py`；`docs/02-部署/内网打包清单.md` |
| 异步任务基建已存在（create/save/update/run/cancel + 产物目录） | `server/app/secretary/doc_jobs.py` |
| 设计稿里 `task=pptx` 明确标为"⬜ 未实现" | `docs/03-设计/办公文档能力-接口设计.md:263` |

**这意味着：所谓"给 agent 加办公技能"，缺的不是架构，缺的是一个 `docgen_ppt.py` 和一个工具入口。**

### 7.2 三条路线的具体工程量

#### 路线 A：直接 Python 函数工具（推荐）

| 改动 | 文件 | 代码量 |
|---|---|---|
| 新增 PPT 生成（模板占位符替换 / 纯 python-pptx 生成） | 新建 `server/app/secretary/docgen_ppt.py` | **150–250 行**，结构与 `docgen.py` 同构（常量放顶部、只写 XML、不渲染） |
| 加 1 个工具 schema + 1 个分发分支 | `agent.py`：`TOOLS` 末尾加一项（~15 行）、`execute()` 加 `if name == 'make_pptx'`（~6 行） | **~25 行** |
| 走异步任务（20 页以上必异步） | `doc_jobs.py` 的 task 白名单加 `'pptx'`，`run()` 加一个分支 | **~20 行** |
| 依赖 | `server/requirements.txt` 加 `python-pptx>=1.0.0`（+离线 wheel 1 个） | **1 行 + 1 个 wheel** |

- **新进程：0 个。新端口：0 个。**
- 风险：**自查可控**（代码是自己写的 200 行，不引入无维护者仓库）；工具数 4→5，工具表增量约 800–1,200 字符，对 `tool_choice='required'` 的查数轮影响可忽略。
- 适用条件：只服务本系统；生成规则由本系统 LLM 与本系统模板决定。

#### 路线 B：MCP（挂第三方 office server）

| 改动 | 说明 |
|---|---|
| 新增 MCP 客户端适配层 | 新建 `server/app/secretary/mcp_client.py`：**100–200 行**（拉 `tools/list` → 转 OpenAI `tools[].function.parameters`（JSON Schema 基本可原样透传）→ `tool_calls` 转 `tools/call` → 结果转 `role=tool` 消息）。若改用 `langchain-mcp-adapters`/`mcp-use` 这类库，代码少但会拖进 langchain 依赖树，与现在"urllib 直连 + 零框架"的风格冲突。 |
| 改 `_chat` | 工具表由"常量"变"常量 + 动态注入"，并且**必须按意图路由**（办公类工具绝不能进查数轮，否则 `tool_choice='required'` 会把查数轮导向 `create_workbook` 之类） |
| 改 `execute` | 加"未知工具名 → 转发给 MCP"的分支 |
| **新进程** | stdio：每次调用拉子进程（冷启动开销，**未实测**）；或 streamable-http：**多一个常驻进程 + 一个端口 + 一个守护**（现在没有进程守护基建） |
| 离线依赖 | Python 版 server：额外 wheel（fastmcp/mcp 与主服务可能版本打架）；Node 版 server：**多一套 Node 运行时 + node_modules**（§6.2） |

- 风险（按严重度）：① 选中的 Word/PPT server **已归档**，等于接手死代码；② 工具膨胀（§4 数据）；③ 协议代际差（server 停在一代前，客户端要兼容两代）；④ 多一个进程与端口，内网运维成本上升。
- 适用条件：要复用社区 server 的成熟能力（例如 Excel 的图表/PivotTable/切片器，自己写得写几千行）、或未来多个 agent/多个系统共用同一套办公工具、或要接 Claude Desktop 生态。

#### 路线 C：独立微服务 HTTP（把办公生成拆出去）

| 改动 | 说明 |
|---|---|
| 新服务 | 新增一个 FastAPI 应用（~300–500 行）：接收 `{template, data}` → 返回文件；带鉴权、限流、健康检查 |
| 主系统 | `agent.py` 里**不加工具**，改为在已有的 `/api/docs/jobs` 里 HTTP 调用；或加 1 个薄工具转发 |
| 部署 | **多一个进程 + 端口 + nginx 反代规则 + 第二份离线依赖**；新增一份运维文档 |
| 适用条件 | 生成量大到需要独立扩缩容；多个系统共享同一套模板与生成规则；生成要做成对外产品能力 |

### 7.3 结论与建议（**加粗**）

**推荐路线 A，本轮就做，约 250 行、0 新进程：**
1. 新建 `server/app/secretary/docgen_ppt.py`（照 `docgen.py` 的写法：字体/字号/行距全在文件顶部常量，只写 XML 不渲染，末尾固定加"本文件由系统辅助生成，请人工复核"）。
2. `agent.py` 加 1 个工具 + 1 个 `execute` 分支（**约 25 行**）。
3. `doc_jobs.py` 的 task 白名单加 `'pptx'`（**约 20 行**），产物走现有 `outputs[].url` 下载链路——前端不用改。
4. `server/requirements.txt` 加 `python-pptx`，离线 `wheels/` 加 1 个轮子。

**关键设计约束（这条比选哪条路线更重要）：办公类工具不能进"查数轮"的工具表。** 现有 `ask()` 在查数轮强制 `tool_choice='required'`（`agent.py:212-215`），一旦把 10+ 个办公工具塞进同一个 `TOOLS`，模型被强制调用时就有概率去调 `create_workbook`——这不是"准确率略降"，是**流程性错误**。要么走 job 接口（不经过工具表，路线 A 天然如此），要么做**按意图分工具集**（§4 的推荐架构），二者选一，不要混。

**为将来留门**：如果之后确实需要 MCP（比如要接 Excel 的 PivotTable/切片器，或要让别的 agent 复用），把 `docgen_*` 保持成**纯函数 + 无 FastAPI 依赖**，外层再包一个 MCP server（stdio，~100 行）就是增量改动——路线 A 不会白做。
