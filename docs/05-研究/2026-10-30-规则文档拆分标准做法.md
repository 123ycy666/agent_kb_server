# 制度/规则类文档，给 RAG + 工具调用用：标准拆分与结构化做法

> 2026-10-30 · 查证方式：GB/T 与 OASIS/OMG 规范原文、Anthropic/Azure/LlamaIndex/LangChain 官方文档、arXiv 原始论文。
> 约定：每条结论后跟来源；凡属我推断而无一手来源的，显式标 **未找到一手来源，属推断**。

## 一、结论摘要

1. **结构层**：中文规范性文件的标准骨架是「章→条→段→列项」，只有「条」带编号（`5.1` / `5.1.1`），段无编号，列项用 `——` 或 `a)`；且要求同一层次的编号、顺序、标题表述保持一致。→ 拆分的天然最小单元是「条」，不是段落。
2. **没有"一条判据一节"的国标**，但有同构的行业规范：DMN 决策表把「一条规则 = 一行（输入条件格 → 输出结论格）+ 命中策略 + 注」写成了标准；OPA 要求每条规则可挂 `title/description/authors/related_resources/custom` 元数据。**四行结构可视为这类规范的简化版，但要补 id、值域、出处。**
3. **切分**：官方文档一致推荐"按标题层级切"，并把完整标题路径/文档标题写进每个 chunk；进阶做法是给 chunk 前置 50–100 token 的自述语境（Anthropic：检索失败率 -35%～-49%）。
4. **检索粒度**：小片建索引、大片回填（parent-child / small-to-big），LlamaIndex、LangChain 都有成品抽象；论文层面细粒度单元（命题级）检索效果显著优于段落级。
5. **方法 vs 判据要分开**：CoALA 把「语义记忆（可检索的事实/文本）」与「程序性记忆（模型权重 + 智能体代码）」列为两类不同模块；Anthropic 明确警告"把复杂脆弱逻辑硬编码进提示词"是失败模式。→ 分析方法常驻系统提示词、阈值判据走向量/关键词检索，方向正确。
6. **例外**：规范化的做法是「可废止规则（defeasible）+ 覆盖优先级 + 辖区/时间限定」，不是自由文本备注。我们的 `覆盖：<主题>` 语义上对得上，但缺"谁覆盖谁、生效范围、生效时间"。

## 二、规范性文档的标准结构

### 2.1 国标本体：GB/T 1.1-2020 的「层次」

- GB/T 1.1-2020《标准化工作导则 第1部分：标准化文件的结构和起草规则》，2020-03-31 发布、2020-10-01 实施，**非等效采用 ISO/IEC Directives Part 2:2018**。官方登记页（含采标情况、起草单位、替代关系）：<https://std.samr.gov.cn/gb/search/gbDetailed?id=A24AF19F41445C2EE05397BE0A0A5E0D>；国家标准全文公开系统条目：<https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=C4BFD981E993C417EF475F2A19B681F1>
- 层次的官方规定（引自国家市场监管系统对该标准的宣贯解读，条款与 GB/T 1.1-2020 正文对应）：**层次使用「部分、章、条、段、列项」；任何文件至少有章、条、段三个层次，其余可选；部分/章/条编号采用阿拉伯数字加下脚点（章 `5`、`6`；条 `5.1`、`5.1.1`）；段无编号；列项符号 `——`、`•`，编号为 `a)`、`b)` 或 `1)`、`2)`**。→ 辽宁省市场监督管理局《标准化文件的起草（解读 GB/T 1.1-2020）》第 11 条"层次"：<https://scjg.ln.gov.cn/scjdglj/zt/ywxx/xxwj/2023051914101874905/2023051914100487217.pdf>
- 同材料给出的两条对拆分有直接影响的规则：**①「段」是章或条内没有编号的细分层次，且条标题与下一层次条之间不宜设段（"悬置段"）；②条标题可选，但在同一章/条下同一层次的各条"有无标题应一致"**（同上 PDF，第 17 条"段的编写"）。
- 一致性原则：**"章、条的编号、排列顺序、标题表述等宜尽可能一致"**（同上 PDF，第 29 条"文件的表述原则·一致性"）。
- 术语上要区分**规范性要素 / 资料性要素**、**必备要素 / 可选要素**——原文（制度正文）属规范性要素，示例、注、参考文献属资料性要素（同上 PDF，第 12 条"要素"）。

> 说明：openstd 的全文在线预览需人工验证码，**标准正文 PDF 未能抓取**；上面引的是国家标准委系统内省级局的官方宣贯解读，条款编号与标准正文一致。若要做条文级引用，建议人工核对纸质/正版 PDF。

### 2.2 党政机关公文的条款编号惯例

- GB/T 9704-2012《党政机关公文格式》（中办、国办提出，全国标准信息平台登记：<https://openstd.samr.gov.cn/bzgk/std/newGbInfo?hcno=F3CC9BEF482524C895FDA7A08BB4A70E>）7.3.3 正文：**"文中结构层次序数依次可以用'一、''（一）''1.''（1）'标注"**，并规定第一层黑体、第二层楷体、第三、四层仿宋。全文（法院系统转载，含 7.3.3 原文）：<http://cyzqfy.nmgfy.gov.cn/article/detail/2013/08/id/1045629.shtml>
- 同标准 7.1 把版心内要素划分为**版头、主体、版记**三部分，并对每个要素的编排位置逐条规定——即"公文是要素化容器 + 固定字段"的先例（同上）。
- 结论：党政机关文书的层次序数是**四层固定序列**（`一、` → `（一）` → `1.` → `（1）`），与 GB/T 1.1 的"章条款项"是两套并行惯例；制度类文档常用后者（条带数字编号），公文/通知类常用前者。

### 2.3 法律/规范文档的机器可读结构标准（结构化拆分的正统先例）

- **Akoma Ntoso 1.0（OASIS Standard, 2018-08-29）** 给出立法/司法文档的层次容器命名集合：`title, book, tome, part, chapter, section, paragraph, article, clause, division, level, list, subtitle, subpart, subchapter, subsection, subparagraph, subclause, sublist, point, indent, alinea`；名字对不上的层级用通用容器 `hcontainer`。→ <https://docs.oasis-open.org/legaldocml/akn-core/v1.0/os/part1-vocabulary/akn-core-v1.0-os-part1-vocabulary.html>（§5.2、§6.3 "Hierarchical Structure"）
- 该标准的设计原则里有一条对我们的 heading_path 直接适用：**"each fragment must be identifiable"（一切都要有名字）**，每个可切分单元都应有可解析的唯一标识（`eId`/`wId`），从而支持"引用到条/款/项"而不只是"引用到文件"（同上，§2.2 "Descriptiveness: everything has a name"）。
- **DMN 1.6（OMG）** 对"规则表"的规定见第三节。

## 三、RAG 文档切分的标准做法

### 3.1 标题层级感知切分（heading-based / section-based）

- Azure AI 搜索官方分块指南把切分方法分成四类并在文内对比：固定大小、**基于内容特征的可变大小**、语义、自定义组合；其中明确写"**嵌入式标记（如 HTML 或 Markdown）具有标题语法，可用于按节对数据进行分块**"。→ <https://docs.azure.cn/zh-cn/search/vector-search-how-to-chunk-documents>
- 同一篇给出的"自定义组合"做法几乎就是我们想要的效果：**"在处理大型文档时，可以使用可变大小的区块，但也可以将文档标题附加到文档中间的区块中，以防止上下文丢失"**（同上）。
- 参数基线（官方建议而不是经验值）：**固定大小从 512 token（约 2000 字符）起步、重叠 25%（约 128 token）**；高度结构化数据宜少重叠（同上）。
- LlamaIndex 提供现成的标题感知解析器：`MarkdownNodeParser`"parses raw markdown text"（按 Markdown 标题切 Node）。→ <https://developers.llamaindex.ai/python/framework/module_guides/loading/node_parsers/modules/>
- 若文档本身是结构化文档（如 PDF 版制度），Azure 的 Document Intelligence Layout 技能可输出 markdown 再语义分块（同 3.1 首条链接，表格"基于内容特征的可变大小的区块"行）。

### 3.2 上下文增强检索（contextual retrieval）

- Anthropic 的原始公告给出方法：切块后让模型为每个 chunk 生成 50–100 token 的"在全文中的定位说明"，**前置到 chunk 文本再分别建向量索引与 BM25 索引**。实测：只用 contextual embeddings 使 top-20 检索失败率降 35%（5.7%→3.7%）；再加 contextual BM25 降 49%（→2.9%）；再加 rerank 降 67%（→1.9%）。→ <https://www.anthropic.com/news/contextual-retrieval>
- 成本口径（同一篇）：800 token chunk、8k 文档、每个 chunk 100 token 语境，**一次性生成成本约 $1.02 / 百万文档 token**（靠 prompt caching）。
- 一条对生成端很重要的官方建议：**"Response generation may be improved by passing it the contextualized chunk and distinguishing between what is context and what is the chunk"**——即注入时要显式标出"哪段是语境、哪段是原文"（同上，"Always run evals"段）。
- 传统 RAG 的失败模式被点名为：**chunk 自身缺上下文导致召不回/用不对**（同篇"context conundrum"举例：单独一句"营收环比增长 3%"没有公司名和时间就废了）。

### 3.3 父子块 / 小片检索大片返回（parent-child, small-to-big）

- LlamaIndex `HierarchicalNodeParser`：把一份输入切成**多个粒度层级**的节点，**每个节点持有指向其父节点的引用**；配合 `AutoMergingRetriever`，当命中的叶节点中有足够比例属于同一父节点时，**自动把父节点整块返回**。→ <https://developers.llamaindex.ai/python/framework/integrations/retrievers/auto_merging_retriever/>
- LangChain `ParentDocumentRetriever`：**用向量库只存小块用于检索，父文档落在 docstore/byte_store**，检索后按 `doc_id` 召回父文档（参数 `vectorstore` / `docstore` / `byte_store` / `id_key`）。→ <https://reference.langchain.com/python/langchain-classic/retrievers/parent_document_retriever/ParentDocumentRetriever>
- 论文层面的粒度依据：**按"命题（proposition）"这类细粒度单元建索引，检索效果显著优于按段落单元**；且在给定算力预算下，用细粒度检索结果拼提示能提升下游 QA。→ Dense X Retrieval, arXiv:2312.06648 <https://arxiv.org/abs/2312.06648>
- 我们没有显式父子表，但"条级 chunk + heading_path"等价于"父块标识已落在每个 chunk 里"，可用 heading_path 反查整节，属同一机制的手工版。

## 四、「规则即数据 / 政策即代码」的既有规范

### 4.1 DMN 决策表：一条规则该长什么样（最贴近我们的先例）

- 定义（DMN 1.6 正文）：**"决策表是决策逻辑的表格化表示，基于对决策输入取值域的离散化，并按规则组织——规则把离散化的输入值映射到离散的输出值"**。→ OMG DMN 1.6 规范 PDF：<https://www.omg.org/spec/DMN/1.6/PDF>
- 一张决策表的组成（规范原文）：`DecisionTable` 有 `inputClauses`（输入子句）、`outputClauses`（输出子句）、`rules`（`DecisionRule` 列表）与 `RuleAnnotationClause` 列表，另有 `preferredOrientation`（Rule-as-Row / Rule-as-Column / CrossTable）与 `hitPolicy`；**每条 `DecisionRule` = `inputEntry[1..*]`（输入条件格）+ `outputEntry[1..*]`（输出结论格）+ `annotationEntry[0..*]`（注，按索引对应 annotation 列）**（同上第 8 章"决策表"，其中 `DecisionRule` 与 `RuleAnnotation` 的模型表）。
- 条件语义（同上）：规则的输入格为 `t1..tN`，对应输入表达式列表 `e1..eN`（可带输入值域 `v1..vN`）；**"若某规则被匹配且命中策略允许，则其输出值进入决策表结果"**。
- 命中策略（hit policy）解决"多条规则同时命中"：规范明确"**若规则重叠，由 hit policy 规定如何处理重叠并给出确定的结果，以避免不一致**"；**规则编号是从 1 开始的连续自然数，当命中策略为 F（first）或 R（rule order）时，编号必须存在，因为含义依赖顺序**（同上，§8.2）。
- 规范化标准化了什么（同上 §8.2 原文列举）：方向（按行/按列/交叉表）、信息项名称与命中标记 H 的位置、规则编号位置、各格内容的写法。
- 对我们的直接含义：**"一条判据一行"是标准做法；但标准里还强制了三件我们缺的东西——输入值域（口径）、输出取值/默认值（结论）、命中策略（冲突时谁赢）**。

### 4.2 OPA / Rego：规则 + 元数据注解

- Rego 里**一条规则 = 规则头（名字 + 值）+ 规则体（表达式合取），语义可读作 `rule-name IS value IF body`**。→ <https://www.openpolicyagent.org/docs/policy-language>
- 官方要求（Annotations）：**包与单条规则可带 `# METADATA` YAML 元数据块，字段含 `title`（人类可读名）、`description`、`authors`、`related_resources`（相关资源 URL 列表）、`custom`（自定义字段）、`scope`、`schemas`、`entrypoint`**。→ <https://www.openpolicyagent.org/docs/v0.51.0/annotations/>
- OPA 的整体设计把**策略（policy）与数据（`data` / `input`）分离**：规则不写死事实，事实从外部 `data` 文档和 `input` 请求进来（同上，policy-language 的 `input`/`data` 语义）。→ 即"判据是逻辑、事实是数据"，与"方法别塞进知识库"同构。
- 对我们的直接含义：**"字段/别名/出处"适合放元数据，不适合混进规则正文**；`related_resources` 正是"这条判据出自哪份制度第几条"的标准位。

### 4.3 LegalRuleML：一条法律规范应携带的语境要素

- OASIS Standard《LegalRuleML Core Specification v1.0》（2021-08-30）。→ <https://docs.oasis-open.org/legalruleml/legalruleml-core-spec/v1.0/os/legalruleml-core-spec-v1.0-os.html>
- 它明确建模的东西（引言列举）：**规则的可废止性（defeasibility）/道义算子（义务、许可、禁止、权利）/否定的语义处理/规则中的时间管理/规范分类（构成性 constitutive、规定性 prescriptive）/辖区（jurisdiction）/权威（authority）/主体角色（LegalRole）**（同上，引言部分）。
- 术语表两则关键定义（同上，术语定义处）：**Jurisdiction = "a geographic area or subject-matter over which an Authority applies its legal power"（权威行使其法律权力的地理范围或事项范围）**；**LegalSource = "a source of one or more Legal Norms ... endorsed by an Authority"**。
- 语境属性（同上，规范正文的属性定义表）：`appliesModality`（道义模态）、`appliesSource`（该规则适用的法律来源）、`appliesPenalty`（罚则）、`atTime`（时间限定）、`filledBy`（角色由谁填充）。
- 对我们的直接含义：**"一条判据"的完整要素不止 判据/口径/字段/别名，还应能挂 时间（生效/失效）、范围（哪家单位、哪类业务）、出处（制度条款）、例外（可废止）**。"覆盖：<主题>"是"可废止"的极简表达，规范里对应的是 defeasible rule + 覆盖关系。

### 4.4 归纳：一条规则的标准字段集（跨三份规范的交集）

| 要素 | DMN 1.6 | OPA | LegalRuleML | 我们的四行 |
|---|---|---|---|---|
| 唯一标识 | 决策 id / 规则编号（F、R 策略时必需） | 规则名 + `scope` | Rule `key` / IRI + AKN `eId` | ❌ 缺 |
| 条件 | `inputEntry` + 输入表达式 `e_i` | 规则体 | 规则体 | ✅ 判据 |
| **值域 / 单位 / 度量定义** | `inputValues`、`outputValues`、`typeRef` | `input`/`data` 结构（schema 注解） | 时间、角色、辖区的取值域 | ⚠️ 口径（半覆盖） |
| 结论 | `outputEntry` + 默认输出 | 规则头的值 | 规范结论 | ✅ 判据的落点（弱） |
| 注 / 解释 | `annotationEntry` | `description`、`custom` | `@note`、说明性语句 | ⚠️ 无独立行 |
| 出处 | （在 BKM/DRD 层） | `related_resources` | `appliesSource` / References | ❌ 缺 |
| 时间 / 生效 | 外部 | 外部 | `atTime` | ❌ 缺 |
| 冲突/优先级 | `hitPolicy`（U/A/P/F/C/O/R） | 规则求值序 | defeasible + 覆盖 | ⚠️ `覆盖：<主题>` |

## 五、方法（怎么分析）与判据（阈值标准）是否应分开

### 5.1 论文层面：程序性知识 vs 陈述性/语义知识是两类模块

- CoALA（arXiv:2309.02427）把语言智能体的长期记忆分为**语义记忆（semantic：世界的事实性知识）、情节记忆（episodic：过往经历）、程序性记忆（procedural：智能体代码 + LLM 权重）**，并明确把 RAG 归类为"从非结构化文本的语义记忆中检索"。→ <https://arxiv.org/abs/2309.02427>
- 原文关键判断：**"Language agents contain two forms of procedural memory: implicit knowledge stored in the LLM weights, and explicit knowledge written in the agent's code."**；并且 **"agent code (deterministic rules)" 与 "LLM parameters" 是两种程序性记忆，代码可解释但脆弱，只能覆盖设计者预先想到的情形，因此"建议克制地用代码实现通用算法"**（同上，长期记忆一节 与 "LLMs vs. code in agent design" 一节）。
- 对我们的直接含义：**"怎么分析一类题"属程序性知识，应当以确定性载体（系统提示词/代码/skill）存在并以版本控制管理；"审批停留 90 天算积压"属语义知识，应当是可检索、可更新、可引用出处的数据。** 两者混在同一个 md 里，正是把语义事实塞进程序性载体。

### 5.2 工程规范层面：系统提示词只放"方法与高度"，事实走检索

- Anthropic《Effective context engineering for AI agents》：**系统提示词应"在恰当的抽象高度（the right altitude）"，两种典型失败是"把复杂、脆弱的逻辑硬编码进提示词"和"只给模糊的高层指导"**；目标是"用最小信息量完整表达期望行为"；并建议用 **XML 标签或 Markdown 标题分隔不同区块**。→ <https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>
- 同篇把上下文状态明确分为 `system instructions`、`tools`、`external data`、`message history` 几类，并提"渐进披露（progressive disclosure）/即时检索（just-in-time）"：**前沿做法不是把所有知识塞进提示词，而是让模型按需取。**
- Anthropic《Equipping agents for the real world with Agent Skills》：一个 skill = 目录 + `SKILL.md`，**frontmatter 的 `name`/`description` 常驻系统提示词，正文只在判断相关时读入**——这是"元数据常驻、正文按需"的三级渐进披露。→ <https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills>
- 补充一条同向证据：Anthropic 在 Contextual Retrieval 里的生成端建议也是"把检索来的上下文与模型自身的指令在文本上区分开"——即**上下文里的"方法"与"素材"必须可分辨**（见 3.2 末条）。

### 5.3 结论

三条独立来源（认知架构论文、模型厂官方上下文工程指南、skill 机制规范）都指向同一件事：**"方法/程序"与"事实/判据"应当分层——方法常驻且确定，事实检索且可溯源**。把二者拆开不是我们的发明，而是主流做法；我们额外多出的一层（"口径/字段/别名"）属规则数据化范畴，对应 DMN 的输入/输出子句 + OPA 的元数据。

## 六、我们这套做法与标准的对照

| 我们的做法 | 标准做法 | 差异 | 建议改法 |
|---|---|---|---|
| 一份 md 混「分析方法 + 判据 + 制度原文」三类 | 程序性知识与语义知识分层：方法与 skill/系统提示词；事实与判据可检索；原文属 legal source 单独标识（CoALA 长期记忆一节；Anthropic Context Engineering；LegalRuleML `appliesSource`） | 三类内容共用一个载体、一套切分参数、一套索引 | 拆成 3 个物理来源，各自独立的 ingest 管道与元数据 schema；原文只做"可引用底稿"，不作为检索主入口 |
| 按"一条判据一节"拆 | DMN：一条规则一行，条件格→结论格 + 命中策略 + 注；GB/T 1.1：最小可引单元是带编号的"条" | 粒度对得上，但"节"不是带编号的标准单元，跨版本无法稳定引用 | 给每条判据一个稳定 id（如 `R-<制度号>-<条号>-<序号>`），并把原制度条号作为字段保留（AKN `eId` 的等价物） |
| 每节四行：判据 / 口径 / 字段 / 别名 | 规范字段集：标识、条件、值域（含单位/类型）、结论+默认值、注、出处、时间、优先级 | **缺 唯一 id、出处、生效/失效时间、冲突处理**；"别名"是自定字段 | 四行扩成"4 行正文 + 6 个字段"：`id / 出处(制度+条款+版本) / 生效期 / 状态 / 别名 / 覆盖对象`。字段化的部分放元数据列，不要混进正文 |
| 口径写在正文一行文字里 | DMN 要求输入/输出**值域与类型**显式建模（`inputValues`/`outputValues`/`typeRef`），"口径"实为度量定义 + 单位 + 边界（含/不含、自然日/工作日） | 口径是自由文本，机器无法据此判定边界 | 口径拆成结构化三元组：`单位`、`边界规则`（>90 还是 ≥90）、`计算基准`（自然日/工作日/日历）。至少把比较符和数值单独成列，否则工具调用无法直接消费 |
| 分析方法常驻系统提示词 | 系统提示词放"方法与高度"，事实走检索（Anthropic；CoALA） | 方向一致；风险是方法文档里再次混进具体阈值 | 系统提示词中禁止出现任何具体数值/单位；加一条自检规则"出现数字即为越界"。方法的修订走版本号，与检索库解耦 |
| 例外用 `覆盖：<主题>` 一行写在个人库 | 可废止规则（defeasible）+ 覆盖关系 + 范围/时间/权威（LegalRuleML）；DMN 用命中策略表达重叠（P/F/O） | 只有"覆盖什么主题"的声明，没有"覆盖成什么"、"覆盖谁（个人库 vs 单位库）"、"何时失效" | 改成四要素声明：`覆盖:<主题>` / `新判据:<值>` / `优先级:个人>单位` / `生效期:<>`；检索时按优先级合并，冲突留痕而不是静默替换 |
| 切片进 PG `document_chunk`，带 `heading_path`，向量+关键词混合检索 | 标题层级切分 + 完整标题路径入块（Azure）；混合检索（BM25+向量+融合）是 Anthropic 的基线推荐，再加 rerank 可把失败率从 2.9% 压到 1.9% | 做法合规；但 **chunk 内容里没有"这段在讲什么"的自述语境**，跨节召回仍然弱 | ①每个 chunk 前置 1 句定位语（"本段出自《XX 办法》第 5 章第 12 条，规定积压认定口径"）；②heading_path 同时参与 BM25 字段；③加 rerank 层 |
| 判据的四行正文直接进 embedding | 小块检索、父块返回（LlamaIndex AutoMerging / LangChain ParentDocumentRetriever）；细粒度索引效果更好（DenseX） | 没有父子层级，命中一条判据时无法带回整节上下文 | 用 heading_path 建父子关系：叶 = 单条判据，父 = 整节；上下文不足时按 heading_path 回填父节 |
| 无出处字段 | OPA `related_resources`；LegalRuleML `appliesSource`；AKN 引用结构 | 答案无法回溯到制度原文，"制度依据"只能靠模型编 | **最高优先级改动**：每条判据必带 `出处 = 制度名 + 版本 + 条号`，且出处文本单独建一个可引用块；回答时强制输出出处 |

> 表中"差异/建议"是我的工程判断；"标准做法"列均有上文 URL 支撑。
