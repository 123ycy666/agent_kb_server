# 查数口径该放哪、收尾字段怎么强制：本机实测 + 工业做法对齐

2026-11-05。所有数字本轮实跑（本机 PG `ad_new` 真数据 + 网关真请求）。证明方式见每节末尾的「怎么复现」。
上游文献见同目录 `2026-11-05-长系统提示词与工具编排-工业做法.md`（下称「文献篇」），本文只补它没答的三件：口径放哪、工具说明放哪、收尾字段怎么变成机制。

## 0 结论

1. **「收尾看不到回答规则」不是模型被长上下文弄丢的，是换段代码从来没生效**：`prompt_stack._block()` 对正文做了 `.strip()`，把 `prompt_material.block()` 开头那两个换行吃掉，`strip_block()` 用 `find(MARK)` 永远 -1。实测查数 system 18,164 字符，收尾 system 18,615 字符（回答规则 427 字在最后，口径 17,802 字还在前面）。
2. 修这一处：收尾 system 从 18,615 → **786 字符**（基础 335 + 回答规则 451）。这一步与「长短是否影响遵从」无关，它是确定性 bug，先修，才有对照组。
3. **口径不能整体删，要拆两类**：事实目录（哪张表有哪些字段）走 `describe_table`（已存在，实测单表 1,037–2,052 字符，且比提示词里那份新）；判断约定（口径限定、单位、必加条件）常驻但压到 ≤2,000 字。
4. **本网关做不了约束解码**：`response_format={"type":"json_schema"}` 实测 400「This response_format type is unavailable now」；`json_object` 只能保证「是 JSON」；`strict:true` 字段被接受但服务端是否真约束未证。所以「收尾字段靠 schema 强制」这条路在本案不通，只能用「代码断言 + 后处理清洗」。
5. **工具说明别在 system 里抄第二份**：现在 `TOOLS[].function.description`（10 个工具，合计 3,729 字符）与 `prompt_text.DEFAULT_TOOLS_GUIDE`（234 字符）两处都写，必然漂移。

## 1 复现：收尾那次 system 仍是 18,615 字符

实测（`server/` 下用真身份与真材料装配）：

| 项 | 字符数 |
|---|---|
| 查数轮 system（身份+模式做法+fetch/judge 材料） | 18,164 |
| 其中 `fetch` 三节（全部 pinned） | 17,802 |
| 　表说明 | 2,793 |
| 　字段说明 | 12,477 |
| 　字典说明 | 2,532 |
| `answer` 一节 | 427 |
| 收尾 system（现状，`_answer_system`） | 18,615 |
| 收尾 system（修 `strip_block` 后） | 786 |

失效链条（逐行可查）：

1. `prompt_material.block()` 返回的串以 `MARK = '\n\n===== 规则材料（本阶段） =====\n'` 开头。
2. `prompt_stack.add()` 把它交给 `_block(title, body)`，而 `_block` 里是 `(body or '').strip()` → 两个前导换行没了。
3. `strip_block()` 用 `s.find(MARK)` 找带 `\n\n` 的串 → 找不到 → 原样返回整段 system。
4. 于是每次「换材料」都是**保留旧材料 + 追加新材料**，`_swap_materials` 与 `_answer_system` 两处都受同一影响。

**怎么复现**（不靠读代码，靠跑）：

```powershell
cd D:\秘书智能体\server
# 断言 1：现状必须是「切不掉」
python -c "import sys; sys.path.insert(0,'.'); from app.secretary import prompt_material as pm, prompt_stack, prompt_text, prompts_data, project; rm=pm.block(('fetch','judge'),index_slots=pm.SLOTS); base=prompt_stack.build(identity=project.fill(prompt_text.get('identity',prompts_data.IDENTITY)),modes=prompt_text.mode_texts(prompts_data.MODE_TEXTS),rules_menu=rm or None)['system']; print(len(base), pm.strip_block(base)!=base)"
# 期望现状： 18164 False   ← False 就是「没切掉」
```

## 2 这 17,802 字是什么，和 `describe_table` 重复到什么程度

- `fetch` 三节覆盖 **17 张表、115 行字段说明**；逐表字符数中位 1,220，最大 1,404。
- 一个查数题通常只碰 1–3 张表 → 按需取的量级是 **1,000–4,000 字符**，不是 12,477。
- `describe_table('t_power_ai_station_summary')` 实测 1,037 字符，`describe_table('t_power_ai_work_order')` 2,052 字符；内容来自业务库 `ai_column_metadata`（数据组维护），**比提示词里那份更细**：提示词写「必须和 stat_month、summary_type 一起用」，库里那份还写了「不是本月新增次数」「不能使用 COUNT(*) 替代」。
- 结论：常驻的字段说明是**维护中数据源的一份旧副本**，越往后越容易教错 SQL。

顺带：表清单本身只要 1,118 字符（`semantic.table_list_menu()`），字典说明 671 字符（`semantic.codes_menu()`）。

## 3 本案网关实测：约束解码这条路是断的

对 `LLM_BASE_URL`（百炼兼容模式，`deepseek-v4.1-flash`）直接发最小请求：

| 请求形态 | 结果 |
|---|---|
| `response_format={"type":"json_object"}` | 200，返回 `{"a":12}`；按 DeepSeek 文档这只保证「是合法 JSON」，不保证字段 |
| `response_format={"type":"json_schema",...}` | **400** `This response_format type is unavailable now` |
| `tools[].function.strict=true` + 强制 tool_choice | 200，正常返回 tool_calls；**服务端是否真按 schema 约束未证**（没有违例样本可验） |
| 纯文本、`enable_thinking=false` | 200，直接给正文 |

含义：
- 行业里最硬的那档（grammar / JSON-schema 约束解码，vLLM 的 `guided_json`、OpenAI 的 strict structured outputs）**在这个网关上拿不到**。
- DeepSeek 文档自己写明：JSON Output 在识别失败时会把非 JSON 内容替换成空格，`content` 可能整段变空（`finish_reason` 仍是 `stop`）——它不是约束，是事后过滤。所以拿它当「必出字段」的保证会换来空回答。
- 而且「把正文塞进 JSON」本身有害：arXiv 2408.02442 实测格式限制越严、推理掉得越多（文献篇未收录，本文补上）。

能用的三层（按可靠性从高到低）：

1. **代码断言**：不改模型，改程序。`_clean_answer` 已经是这一层（洗 `**`、`#`、`|`、过程话术），注释里写的就是「提示词对它约束力不够，清洗是确定性的」。
2. **调用形状**：收尾单独一次调用，system 只放基础段 + 回答规则，输入只放事实清单（现状代码已经这么设计，被 `strip_block` 一个 bug 废掉）。
3. **提示词**：只放代码判不了的那部分（语气、是否分条、要不要说假设），且必须靠近生成点。

## 4 三个问题逐个答

### 4.1 查数口径该不该进提示词

拆两类，别整体搬：

| 类别 | 例子（本仓库真实内容） | 放哪 | 依据 |
|---|---|---|---|
| 事实目录 | 17 张表各有哪些字段、中文名、单位 | `describe_table` 按表取 + 1,118 字表清单常驻 | 文献篇 §3.2 混合法；本轮实测单表 1,037 字符且更新 |
| 判断约定 | 「同一期间当月行与累计行并存，不加 summary_type 会把两种口径加在一起」「必须 deleted_flag=0」「售电量单位 kWh，禁止逐月累加」 | 常驻，但压到 ≤2,000 字 | 这类是每次写 SQL 都要用的陷阱，取一次再算一次并不省钱；文献篇 §1.3（无关上下文让模型同时做检索和推理） |

判据（可跑）：常驻段 ≤2,000 字符，`describe_table` 返回里必须仍能查到被删掉的字段说明（抽样 20 个字段名逐个比对）。不通过就说明删掉的是「判断约定」而不是「目录」，退回去重分。

### 4.2 提示词长了/绕乱了怎么处理

不是靠人看着整，靠三道闸：

1. **结构**：稳定段（身份/红线/优先级）→ 阶段材料段（fetch/judge 或 answer）→ 工具说明。阶段段必须能被**精确切掉**，切法是「按分隔行匹配」，不依赖前后换行（见 §5）。
2. **预算闸（测试里写死上限）**：`assert len(查数 system) <= 6000`、`assert len(收尾 system) <= 1200`。超了 CI 红，不靠评审。文献篇 §5 的可测判据 + 本机 harness 的结论一致（文字规则不改变行为，能跑出 pass/fail 的检查才改得动）。
3. **单一事实源**：工具说明只在 tool schema 里；规则只在 `prompt_material` 里；页面文案不另抄一遍业务词。重复的那份一定会旧。

### 4.3 工具说明放哪

现状：`agent.TOOLS` 里 10 个工具，description 合计 989 字符、参数 schema 合计 1,702 字符，整套 3,729 字符/轮；`prompt_text.DEFAULT_TOOLS_GUIDE` 又用 234 字符在 system 里重复说「先 kb_search 查做法 / read_file 分页 / make_file 自检」。

做法：把 `DEFAULT_TOOLS_GUIDE` 那 4 条按工具拆进各自的 `description`，system 里只留一句流程策略（例如「做任何一类活之前先 kb_search 查做法」）。依据：Anthropic 的工具评估文章给的最强数字就是这条——「precise refinements to tool descriptions」让 Sonnet 3.5 拿到当时 SWE-bench Verified 的 SOTA；且官方明说工具说明是「loaded into your agents' context」时影响力最大的杠杆。8–10 个工具**不需要**工具检索（Anthropic 自己说 <10 个时 Tool Search 收益很小，文献篇 §2.4）。

判据：`DEFAULT_TOOLS_GUIDE` 里的每条规则都能在某个 `function.description` 里找到（字符串包含检查），且 system 里不再出现「【工具说明】」段。

## 5 修法与判据（可直接抄）

最小修法：把匹配从「带前导换行」改成「按分隔行」：

```python
# prompt_material.py
LINE = '===== 规则材料（本阶段） ====='          # 不含前导换行

def strip_block(system: str) -> str:
    s = str(system or '')
    i = s.find(LINE)
    return s[:i].rstrip() if i >= 0 else s
```

本轮实测：改后查数 system 不变（18,164），收尾 18,615 → 786，且「切 → 再贴新段 → 再切」来回两次结果一致（幂等）。

必须同时加的单测（`server/tests/agent/test_prompt_stack.py`）：

```python
def test_strip_block_roundtrip():
    from app.secretary import prompt_material as pm, prompt_stack
    blk = pm.MARK + 'X' * 100                     # 不依赖库，纯字符串
    sys_txt = prompt_stack.build(identity='I', modes={'data': 'M'}, rules_menu=blk)['system']
    assert pm.strip_block(sys_txt) and 'X' * 100 not in pm.strip_block(sys_txt)
    assert pm.strip_block(pm.strip_block(sys_txt) + blk) == pm.strip_block(sys_txt)
```

加这条的原因：这个 bug 已经存活了（`_swap_materials` 与 `_answer_system` 两处都写着「换，不叠」的注释，实际一直没换），没有断言就还会再犯。

## 6 验证设计（改完怎么知道有没效）

别用「感觉啰嗦少了」。两个层次：

**A 确定性（必过，不需要模型）**
1. 上面的 `test_strip_block_roundtrip`。
2. 预算：`len(收尾 system) <= 1200`。
3. `answer` 段必须出现在收尾 system 的末尾 500 字符内（`tail[-500:].find(answer_body) >= 0`）。

**B 行为（需要模型，用正则判分，不用人看）**
取 20 道真问题（查数 10 + 情况 10），每题的两种配置各跑 3 次，同一批数据同一时间：

| 指标 | 判法 | 期望 |
|---|---|---|
| 违规符号 | 正则数 `**`、`#`、`\|`、`` ` ``、`>` 出现次数 | 修后 ≤ 修的 1/3 |
| 过程话术 | `_PROCESS_PATTERNS` 命中数 | 修后 0 |
| 分条 | `^\s*\d+[.、]` 行数（非「有哪些」题） | 修后中位 0 |
| 提及实现 | 「SQL / 表名 / 字段 / 数据库」出现次数 | 修后 0 |
| 长度 | 中位字符数 | 修后 ≤ 修前 80% |

判据写死：**四项里至少三项达到期望，才算这条改动有效**；只达到一两项就说明问题不在这段 system，回去查是不是工具结果把回答喂成了清单。

更省事的近似：仓库已有 `_clean_answer` 清洗，所以「违规符号」这一项大概率看不出差别——那就把这一项换成「清洗前的原始回答」统计（在 `_clean_answer` 前打点），否则测的是清洗器不是提示词。

## 7 不做清单

1. **不用 `json_object` 强套回答格式**：本网关下它只保证合法 JSON，识别失败还会把内容替换成空格（DeepSeek 文档原文），且格式约束会掉推理（2408.02442）。
2. **不上工具检索 / 动态工具加载**：8–10 个工具，Anthropic 明说 <10 时收益很小。
3. **不靠「再写一句更强的规则」压格式**：仓库 `_clean_answer` 的注释已经给出结论——提示词约束力不够时，确定性的清洗才管用。
4. **不为了缩短先把口径删了**：先修 `strip_block` 拿到对照组，再按 §4.1 拆两类；顺序反了就无法归因。
