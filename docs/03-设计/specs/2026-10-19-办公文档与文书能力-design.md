# 办公文档与文书能力（V2）—— 场景清单与设计

> 状态：**设计稿，等 Fred 确认后出实施计划**（未动代码）
> 起因：现在只会"查库 + 问答"。内网给业务人员用时，最高频的活其实是**看文件、写材料、做表、做汇报**。
> 本文件回答两个问题：① 还能加哪些场景？② 要加这些，底子缺什么？

---

## 0. 一句话结论

**缺的不是提示词，是"手"。** 模型现在只有 4 个工具（`kb_search` / `find_column` / `run_sql` / `finish`），全是"查"；问数页没有上传入口；技能全是提示词文档。要支持"读 20 页文件、写 word/excel/ppt、纠错、润色、写报告"，必须先建一条**文件底座**：文件进出 → 解析 → 分块抽字段 → 生成 → 自检。底座建一次，上面能挂 15+ 个场景；底座不建，每加一个场景都得重写一遍解析和排版。

## 2. 用户是谁、他一天在干什么

| 角色 | 每天的活 | 最痛的点 | 他要什么 |
|---|---|---|---|
| **A 领导/管理者** | 看上级下发的 20 页文件、听汇报、签意见 | 时间碎，读整篇不划算，怕漏关键要求 | **省阅读时间**：一页纸 + "跟我有关的是哪几条" |
| **B 专责/写材料的人** | 起草通知/请示/报告、汇总各所材料、做表做 PPT | 格式反复改、数据反复核、框架反复搭 | **省写作时间**：给框架、给措辞、给格式、数据自动填 |
| **C 所里经办** | 填表、报数、对账、查条款口径 | 不知道填什么口径、表与表对不上 | **省翻文件时间**：问一句就给条款和数 |

三类人的共同底线：**别编、能追溯、格式别出错**。这三条比"回答得漂亮"重要得多，设计里必须硬约束。

## 3. 场景清单（S1–S20）

难度：● 小（复用现有能力，1–3 天）｜◐ 中（要新模块，3–8 天）｜○ 大（要数据/模板/外部依赖）

### 第一组：读 —— 省阅读时间（**优先做，不需要模板，见效最快**）

| # | 场景 | 给谁 | 输入 → 输出 | 关键判据 | 难度 |
|---|---|---|---|---|---|
| **S1** | **长文速读**（锚点） | A/B | 10–50 页 docx/pdf → 一页纸摘要 + 要点清单表 + "跟我有关的" + 高风险提示 | 20 页 3 分钟内；抽出的时限/金额/责任单位**逐条能回指原文**；没有的写"未提及"而不是编 | ◐ |
| S2 | 条款问答 | C | "XX 规定里对 YY 怎么要求的" → 答案 + 文号 + 条款号 + 原句 | 答案里必须带条款号，能点回原文 | ◐ |
| S3 | 多文件对比 | B | 新旧两版制度 / 两个所的材料 → 差异清单（增/删/改，逐条带原文） | 差异逐条可回指；不改的地方不乱标 | ◐ |
| S4 | 扫描件识别 | C | 纸质文件拍照 → 文字 | 先明确：**内网无成熟离线 OCR，暂不做**，见 §8 | ○ |

### 第二组：审 —— 省返工（**性价比最高：不用模板、不用接数据、错了也不至于误导决策**）

| # | 场景 | 给谁 | 输入 → 输出 | 关键判据 | 难度 |
|---|---|---|---|---|---|
| **S5** | 公文纠错 | B | docx → 问题清单（位置/原文/问题类型/建议/依据）+ 修订版 | 预置 20 处错误的样稿，召回 ≥80%、误报 ≤5 处 | ◐ |
| **S6** | 公文格式合规 | B | docx → 格式问题清单（字体/字号/行距/层次序号/发文字号/成文日期/页边距） | 按 GB/T 9704-2012 逐项给"合规/不合规"，不合规**指到哪一段** | ◐ |
| S7 | 一致性审查 | B | docx → 前后矛盾清单（数字、日期、人名、单位、简称） | 同一事实两处不同必须报出来 | ◐ |
| S8 | 与制度比对 | B | 稿件 + 相关制度 → 引用是否有出处、口径是否一致 | 编造的引用必须报"查无此条" | ◐ |
| **S9** | 表格审查（Excel） | C/B | xlsx → 问题清单（空值/重复/合计不平/单位混写/日期格式/异常值）+ 清洗后表 | 合计对不上必须查出；问题定位到 **sheet + 单元格** | ● |
| S10 | 多表对账 | C | 预算表 vs 执行表 / 申报表 vs 批复表 → 差异清单 | 逐行给"只在 A / 只在 B / 金额不符" | ◐ |

### 第三组：写 —— 省写作时间（**依赖模板，没模板做出来"像但不是"，见 §9**）

| # | 场景 | 给谁 | 输入 → 输出 | 关键判据 | 难度 |
|---|---|---|---|---|---|
| S11 | 公文起草 | B | 要素（什么事、给谁、要什么）→ 通知/请示/报告/函/纪要初稿 docx | 结构要素齐全；格式合规；**所有数字标来源** | ○ |
| S12 | 报告生成 | B | 数据（问数结果/上传表）+ 报告模板 → 周报/月报/专项/验收报告 docx | 数字与来源一致（复用现有 `_num_pool` 守卫）；模板占位符 100% 替换 | ◐ |
| S13 | 润色改写 | B | 一段文字 → 压缩 30% / 扩写 / 换对象（给领导↔给基层）/ 换语气 | 事实不改，只改表达；改完标出动了哪几处 | ● |
| S14 | 长文转 PPT | B | 20 页文件 → 汇报提纲（一页一要点 + 备注页讲稿）pptx | 页数自动定；每页 1 个观点 ≤3 条支撑；讲稿口语化 | ◐ |
| S15 | 汇报讲稿 | B | 材料/PPT → 5 分钟口播稿 | 与材料逐条对应；时长可控（按字数折算） | ● |
| S16 | 会议纪要 | B | 录音（已有 ASR）→ 议题/决议/待办/责任人/时限 → 纪要 docx | 待办必须有责任人 + 时限；听不清的标"待确认"不猜 | ◐ |

### 第四组：办 —— 省跑腿（**和现有预警能力天然咬合，差异化在这里**）

| # | 场景 | 给谁 | 输入 → 输出 | 关键判据 | 难度 |
|---|---|---|---|---|---|
| **S17** | 事项 → 督办台账 → 到期提醒 | A/B | 文件/纪要里抽出的"要求事项" → 台账表 → 每天按账号推"今天该办什么"（接 `/api/alerts/daily`） | 台账每条带来源文件 + 页码；提醒不许重复推 | ◐ |
| S18 | 格式转换/合订 | B | docx↔pdf、多份合并成册（目录+页码）、加水印、拆分 | 转换后版式不塌（用 WPS COM 渲染比对） | ● |
| S19 | 批量填表 | C | 一个模板 + 各所数据 → 一表一所，打包下载 | 每份表都填对；缺数的留空**不编** | ◐ |
| S20 | 上传表直接问 | C | xlsx + "哪个所超预算最多" → 答案 + 依据行 | 答数字必须能定位到行 | ◐ |

**还有两条不属于文件、但同属"常见智能体功能"的缺口，建议一并补：**
- **计算器工具**：造价、线损率、负载率这类换算，模型口算必然错 → 给一个 `calc` 工具（安全表达式求值，不做代码执行）。
- **通讯录/职责查询**：`t_employee` 已只读接进来了，"这事该找谁"是真实高频问题。

## 4. 横切底座（C1–C8）—— 真正决定成败的部分

场景只是皮，这 8 件事做不好，场景越多越乱。

| # | 底座 | 要做的事 | 为什么必须 |
|---|---|---|---|
| **C1** | 文件进出与归属 | 上传/下载、原件留存、成果落盘、**谁传的谁能看**、审计留痕 | 没有入口就一切免谈；文件是敏感资产 |
| **C2** | 解析统一入口 | 复用 `ingestion/parsers/`，补 **pptx**；`.doc/.wps` 走 WPS COM 另存为 docx（不自己写解析器） | 一套解析，多处复用；旧格式别硬啃 |
| **C3** | 长文分块与结构化抽取 | 按 `heading_path` 边界切块（≤1200 字）→ 每块抽固定字段 → 归并去重 → **定位回原文** | 20 页 ≈ 2–3 万字，内网模型 8k–32k 上下文，**整篇塞不进去**，必须分块 |
| **C4** | 生成器 | docx（模板占位符 + 公文样式：三号仿宋_GB2312、行距 28 磅、页边距）/ xlsx（样式、冻结、合计、数字格式）/ pptx（版式套用，图表用 **pptx 原生 chart**，不用 matplotlib，省字体麻烦） | 生成不稳定，前面全白做 |
| **C5** | **自检**（关键差异点） | 生成后**回读校验**：数字能否回指来源、占位符有没有残留、字数、格式清单、必备要素齐不齐 | 这一条决定"敢不敢交给上级" |
| C6 | 任务化与进度 | 上传 → 建任务 → 轮询进度 → 出结果（复用现有 `tasks` 模式） | 20 页要几十秒到几分钟，同步请求会超时 |
| C7 | 模型适配 | JSON 抽取要**schema 校验 + 重试一次 + 兜底降级**；小上下文模型自动加分块 | 内网模型 JSON 经常不合法，不能一崩就整篇失败 |
| C8 | 安全与留痕 | 成果页标注"AI 辅助生成，需人工复核"；敏感词/涉密标记检查；不自动对外发送 | 内网也要有人负责；公文出错是要担责的 |

**两条技术真相，先说清楚免得后面返工：**

1. **docx 没有"页码"。** 它是流式格式，页是渲染出来的。所以定位只能靠 `章节路径 + 段落序号`；要真页码，必须先 WPS/Office COM 转 PDF 再解析（多一层依赖，且慢）。**默认用章节+段落定位，页码可选增强。**
2. **python-docx 做不了"修订痕迹"（tracked changes）。** 所以纠错的产物是「修订建议表 + 干净修订版」，**不假装能留痕**。要留痕就得操作 OOXML 底层，代价大、收益低，见 §8。

## 5. 三种落地形态

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A 纯工具化 | 在现有 agent 循环里加 `read_docx`/`write_docx`… 让模型自己组合 | 改动最小，一个入口 | 分块、模板、自检这些"流程"交给模型自由发挥 → **20 页文件必漏内容**，且每次都不同，无法验收 | ❌ |
| B 纯流水线 | 每类活一个后端 pipeline，模型只做"这一步的语言活" | 稳定、可测、可给进度 | 新场景要加代码，灵活度低 | 可选 |
| **C 混合（推荐）** | **流程骨架写死在代码**（解析→分块→抽取→归并→生成→自检），模型只在每步内做语言活；对外统一成"文档任务"接口，问数页也能调用 | 稳定可验收；模型只干它擅长的；新场景 = 换抽取 schema + 换模板 | 要写少量框架代码 | ✅ |

## 6. 架构（推荐方案）

```
用户 ──上传──> /api/docs/upload ──> data/docs_in/<user>/<file>  （原样保存，审计留痕）
                                        │
                                        ▼
                              POST /api/docs/jobs  (task_type = 速读|纠错|审查|起草|转PPT…)
                                        │  异步（复用 tasks 模式）
                                        ▼
        ┌────────────────── 文档流水线（代码固定骨架） ──────────────────┐
        │ 1 解析  → blocks（段落/表格/标题路径/序号）                     │
        │ 2 分块  → 按 heading_path 边界，≤1200 字                        │
        │ 3 抽取  → 每块 → JSON（schema 固定，校验+重试+降级）             │
        │ 4 归并  → 去重、同事项合并、冲突标注                            │
        │ 5 生成  → docx/xlsx/pptx（套模板）                              │
        │ 6 自检  → 数字回指、占位符、要素齐全、格式清单                   │
        └───────────────────────────────────────────────────────────────┘
                                        │
                     Markdown 结论（聊天里）+ 成果文件（下载）+ 台账（入库）
```

**新增数据表（少就是好）**

| 表 | 用途 | 关键字段 |
|---|---|---|
| `t_doc_job` | 一次文档任务 | id / 用户 / 任务类型 / 输入文件 / 状态 / 结果文件 / 错误 / 耗时 |
| `t_doc_file` | 文件归属 | id / 路径 / 原名 / 大小 / hash / 上传人 / 谁可见 |
| `t_doc_todo` | 事项台账（S17） | 事项 / 责任单位 / 时限 / 来源文件 / 来源位置 / 状态 |

其余一律不加表：抽取结果存 JSON 列，别做成宽表（换场景就得改表）。

## 7. 分期与验收

| 期 | 内容 | 一眼能判的验收 |
|---|---|---|
| **P0 底座** | C1 文件进出 + C2 解析（补 pptx）+ C3 分块抽取 + C4 docx/xlsx 生成 + C5 自检 + C6 任务化 + 一个"文档工作台"页（上传→选任务→进度→下载） | 上传一份 20 页 docx，5 分钟内拿到「摘要 + 清单表 + 成果 docx」，且清单里每条时限/责任单位都能在原文找到 |
| **P1 三个场景** | S1 长文速读 / S5 公文纠错 / S9 表格审查 | 三个真实文件各跑一遍，按 §3 判据逐条打分并留档（`output/test_results/`） |
| **P2 写作类** | S12 报告生成 + S14 长文转 PPT + S17 督办台账（接每日预警） | 报告数字逐条可回指；PPT 一页一观点；台账条目能触发一次真实提醒 |
| **P3 其余** | S2 条款问答 / S3 对比 / S6 格式 / S7 一致性 / S8 比对 / S10 对账 / S11 起草 / S13 润色 / S15 讲稿 / S16 纪要 / S18 转换 / S19 批量 / S20 表问答 / calc / 通讯录 | 每个都按 §3 判据，没判据的补判据再开工 |

**为什么这个顺序：** 读和审**不需要模板、不需要接新数据、错了也不会误导决策**，投 1 份力见 3 分效；写类要模板，办类要台账数据，放后面。

## 8. 明确不做（免得又过分设计）

| 不做 | 原因 |
|---|---|
| 自己写 `.doc`/`.wps` 二进制解析器 | WPS COM 另存为 docx 就够；自己啃二进制是纯浪费 |
| 修订痕迹（tracked changes） | python-docx 不支持，要手改 OOXML；用"建议表 + 干净版"替代 |
| 扫描件 OCR（P3 以后再议） | 内网无成熟离线 OCR；PaddleOCR 部署重、包里塞模型；先让人把扫描件转文字 |
| PPT 自动美化/排版重做 | 风险高、收益低，做出来"更丑"的概率大于"更好看" |
| 自动写回 OA / 自动发文件 | 无接口，且责任风险不可控 |
| 引入 pandas | 体积大；表格审查用 openpyxl 手写检查就够，只有 S20 大表聚合才可能需要，届时再议 |
| 在线协同编辑 | 没有这个需求，也没有并发基础 |

## 9. 需要你确认的三件事（卡住设计，不是客套）

1. **第一批用户是谁？**（领导看文件 / 专责写材料 / 所里经办）——决定 S1 的抽取字段和"与我相关"怎么判。
2. **文件从哪进来？** 我倾向：**独立"文档工作台"页 + 问数页也能传文件**（工作台适合批量、问数页适合"顺手传一份问问"）。
3. **能给我三份真实样本吗？** 一份上级下发文件（20 页左右）、一份你们常写的报告、一份常用汇报 PPT。**没有真样本，写类和生成类做出来一定"像但不是"**——这不是技术问题，是素材问题。
