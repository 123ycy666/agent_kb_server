# 任务裂变设计（一次下发 → N 条任务）

> 场景：市长/市财务/县财务看到一条**聚合预警**（例如"7 个所预算执行进度偏慢"），
> 一次下发，每个下级各自收到**自己那条任务**。
> 已定口径（Fred 2026-10-28）：层–层转派是对的；上级那条闭环要**子任务全闭环 + 自己数据达标**两个条件。

## 1. 一句话模型

**裂变 = 在同一个事项（同 case_id）下，一次生成 N 条兄弟任务，每条绑定下级自己那条预警，
核销范围只看他自己。**

树形：

```
事项 C20261028-00001
└─ 市级任务  D…-0001  承办：市财务    核销：全市 40 个所
   ├─ 曾都任务 D…-0002 承办：曾都财务  核销：本县 7 个所（station_ids=[38,39,40,41,42,…]）
   │  ├─ 两水任务 D…-0005 承办：两水所长 核销：本所 1 个所（station_ids=[42]）
   │  └─ …其余 6 个所
   ├─ 随县任务 D…-0003 …
   └─ 高新任务 D…-0004 …
```

- 所有节点 `case_id` 相同（一件事一张单）
- 每个节点 `parent_task_id` 指向它的下发人那条
- 每个节点 `verify_rule` **只看自己的范围**

## 2. 裂变到哪一层：只能到直接下一级

保持已定的层级规则：市级只能裂给县财务，县级才能裂给所长。
所以"任务是多条发给不同的所"是**两级裂变的结果**，不是市长一跳到底。

| 下发人 | 可裂变目标 | 不允许 |
|---|---|---|
| 市领导 / 市财务 | 县财务（xgscwb） | 直接到所长（`LEVEL_SKIP`） |
| 县财务 | 本县所长（sz） | 跨县所长（`OUT_OF_CHAIN`） |
| 所长 | 无（最低一级） | 任何裂变 |

## 3. 裂变 vs 协同：怎么判

| 判据 | 结论 |
|---|---|
| 核销范围**能拆开**（每个下级有自己的数据范围） | **裂变**：N 条任务 |
| 核销范围**拆不开**（一件事，几个所一起干） | **协同**：1 条任务、多个 `owner` |
| 下发人显式指定 `mode` | 以指定为准（自动判断只是默认值） |

自动判断实现：目标各自都有"自己的那条预警"（同 subtype、scope 收窄到该目标）→ 判裂变；
找不到这类预警 → 判协同（一条多主责），因为拆开也没法分别核销。

## 4. 每条子任务怎么生成（字段来源，逐一钉死）

| 字段 | 取值规则 |
|---|---|
| `case_id` | 继承父任务（同一事项） |
| `root_task_id` | 继承父任务 |
| `parent_task_id` | 父任务 id |
| `title` | 父标题 + "：" + 目标范围名；或下发时给的 `title_template`（`{scope}` 占位） |
| `requirement` | 继承父任务要求；下发时可覆盖 |
| `creator_*` | **下发人**（不是被执行人）——"申请延期"要回到他这儿 |
| `assignees` | 目标那一级的人，`part=owner` |
| `alert_id` | **目标自己那条预警的 id**（查同 subtype + 该目标 scope）；查不到则空 |
| `verify_rule` | **取目标那条预警的 `verify_hint`**（自带正确 station_ids）；查不到 → `{'kind':'manual'}` |
| `verifier_type` | 有 verify_rule → `auto`；否则 `human` |
| `require_reply` | 下发时指定；默认 1（要回执） |
| `reply_due_at` | 指定值，且**不得晚于**父任务的 `reply_due_at`；默认 = min(父回复时限, 指定) |
| `due_at` | 指定值，且**不得晚于**父任务 `due_at`；默认 = 父的 `due_at` |
| `scope_type/key/name` | 目标自己那条预警的范围（不是父的） |
| `biz_type/biz_keys` | 目标那条预警的对象 |

**为什么时限必须夹住**：子任务比父任务晚到期，会出现"父任务已逾期升级、子任务还早"的荒唐状态。

## 5. 幂等与"已经有单了"怎么处理

对每个目标按顺序判三步：

1. **已有活跃子任务**（同父 + 同承办人 + 未 closed/cancelled）→ **复用**，不新建，返回在 `reused`
2. **该目标自己已经开过单**（同一 alert 有活跃根任务）→ **认领（adopt）**：
   - 不重挂、不改它已有的父子关系
   - 在父任务上记一条 `fanout` 事件，`payload.adopted=[那个 task_id]`
   - 汇总闭环时把被认领的那棵树**也算作子任务**
3. 都没有 → 新建

> 为什么不重挂：重挂会破坏那条单已有的时间线、权限和已经发出去的通知。
> 认领只影响"汇总怎么算"，不动别人的账。

整批请求用 `idempotency_key` 兜底：同一 key 重复提交，返回同一批结果，不重复生成。

## 6. 上级那条怎么闭环（两个条件）

父任务新增判定：`has_children` 为真时，闭环条件变成**两个都要满足**：

```
所有子任务（含 adopted 树）status == closed
        AND
父任务自己的 verify_rule 通过（数据真达标）
```

- 缺一个都不闭环，`verify_state` 记为 `pending`，并在 `dispatch_check.measured` 里写明
  `{"children_closed": false, "data_ok": true, "waiting": ["D…-0005"]}`
- 人工闭环时同样要过这两关；**只有 admin 可以强制闭环并留痕**
- 子任务全闭环但数据不达标 → 给父任务承办人发通知："下级都办完了，但全县执行率还是 12.3%"

## 7. 部分失败不阻塞

某个目标找不到承办人（该所没有所长账号）→ **跳过该目标**，其余照常生成。
响应里必须列出来：

```json
"skipped": [{"target": "厉山供电所", "reason": "该所没有可用所长账号"}]
```

并给下发人发一条通知："已下发 6 条，厉山所因找不到承办人未下发"。
**不允许**因为一个目标失败就整批回滚——他已经点了下发。

## 8. 接口

```
POST /api/tasks/{task_id}/fanout
```

请求：

```json
{
  "targets": [{"employee_id": 123}],   // 省略/空 = 自动按本任务范围找全部直接下级
  "mode": "per_target",                // per_target（默认，裂变）/ joint（协同）
  "title_template": "{scope}：月底前把预算花完",
  "requirement": "可选，覆盖父任务要求",
  "due_at": "2026-11-30T18:00:00+08:00",
  "reply_due_at": "2026-11-05T18:00:00+08:00",
  "require_reply": 1,
  "require_plan": 0,
  "idempotency_key": "fanout-1"
}
```

响应：

```json
{
  "parent_task_id": 3,
  "case_id": "C20261028-00001",
  "mode": "per_target",
  "created": [{"task_id": 11, "task_no": "D…-0011", "assignee": "曾都区财务",
               "scope_name": "曾都区供电公司",
               "verify_rule": {"kind": "budget_rate", "station_ids": [38,39,40,41,42]}}],
  "reused":  [{"task_id": 12, "task_no": "D…-0012", "reason": "该所已有在办任务"}],
  "adopted": [{"task_id": 7, "task_no": "D…-0007", "reason": "该县已自行开单，已并入汇总"}],
  "skipped": [{"target": "厉山供电所", "reason": "该所没有可用所长账号"}]
}
```

错误码：`LEVEL_SKIP`（跨级）、`OUT_OF_CHAIN`（跨单位）、`NO_TARGET`（一个可用目标都没有）、
`INVALID_MODE`、`NOT_PARTICIPANT`（无权下发）。

## 9. 事件与通知

| 谁 | 收到什么 |
|---|---|
| 父任务 | `fanout` 事件：`{targets, created[], reused[], adopted[], skipped[]}` |
| 每条子任务 | `create` 事件：`{parent_task_id, source: "fanout"}` |
| 每个承办人 | `assign` 通知（一条一条发，不合并） |
| 下发人 | 一条汇总通知："已下发 N 条，M 条复用，K 条跳过" |

## 10. 验收判据（全部可测）

1. 选 3 个县裂变 → 生成 3 条，`case_id` 与父相同，`parent_task_id` 指向父
2. 每条子任务的 `verify_rule.station_ids` **等于该县自己的范围**（不是父的全市）
3. 子任务 `due_at ≤ 父 due_at`，`reply_due_at ≤ 父 reply_due_at`
4. 子任务 `creator` 是下发人，`assignee` 是下级
5. 同一批重复裂变 → 不新增（`reused` 命中）
6. 跨级目标（市级 → 所长）→ `LEVEL_SKIP`
7. 某目标没有承办人 → 该目标进 `skipped`，其余照常生成
8. 目标已自行开单 → 进 `adopted`，不新建、不重挂
9. 子任务全闭环、父数据未达标 → 父**不**闭环，且发出提醒通知
10. 父数据达标、子任务未全闭环 → 父**不**闭环
11. 两者都满足 → 父自动闭环，`close_reason=auto_verified`
12. `mode=joint` → 不裂变，只有 1 条任务、多个 owner，且 `verify_rule` 为父的整个范围
