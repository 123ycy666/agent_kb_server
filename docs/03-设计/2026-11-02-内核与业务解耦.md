# 内核与业务解耦（代码里不存业务口径）

日期：2026-11-02　触发：Fred「全部删除，相当于代码里面不存业务逻辑，就是一个正常的智能体，和业务没关系」

## 目标

`server/app` 的内核只做通用智能体的事：模型调用、工具循环、检索、会话、QA 留痕、证据闸门。
**业务口径（状态码、阈值、角色、时限、业务指标公式、业务词）一律不出现在代码里**，全部来自可编辑材料：提示词页 12 步材料、`skills/*.md`、库里的字典表（`t_dict` / `ai_*`）。

## 现状实测（本次盘点）

- `server/app` 下 160 个 .py，其中 68 个文件、775 行命中业务词（供电所/工单/预算/预警/线损/审批/派单/万元/台区/项目）。
- 92 个文件 0 命中 —— 这部分就是内核该有的样子，作为解耦后的基线形状。
- 业务耦合最重的 8 个文件：`name_corrector.py`(174)、`dispatch_ai.py`(75)、`dispatch_rules.py`(59)、`rules_defaults.py`(41)、`alerts.py`(37)、`alerts4.py`(32)、`agent.py`(30)、`time_scope.py`(30)。
- 同一批阈值有两份代码副本：`alert_rules.py:73-81` 常量 + `rules_defaults.py` 生成副本，由 `alert_rules.py:138` 运行时互相覆盖。

## 边界（要删的具体是什么）

| 模块 | 现状 | 处置 |
|---|---|---|
| `secretary/metrics.py` | 固定 SQL 算预算执行率、状态 3/6/7 | 整文件删除，口径回到材料 + `run_sql` |
| `secretary/alert_rules.py`、`alerts.py`、`alerts4.py`、`alert_wording.py`、`alert_scope.py` | 预警判据、阈值、角色、节点映射 | 判据搬 `skills/判据规则.md`；角色与阈值搬库表；代码只留通用调度 |
| `dispatch_rules.py`、`services/dispatch_ai.py` | 派单时限、承诺文案、建议模板 | 模板搬材料；代码留通用任务模型 |
| `secretary/rules_defaults.py` | 313 行业务默认值（生成件） | 删除，值进库表 |
| `secretary/report.py` | 业务报告口径与禁词 | 报告结构搬材料 |
| `libs/name_correction_lib` 业务词表层 | 174 行业务词 | 词表已在 `t_nc_wordlist`，删代码里的那一层 |
| `time_scope.py` 业务时间口径 | 30 行（1–9 月累计、季度无口径等） | 保留时间解析，业务口径搬材料 |

## 不改什么

- 工具机制、循环与收敛、证据闸门、检索、会话与摘要、QA 日志、权限：这些是内核，含"不许编数""空集就是答案"这类纪律，属通用质量控制，不是业务口径。
- 不动 `docs/`、`skills/*.md` 的内容（它们本来就是材料）。

## 必须说清的代价

1. **数值可复现性下降**：`metrics.py` 当初就是为了修「同一问两次 22.79% / 0.00%」才写的固定 SQL。删掉后预算执行率由模型读材料 + 自己写 SQL，同一问两次结果可能不同。
2. **预警与派单**不再是代码保证的行为，变成提示词驱动的"大概会做"；`api/v1/alerts.py`、`api/v1/dispatch.py` 的路由要一并下线或退化为通用接口。
3. 一次改 68 个文件无法验证，必须分批，每批跑测试并贴输出。

## 分批与验收

| 阶段 | 做什么 | 验收判据 |
|---|---|---|
