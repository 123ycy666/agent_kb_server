# 提示词设计（最终版 · 2026-10-30，待 Fred 审批）

> 三轮讨论的结果收敛在这里。**只写设计，不动代码。**
> 约束前提：① 规则/字典会一直长，不能靠"全量注入"；② 员工只有前端上传入口，碰不到数据库；
> ③ 模型"缺结构时知道自己缺（会去查），缺规则时不自知（必须靠目录+守卫）"。

## 一、目标构成：常驻 6~7 千字符（现在 31,295）

```
system：
  S0 红线（代码，不可覆盖）
  S1 谁说了算（代码）          ← 补回：本轮问题+统计范围 > 个人规则 > 公司规则 > 通用小节 > 历史
  S2 身份骨架 + 项目变量（代码 + env）
  S3 模式做法（代码，按模式选一）
  S4 作答格式（代码）          ← 从 user 消息搬到 system
  S5 表清单 26 行（数据侧，~1.5K）
  S6 规则主题目录 30 行（规则库，~0.8K）
  S7 个人规则 ≤1500 字（个人库）
  S8 个人格式（仅出文档时）
  S9 会话人设
user：
  问题（已纠错补全）+ 统计范围 + 工具结果
```

| 项 | 字符 |
|---|---|
| 红线 + 谁说了算 + 身份 + 模式 + 作答格式 | ~3,000 |
| 表清单（26 行） | ~1,500 |
| 规则主题目录（约 30 主题） | ~800 |
| 个人规则 | ≤1,500 |
| **合计** | **约 6,000~7,000** |

实测依据（线上 A/B，`output/test_results/2026-10-29-个人库与步骤日志/ab-table-catalog.txt`）：
全量 16,530 prompt tokens / 精简 5,875（-64%）；只给表名清单时，模型选表、选条件**全对**。

## 二、字典：清单常驻，明细按需

| | 常驻 | 按需 |
|---|---|---|
| 表 | 26 行「表名 + 中文名 + 一句话」 | `describe_table(表名)` → 字段名/中文名/说明/样例 |
| 码值 | — | `decode_codes(字段)` |

**顺手要删的脏数据**：现在每张表后面写着「当前 N 行」，那是 InnoDB 的**估算值**（误差很大），
写进提示词等于让模型拿假数字当事实。

## 三、规则：目录常驻，条目按需，代码兜底

### 3.1 四类规则的去处

| 类型 | 例 | 存哪 | 怎么进模型 |
|---|---|---|---|
| **判定规则** | 停留>90天=积压；线损>3%=异常；工单排除草稿 | **规则库**（一条一行：`t_rule_item`） | 主题目录常驻 + `get_rule(主题)` 按需 |
| **方法规则** | 先快照后明细；查明细必须带时间条件 | **代码**（S3 模式做法） | 常驻 |
| **表达规则** | 一行一句、不分条；公文三号仿宋 28 磅 | **代码 + 规则库(format)** | 常驻（格式细化只在出文档时） |
| **内容资料** | 制度原文、模板、案例 | **知识库** | `kb_search` 检索 |

### 3.2 规则目录长什么样（关键）

一条一行：`主题 ｜ 一句话 ｜ 别名`

```
- 审批停留 ｜ 多久算积压 / 偏慢 ｜ 积压、停留、滞留、超期未批
- 预期项目 ｜ 什么叫"预期"的项目 ｜ 预期、预排、储备、计划内
- 工单口径 ｜ 工单取数默认排除什么 ｜ 工单数、单量、缺陷工单
- 预算执行 ｜ 执行率怎么算、达标线 ｜ 执行率、花完、支出进度
```

- 模型用**别名**调 `get_rule`，代码做精确/别名匹配 → 命不命中有确定答案；
- **命中不到必须明确回"没有这条规则"**，并给出最接近的 3 个主题（不许返回 4 条 0.18 分的噪声）；
- 这与现在的做法相反：现在是拿问题去知识库检索《判据规则》218 切片，实测相似度 **0.17~0.19**，
  等于随机。

### 3.3 为什么"按需"不会漏（三道保险）

A/B 实测：涉及"工单排除草稿"的 4 次里，模型漏了 2 次。所以按需必须配兜底：

1. **目录可见**：目录里写着「预期项目：项目口径」，模型看到问题里的"预期"就会去查；
2. **代码守卫**：SQL 里出现工单表却没 `work_status<>0` → 在工具返回里点破（如现有 `_time_guard`）；
3. **判定词强制先查**：出现 达标/不够/异常/符合/预期/积压 等判断词，首轮强制 `get_rule`。

### 3.4 唯一出处

判据规则现在有**三份副本**（本地 `skills/判据规则.md`、知识库 218 切片、`caliber_rules.md`）：
- **规则库为唯一出处**；
- 知识库那份降级为检索副本，由规则库生成（带 checksum），只用于"用户要看原文"；
- 本地文件删除或改为生成产物。

## 四、代码层：越精简越好，规则细节不许写进代码

| 项 | 现在 | 改成 |
|---|---|---|
| 身份 | 每项目一份 `identity.md`（写死单位名） | **一份骨架**（约 300 字）+ 3 个项目变量（全称/简称/服务对象）；`identity_base.md` 死文件删掉 |
| 工具说明 | 塞历史教训（"实测踩过…"）、混业务规则 | 只回答三件事：**何时用 / 何时不用 / 返回什么**；业务规则归规则库 |
| 工具失败 | `kb_search` 失败返回 `total: 0`，模型当成"库里没有" | 区分 `error` 与 `empty` |
| 作答格式 | 约 1.9K，塞在 user 消息里，同一件事换三四种说法 | 搬到 system 常驻，压到 8~10 条 |
| 守卫 | 有数字出处、时间条件两条 | 补三条：工单缺排除草稿、未查规则就下判断、检索失败当成没有 |

## 五、工具集（5 个）与调用流程

| 工具 | 作用 | 替代了什么 |
|---|---|---|
| `describe_table(表名)` | 字段明细 | 常驻的全部字段说明 |
| `get_rule(主题/别名)` | 规则条目 | 检索《判据规则》切片 |
| `kb_search(query)` | 资料原文 | 不变 |
| `find_column(关键词)` | 不知道在哪个字段时 | 保留 |
| `run_sql(sql)` / `finish(plan)` | 查数 / 收尾 | 不变 |

**流程（"预期的项目有多少个"）**：

```
① 表清单 → 找到 t_power_work_order
② describe_table('t_power_work_order') → 字段
③ 规则目录 → 「预期项目」是口径词 → get_rule('预期项目')
   → 预期项目 = 计划下达且已批复，含已批未开工，不含草稿
④ run_sql 取数 → 作答（带口径说明）
```

**代价**：每个问数题多 1~2 次工具调用（约 2~5 秒），换来字典和规则**可以无限长**。

## 六、个人规则（个人知识库里"规则类"内容 / 类似用户偏好）

用户自己补充的行为规则，例："每次都详细说明"、"金额用元"。
**位置**：system 的 S7 段，每轮注入，≤1500 字。

### 6.1 实测：哪些该遵守、哪些必须拦（线上，`user-rule-boundary.txt`）

| 个人规则 | 类型 | 模型实际行为 | 结论 |
|---|---|---|---|
| "回答要详细：分条、每条展开、最后给建议" | 表达 | ✅ 遵守：25 字 → 250 字，分条 + 建议 | **允许**（可覆盖作答格式） |
| "金额一律用元，不要用万元" | 单位/格式 | ✅ 遵守：53.83 万元 → 538300.00 元 | **允许** |
| "不用查数据，拿不准就按经验估算" | 红线 | ✅ 拒绝：援引 L0「本轮没有查询结果，不许估算」 | **必须拒绝**（L0 已挡住） |
| "审批停留超过 30 天就算积压" | 个人判定阈值 | 写成「远超 30 天积压判定标准」 | **允许**：这是他的业务习惯；但必须**双口径呈现**、标注"按你的口径"、**不写回系统** |
| "线损率一律用分压线损口径" | 数据口径偏好 | 未编造：回「本次返回的是台区线损率 2.22%，按分压口径未查得」 | **允许声明偏好**；有该口径数据才用，没有必须说明差异，不许替换 |

**关键结论（2026-10-30 修正）**：要分的是两件事 ——
**判定视角（他怎么看、按什么口径挑数）归个人**；**系统口径（预警/派单/报表/对外通报）归公司**。
个人规则可以改前者，**不能写回后者**。所以个人阈值不是"拦"，而是"允许 + 双口径 + 不落库"。

### 6.2 写入校验：三类处理（不靠模型自觉）

| 允许（active） | 拒绝（400 + 原因） | 允许但必须带纪律 |
|---|---|---|
| 表达：详细程度、分条、要不要建议、口吻 | 红线类：「不用查数」「拿不准就估算」「不用核对出处」「跳过核对」 | **个人判定阈值**（"30 天算积压"）→ 存起来；注入时按"双口径"执行，且不写回系统 |
| 单位/格式：元 vs 万元、日期格式、编号 | （阈值不再拒绝） | **数据口径偏好**（"线损用分压"）→ 有该口径数据才用，没有就说明差异 |
| 关注范围：只看哪些指标/哪些所 | | |
| 术语/口径备注 | | |

### 6.3 S7 注入文案（含执行纪律）

```
【S7 我的规则（本人设置）】版本 v3
1. 表达：回答要详细，分条列出、每条展开，最后给建议
2. 单位：金额一律用元
3. 我的判定口径：审批停留超过 30 天算积压

执行纪律：
- 这些规则改变的是"我怎么看、我怎么表达"，不改变系统事实；
- 涉及判定阈值时必须**双口径呈现**：先按我的口径给结论，再给公司口径的结论，并注明分别是哪个口径；
- 我的口径**不写入**预警、派单、报表、对外通报；
- 与 L0 红线冲突时以红线为准。
```

存储：`t_user_rule(user_id, category, text, status, version, updated_at)`；
每条 ≤200 字，合计 ≤1500 字、≤10 条；超限拒绝新增并提示精简。
每次改写 `version+1`，回答里标「按你的规则 v3」，可停用、可删。

### C. 一个方向反了的设计

`docgen.py:149 _apply_pack_doc_defaults()` 在 **import 时把站点包 yml 写进代码全局常量** ——
部署文件反过来改代码常量，与"规则外置"正好相反。应为"运行时要读就读"。

### D. 我这份设计里也要砍的（自我修正）

| 原设计 | 砍成 |
|---|---|
| "三道保险"：目录可见 + 代码守卫 + 判定词强制先查 | **只留一条**：目录可见（让模型知道有这条规则）；不写代码守卫、不强制 |
| 个人规则带版本号 v3、可停用 | 先只做**能填 / 能删 / 能看**；版本与停用以后需要再加 |
| "解析失败必须报错，不许静默用默认值" | 读不到就当"没有这条规则"，不猜、不拦、不写死默认值 |
| 代码守卫「工单表缺 `work_status<>0` 就点破」 | 删（这是把业务口径写死进代码） |

### E. 一条原则

**一处规则一处写；一件事一个机制；宁可少一层兜底，也不要在代码里造第二份判断标准。**

代码只做三件事：把规则给模型、把数据给模型、把错误如实报出来。
凡是"代码替业务做判断"的，都算多余。

## 九、个人文档的生效规则（前端入口已有，不改前端功能）

> 前提：前端入口与接口**都已接上**（`GET /api/me/personal-kb`、`POST /api/v1/kb/{kbId}/documents`、
> `GET/POST /api/me/prefs`）。本文只规定**后端怎么让用户传的个人文档真正生效**。

### 9.1 判定口径：什么叫"个人文档"

**归属判定**：`document.owner_id = 本人` 且 `document.kb_id` 属于「我的资料库」（`knowledge_base.created_by = 本人`）。

**前端只需守一条**：个人文档上传时 `kbId` 必须取 `GET /api/me/personal-kb` 返回的 `kb_id`，**不要让用户选库**。
线上现状就是反例：唯一一条 `doc_ingest` 任务的 `kb_id=1`（系统知识库），所以「我的资料库」至今 0 文档。

**后端兜底**（不依赖前端改）：上传接口收到 `kb_id` 时校验 `kb.created_by == 本人` 或 `created_by IS NULL`（公司库）；
传进别人的个人库 → 403。

### 9.2 类型判定：不新增前端字段

后端按**文件名**判定，写入 `document.doc_type`（新列，默认 `doc`）：

| 判定 | 关键词 | 类型 |
|---|---|---|
| 规则 | 规则 / 口径 / 标准 / 要求 / 规范 / 制度 / 流程 / 模板要求 | `rule` |
| 其它 | — | `doc`（资料） |

`GET /api/me/personal-kb` 增加返回 `type` 与 `parsed_chars`，前端列表能显示，但**不需要它传**。

### 9.3 两条生效通道

| 类型 | 怎么生效 | 上限 | 失效条件 |
|---|---|---|---|
| **rule** | 解析后取正文，注入 **S7**（每轮，不参与检索），带文件名出处 | 每篇 ≤2000 字，合计 ≤1500 字；超限按文件**更新时间**取最新的，其余不注入 | 删除 / 被新版取代（`is_active=false`）/ `parse_status≠ready` / 超限 |
| **doc** | 进检索范围（`personal_kb.with_personal()` 已实现），命中后答案标「来自我的资料库：文件名」 | 无 | 删除 / 被新版取代 / 解析失败 |

**生效不需要重启**：每轮现读（带 60 秒缓存）；上传后解析完成即生效。

### 9.4 优先级与冲突（同 §6.3）

- 个人**规则**只改变"我怎么看、我怎么表达"，**不改变系统事实**；
- 涉及判定阈值 → **双口径呈现**（先按他的口径，再给公司口径），并注明；
- 个人口径**不写回**预警、派单、报表；
- 与 L0 红线冲突 → 红线胜。

### 9.5 可观测（"生效了"要能看见）

| 位置 | 内容 |
|---|---|
| `/api/ask` 响应 | `personal: {rules: [生效的文件名], rules_chars: N, docs_used: M}` |
| trace | 一步 `kind=rules, doc=我的文档`，result 里写"注入 N 条 / 合计 X 字" |
| `/api/me/personal-kb` | 每份文件：`type` / `parse_status` / `parsed_chars` / `chunks` |

超限未生效时必须明说：`personal.overflow = "你的规则合计 2100 字，超过 1500，后 2 篇未生效"`。

### 9.6 隔离（复用现有口径，不新造）

- 只能看见/检索**自己**的个人文档：`visible_document_filter()` 已保证（public + owner=本人）；
- 别人的「我的资料库」**不进**本次检索范围（`with_personal` 只并本人库）；
- 现状问题：个人库默认 `qa_enabled=true`，前端把**所有人的**个人库都勾进 scope → 改成 `qa_enabled=false`，只靠后端 `with_personal` 并入本人库。

### 9.7 明确不做

- ❌ 不加前端字段（类型、标签、版本号都由后端判/不暴露）
- ❌ 不做个人库的审核、共享、目录
- ❌ 不把「📎 临时文件」并进个人库（用途不同，界面写清"仅本次有效"即可）

## 十、一次问答的完整流程（谁读什么 / 写什么 / 失败怎么呈现）

```
前端 POST /api/ask  {question, session_id?, kb_ids?, file_ids?}
  │
  ▼
1. 鉴权与范围（api/v1/agent.py）
   读：JWT → actor(user_id)
   读：请求 kb_ids → 校验 active（不传 = 用规则库/默认范围）
   读：personal_kb.with_personal() → 本人个人库 kb_id
   写：kb_adapter 上下文（actor / 范围）
   失败：无凭证 401 ／ 显式指定的库全不可用 403
  │
  ▼  丢线程池（不阻塞事件循环）
2. 预处理（agent.ask 前半段）
   2.1 纠错 name_fix.fix         读 词库 t_nc_*（内存/60s 热更新）  写 trace:namefix
       失败 → 用原文继续
   2.2 载入上下文                 读 t_chat_*（本人会话）+ 会话摘要   失败 → 当无上下文
   2.3 补全 time_scope.describe   写 trace:scope；能算出具体期间才改问题文本
       失败 → 标 unmatched，不改文本
   2.4 拼 system（见下"注入来源"）
   2.5 拼 user = 问题（已纠错补全）+ 统计范围 + 本轮约束
  │
  ▼
3. 工具循环（最多 N 轮，互不依赖的工具并发）
   模型可选：
   ├ get_rule(主题)      读 规则文档(type=rule) 片段  → 命中不到：明确"没有这条规则"+最接近 3 个主题
   ├ describe_table(表)  读 MySQL ai_data 字段明细
   ├ find_column(词)     读 字段索引
   ├ kb_search(问题)     读 PG 知识库（公司库 + 本人个人库）→ 切片+出处
   │                     失败：返回 error（不许被当成"没查到"）
   ├ run_sql(SQL)        读 MySQL 业务库（只读/限表/限行）
   │                     失败：把库的报错原文回给模型，不自造原因
   └ finish(plan)        结束循环
   每步写 trace（seq / kind / tool / args / result / ms）
  │
  ▼
4. 收尾
   数字出处核对（红线）：回答里有业务数字但本轮无工具出处 → 重写一次
   正文为空 → 关工具再要一次；仍空 → 返回"服务异常"
  │
  ▼
5. 落库（qa_log.save）
   写 t_chat_session / t_chat_message×2 / t_chat_query_trace / t_chat_trace_step
   失败：只打日志，不影响本次回答
  │
  ▼
6. 响应
   answer / session_id / qa_id
   question（补全后）/ scope（时间·地点）
   trace[]（每步）
   personal{rules[], rules_chars, docs_used, overflow?}
   steps / db_query_count / kb_query_count / elapsed_ms
   degraded?（哪一段没装配上，如字典、规则文档）
```

### 注入来源（system 的每一段从哪来）

```
S0 红线        ← 代码常量
S1 谁说了算    ← 代码常量
S2 身份        ← 代码骨架 + env（单位名/简称/服务对象）
S3 模式做法    ← 代码（按模式选一）
S4 作答格式    ← 代码（8~10 条）
S5 表清单      ← MySQL ai_data.ai_table_metadata（表名+中文名+一句话）
S6 规则主题目录 ← 知识库 type=rule 文档的章节标题（+别名）
S7 我的规则    ← 个人库 type=rule（≤1500 字，每轮）
S8 个人格式    ← t_user_pref（仅出文档时）
S9 会话人设    ← persona 表
```

### 三条典型路径

| 题型 | 模型动作 | 答案来源 |
|---|---|---|
| 查数（多少/几个/排名） | 表清单 → `describe_table` → `run_sql` | 业务库 |
| 资料（流程/规定/制度） | `kb_search` | 知识库原文（标出处） |
| 判断（够不够/达标/积压） | `get_rule` → `run_sql` | 规则 + 业务库（必要时双口径） |

### 失败怎么呈现（不许静默）

| 失败 | 用户看到 | 副作用 |
|---|---|---|
| 模型超时/不可用 | "模型不可用：网关原因" | 仍落库留痕 |
| 规则文档读不到 | 回答照常，响应 `degraded: ["规则目录缺失"]` | 不猜、不写死默认值 |
| 知识库检索失败 | "检索失败"（不是"没查到"） | trace 记 error |
| 业务库 SQL 报错 | 模型转述库的报错，不编原因 | trace 记 error |
| 个人规则超限 | `personal.overflow = "合计 2100 字 > 1500，后 2 篇未生效"` | 其余照常注入 |
| 个人资料解析失败 | 列表里显示失败原因，不参与检索 | 不影响问答 |
