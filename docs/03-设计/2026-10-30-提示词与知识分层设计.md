# 规则外置：什么放哪 + 偏好提示词设计（v3 · 2026-10-30）

> Fred 的命题：**不是"换项目"，是"规则外置"** —— 规则要从代码里搬出来，做到能改、能版本、能审计；
> 然后想清楚"什么东西放在哪里"；以及**个人文档 / 系统文档的偏好提示词**怎么设计。
> 本文只谈这三件，不扩散。

---

## 一、先定死三个词

| | 是什么 | 例子 | 必须放哪 |
|---|---|---|---|
| **机制** | 怎么算、怎么判、怎么组装、怎么守 | 循环、并发调工具、数字守卫、提示词装配顺序 | **代码**（改它=改产品） |
| **规则** | 按什么标准算/判/写 | 停留 >90 天=积压、线损优秀线 3%、回款时限 24h、口径"线损率指台区线损"、公文默认三号仿宋 28 磅 | **规则库（数据，带版本）** |
| **内容** | 具体的文字材料 | 制度原文、模板、案例、台账 | **知识库**（可检索、带出处） |

**规则外置 = 把"规则"从代码里彻底搬出来。** 现在只搬了一半：

| 现状 | 证据 | 问题 |
|---|---|---|
| 阈值写进 python 常量 | `alert_rules.py`：`STAY_BACKLOG_DAYS=90`、`STAY_SLOW_DAYS=15`、`UNDERSPEND_COEF=0.6`、`NOT_STARTED_DAYS=30`、`EXTREME_AMOUNT=1000000.0`、`STATUS_APPROVED=('3','6','7')` | 改 90→30 要**发版**；没有版本号、没有审计、谁改的查不到 |
| 派单/时限写进 python 常量 | `dispatch_rules.py`：`LEVEL_REPLY_HOURS`、`LEVEL_TARGET_DAYS`、`LEVEL_GRACE_DAYS`、`URGE_BEFORE_HOURS`、`REOPEN_DAYS`、`DRAFT_DAYS`、`RATE_TARGET`、`LOSS_RATE_MAX=3.0`、`ROI_MIN=0.1` | 同上（形式上外置成模块，实质上仍是代码） |
| 口径写成 md 文件 | `caliber_rules.md`（7.4K）、`business_rules.md`（2.2K） | 改一个字要发版 |
| 判据规则三份副本 | 本地 `skills/判据规则.md` + 知识库 218 切片 + `caliber_rules.md` | 必然漂 |
| 系统文档默认格式 | `_platform/doc_defaults.yml` | 单位要改格式也得发版 |
| 词表两份 | `business_terms.yml` vs PG `t_nc_*`（4 万行） | 双份 |

## 二、什么东西放在哪里（按现状穷举）

| 类别 | 现在在哪 | 该在哪 | 判据 |
|---|---|---|---|
| 红线、数字守卫 | 代码 | **代码** | 改错要命 |
| 工具契约（kb_search/run_sql 的描述） | 代码 `TOOLS` | **代码** | 必须与实现同版本 |
| 编排流程 | 代码 `agent.ask` | **代码** | 机制 |
| 身份骨架 | `sites/suizhou/prompts/identity.md` | **代码骨架 + 项目变量**（单位名/简称/时区） | 内容 90% 通用 |
| 模式做法（问数/写作/公文） | `_platform/mode_*.md` | **代码（产品级一份）** | 不随项目 |
| 作答格式（汇报口吻/交卷检查） | `agent.py` COMMON/CHECK + `answer_data*.md` | **代码（产品级一份）** | 与红线同性质 |
| **判据 / 阈值 / 时限 / 系数** | `alert_rules.py`、`dispatch_rules.py` | **规则库** | 业务会改、要回滚、要审计 |
| **口径 / 术语 / SQL 规范 / 工单口径 / 指标口径** | `caliber_rules.md`、`business_rules.md`、`sql_plan_rules.md`、`work_order_rules.md`、`metrics_rules.md` | **规则库** | 同上 |
| **判据规则正文** | 三份副本 | **规则库（唯一出处）**；知识库只放由库生成的检索副本 | 唯一出处 |
| **词表 / 同义词补充** | `business_terms.yml` + `t_nc_*` | **规则库/词库表（唯一出处）** | 双份必漂 |
| **模式关键词**（哪些词算问数） | `_platform/mode_rules.yml` + `modes.py` 兜底 | **规则库**（代码只留兜底） | 业务词会变 |
| **预警/派单规则的文本说明** | `rules/alerts.yml`、`rules/dispatch.yml` | **规则库** | 业务会改 |
| 表 / 字段 / 码表 | MySQL `ai_data.ai_*` | **MySQL（跟业务库走）** | 数据侧 |
| 制度 / 模板 / 案例 / 台账 | 知识库 | **知识库** | 内容 |
| **系统文档格式默认** | `_platform/doc_defaults.yml` | **规则库**（`domain=format`，产品默认可被单位覆盖） | 单位要改格式 |
| **个人格式偏好** | `t_user_pref`（8 键白名单） | **保留**（规则库不掺个人数据） | 员工自己改 |
| **个人口径 / 规则** | 个人库（**没有类型标记**） | **个人库（规则类）** | 员工上传，见 §四 |
| 会话人设 | `persona` 表 | 保留 | 会话级 |
| 预设问题 | `presets.yml` | 规则库或前端配置 | 内容运营 |
| 定时任务 | `jobs.yml` + `t_site_job` | `t_site_job` 表 | 已有表 |

**一句话**：代码只留"机制 + 与安全强绑的文本（红线/工具/作答格式）"；**凡是业务方可能想改的，进规则库**；**凡是长出来的文字材料，进知识库**；**凡是因人的，进个人层**。

## 三、规则库最小设计

```
t_rule_item(
  id, project_id, domain, key, kind, value, unit, note,
  version, status(active/disabled), effective_at, updated_by, updated_at
)
```
- `domain`：`threshold / deadline / caliber / rule_doc / mode_keyword / lexicon / format / dispatch`
- `kind`：`value`（数值/枚举，如 90 天、0.6）｜`text`（整段口径，如"S 线损率统一用台区线损率"）
- 读法：启动加载 + 60 秒版本探测热更新（复用现有 `t_nc_*` 词库那套机制）
- 一条规则一行 → 改一条只动一条，历史版本都在
- `/health` 增加 `rules: {domain: version}`，改完能立刻确认生效

**验收（可机器判）**：
1. 把积压阈值 90 改 30，**不打包不发版**，60 秒内预警结果与 `/health` 版本都变；
2. 判据规则三副本 → 一份，且带 hash；
3. grep 断言：代码里不再出现 `90`/`0.6`/`3.0` 这类业务阈值字面量（挪进库）。

## 四、个人文档 vs 系统文档：偏好提示词怎么设计

现在有三处"偏好"，但只有一处真在起作用、而且呈现方式很差：

| 来源 | 存哪 | 现状问题 |
|---|---|---|
| 产品默认格式 | `_platform/doc_defaults.yml`（三号仿宋/28 磅/首行 2 字） | **完全没进提示词**，只作用于 docx 生成函数 → 模型不知道默认是什么 |
| 个人格式偏好 | `t_user_pref`（8 键） | 注入成**裸键值**：`body_pt：15`、`line_spacing_pt：26`、`sign_off：环潭供电所` —— 没中文名、没单位、没说何时用；且**问答时也无条件注入**（纯噪声） |
| 个人口径/规则 | 个人库 | 没有类型标记、没有注入通道（这就是"个人知识库不生效"） |

### 4.1 三级覆盖（沿用 `prefs.merge_fmt`，但要把"人话"补上）

```
【S6 文档格式｜三级覆盖，越具体越优先】
1. 产品默认：正文 仿宋_GB2312 三号(16pt)、固定行距 28pt、首行缩进 2 字；标题 方正小标宋 二号(22pt)
2. 单位默认：（本项目若有覆盖才写，没有就不写这一行）
3. 本人偏好：正文 15pt（覆盖默认 16pt）、行距 26pt、落款「环潭供电所」、金额用万元、日期 YYYY-MM-DD
4. 本轮要求：（用户本轮明确说了才写）
硬约束：格式只影响排版，不改数字与结论；与红线冲突时以红线为准。
```

- **注入时机**：只在 `doc` / `office` 模式、或用户明确要"出文件"时注入；纯问答不注入（现在是无条件注入）。
- **键要翻译**：`body_pt` → "正文字号 15 磅"、`sign_off` → "常用落款「环潭供电所」"、`amount_unit` → "金额单位 万元"。裸键值模型读不懂。

### 4.2 个人口径 vs 公司口径（S5 / S4）

```
【S4 公司口径与判据】（来自规则库，按问题检索相关条目）
- 线损率：台区线损率口径见 判据规则 三.1 …
- 阈值：审批停留 >90 天 = 积压；工单默认排除草稿（work_status<>0）

【S5 我的口径与规则】（本人上传，优先于公司通用口径，但不能改阈值与红线）
- 我们所说线损率指台区线损率，不含分压线损
冲突处理：数字以业务库为准 → 口径按 S5 → 判据阈值按 S4 → 红线最高。
```

### 4.3 个人上传的文档分两类（前端上传时选，可按文件名猜）

| 类型 | 判定 | 怎么用 | 变更 |
|---|---|---|---|
| **规则/口径**（"我们这么说"、"按这个口径"、"规范"） | 上传时选"规则"，或文件名含 规则/口径/标准/要求/规范/制度 | 抽成 `t_rule_item`（`scope=personal`），**每轮注入 ≤1500 字** | 可看/可改/可停用，回答标"按你的规则 v3" |
| **资料**（模板、样例、常用材料） | 默认"资料" | 正常切片入库，走检索；命中标「（来自我的资料库）」 | 可删可重传 |

**边界（要守住）**：个人规则能改"口径与术语"，**不能改阈值、不能改红线**；与公司判据冲突时按 S4。
