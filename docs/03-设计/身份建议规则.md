# 身份建议规则（智能体给什么建议）

> 真源是 `server/app/dispatch_rules.py` 的 `ROLE_ADVICE` 表。本文只解释"为什么这么定、怎么用"，
> **不准比那张表多出一条规则**——多出来的部分测试卡不到，就会漂。

## 一、问题在哪

同一条「预算花不完」，四个人要的答案完全不同：

| 谁 | 他心里问的是 | 给他"怎么花钱"的答案会怎样 |
|---|---|---|
| 市领导 | 谁垫底、怎么让他们动 | 他不管项目，给了他也不会用，反而显得系统不懂他 |
| 县财务 | 这事我本级能不能了结 | 说"你去报个项目"是越位，那是所长的活 |
| 县运检 | 我从专业侧能配合什么 | 给他派活会被层级规则拒掉，白说 |
| 所长 | 这笔钱该花到哪个方向 | 说"加强领导重视"等于没说 |

一套话术打天下，结果就是：每个人都收到一段"看起来对、其实用不上"的文字。
**这是当前最大的问题，比流程通不通更严重**——流程是通的，建议是空的。

## 二、规则文档的最小结构

一个身份一张卡，五个字段，缺一个就测不过（第7组）：

| 字段 | 作用 | 写不对会怎样 |
|---|---|---|
| `angle` | 一句话说清"你是谁、你该回答什么" | 直接进提示词，写错整段就跑偏 |
| `data` | 这个身份该看的数据维度 | 不给维度，模型就开始编 |
| `must_any` | 结论至少命中一个（粗判"说到点上"） | 不给，模型给一段正确的废话 |
| `must_not` | 命中即失败（越界词表） | 不给，市领导会收到"新建项目" |
| `actions` | 这个身份允许的下一步动作 | 不给，模型会建议他做层级规则不允许的事 |

另有两个全局闸门，所有身份共用：

- **`ADVICE_BANNED`**：`加强管理 / 高度重视 / 进一步提升 / 切实做好 / 狠抓落实 / 不断优化 / 全面推进 / 有效提升`
- **数字溯源**：建议里每个金额、百分比、天数、单数，必须能在业务库查到出处；编一个整组不过。

## 三、四份身份卡

### 市领导（master）
- **结论口径**：哪些县垫底、卡在哪个环节、用什么办法让他们动起来。
- **该看**：县级执行率排名、全市执行率、已批未开工总额、最长审批停留天数。
- **必须说到**：执行率 / 排名 / 已批未开工 / 停留 / 督办 / 限期 / 约谈。
- **不许说**：新建项目、申报项目、报审批、调整线损、编制预算、储备项目、可研、施工。
- **能做的下一步**：下发要求、抄送知会、写说明。

### 县公司财务部（xgscwb）
- **结论口径**：一句"本级能不能了结"。能——给县内调剂方案；不能——明确往下压给哪几个所、各要完成多少。
- **该看**：本县各所执行率排名、卡住的审批节点与单数、县内可调剂额度。
- **必须说到**：本级 / 了结 / 调剂 / 往下 / 下发 / 上报 / 各所。
- **不许说**：新建项目、申报项目、技术方案、调整线损。
- **能做的下一步**：本级办结、往下发子任务、上报市公司财务部、补充说明。

### 县公司运检部（cto）/ 营销部（yxb）
- **结论口径**：预算怎么花不是你的活，回答"从这条专业线能配合什么、能消化多少"。
- **该看**：运检—线损率、跳闸次数、平均停电时长、抢修工单；营销—售电量、投诉工单、业扩报装、电费回收。
- **必须说到**：本专业的指标词 + 配合 / 协办 / 消纳。
- **不许说**：新建项目、编制预算、下发任务、要求各所。
- **能做的下一步**：协办、抄送知会、写说明（同级不能派活）。

### 供电所所长（sz）
- **结论口径**：本所哪个指标拖后腿、这笔钱该往哪个方向花、先动哪个具体项目。
- **该看**：本所预算分配与执行、线损率、跳闸次数、平均停电时长、抢修/投诉工单、
  本所项目（审批中 / 已批未开工 / 施工中）与金额、审批停留天数。
- **必须说到**：线损 / 跳闸 / 停电 / 工单 / 已批未开工 / 审批 / 储备 / 报项目 / 推进。
- **不许说**：要求下级、责成各所、全县排名、下发任务、督办各县（他没有下级）。
- **能做的下一步**：自己办、上报县公司财务部、交方案、补充说明。

## 四、提示词怎么拼

固定顺序，前两段来自表，后两段来自实时查询：

```
1. 你是谁      ← ROLE_ADVICE[role].angle
2. 你看什么    ← ROLE_ADVICE[role].data（要求逐项引用，查不到就写"未取到"）
3. 实测数据    ← 现查的：指标值、项目、审批、金额（带出处）
4. 约束        ← must_not 词表 + ADVICE_BANNED + "不许出现数据里没有的数字"
5. 输出格式    ← 第一句是结论；然后 3 条动作，每条后面跟依据
```

**顺序不许换**：先定身份，再看数据。反过来模型会先顺着数据编动作，身份就丢了。

## 五、两个闸门（输出后跑）

1. `advice_violations(role, text)` —— 命中 `must_not` / `no_noise` / `ADVICE_BANNED` 任一词，
   整段打回重写一次；还命中就用规则版兜底，不把越界的话发出去。
2. **数字溯源** —— 抽出文本里所有数字，逐个到出处比对；对不上就打回。
   这条已经在"报告正文"上有实现，建议正文要复用同一套，不许另写一套。

## 六、怎么测

- **第7组**：四个身份在 `ROLE_ADVICE` 里齐全、五个字段都不空、`must_any` 与 `must_not` 不重叠。
- **第4组**：每个身份真跑一次，判五条——
  有结论；动作 ≥3 条且带依据；数字 100% 可溯源；不命中 `must_not`；点名的指标/项目/所在库里真实存在。
- **人工抽检**：每个身份贴一条原文，由 Fred 判"像人话 / 是废话"。

## 六点五、范围边界：身份卡不是禁答清单

**这张表只决定"系统主动推给这个人的默认建议长什么样"，不限制他问什么。**

- 市领导的默认建议里不出现"新建项目"，是因为**主动推给他**时那没用，不是不许他知道。
- 他在对话里问"两水所那个台区改造该不该报"，系统必须照实答，还能给出项目名和金额。
- 所以 `advice_check()` 只在 `brief()`（默认建议）里调用一次，问答路径（`ask`）不经过它。

把身份卡当过滤器去卡所有输出，就会变成"问什么都被弹回一句符合身份的套话"——
那不是懂身份，是把人关进笼子。

## 七、改口径只改一处

换单位、换专业分工、换领导关注点，**只改 `ROLE_ADVICE`**。
提示词、闸门、测试都从这张表读，不许在别处再写一份"市领导应该关注……"。
