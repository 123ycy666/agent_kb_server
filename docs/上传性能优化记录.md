# 上传耗时优化记录

> 2026-10-15 · 起因：用户反馈「上传文档很慢，不是异步」，并指出「之前单个项目时没这么慢」

## 一、根因：不是合并变慢，是档位从假模型换成了真模型

| 证据 | 说明 |
|---|---|
| 原项目 `本地知识库系统/server/app/providers/` 下**没有** `online_aliyun.py` | 它被移到了旁边的 `_backup_online_providers/` —— 原项目实际以 **mock/local** 档运行 |
| mock/local 档 | 向量化与冲突判定都在**本地瞬时**完成，零网络往返，所以「单项目不慢」 |
| 合并系统 `.env` | `MODEL_CHANNEL=online`（阿里云百炼），每次向量化/判定都是**真实网络请求 + 真实推理** |

## 二、四处具体瓶颈

| # | 位置 | 问题 | 量级 |
|---|---|---|---|
| 1 | `providers/base.py::embed_batch` | 分批是**串行 for 循环**；而阿里云单请求**硬限 10 条**（超过直接 HTTP 400），1500 段 = 150 次串行请求 | ≈139s |
| 2 | `providers/online_aliyun.py::embed` | 每批都 `with httpx.Client(...)` **新建连接**，重复付 TLS 握手 | 每批多 ≈0.4s |
| 3 | `conflict/detector.py::_rerank_candidates` | 精排是「每切片一次请求」且**串行**（rerank 接口不支持多 query 批处理） | 大文档数十秒 |
| 4 | 冲突判定 LLM | 使用 `qwen3.8-max`，单次判定 ≈14s | 12 对串行时 168s |

> 注：上一轮只优化了瓶颈 4 的并发，故体感「还是很慢」——真正的大头是瓶颈 1。

## 三、实测数据

### 在线档向量化（text-embedding-v4，1024 维）

| 场景 | 耗时 |
|---|---|
| 单批 10 条 | 1.40s（含首次 TLS 握手） |
| 100 条**串行**分批 | 9.28s（每批 0.93s） |
| 20 条一批 | **HTTP 400** → 确认 batch 硬上限为 10，加大批次这条路走不通 |
| 100 条**并发 10 路** | **0.61s** |

### 网关可用模型（专属 maas 网关）

| 模型 | 可用 | 空跑延迟 |
|---|---|---|
| `qwen3.8-max`（原） | 是 | 2.43s |
| **`qwen-plus`（现用）** | 是 | **0.60s** |
| `qwen-flash` | 是 | 0.34s（质量偏弱，仅参考） |
| `qwen-max` | 是 | 0.56s |
| `qwen-turbo` / `qwen3.8-plus` | **否（404）** | 该网关未部署 |

### 端到端上传（1200 切片文档，kb3，online 档）

| 阶段 | 优化前（估算） | 优化后（实测） |
|---|---|---|
| 受理返回（202） | 0.04s | 0.04s |
| **入库完成、文档可检索** | ≈112s（仅向量化） | **14.3s** |
| 冲突检测完成 | ≈150s+ | 19.4s（检测本身仅 5s） |

## 四、改动清单

| 文件 | 改动 |
|---|---|
| `providers/base.py` | `embed_batch` 串行 → **并发**（`ThreadPoolExecutor` + `ex.map` 保序） |
| `providers/online_aliyun.py` | 共享 `httpx.Client` 连接池（懒加载+双检锁）；`_post_with_retry` 对 429/5xx 指数退避重试 3 次 |
| `core/config.py` | 新增 4 个并发/上限配置项（见下表） |
| `services/conflict/detector.py` | 精排改**并发**；新增候选组数上限；判定的截断由「按切片顺序」改为**按可疑度降序**取前 N（原顺序截断会把最可能冲突的候选排到后面 → 漏判） |
| `services/permission.py` | `visible_document_filter` 增加 `doc_cls` 参数以支持 aliased 表；**权限口径仍是单一出口** |
| `tasks/__init__.py` | 任务改**两段式**：入库即 `done`（文档可检索），冲突检测后台续跑并回写 `result.conflict_status`；删除重复定义的 `enqueue_ingest` |
| `web/src/api/index.ts` | `uploadAndWait` 适配两段式（入库即返回，冲突结论最多再等 45s） |
| `web/src/components/UploadModal.tsx` | 区分「检测中 / 检测失败 / 检出冲突 / 无冲突」四种文案 |
| `web/vite.config.ts` | `emptyOutDir: false`（本机 safe-delete 会拦截 vite 清空 dist） |
| `tests/acceptance.py` | 新增 B3b「任务结果必须含 conflict_status」回归断言 |

## 五、新增配置（.env）

| 键 | 默认 | 说明 |
|---|---|---|
| `EMBED_BATCH_CONCURRENCY` | 8 | 向量化分批并发度。**设 1 = 退回串行**（内网 embedding 服务不支持并发时用） |
| `CONFLICT_JUDGE_CONCURRENCY` | 8 | 冲突判定（LLM）并发度 |
| `CONFLICT_RERANK_CONCURRENCY` | 8 | 候选精排（rerank）并发度 |
| `CONFLICT_RERANK_MAX_GROUPS` | 200 | 单次检测精排的组数上限（病态输入保护，超出按相似度取前 N） |
| `ONLINE_LLM_MODEL` | `qwen3.8-max` | **主模型**：知识库问答 + 问数 agent（保持旗舰不动） |
| `ONLINE_JUDGE_MODEL` | `qwen-plus` | **冲突判定专用**模型（留空 = 跟随主模型）；local 档对应 `LOCAL_JUDGE_MODEL` |

## 六、验证结果

- `server/tests/acceptance.py`：**34 通过 / 0 失败**（含新增两段式回归断言），全程 17s
- 在线档向量化单测：100 条 9.28s → **0.82s（约 11x）**
- 端到端：1200 切片文档入库 **14.3s**，冲突检测完成 19.4s，检索/删除链路正常
- 此前 `conflict_record` 外键报错（doc 17/18）**本次未复现**，判断为当时改造半成品状态所致

## 七、遗留

1. `local` 档端点待内网填入；若内网 embedding 服务不支持并发，把 `EMBED_BATCH_CONCURRENCY` 设为 1 即可退回串行。
2. 冲突判定现用 `qwen-plus`：实测单次 **2.2~2.6s**（`qwen3.8-max` 约 14s，快约 5 倍），
   判定准确度实测正常（真冲突 → `contradiction`、无关 → `unrelated`）。
   若日后发现漏判，把 `ONLINE_JUDGE_MODEL` 留空或改回 `qwen3.8-max` 即可 ——
   **只影响判定，不会波及知识库问答与问数 agent**。

## 八、对「接入内网」的影响

**结论：主体逻辑不受影响，内网同样吃到这次提速；但内网有两个前提要先确认。**

### 8.1 与档位无关、内网自动继承

任务两段式、候选精排并发、批量召回、判定截断按可疑度排序 —— 均不依赖具体档位，
切到 `local` 后照样生效。

### 8.2 ⚠️ 并发度对内网是新的未知数

本次新增的并发（向量化分批 8 路 / 精排 8 路 / 判定 8 路）**对 local 档同样生效**。
阿里云扛得住 8 路，内网自建的 bge-m3 服务未必（可能是单卡小服务）。

→ 接入前先压测，再定并发度；**留了开关**：`EMBED_BATCH_CONCURRENCY=1` 即可退回串行，
`CONFLICT_JUDGE_CONCURRENCY` / `CONFLICT_RERANK_CONCURRENCY` 同理，都不用改代码。

### 8.3 已补齐的 local 档缺口

原先 online 档有连接池与重试、local 档没有（行为不一致，最难排查）。现已抽出
`providers/http_client.py`，两档共用同一套「共享连接池 + 429/5xx 退避重试」。

### 8.4 接入内网 checklist

1. 填 `LOCAL_LLM_BASE_URL` / `LOCAL_EMBEDDING_URL` / `LOCAL_RERANK_URL` 三个端点；
2. 小并发压测，定出安全的并发度（必要时下调或设为 1）；
3. **切档后必须重建索引** —— 两个模型的向量空间不通用（代码已有 `embedding_model`
   校验 + 重建接口，这个机制是好的）；
4. 确认内网 LLM 支持 **JSON 结构化输出**（冲突判定强依赖 `json_mode`，否则判定会退化成乱答）；
5. 问数 agent 的模型下拉清单（`secretary/config.py` 的 `MODELS`）现在**写死了通义千问系列**，
   换 DeepSeek 等内网模型需同步改这里。
