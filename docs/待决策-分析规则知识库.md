# 待决策：把「分析规则」做成分析流程专用的知识库

> 这份是**问题整理**，给新一轮讨论用。结论不用现在给，先把事实和待定项摆清楚。

## 一、我理解的目标（一句话）

**skills 只负责「提醒」**（定时触发 → `/api/skill/title` → 只回一句标题）；
**真正的回答，全部走普通问答**（`/api/ask`，带历史对话，**不带 skill_id**），
而普通问答要能**一步步问出来** —— 不靠任何特殊处理。

为此需要一个**分析流程专用的知识库**：把「每个问题该怎么分析、从哪些方面回答、判断标准是什么」
提炼成**一条条具体的问题条目**；检索返回切片时，**看到那一条就知道该怎么答**。

## 二、现状（已实测，可作为判断依据）

**链路现状**

| 环节 | 现在怎么跑 |
|---|---|
| 定时提醒 | 声明式：技能配置里 count_metrics 指向字典指标（ai_data.ai_metric_metadata.metric_formula），服务直接执行后套模板 → 只回标题。**模型不参与计数** |
| 定时提醒表现 | 4 个技能各连打 5 次稳定：**13 / 118 / 0 / 0**，约 90ms |
| 普通问答 | 名称纠错 → 时间/地点补全 → 模型循环（run_sql / find_column / kb_search）→ 回答；要图表再加一次调用出页面 |
| 判断标准从哪来 | 传了 skill_id → 直接读服务器上 skills/技能名.md；**没传 → 模型自己用 kb_search 去知识库检索** |

**问题：不带 skill_id 时，检索命中不了对的文档。** 实测（追问跟在标题之后）：

| 追问 | 只拿问句检索 | 问句 + 上一轮标题 一起检索 |
|---|---|---|
| 是哪些项目？ | **没命中「各层级审批」**（命中问法归一/项目流程实时监控） | **各层级审批 0.977（第一）** |
| 卡了多久？ | 各层级审批 仅 0.67（第三档） | **各层级审批 0.964（第一）** |
| 一共多少钱？ | **跑偏到「项目执行进度异常提醒」** | — |
| 各多少钱？ | **跑偏到「预算分配」** | 项目执行进度异常提醒 0.889 命中 |
| 今天我先办哪几张？ | 各层级审批 0.958 命中 | 各层级审批 0.978（第一） |

**6 条里 3 条只靠问句会跑偏；拼上「上一轮那句标题」后，正确文档全部进前列。**

## 三、要解决的问题（三条）

1. **普通问答（不带 skill_id）不能可靠拿到「该用哪条规则」** —— 尤其「看到提醒后的追问」，问句本身几乎没有线索。
2. **「怎么分析」现在散在技能文档里**，普通问答检索到的是「文档切片」，不一定正好是「这个问题的分析角度 + 判断标准 + 回答要点」。
3. **没有历史对话的新会话**里直接问一个残缺问题（如「是哪些项目？」），既无上下文可拼、也无从判断该用哪条规则。

## 四、你说的目标形态（我复述，请纠正）

    定时任务 ──► /api/skill/title ──► 一句标题（提醒）
                                        │
    用户看到提醒 ──► 在问答窗口追问（普通 /api/ask，带历史对话、不带 skill_id）
                        │
                        ▼
                 普通问答自己判断「这要分析」
                        │
                        ▼
            从【分析规则知识库】取到「这个问题该怎么分析」的那一条
                        │
                        ▼
                  按那条的方面与标准作答（要图表就顺带出页面）

**skills 的职责边界：只到「提醒」为止。回答完全归普通问答。** 唯一的区分是「分析」与「普通查数」。

## 五、待你拍板的问题

**Q1. 规则条目的「一条」怎么定义？** 一条 = 一个具体问题（问法）吗？每条要带哪些字段？我的建议字段：
问法（标准问法 + 常见口语说法）｜ 分析角度（从哪几个方面答）｜ 判断标准（阈值/口径，可指向判据）｜ 取数口径（哪张表/哪些状态）｜ 回答要点与格式（多长、要不要逐条列清单）｜ 不要做什么（反例）

**Q2. 颗粒度与切分**：一条一个问题成一篇文档，还是一篇文档放一类问题？
（索引 chunk_size=600，一条规则太长会被切碎，可能「看到半个角度」）

**Q3. 放在哪个索引？**
- 继续放 r57xtq9ypm（**检索已授权、零运维**，但与现有 16 篇混在一起，可能互相挤名额）
- 还是新建专用索引（**要先在百炼控制台给检索服务授权**，否则检索 401）
我的建议：**先放 r57xtq9ypm**（能立刻见效），条目化改造完成、验证有效后再决定要不要拆库。

**Q4. 检索词怎么拼？** 我建议：**本轮问句 + 最近一轮（问题/标题）** 一起检索；新会话则只用自己的问句。
—— 这一条已实测有效（见第二节表），是否采纳？

**Q5. 没有上下文的新会话怎么兜？** 是否在系统提示里常驻一份**规则条目目录**（每条一行：问题 → 该看哪篇），
让模型知道「有哪些规则可用、该查哪条」，再用 kb_search 取细节？

**Q6. 现有的 14 篇技能文档怎么办？** 被条目化的规则库**取代**，还是**并存**（技能文档继续给「带 skill_id」的定时场景用）？

**Q7. skill_id 这条路保留吗？** 我建议保留但**降级为可选加强**（前端从提醒页跳进来时能带就带），不作为普通问答的前提。
